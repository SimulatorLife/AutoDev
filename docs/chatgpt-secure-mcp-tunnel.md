# ChatGPT Secure MCP Tunnel

> **Target-state boundary:** This operational guide describes the current tunnel integration. Under the canonical [mandatory shared MCP gateway](autodev-console-target-state.md#mandatory-shared-mcp-gateway) and [unified execution entrypoints](autodev-console-target-state.md#unified-user-chat-and-cli-execution-entrypoints) target, ChatGPT is a first-class, provider-agnostic agent participant governed by the same canonical role and execution contracts as Codex, Claude, Antigravity, Copilot, and mcode. External authentication establishes trusted identity and authorization, not a separate read-only capability model. All AutoDev-managed provider MCP traffic converges on Supergateway, with OpenAI Secure MCP Tunnel as optional authenticated external ingress.

Under the [unified desktop, IDE, CLI and external agent integration target](autodev-console-target-state.md#unified-desktop-ide-cli-and-external-agent-integration), ChatGPT desktop and web are enrolled native interfaces, not separate configuration authorities. Share supported plugin skills, prompts and gateway connections from canonical sources; qualify native hooks/telemetry per host rather than assuming Codex capabilities exist in ChatGPT. Current tunnel connectivity alone does not prove per-conversation authorization or visibility of native model/token activity.

AutoDev publishes a private, role-bound MCP surface to ChatGPT through OpenAI Secure MCP Tunnel. Two LaunchAgents split the work:

- **`com.codex.autodev-mcp-gateway`** (mandatory, always reconciled by the installer, `runtime/src/platform/mcp-gateway-service.ts`) runs [Supergateway](https://github.com/supercorp-ai/supergateway) in loopback-only stateful Streamable HTTP mode (`127.0.0.1:3312` by default, `stateful: true`, 60-second idle session timeout) with AutoDev's in-process backend pool (`runtime/src/mcp/chatgpt-backend-pool.ts`). Supergateway owns external Streamable HTTP transport, `Mcp-Session-Id` session isolation, tool prefixing, combining, and local Bearer authentication. Every member of every role surface is a route on the pool, which multiplexes repeated one-shot client sessions (such as ChatGPT opening a new MCP session per tool call without `DELETE`) onto at most one lazily started, idle-reaped, OS-confined backend process per role and MCP server (and one shared HTTP transport per remote server), and replaces a backend that exits. Sessions therefore share backend state: a language server one session started is warm for the next.
- **Local clients in any directory.** The same gateway also serves every role's servers to local clients (Codex, Claude Code, ACP providers and the other CLIs) at `/local/<role>/<server>/mcp`, one surface per server so clients keep canonical server and tool names. These surfaces accept only the local key `~/.codex/mcp-gateway/local.key`, which the tunnel never holds, and every tool call or task request must carry a session grant in `_meta["autodev/grant"]`: an HMAC (with the private `admission.key`) over the workspace, role, session and expiry (`runtime/src/mcp/session-grant.ts`). Clients launch `run-autodev-mcp.sh <server>`, which starts the gateway client (`runtime/src/mcp/gateway-client.ts`): it admits its launch directory (or the workspace an ACP session's Runtime resolved, handed over in `AUTODEV_MCP_GRANT`), refuses the home directory, its ancestors and the AutoDev configuration homes, and relays stdio to the role's surface with the grant attached. No directory needs registering. The pool verifies each grant and runs the call in backends started lazily for that workspace (`admitted` pool routes, `runtime/src/mcp/gateway-admission.ts`), confined to it by the same Seatbelt profiles; delegation (`xacpx`) gets a backend per session, whose coordinator is that session. A missing, forged, expired or other-role grant is refused. The one server that is not a gateway surface is `playtest`: it serves a single Playtesting run whose trusted context (run, task, actor, analysis) the Runtime passes in the server's process environment under the run's isolated `CODEX_HOME`, so `run-autodev-mcp.sh playtest` starts it directly, bound to that run, and it has no external confinement profile. `runtime/tests/gateway-local-admission.integration.test.ts` drives this through the real Supergateway with a real confined filesystem backend, from a registered and an unregistered directory.
- **`com.codex.autodev-chatgpt-tunnel`** (optional, `runtime/src/platform/chatgpt-tunnel-install.ts`) runs only `tunnel-client`, publishing the live gateway's role surfaces. It waits for the gateway's `/readyz` before starting and never starts, configures or stops the gateway: disabling, forgetting or losing the tunnel leaves local MCP access untouched.

AutoDev owns role-contract rendering, workspace/OS confinement, loopback binding, XACPX orchestration IPC, and the gateway's local Bearer key. No non-loopback listener, public IP, port forwarding, or external gateway service is required.

## Installation (macOS)

Every normal install reconciles the gateway; materialize-only installs never start or restart a service. Enable the tunnel explicitly on the first normal install; subsequent normal installs reconcile the existing tunnel after the gateway. A reconcile restarts a service only when its configuration, LaunchAgent or installed Runtime generation changed: each LaunchAgent names the resolved `$CODEX_HOME/src` generation, so a new Runtime restarts the services that would otherwise keep running superseded code. The installer taps `openai/tools` and installs the official Homebrew tunnel-client (minimum v0.0.21) when absent or outdated; Supergateway is an exact runtime dependency in `runtime/package.json` and is installed by the ordinary workspace package installation. It creates a dedicated login LaunchAgent and private local configuration; the runtime key is stored in macOS Keychain, not a plaintext runtime key file. The gateway's default workspace is the AutoDev checkout and its default primary role is `orchestrator`. Set `AUTODEV_MCP_GATEWAY_WORKSPACE` to an absolute project directory and optionally `AUTODEV_MCP_GATEWAY_ROLE` to any canonical role declared in `config/execution-contract.json` (e.g., `orchestrator`, `worker`, `default`, `smart`, `explorer`, `docs-researcher`, `validator`).

OpenAI requires organization-level tunnel authorization independently of ChatGPT subscription or plugin access. Obtain a restricted runtime key (Tunnels Read + Use) from [Platform organization API keys](https://platform.openai.com/settings/organization/api-keys). An existing tunnel must be associated with the intended ChatGPT workspace. If you already have an administrator key with Tunnels Read + Manage and explicit organization and workspace IDs, the installer can create the tunnel automatically:

```sh
# Supply these secrets securely through your shell, macOS Keychain, or a
# git-ignored .env file at the repository root (loaded automatically by
# scripts/install.sh via Node.js --env-file-if-exists; explicit shell exports
# take precedence). Never commit actual keys or put them in shell history.
# AUTODEV_CHATGPT_TUNNEL_API_KEY: restricted runtime key (required on first install)
# OPENAI_ADMIN_KEY: only for automatic tunnel creation
export AUTODEV_CHATGPT_ORGANIZATION_ID=org_...
export AUTODEV_CHATGPT_WORKSPACE_ID=ws_...
export AUTODEV_MCP_GATEWAY_WORKSPACE=/absolute/path/to/project
export AUTODEV_MCP_GATEWAY_ROLE=orchestrator
./scripts/install.sh --enable-chatgpt-tunnel
```

Alternatively create a tunnel in [Platform Tunnels](https://platform.openai.com/settings/organization/tunnels), then provide its ID using `CONTROL_PLANE_TUNNEL_ID` instead of the admin key (in the environment or repository-root `.env`). Organization and workspace IDs are still required to verify scope. The installer isolates tunnel credentials (`OPENAI_ADMIN_KEY`, `AUTODEV_CHATGPT_TUNNEL_API_KEY`) from dependency installation, materialization, and service restarts, stores `AUTODEV_CHATGPT_TUNNEL_API_KEY` in macOS Keychain (under service/item name `AUTODEV_CHATGPT_TUNNEL_API_KEY`, trusted for `/usr/bin/security` so the unattended LaunchAgent retrieves it across service restarts and system reboots without interactive prompts), configures `tunnel-client` with `--control-plane-api-key-ref env:AUTODEV_CHATGPT_TUNNEL_API_KEY`, and preserves the returned tunnel ID for future installs; the gateway preserves the workspace, roles and policy. It never stores or logs the administrator key. Do not supply an administrator key as the runtime key. The installer cannot grant account permissions or create a restricted runtime credential without prior OpenAI authorization.

## Role-driven MCP access policy and single source of truth

AutoDev renders the Supergateway configuration from the installed `provider-runtime/mcp-servers.json` catalogue (derived from `.rulesync/mcp.jsonc`) and derives effective MCP exposure and permissions directly from the assigned role's canonical execution contract (`agents/roles/*.toml` -> `config/execution-contract.json`) combined with portable denials/allowlists in `.rulesync/permissions.jsonc`. There is no separate ChatGPT-only capability model or read-only blanket restriction:

- **Writable roles** (`orchestrator`, `worker`, `default`, `smart`, `validator`, `github-worker`) receive full authorized tools for every MCP server enabled in their role contract, including workspace-confined `filesystem` mutations (`write_file`, `edit_file`, `create_directory`, `move_file`), writable `lsp` actions where contracted, and read-only access to AutoDev skill roots (`--read-only-dir`).
- **Orchestration roles** (`orchestrator`) also receive the canonical `xacpx` MCP interface (`@ganglion/xacpx`'s `xacpx mcp-stdio`), connected over AutoDev's canonical Unix-socket orchestration IPC (`XACPX_ORCHESTRATION_SOCKET`) to `XacpxSessionManager`. Delegated child agents receive their own contracted role permissions, canonical role prompts, provider pinning, workspace confinement, concurrency limits, and strict coordinator ownership isolation. The coordinator is per ChatGPT conversation: the backend pool runs one `xacpx` backend per conversation, named `chatgpt:<role>:<workspace>:conversation-<digest>` from a SHA-256 digest of the platform-supplied `_meta["openai/session"]` on each tool call (the raw identifier never reaches a process, environment or log). ChatGPT opens a fresh MCP session for every call, so the MCP session cannot carry this identity. A delegation or task call without a conversation identity is refused rather than run under a shared coordinator, so one conversation can never see or steer another's children. At most 32 conversations keep a backend at once; a new one evicts the least recently used idle one.
- **Native MCP tasks are owned.** The pool binds every task a `tools/call` creates to its creator: the ChatGPT conversation when `_meta["openai/session"]` is present, otherwise the MCP session it arrived on. `tasks/get`, `tasks/result` and `tasks/cancel` for someone else's task answer `Task not found`, and `tasks/list` returns only the caller's own tasks, so a task ID is a handle, never a credential (`runtime/tests/backend-pool-tasks.test.ts`).
- **Read-only roles** (`explorer`, `docs-researcher`, `browser-tester`, `playtester`, `playtest-analyst`) remain strictly read-only at both the MCP tool layer (`--read-only` on `filesystem`, read-only tool filtering) and the OS Seatbelt layer, and never receive `xacpx` delegation tools.
- **Operator narrowing:** Operators may optionally narrow tool grants within the assigned role's authorized set through a private override JSON named by `AUTODEV_MCP_GATEWAY_POLICY_FILE` and applied by the installer, and can never widen beyond the canonical role contract. Grants are repository/installer-owned: the Console shows reviewed and effective grants read-only and offers no grant control. When `config/execution-contract.json`, `.rulesync/permissions.jsonc`, `provider-runtime/mcp-servers.json`, or the assigned role changes, normal installs re-discover tool inventories and reconcile automatically.

The gateway gives Supergateway and the pool a clean explicit environment, setting `AUTODEV_AGENT_ROLE`, `AUTODEV_MCP_WORKSPACE`, `AUTODEV_XACPX_WORKSPACE`, `AUTODEV_XACPX_COORDINATOR_SESSION`, `XACPX_ORCHESTRATION_SOCKET`, and `AUTODEV_MCP_READ_ONLY=1` **only** when the assigned role has `readOnly: true`. Local backends run under role-aware confinement enforced by `externalMcpBackend`:

- `filesystem` runs inside macOS Seatbelt (`sandbox-exec`) with `--confine-roots`, read-only skill roots (`--read-only-dir`), blocked `.env*` secrets (except workspace `.env.example`), blocked host secrets (`.ssh`, `.aws`, `.gnupg`, `mcp-gateway`, `chatgpt-tunnel`), and blocked network; writes are strictly confined to `workspace` for writable roles and completely denied (`--read-only`) for read-only roles.
- `lsp`, `cocoindex-code`, `codegraphcontext`, and `xacpx` run under Seatbelt profiles enforcing role-scoped workspace write boundaries, blocking host secrets and non-local outbound network traffic, while permitting local Unix-socket IPC (`xacpx` orchestration socket, CocoIndex/CGC local daemons).
- `commands` serves only the operator-approved catalogue in `$CODEX_HOME/config/commands.json`. Its gateway grant is the backend's own discovered listing for the role, bounded by the role contract, so a checkout catalogue revision still pending approval (`--approve-command-catalogue`) never adds tools to the reviewed grants or fails the gateway preflight; the previous revision keeps serving until it is approved.
- Role-authorized `playwright`, `playtest`, and `github` servers launch through AutoDev's canonical `launcher.ts`; the pool exposes only each role's granted tools.
- Remote Streamable HTTP documentation servers (`openaiDeveloperDocs`, `context7`, and `googleDeveloperKnowledge` when credentialed) are pool routes that resolve only the declaring server's credentials in memory, never exposing secrets to Supergateway or sibling local servers.
- The pool preserves truthful upstream tool annotations (never forging `readOnlyHint: true` on mutating or delegation tools) and exports native OpenTelemetry spans for every local and remote backend.

For the gateway, the installer runs the pinned Supergateway binary's `--checkConfig` and a real Streamable HTTP SDK initialize/tools/list probe (with its own backend pool) across independent client sessions, verifying unauthenticated `401` rejection, distinct `Mcp-Session-Id` isolation, the exact role-authorized tool inventory, and rejection of unapproved non-tool capabilities, then requires a launchd-owned `/readyz` listener on `3312`. A failed candidate leaves the previous gateway running. Supergateway binds exclusively to `127.0.0.1` using Streamable HTTP (not SSE) and requires the gateway's 256-bit `apiKeyFile` Bearer token, which lives at the gateway directory's root and survives regeneration, so clients holding its header file keep working. Supergateway 4.2.2 has a reported stdio-to-SSE denial-of-service vulnerability (CVE-2026-131857); that transport is not used here. Reassess the pin when updating dependencies.

For the tunnel, the installer generates the official `tunnel-client` Streamable HTTP profile (`sample_mcp_remote_no_auth`) with one channel per published gateway role (`http://127.0.0.1:<mcpPort>/<role>/mcp`), runs `doctor` against the live gateway (with `MCP_OAUTH_DISCOVERY=disabled` and the gateway's `file:`-referenced `Authorization` header), checks tunnel metadata with the runtime key, and requires a launchd-owned readiness listener for `tunnel-client` (`3311`). The previous profile and key are retained until replacement succeeds.

`tunnel-client` requires one MCP target on its `main` channel: it refuses to pass `doctor`, and the daemon refuses to start, without one. The primary role's surface is therefore published on `main`, and every additional published role gets a channel named after it (`orchestrator` -> `main`, `explorer` -> `explorer`). The profile's routing table and the arguments `doctor` validates are both generated from that one plan, so they cannot disagree about which channel carries which surface. When a stage fails, the installer reports that stage's own output -- `tunnel-client doctor` writes its check report to stdout -- instead of only naming the stage.

## Attach ChatGPT

Once installation prints the ready tunnel ID, open ChatGPT Plugins > Add custom MCP server > Tunnel. Choose the AutoDev ChatGPT tunnel (or use the printed ID), choose no MCP-level authentication for this private tunnel gateway (local loopback traffic is authenticated by `tunnel-client` with the gateway's Bearer token), and create/install the plugin. The OpenAI tunnel itself authenticates the runtime.

### Published roles

The gateway publishes one role-scoped surface per published role, each at its own path (`/<role>/mcp`) with that role's tool allowlist, that role's coordinator and that role's read-only confinement. The tunnel publishes one channel per role, so each surface is independently addressable: the primary role is published on tunnel-client's required `main` channel, and each additional role on a channel named after it. The primary role comes first and owns the gateway's delegation coordinator; the primary role (`AUTODEV_MCP_GATEWAY_ROLE`), additional roles (`AUTODEV_MCP_GATEWAY_ROLES`) and workspace (`AUTODEV_MCP_GATEWAY_WORKSPACE`) are chosen at install time. When the installer republishes the gateway's roles, the next tunnel reconcile re-projects an enabled tunnel's channels; the tunnel never reconfigures the gateway.

AutoDev names each role's ChatGPT app: `AUTODEV_CHATGPT_MCP_APP` names one app for every role, and `AUTODEV_CHATGPT_MCP_APP_BASE` (default `AutoDev`) names the base the role name is appended to, so the orchestrator's app is `AutoDev` and the `explorer` role's app is `AutoDev explorer`. Name the connected app in ChatGPT to match, so the Runtime's `opencli chatgpt ask --app <app>` selects the right surface. The app is selected in ChatGPT's own composer menu before the prompt is sent, so only that role's tools reach the model.

The gateway uses label `com.codex.autodev-mcp-gateway` (with `ProcessType: Interactive` so launchd does not throttle multi-backend session startup) on port 3312; the tunnel uses `com.codex.autodev-chatgpt-tunnel` with local health port 3311. Check:

```sh
curl -fsS http://127.0.0.1:3312/readyz
curl -fsS http://127.0.0.1:3311/readyz
open http://127.0.0.1:3311/ui
launchctl print "gui/$(id -u)/com.codex.autodev-mcp-gateway"
launchctl print "gui/$(id -u)/com.codex.autodev-chatgpt-tunnel"
```

The gateway's generated `supergateway.json` and `backend-pool.json`, its mode-`0600` Bearer key files (`supergateway.key` and `supergateway-auth.header`), persisted settings and logs reside under `${CODEX_HOME:-$HOME/.codex}/mcp-gateway`; the tunnel's profile, settings and logs reside under `${CODEX_HOME:-$HOME/.codex}/chatgpt-tunnel`. Both directories are private (`0700`) and denied to confined MCP backends. The runtime credential (`AUTODEV_CHATGPT_TUNNEL_API_KEY`) is stored in macOS Keychain rather than in a plaintext file, injected only into `tunnel-client` at LaunchAgent startup (`env:AUTODEV_CHATGPT_TUNNEL_API_KEY`), and never reaches the gateway or MCP tools. Disable the tunnel persistently with `./scripts/install.sh --disable-chatgpt-tunnel`; later normal installs honor that state and the gateway keeps serving. Re-enable explicitly with `--enable-chatgpt-tunnel`. Set `AUTODEV_CHATGPT_TUNNEL_PORT` to override 3311, `AUTODEV_MCP_GATEWAY_PORT` to override 3312, and `AUTODEV_MCP_GATEWAY_ROLE` to change the primary role. Run `./scripts/install.sh --check` to check gateway and configured tunnel readiness. An interrupted install may leave an `install.lock` directory in either service directory; remove it only after confirming no installer is running. Revoke the tunnel/key in Platform when no longer needed.

References: [OpenAI Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels), [official tunnel-client](https://github.com/openai/tunnel-client).

## Local protocol acceptance test

After the repository dependencies are installed, run `AUTODEV_TEST_SUPERGATEWAY=1 pnpm --filter @simulatorlife/autodev-runtime exec node --test tests/chatgpt-supergateway.integration.test.ts`. This exercises the workspace-installed Supergateway with its backend pool, as the gateway service runs them (and `tunnel-client dev proxy` when installed), over stateful Streamable HTTP, covering:

- concurrent client sessions, repeated initialization, reconnection, Supergateway restarts, shared pooled backends and their replacement after an exit;
- authorized filesystem mutations (`write_file`, `edit_file`, `create_directory`) under writable roles and strict write denial under read-only roles, with workspace/symlink/secret confinement and truthful tool annotations;
- end-to-end `xacpx` child delegation scoped to the calling conversation (`_meta["openai/session"]`), task watching/listing/messaging/cancellation, delegated role isolation (read-only vs. writable child permissions), role-escalation denial, workspace-escape denial, and cross-session coordinator isolation;
- Seatbelt-confined LSP and CocoIndex semantic search plus authenticated remote documentation MCPs with credential isolation.

## Console controls

The `/mcps` Console page shows the shared MCP gateway's own health first, in the read-only **Shared MCP Gateway** panel (from `GET /control/mcps`): service readiness, published role surfaces and effective grants. Tunnel health is reported separately because the tunnel is only an optional client of the gateway.

After initial credential provisioning, the tunnel panel on `/mcps` displays tunnel readiness, the tunnel ID and the gateway roles it publishes as channels (`GET /control/chatgpt-tunnel`, `autodev-chatgpt-tunnel-v2`, which carries no grants or workspace). Its only controls are the tunnel's own lifecycle and credential operations: disconnect, re-enable, rotate the local restricted runtime key, or forget that key. Roles, workspace and grants are not tunnel controls; change them through the canonical sources and the installer. All mutations use the authenticated Control API with a revision check; the browser never receives the stored key. Forgetting the local credential does not revoke it remotely: use OpenAI Platform to revoke the credential or delete the tunnel.

Developer dependency update: after changing dependencies, regenerate the root `pnpm-lock.yaml` with the repository-pinned pnpm (`pnpm install --lockfile-only`), then run `pnpm install --frozen-lockfile`. The lockfile must be committed before merging; no separate Supergateway installation or lockfile is maintained.
