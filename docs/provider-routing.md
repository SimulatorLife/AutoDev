# Codex agent and provider routing

This is the canonical repository guide for choosing and invoking agents across
the OpenAI, Claude, MiniMax, Antigravity, and GitHub Copilot providers. Role files and scripts remain the source of truth for exact model settings; this document owns the
routing policy, execution boundaries, and the setup needed to use the
versioned local integration safely.

## Available roles

Callers select a capability role, never a provider or model:

| Role              | Capability                                        | Sandbox         |
| ----------------- | ------------------------------------------------- | --------------- |
| `default`         | General-purpose development                       | workspace-write |
| `docs-researcher` | Targeted documentation research                   | read-only       |
| `browser-tester`  | Browser/runtime evidence                          | read-only       |
| `explorer`        | Architecture and dependency exploration           | read-only       |
| `worker`          | Bounded implementation                            | workspace-write |
| `validator`       | Independent validation                            | workspace-write |
| `smart`           | Full-capability browser/docs/implementation agent | workspace-write |

Roles other than `browser-tester` and `smart` use the configured `default` model
tier. `browser-tester` has a dedicated tier containing only providers that can
isolate its required Playwright MCP; Antigravity now qualifies because each `agy`
process receives a role-scoped temporary MCP home. `smart` uses the configured
`smart` tier. Providers without a model override for a tier use their `default`
model. Every role uses the `local_model_router` with an `autodev/<role>` model
alias.

A provider has two operator roles: `orchestrator`, which governs the root
agent, and `subagent`, which governs every tier a subagent runs in (its
priority ranks the provider in those tiers and its `Disabled` removes it from
all of them). Each may name its own model. For a subagent request the model is
chosen in this order:

1. the agent role's own model on that provider (`agentModels`, e.g. `explorer`
   on `opencli-chatgpt-fast`);
2. the provider's `subagent` assignment model;
3. the tier's configured model.

The Console's Providers tab writes the role assignments through
`PATCH /control/providers/<provider>/roles/<role>` and the agent-role models
through `PATCH /control/providers/<provider>/agents/<role>` (`{"model": null}`
clears one). Both are operator overrides layered on top of the routing
config's tier defaults, not a second place to define tiers. Clearing an
override restores the next model in the order above. A model named by an assignment must route to the same provider
and must be enabled, or the provider drops out of that role's candidates rather
than falling back — a role assignment that names an unusable model removes that
provider from the role rather than silently serving a different one.

### Model routing, provider catalogs, and UI data (DRY model architecture)

[`config/model-routing.json`](file://config/model-routing.json) is the single source for which model each provider uses at each routing tier and which providers are eligible for that tier. Provider-specific [`config/catalogs/*-model-catalog.json`](file://config/catalogs) files own model metadata such as display names, context windows, and supported reasoning levels. These are separate responsibilities: the routing config references catalog model IDs; it is not a second list of model metadata.

- **Generated Codex catalog**: [`config/catalogs/codex-model-catalog.json`](file://config/catalogs/codex-model-catalog.json) is generated by [`renderModelCatalog`](file://runtime/src/config/render-model-catalog.ts) from the routing assignments plus the provider catalog entries. Do not edit this merged artifact directly. The installer materializes and validates it during `bash scripts/install.sh` and `node runtime/src/cli/install.ts --check`.
- **Re-render after editing a provider catalog**: the provider catalog rows are embedded verbatim in the generated Codex catalog, so editing a `config/catalogs/*-model-catalog.json` file leaves the checked-in copy stale and the catalog sync tests fail. Re-render it with `node runtime/src/config/render-model-catalog.ts --routing-config config/model-routing.json --catalogs-dir config/catalogs --output config/catalogs/codex-model-catalog.json` and commit the result.
- **Console Models tab**: the Runtime's `/control/models` response derives its IDs, providers, and tiers from `RoutingPolicy.configuredModels()` over the active routing config. The Console passes those records directly to the Models view; it owns no separate model-ID list. Display names are joined from the generated Codex catalog and do not decide whether a model appears. `ROUTING_POLICY` loads the routing config at Runtime startup, so restart the router after editing that file before expecting the Console to reflect the change.
- **Codex model list**: profiles point `model_catalog_json` at a provider catalog or the generated Codex catalog. The router's `GET /v1/models` also reads the catalog and adds configured Codex models when needed.
- **Regression coverage**: [`tests/model-routing-dry.test.ts`](file://tests/model-routing-dry.test.ts), [`tests/codex-model-catalog.test.ts`](file://tests/codex-model-catalog.test.ts), and the Control API model-list test verify routing assignments, provider catalog entries, the merged catalog, and the API model response stay in sync without pinning specific model IDs.

The editable provider/model choices live in
`config/model-routing.json`: `providerGroups` defines ordered fallback groups per capability tier,
`providers.<name>.models` contains named tiers such as `default` and `smart` (specific tiers like `smart` are optional and fall back to that provider's `default` model if omitted), and
`roles.<role>.tier` selects the tier for each capability role. Optional
`providers.<name>.links.usage` and `providers.<name>.links.documentation` hold
that provider's external usage/billing and documentation pages (absolute
`https` URLs, validated at load); the Control API exposes them on each provider
record and the Console's Providers row and provider detail render them. For example, set
Claude's smart model to `claude-opus-5-5` or Codex's to `gpt-6-sol` there. Providers may omit an optional tier and inherit their `default`; MiniMax defines a separate smart-tier model while its default remains unchanged. The installer materializes this file as
`$CODEX_HOME/codex-model-routing.json`.
Every model listed under a provider must match that provider's route
`pattern`, or the router refuses to load the file. The Claude route accepts
the family aliases (`sonnet`, `opus`, `haiku`) and Anthropic's lowercase,
hyphen-separated ids, so a mistyped `claude-opus-5.5` fails at startup (and in
the test suite) instead of turning every Claude turn into a CLI error. A valid
id still has to be supported by the installed Claude CLI: a newer model can
need `claude update` first, which the bridge reports as `invalid_model`.

Two providers serve Claude, so the model id alone has to name which one.
Antigravity's `agy` CLI encodes reasoning depth in the id itself
(`claude-opus-5-5-high`, `claude-sonnet-5-5-medium`), while Anthropic's own ids
carry no suffix (`claude-opus-5-5`). An effort-suffixed Claude id therefore
belongs to Antigravity and every other Claude id to the Claude bridge, and each
route's `pattern` encodes that split — which is what keeps
`validateProviderModelRoutes` from rejecting an Antigravity-served Claude model
as one that "routes to claude". `ANTIGRAVITY_MODEL_PATTERN` and
`CLAUDE_MODEL_PATTERN` in `runtime/src/shared/provider-model-ids.ts` are the
single definition of that boundary; the router's built-in routes and the proxy
lifecycle gates (`antigravity-ensure.ts`, `claude-ensure.ts`) all consume them,
so selecting an Antigravity Claude model starts the `agy` proxy and never the
Claude bridge.
For the `default` capability tier, the router randomizes Claude, Gemini/Antigravity, and MiniMax, then falls back to Copilot and OpenAI/Codex. For `smart`, it randomizes Claude, Gemini/Antigravity, and MiniMax, then falls back directly to OpenAI/Codex Sol. MiniMax's smart assignment uses MiniMax-M3.1-Flash-Preview; its ordinary/default assignment remains MiniMax-M3. Providers that are unavailable or return fallbackable limit errors are skipped and the next provider in the current group is tried before progressing to the next group. A skipped provider is not forgotten: if no candidate serves the turn, the router reconsiders the ones it skipped as a bounded last resort before giving up (see "Cooldowns and provider selection"):

1. `default`: Claude, Gemini/Antigravity, MiniMax (randomized), then Copilot, then OpenAI/Codex Luna
2. `smart`: Claude, Gemini/Antigravity, MiniMax (randomized), then OpenAI/Codex Sol

### Orchestrator routing and fallback

The root Codex orchestrator is not a leaf role, but it uses the same
`providerGroups` fallback machinery through a dedicated `autodev/orchestrator`
alias. `config/config.autodev.toml` sets the parent `model` to that alias
(composed into `$CODEX_HOME/config.toml`), and `config/model-routing.json`
defines its chain under the top-level
`orchestrator` block (`alias`, `tier`, and an optional per-provider
`reasoningEffort` map) plus a `providerGroups.orchestrator` tier and an
`orchestrator` entry in each provider's `models`.

The default order pins the primary provider and load-balances the rest:

3. `orchestrator`: OpenAI/Codex Luna, then Claude Opus, Copilot, and Gemini/Antigravity (randomized)

Differences from a role request:

- The orchestrator never consumes a per-session subagent slot; it is gated by
  neither `max_concurrent_threads_per_session` nor the process-fallback bucket.
- The primary provider is dispatched with the caller's own reasoning effort
  (`model_reasoning_effort` in the parent config). Fallback providers with a
  declared entry in `orchestrator.reasoningEffort` use that provider-specific
  effort (`claude` medium and `antigravity` high by default); Copilot uses its
  CLI-selected effort because its bridge has no compatible override.
- Usage telemetry keeps orchestrator fallback traffic under the `orchestrator`
  origin even when it lands on a non-Codex provider, rather than
  reclassifying it as `direct`.
- A direct concrete `gpt-*` request is still never rerouted. Only the
  `autodev/orchestrator` alias degrades across providers.
- The root-delegation `UserPromptSubmit` hook matches `autodev/orchestrator`
  before its leaf-alias glob, so the parent still receives the delegation
  policy while `autodev/<role>` leaves do not.
- Every outbound provider request carries an `x-autodev-agent-role` header the
  router generates from its own alias dispatch (`orchestrator` for the
  orchestrator alias, the role name for an `autodev/<role>` alias). Provider
  bridges select their role instructions from it, so an orchestrator turn that
  degrades onto a bridge-backed provider receives the orchestrator policy
  rather than the leaf policy. See "Agent role across the bridge boundary".

#### Active-subagent routing protection

When an orchestrator spawns subagents and then waits for their results, its
response turn ends but its session is not idle. The router keeps the
orchestrator in `subagent_wait` on its original provider as long as any of
these hold:

- The caller declared `hasActiveSubagents` (open concurrency slots or pending
  bridge children) when it ended the request.
- The orchestrator's session key has live child activity records (children
  tagged with the session key or referencing it as `parentRequestId`).

Because `subagent_wait` is a live state, `countLiveAgentActivity({ provider })`
still reflects the waiting orchestrator. The candidate ranking's
`liveProviderCount` therefore penalizes the occupied provider, and subsequent
orchestrator requests route to idle providers first. This prevents the
following cascade:

1. Orchestrator A starts on Claude and spawns subagents.
2. A's response turn ends; A waits for children.
3. **Without the protection**: Claude appears idle; the router sends
   Orchestrator B to Claude. A's children finish and A resumes — now two
   concurrent Claude orchestrators trigger rate limits.
4. **With the protection**: Claude reports `liveProviderCount: 1`; the
   router sends B to MiniMax, Gemini, or Copilot instead.

One agent is one Codex thread. A subagent shares its root's session key, so
its requests use a distinct `thread:<threadId>` activity subject, taken from
the canonical `thread-id` header, `client_metadata.thread_id`, or the turn
metadata Codex sends on every request, and tagged with the parent's session key.
The former `x-codex-thread-id` header is retired. Those requests refresh the
parent's TTL without overwriting its provider or role, and all of
one child's requests are one live agent: keying each request separately once
counted a child making 45 tool calls as dozens of live agents, each parked in
`tool_wait` until the TTL. The root's thread id equals its session key, so the
root keeps that subject. A caller that sends no thread id falls back to a
per-request `req:<requestId>` subject. When
the last child settles (slots released and bridge subagents closed), the
orchestrator transitions to `resumed` and continues its final integration
turn. If no children remain and the orchestrator's own turn is also done, it
transitions to `finished`.

The staleness TTL still applies: an orchestrator in `subagent_wait` whose
children all died without reporting back will age out of live counts once no
heartbeat arrives within `CODEX_ROUTER_AGENT_ACTIVITY_TTL_MS`, preventing
abandoned sessions from permanently blocking a provider.

### Diagnosing an agent that fails to create or stops unexpectedly

The Desktop message `Failed to create an agent` is a wrapper around several
independent failure boundaries; it is not evidence that the target repository's
code failed. First check the router `/status` snapshot and the provider bridge
logs, then classify the first failing boundary:

- **Native spawn admission:** Codex's `multi_agent_v1__spawn_agent` can be
  rejected by the app's available-thread limit or the configured
  `max_concurrent_threads_per_session` (currently `2` in
  `config/config.autodev.toml`). This is an admission/configuration failure, not
  a child code failure. A batch uses `Promise.allSettled`, so a rejected entry is
  returned as `Spawn failed: ...` and successful siblings remain trackable.
- **Antigravity process startup/transport:** `agy` can exit without a terminal
  result, return `status: ERROR`, or report `timeout waiting for response` / a
  network issue. The bridge returns a retryable upstream response and logs the
  terminal status, exit code, and a bounded stderr tail; it no longer reduces an
  empty terminal response to the unhelpful `completed without a response`
  message. A live `/health/liveliness` only proves the local adapter is alive,
  not that the upstream Antigravity service answered a turn.
- **Headless permissions and MCP scope:** in headless print mode (`-p`),
  `--dangerously-skip-permissions` is passed when `AGY_SKIP_PERMISSIONS=true`
  so unpromptable interactive permission gates do not crash turns. Read-only
  roles are sandboxed with agy's `--sandbox` flag. The bridge starts each `agy`
  turn in a temporary home containing only that role's contracted MCP servers and
  exact permissions. When a role contract declares a per-server tool list, the bridge
  also filters the MCP `tools/list` response and rejects direct calls outside
  that list. For a read-only turn, the temporary settings grant literal `read_file`
  access to the request's validated workspace, shared agent/codex roots, and the
  invocation's isolated home, preserve explicit denies, and do not inherit command,
  write, or `unsandboxed(...)` grants.
  User-configured `read_url(...)` rules remain separate from local file access.
  Write-capable turns keep their existing user non-MCP permissions. The global
  Antigravity settings and MCP registry are never modified by a request.
  `AUTODEV_AGY_READ_ROOTS` still
  configures installer-managed permissions for direct CLI use; router-managed
  turns use their validated workspace instead. If a native tool is denied in
  headless mode, the bridge returns an incomplete result with a typed,
  path-free failure diagnostic. The parent treats it as failed work, reports
  useful partial output, and does not retry a deterministic permission denial
  until its cause is corrected.
- **Workspace resolution:** bridge requests must carry structured workspace
  metadata (or an explicit `CODEX_PROJECT_ROOT`). The bridge fails closed rather
  than taking a repository path from task prose. Invalid requests are rejected
  before delegation state is opened, so a failed pre-flight cannot leave a stale
  spawn session attached to a later turn. The router also retains the last
  successfully resolved workspace for an identified conversation and restores
  it when a continuation drops the turn-metadata transport header. This is
  session continuity, not process-cwd discovery: anonymous sessions and
  invalid/ambiguous workspace claims still fail closed.

The most useful evidence is the bridge log line immediately after `agy request`:
`agy turn failed after ...: status ERROR; timeout waiting for response; ...`,
`agy workspace resolution failed: ...`, or a successful turn line. Router
`status` also separates provider failures from concurrency denials and records
which provider/model was selected. A clean provider health check with a failed
turn should be investigated as an upstream CLI/account/network or permission
problem, not as a target-repository build failure.

### Truncation reasons when an orchestrator turn cuts short

The router and all four typed provider bridges share one vocabulary for
why a turn stopped before it finished (`@simulatorlife/autodev-runtime/shared/provider-limits`
and the `tests/provider-limits.test.ts` mirroring test pin both sides).
`provider_limit`, `provider_timeout`, and `provider_interrupted` were the only
values through early 2026; the cluster of long-running antigravity-orchestrated
turns that died with "The antigravity provider stopped unexpectedly" without
any clue whether agy had crashed or the upstream had walked away led to the
addition of `client_disconnected`. The antigravity bridge detects the new
cause at the request handler -- it tracks the most recent delegator step in
a closure-scoped state object and routes `response.on("close")` and
`response.on("error")` to a `do-not-kill` branch that lets agy finish to its
`--print-timeout` instead of `SIGTERM`-ing it mid-delegation. The launchd log
distinguishes the two cases by name (`agy turn aborted-delegation` vs.
`agy turn aborted`); the truncation notice carries the new reason to any
future re-attach path.

The delegator step is not the child lifetime. `invoke_subagent` reports `DONE`
when its hand-off completes, while the child continues in the background and
agy may report that the root agent is waiting for background tasks. The bridge
therefore keeps a pending-child count separate from the active step: its
heartbeat continues while that count is nonzero, and a client disconnect does
not SIGTERM agy until the parent turn settles. This prevents the stream-idle or
15-minute upstream timeout from killing the process that owns still-running
children. A launchd line naming `agy turn aborted-delegation` confirms this
protected path; `agy turn aborted` means no active or pending delegation was
observed.

Adding a new reason is a small but cross-cutting change: the JS-side
the shared typed `INCOMPLETE_REASON_*` contract, each provider cause
ladder, and the tests that assert all bridges agree.

All providers are treated as capable of MCP, skills, and subagent spawning;
role TOMLs remain the sole source for role MCP/skill exposure and normal Codex inheritance.
Routing does not gate on duplicated provider capability declarations in
`config/model-routing.json`. The orchestrator's entire job is delegating,
so a provider serving it must have a viable delegation path. There are two
delegation paths:

- **Native Codex spawn** (`codex`, `minimax`): the parent drives Codex's own
  `multi_agent_v1` spawn tool, which creates a child thread that asks this
  router for an `autodev/<role>` alias.

  Note how that call actually reaches Codex, because it is not what the model
  catalog suggests. These models run in **code mode**: the request carries no
  `tools` array at all, and the entire tool surface arrives as a single `exec`
  tool -- declared `"type": "custom"` inside an `additional_tools` input item
  -- whose payload is raw JavaScript evaluated in a V8 isolate. The spawn
  function is reached from inside that script as
  `tools.multi_agent_v1__spawn_agent({ agent_type, message })` and is never
  named in the request. Two consequences worth knowing before changing
  anything here:
  - The role must travel as `agent_type`. `agent` is accepted and silently
    ignored, and the child comes back as a generic agent rather than the
    role that was asked for.
  - Fan-out happens inside one script (`await Promise.allSettled(tasks.map(...))`),
    which is why Codex sending `parallel_tool_calls: false` does not cap it. Settling
    each child independently keeps successful siblings visible when the configured
    concurrency limit rejects one child; the tool output names that rejected child
    instead of collapsing the whole batch into an opaque `Failed creating` error.
    The canonical `orchestration` skill documents this contract, and
    `buildSpawnToolCallOutput` in `runtime/src/agents/spawn-tools.ts` owns the
    shared script-and-event assembly; provider bridges only drain their
    per-turn delegation and attach the returned events.

- **Bridge-native spawn** (`antigravity`): the CLI behind the bridge
  delegates inside its own runtime -- Antigravity's `invoke_subagent` -- and no
  router request is made for the child. Claude is not in this category: it acts
  only through Codex's tools (see "Claude bridge: Codex executes every tool"),
  so a Claude orchestrator spawns with `tools.multi_agent_v1__spawn_agent`
  inside `exec`, exactly like a Codex-served one -- through the bridge's
  `autodev_spawn` shim, which is what turns that request into a real Codex
  child. Watched spawn tool names are defined in the execution contract
  (`providers.<provider>.spawnTools`); see "Counting subagents across providers".

  Antigravity's native subagent `Model` accepts tier aliases, not concrete
  model ids: the installed CLI accepts `inherit`, `flash_lite`, `flash`, and
  `pro`, and rejects an explicit Claude 5.5 id. With a Claude 5.5 parent,
  `Model: "inherit"` does run the child on that same Claude model; cross-model
  Sonnet/Opus targeting from a Gemini parent is not supported by this CLI.
  Google's [custom-subagent docs](https://antigravity.google/docs/subagents)
  document `inherit`, `flash`, and `pro` as the model tiers. The separate
  `autodev_spawn` Codex shim converts Antigravity child requests to
  `{ agent_type, message }` and does not forward the native `Model` field, so
  those real Codex child threads use their configured role/routing model rather
  than inheriting the Antigravity Claude model implicitly.

  Browser-capable bridge roles follow the same role contract as native Codex
  roles. A Claude turn reaches its role's MCP servers through Codex's own
  `tools` global, so Codex's role TOML -- including the Playwright tool
  allowlist -- is the only MCP boundary it has. Claude keeps its native
  `WebSearch` and `WebFetch` only on turns where Codex offered its hosted
  `web_search` tool, which no tool script can perform.
  Playwright is strictly reserved for UI and browser testing and is never exposed
  to the orchestrator. Antigravity's CLI reads MCP configuration from a global
  home directory, so the bridge gives each `agy` process an isolated temporary
  home containing only the current role contract's MCP servers. For servers
  with a tool allowlist, a stdio MCP policy process advertises and accepts only
  those tools. It carries the user's existing Antigravity state through without
  editing the global MCP registry or settings. The `browser-tester` tier now
  includes Antigravity; `browser-tester` and `smart` can use only their declared
  Playwright tools, while other roles (including the orchestrator) do not receive
  that server.
  A router-managed Antigravity leaf returns its report as visible final text;
  the bridge turns the CLI's terminal response into the Responses `output_text`
  received by the parent thread. Leaf instructions prohibit provider-local
  messaging, interactive waits, nested delegation, and hidden artifacts. An
  empty or failed CLI response remains incomplete rather than being presented
  as a successful summary.
  Antigravity also uses its native `search_web` and `read_url_content` tools
  backed by pre-approved `read_url(*)` permissions.
  Copilot explicitly allows `web_search` and `web_fetch` for research-capable roles
  without granting blanket `allow-all` permissions. MiniMax's adapter forwards `web_search`
  tool payloads unchanged; MiniMax's Responses API supports `web_search` natively.

  Copilot's CLI is in the orchestrator tier through the per-request
  `autodev_spawn` MCP shim. The shim collects the CLI's delegation request and
  returns a synthetic Codex `exec` item, so the child is created by Codex and
  counted as `router_alias` rather than as an invisible Copilot child. The
  static Rulesync MCP projection intentionally does not expose this server:
  its session-scoped URL and token are generated by the bridge for one root
  turn only.

  The Claude bridge is in the orchestrator tier through the same per-request
  `autodev_spawn` MCP shim. The Claude CLI has no delegation tool of its own
  -- it runs without `Agent`/`Task` -- so the bridge offers its model the shim
  and turns the request into Codex's own spawn, exactly as it does for
  Copilot. The shim is offered **independently of the tools Codex put on the
  request**: a Claude turn that Codex offered no tools to still gets the
  delegation surface, because the child is created by Codex rather than by the
  CLI. That independence is the point. A turn with no Codex tools has no `exec`
  cell, and a model that can only delegate through `exec` has no way to create
  a child at all -- which is what a bare request used to produce: a Claude
  model answering "no tools are available to me this turn".

- **A CLI bridge states the delegation call its own surface can serve.** The
  shared orchestrator prompt names the Codex-native surface
  (`multi_agent_v1__spawn_agent`, reached through the `exec` cell's `tools`
  global), because that is what a Codex-native model and the Claude bridge
  have. A CLI bridge has no such surface: the bridge reaches Codex through an
  MCP server, and the one delegation tool it actually serves -- the
  `autodev_spawn` shim -- has to be named the way that CLI names MCP tools.
  `runtime/src/agents/bridge-delegation.ts` owns the wording; the bridge
  passes how its CLI names an MCP tool (agy reaches every server through one
  `call_mcp_tool` built-in, so the call names `ServerName`, `ToolName` and
  `Arguments`; the Copilot and Claude CLIs advertise each tool directly, so the
  call names `mcp__autodev_spawn__spawn_subagent`). The instruction is published
  for exactly the turns the bridge holds delegation state for -- the spawn
  registry owns that fact -- so a turn that may not delegate is told nothing.

  The surface itself is the bridge's, and it does not depend on what the
  caller declared. The shim's launch has one owner
  (`runtime/src/agents/spawn-shim-server.ts`), which fixes the shim's path, the
  bridge it calls back, and the turn its calls belong to; each CLI renders
  that one entry in its own MCP config schema, and each delivers the shim's
  identity the way its own config can carry it safely: Claude and Copilot pass
  their config on the command line, so the entry carries the bridge's address,
  token and session inline, while Antigravity reads its config from a **file**
  in the isolated home, so that identity travels in agy's process environment
  instead -- a token written into a file outlives the turn. The session the
  calls belong to has one owner too (`openSpawnSession` in
  `runtime/src/agents/bridge-spawn-session.ts`), which is what decides whether
  the router identified the conversation the turn belongs to.

  This is not a formality. An Antigravity-served orchestrator turn
  (`01a19247-af45-7240-adc4-f1be011ffa44`) ran 821 `exec` calls and created no
  child: the shared prompt named only the Codex-native surface, and the
  bridge-injected shim was named `tools.mcp__autodev_spawn__spawn_subagent` --
  a name that exists only for a model that reaches MCP tools through Codex's
  `tools` global -- and the shim is an agy-side server, so it is not on
  Codex's global either. agy has no `tools` global of its own and advertises
  no MCP server names at all, so the tool that was present, registered and
  permitted (`spawnAllowed: true`, with `mcp(autodev_spawn)` already allowed)
  had no usable name.

- MiniMax delegates natively (`delegation: "native"`). It was marked `none`
  on 2026-09-17 ("no supported orchestration path"), before code mode moved
  every tool -- `multi_agent_v1__*` included -- into Codex's `exec` tool. The
  MiniMax proxy is a pass-through Responses adapter, so a MiniMax model gets
  the same `exec` surface a Codex-native model does and Codex runs its spawn
  calls; the `none` marking was stale. It serves the orchestrator tier once
  the operator gives it an Orchestrator priority.
- Codex CLI defines subagent tools in a `type: "namespace"` structure (`multi_agent_v1`). The
  router flattens namespaced tools into standard `type: "function"` definitions
  (e.g., `multi_agent_v1__spawn_agent`) on every non-Codex route and re-expands
  them in downstream responses. MiniMax's Responses API also accepts namespace
  tools natively and answers with the `namespace` set (verified live
  2026-09-15), so the MiniMax adapter forwards tools unchanged.

  The MiniMax adapter (`runtime/src/providers/minimax.ts`) also
  coerces **freeform tool calls**. MiniMax documents only `function` tools. It
  now usually answers Codex's code-mode `exec` with a native `custom_tool_call`,
  or calls the nested `exec_command` directly, which Codex executes. But it has
  also answered `exec` with an ordinary `function_call` carrying JSON arguments
  -- typically the `{cmd, workdir}` shape of `exec_command`. Local rollouts
  show 1,049 such calls coerced between 2026-07-14 and 2026-09-10. Codex rejects
  that outright with
  `tool exec invoked with incompatible payload`, which meant a MiniMax-served
  turn could reason but never actually run anything, and every such turn logged
  a burst of those errors. The proxy now rewrites those calls into a
  `custom_tool_call` whose script performs the same work, keeping the `event:`
  header and the terminal `response.completed` snapshot in step with the
  rewritten payload. Freeform tool names are learned from the request's own
  `"type": "custom"` declarations rather than hard-coded, and an argument shape the adapter does not recognise is never guessed at -- a wrong guess would replace a visible failure with a script that runs and does the wrong thing. Such a call instead becomes a script that throws an explanation naming only the argument keys, so the model learns what `exec` expects instead of repeating the same broken call.

### Item ids are corrected at the router, not in the adapters

Every item in a Responses request carries an `id` whose prefix encodes its type
-- `rs_` for `reasoning`, `ctc_` for `custom_tool_call`, `msg_` for `message`
-- and the OpenAI backend rejects the whole request when a prefix and a type
disagree:

```
Invalid 'input[18].id': '06ef3bc08924acade1facee14da0af2e_fc_0'.
Expected an ID that begins with 'ctc'.
```

Not every provider honours that contract. MiniMax mints ids shaped
`<32 hex>_rs` and `<32 hex>_fc_<n>`, and the freeform coercion above retypes a
`function_call` as a `custom_tool_call` while keeping the id it arrived with.
Codex stores whatever a provider hands back and replays it on every later turn,
so a single turn served by a lax provider poisons the session for good: the
next turn that lands on a provider which validates fails, and so does every
turn after it, because the history only grows. Because the orchestrator tier is
pinned to `codex` with `minimax` in its fallback group, and a fresh turn is not
a continuation and so is not pinned to the provider that served the last one,
one failover is enough to end a session.

`upstreamPayload` in `runtime/src/router/responses.ts` therefore rewrites any
non-conforming id on a self-contained item, using
`@simulatorlife/autodev-runtime/shared/responses-item-ids`. The router
is the right place for it rather than each adapter: it is the one point every
upstream call passes through, and since stored history is re-sent rather than
re-read, correcting outbound also repairs sessions that are already carrying
bad ids -- no rollout file is touched. The MiniMax proxy's id passthrough is
left deliberately alone; one normalisation layer is easier to reason about than
two that can disagree.

Three properties the rewrite has to keep:

- The replacement is `<prefix><sha256(original)>`, not a random value. The same
  item is re-sent every turn, and an id that moved between turns would change
  the serialised request prefix each time and defeat upstream prompt caching.
- `call_id` is never touched. A tool call and its output are paired by that
  field alone, so rewriting one side would strand the other.
- An item with no `id` does not acquire one. Codex legitimately omits it on
  some tool outputs, and an invented id would name an item the upstream never
  issued.

Normalisation runs on every route for self-contained items (messages, tool calls, and tool outputs). Requests that need a correction emit an
`item_ids_normalized` router event carrying the count, so upstream protocol
drift is visible immediately rather than as a dead session weeks later.

### Reasoning items are dropped when unresolvable, not rewritten

Reasoning items are fundamentally different from tool calls. While a tool call
carries its own name, input, and `call_id`, a reasoning item without
`encrypted_content` is only a _reference_ to an item the backend stored. Because
Codex requests operate with `store: false`, the OpenAI backend persists nothing;
an unencrypted reasoning item minted by a foreign provider (such as MiniMax's
`<32 hex>_rs` or bridge-minted activity summaries) has nothing to resolve to.
Rewriting its id to a conforming `rs_<32 hex>` simply converts a 400 format
validation error into a 404 (`Item with id 'rs_...' not found. Items are not persisted
when store is set to false`).

Encrypted content alone is not enough to establish continuity. Codex validates
the item id before decrypting the content, so a foreign encrypted reasoning item
whose id is still `<32 hex>_rs` is rejected with `Expected an ID that begins
with 'rs'`. Rewriting that id would not make another provider's ciphertext
portable; on a Codex route it is dropped along with other unresolvable foreign
reasoning items. A conforming `rs_` id and non-empty `encrypted_content` are
both required for the router to preserve a reasoning item for Codex.

Therefore, reasoning items are excluded from id rewriting. Instead:

- On Codex routes (`route.provider === "codex"`), `dropUnresolvableReasoning`
  drops reasoning items lacking `encrypted_content` or carrying a non-conforming
  id. Genuine OpenAI reasoning items with a conforming `rs_` id and
  `encrypted_content` are preserved. When foreign or malformed reasoning items
  are removed, the router emits a `foreign_reasoning_dropped` event with
  `droppedReasoningItems: <count>`.
- On non-Codex routes, reasoning items are passed through untouched so the
  provider that minted them retains its own reasoning continuity on subsequent
  turns.

When the orchestrator tier is genuinely exhausted, the router reports
`router_provider_exhausted` -- but only after the last-resort pass and the
bounded wait below have both failed. The status follows whether a retry can
help: `503` when one might, and a non-retryable `400` when none can. That covers
every candidate failing for a configuration reason (a model the provider
rejects, bad credentials) and every candidate being out of usage (a quota
exhausted, a session limit reached) or switched off. See "Retryable and
terminal exhaustion" below.
That distinction matters for the orchestrator specifically: its answer ends the
root turn and every child with it, so exhausting the tier is the most expensive
failure in the system and worth the extra attempts to avoid -- but an answer
that arrives as a 503 is one the client retries, and a client that retries a
request whose providers are all out of usage waits out the window with the turn
still open.

A subagent that comes back with `status: "incomplete"` is a normal, actionable
outcome rather than a lost turn: the child hit a limit partway through, and the
work it finished is in the response. An orchestrator reading one should use that
work and decide whether to re-delegate, not treat the turn as having produced
nothing. See "Partial results on provider exhaustion".

Provider availability is checked through local health endpoints and credential
checks. HTTP 429/5xx, quota, session-limit, high-demand, timeout, and
unavailable responses cause the router to try the next provider. A malformed
request is returned immediately rather than hidden by fallback. Streaming
fallback happens before response headers are sent; a provider that fails after
streaming has begun cannot be safely replayed. Claude's `rate_limit_event` is
informational when `rate_limit_info.status` is `allowed`; only a non-allowed
status is treated as a Claude limit.

### Cooldowns and provider selection

A cooldown is load-shedding advice, not proof a provider is dead. There are four
kinds, and which one applies decides both how long it lasts and whether the
provider can still be attempted when nothing else is left. `GET /status` reports
the kind as `cooldownKind`, with `cooldownFailureClass`, `cooldownResetsAt` and
`lastResortEligible` alongside it.

| Kind        | Applies to                                                                  | Duration                                                   | Last resort?                      | Survives a restart? |
| ----------- | --------------------------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------- | ------------------- |
| `transient` | any fallbackable failure, and any limit the router only inferred from prose | 30s doubling to 10min                                      | yes                               | no                  |
| `hard`      | `quota_exhausted` / `session_limit` that the **provider itself declared**   | until the declared reset, else a 15min floor, capped at 6h | only while no reset time is known | yes                 |
| `probe`     | a local bridge that did not answer its health check                         | 5s doubling to 30s                                         | yes                               | no                  |
| `config`    | `authentication`, and `invalid_model` for the rejected **model only**       | fixed 30s, never escalates                                 | no                                | no                  |

Six rules are load-bearing:

- **A client leaving is not a provider failing.** A stream that stops because
  the client disconnected (Codex Desktop archiving a thread mid-turn, a
  cancelled turn) is recorded as `499 client_aborted` and cools nothing down.
  Recording it as `upstream_error` once put Codex, the only orchestrator
  provider, into a 30s cooldown and failed every other session's root turn.

- **A rejected model is not a provider outage.** A provider answering
  `invalid_model` (the Claude bridge returns `400` with `code: "invalid_model"`
  when the CLI does not know the model or is too old for it) cools down that one
  model; the provider's other models keep serving, so a bad Opus id does not
  take Sonnet subagents down with it. If every candidate fails for such a
  configuration reason, the router answers `400 router_provider_exhausted` with
  `retryable: false`, `recommendedAction: "fix_configuration"`, no
  `retry-after`, and the provider's own explanation in the message. A `5xx`
  would only make Codex retry a request that cannot succeed.

- **A hard cooldown needs corroboration.** `classifyProviderFailure` matches
  keywords, and bridges put CLI stderr tails into error messages, so one stray
  "quota" in an unrelated crash could otherwise take a provider out for fifteen
  minutes. Only a provider _reporting_ a limit -- `x-autodev-limit-source:
reported`, from a Claude `rate_limit_event` or an upstream that sent the limit
  headers -- produces a hard cooldown. An inferred limit stays on the transient
  ladder.
- **Antigravity usage limits follow its separate model-family pools.** Its
  usage panel separates Gemini models from Claude/GPT models. The router maps
  Antigravity's Gemini ids to a `first_party` pool and its effort-suffixed Claude
  ids to a shared `third_party` pool, so exhausting Claude Opus or Sonnet does
  not take Gemini offline (and a Gemini limit does not disable Claude). All
  rate-limit failure classes (`quota_exhausted`, `session_limit`, and
  `throttled`) arm that pool scope on Antigravity; non-rate-limit failures and
  single-pool providers keep their provider-wide cooldown behavior. A successful
  request clears only its own pool, and `COOLDOWNS.get("antigravity", now)`
  reports a provider-level cooldown only when a provider-wide cooldown is active
  or both `first_party` and `third_party` pools are simultaneously cooling.

- **A cooldown belongs to the route that failed.** The router records a failure
  against the provider, the model, or the quota pool the failed route belongs
  to, and the scope follows the limit the provider reported: a pooled provider
  cools one pool, a rejected model cools one model, anything else cools the
  provider. `COOLDOWNS.get(provider, now, model)` is the lookup that resolves
  all three -- provider first, then the model, then the pool that model belongs
  to -- so a reader that asks a _provider_ whether it is cooling down gets the
  provider-wide answer, and reads `null` for a route that is out. `/status`
  reports the provider-wide cooldown as `cooldownKind` and names the routes
  that are out in `poolCooldowns` and `modelCooldowns`; the Control API reports
  the same two under `health.poolCooldowns` and `health.modelCooldowns`.

- **Per-provider, per-subprovider, and per-model quota discovery.**
  `runtime/src/providers/quota-discovery.ts` discovers live usage windows (5-hour
  limits, weekly limits, `% used` / `% remaining`, and reset times) and exposes
  them on `/control/providers` (`provider.quota` and `provider.health.quota`),
  overlaying active router pool/provider cooldowns and synchronizing exhausted
  windows or pools into `COOLDOWNS`:
  - **MiniMax:** Direct REST API query to `https://api.minimax.io/v1/token_plan/remains`
    using `MINIMAX_API_KEY` or the OAuth token in `~/.mmx/config.json`, with
    fallback to `mmx quota --output json`. Maps 5-hour interval and weekly limits
    across configured models (`MiniMax-M3`, `MiniMax-M3.1-Flash-Preview`, `MiniMax-M2.7`).
    `mmx` is not required as an npm or package dependency.
  - **Codex:** ChatGPT `/backend-api/wham/usage` and live `x-codex-*` upstream
    response rate-limit headers (5-hour primary and weekly secondary windows).
  - **Antigravity:** Google Cloud Code `v1internal:fetchAvailableModels` using
    the CLI's keychain/file OAuth token, separating `first_party` (Gemini) and
    `third_party` (Claude) subprovider quota pools and per-model quotas.
  - **Copilot:** `gh api /copilot_internal/user` (`premium_interactions` and
    `chat` snapshots).
  - **Claude:** Claude bridge `/health` (port 4000) `rateLimitInfo` captured from live
    `rate_limit_event` stream events, persisted across bridge restarts at
    `$CODEX_HOME/run/claude-rate-limit.json`, with subscription plan discovery from
    `~/.claude.json` / macOS Keychain (`subscriptionType: "pro"` -> Claude Pro Plan)
    and fallback to Anthropic OAuth `/api/oauth/usage`. Maps rolling 5-hour session and
    weekly windows across configured models (`claude-opus-5-5`, `claude-sonnet-5-5`).
    Every window comes from the event's `unifiedWindows` (the top-level fields only
    describe the window named by `rateLimitType`), and a window whose reset time has
    passed since the reading was captured reports as a fresh, unused window.

  In the Console UI, inline quota bars and reset countdowns render in each
  provider's `Status` cell on `/providers` and in each model's row on
  `/providers?tab=models`, while dedicated **Quota & usage limits** panels render
  on `/providers/:provider` (`ProviderDetailView`) and
  `/providers/:provider/models/:model` (`ModelDetailView`).
  `providerHealthReadiness` in `@simulatorlife/autodev-core` keeps a multi-pool
  provider `ready` whenever at least one pool has remaining usage and is not in
  cooldown, resolves model-scoped failures to their owning pool (keeping
  Antigravity ready when only its third-party Claude pool is exhausted), and
  does not leave a provider stuck in `unavailable` after a rate-limit or
  transient cooldown has expired. A failure that describes a condition which
  passes -- a rate limit, a throttle, a busy upstream, a timeout, a 5xx -- is
  live only while the Runtime is still cooling the provider down for it, and
  stops being live once that cooldown has passed: the Runtime routes to the
  provider again at that point, so the verdict has to agree with it. A failure
  that is not a condition but a fact about the provider (`authentication`)
  stays live until the operator fixes it. In addition,
  `createProviderQuotaDiscoveryService`
  polls provider usage limits every 60s in the background, keeping positive
  readiness evidence fresh.

- **Subagents and orchestrators stay with their session provider across turns.**
  Both orchestrator sessions (`noteOrchestratorSession`) and subagent sessions
  (`noteSubagentSession`) are tracked by the SubagentRegistry. Multi-turn
  subagent sessions and parked subagents reused for follow-up assignments retain
  their allocated provider (`subagentProviderForSession`) rather than reshuffling
  providers mid-session.
- **Short cooldowns on preferred providers are waited out rather than causing mid-session hops.**
  When an orchestrator or subagent session experiences a short transient, probe,
  or rate-limit cooldown (<= 30 s) on its preferred provider, `tryPrimaryRoute`
  waits for the cooldown to lapse (`canWaitOutStickyCooldown`) rather than
  switching providers mid-session. Mid-session hops are reserved strictly for
  unrecoverable hard limits or long exhaustion windows exceeding the wait window.

- **A route that cannot serve a request is not a provider failure.** A bridge
  whose transport cannot carry the request's content refuses it, before the
  provider is started, with the typed error `provider_request_unsupported`, and
  an upstream that rejects a prompt for exceeding its model context window
  (e.g. MiniMax `invalid params, context window exceeds limit (2013)`, OpenAI
  `context_length_exceeded`, or Anthropic `prompt is too long`) is classified
  under the same `unsupported_request` refusal class. The
  router reads that refusal as a fallback: the next candidate may serve the
  request, so the chain moves on and the provider stays healthy (a refusal cools
  nothing down and is recorded as the failure class `unsupported_request`, not
  as an outage). If a stateful primary route (such as Antigravity) was skipped
  only for a transient probe blip or cooldown when a stateless fallback route
  refuses the oversized transcript, the router proceeds to `last_resort` and
  `exhaustion_wait` on the stateful route rather than aborting the turn. A route
  that renders an image as text and answers anyway used
  to answer a question the model was never asked -- HTTP 200, a well-formed
  response, and a caller that read it as an answer -- so the refusal is the
  contract.
- **Stateful/web bridges floor downstream `usage.input_tokens` to the wire transcript estimate, and MiniMax bounds replayed transcripts.**
  Codex triggers native context auto-compaction (`compacted` rollout event)
  based on `usage.total_tokens` in the `response.completed` envelope. Stateful
  CLI and web bridges (`antigravity`, `claude`, `opencli`, `copilot`) execute a
  distilled prompt in their own persistent session and report `0` or delta-only
  `input_tokens`, which previously left Codex blind to wire transcript growth
  across multi-hour sessions. The router now floors downstream `usage.input_tokens`
  (and `usage.total_tokens`) on bridge responses to `estimatePayloadInputTokens(payload)`
  while preserving raw provider token counts on OpenTelemetry attempt spans. As
  defense-in-depth, the MiniMax adapter (`compactMinimaxInputItems` in
  `runtime/src/providers/minimax.ts`) strips bridge-only synthetic `rs_`
  reasoning summaries and empty assistant placeholder messages and bounds
  replayed `input` arrays to `MINIMAX_MAX_INPUT_CHARS` (default `3,000,000` JSON
  bytes, well inside MiniMax's `204,800`-token window) while preserving the
  initial setup prefix, `additional_tools` declarations, and `call_id` pairing
  on the most recent suffix turns. If required input cannot fit, the adapter
  returns a typed request-capability refusal for router fallback instead of
  forwarding an oversized payload. Sizing uses serialized UTF-8 bytes.
- **Every catalog model compacts at `auto_compact_token_limit`, at most 200k tokens.**
  Without the field Codex compacts at 90% of `context_window`, so 1M-window
  routes ran requests at 300k-900k input tokens: in 2026-11-09..11 rollouts,
  42% of all 1.62B input tokens were context above 200k and only 4 sessions
  ever compacted. `autoCompactTokenLimit` in
  `runtime/src/config/render-model-catalog.ts` is the policy
  (`min(90% of context_window, 200_000)`); the renderer applies it to Codex and
  role-alias rows, each provider catalog declares it per model, and
  `tests/codex-model-catalog.test.ts` rejects any row or profile that deviates.
  Provider profiles do not set `model_context_window` or
  `model_auto_compact_token_limit`; the catalog owns both.
- **Token-truncated catalog rows cap each tool result at `TOOL_OUTPUT_TOKEN_LIMIT` (6,000 tokens).**
  A tool result is re-sent on every later request until compaction; in
  2026-11-10..11 rollouts, results over ~20k characters were 12% of calls but
  58% of tool-output volume, mostly unscoped `rg`/`cat` dumps. Codex keeps the
  head and tail of a truncated result. Byte-truncated rows (MiniMax, opencli)
  already sit below the cap; the same catalog test enforces both.
- **What each transport can carry is a property of the CLI, not of the model.**
  The models behind these routes read images; what decides whether a route can
  serve an image-bearing request is the channel the bridge hands the turn to.
  The Claude CLI's print mode takes one NDJSON user message per turn, and that
  message accepts image content blocks, so the Claude bridge carries an image
  the user attached as an image block and the model sees the picture. The
  Antigravity CLI's print mode takes a text prompt, but it delivers an image
  _file_ to the model as media -- the tool that opens an image hands the model
  the picture itself -- so the Antigravity bridge writes the attachment into
  the invocation's own home, names the file in the prompt and in the agent's
  definition, and the model opens it before it answers. MiniMax is a
  transparent proxy, so the request reaches the upstream API with the image
  intact. The distinction is read once, in `shared/request-content.ts`, so the
  bridges and the router agree on what "this request carries an image" means.
  A route whose transport cannot carry the content at all -- the Copilot CLI
  takes a prompt and nothing more -- refuses the request rather than base64 it
  into a prompt, because answering without the picture is answering a question
  the model was never asked.
- **The router names a refusal for what it is.** A route that refused did not
  fail: it cannot serve _this_ request, and it is healthy. Reporting it as
  "available but did not complete the turn" sent the reader looking for an
  outage that was not there, and made providers with usage left look like the
  problem. The exhaustion body now says "cannot serve this request" and names
  the reason the bridge gave. When every candidate refused, no retry can serve
  the request -- the same request will be refused the same way -- so the answer
  is not retryable and carries no `retry-after`: a `retry-after` is an
  instruction to come back, and a client that honours it holds the turn open
  for exactly that long, with nothing to show for it. A candidate that is
  merely out of usage is different: its window lapses, so the request stays
  retryable and keeps its window.
- **Probe failures ride their own ladder.** A local bridge restarting says
  nothing about the provider behind it, and escalating the provider's own backoff
  for it was how a one-minute outage became a ten-minute one.
- **A cooldown only ever moves later.** A short probe cooldown landing on top of
  a long declared limit must not shorten it.

Selection then runs in up to three passes, and only answers if all three come up
empty:

1. **Primary (with sticky session continuity and short-cooldown waiting).** Every
   candidate that is not cooling, in tier order, with the session's sticky
   `preferredProvider` hoisted first (both across an orchestrator session and
   across a subagent's `thread:<threadId>` sub-session, even between tool calls).
   When the sticky preferred provider is in a short non-config cooldown (or
   hits a transient rate-limit/blip that sets a short cooldown) that expires
   within `CODEX_ROUTER_STICKY_COOLDOWN_WAIT_MS` (default 15s for role requests,
   and at least `CODEX_ROUTER_PROVIDER_COOLDOWN_MS` / 30s for orchestrator
   turns), the router waits out that short cooldown and retries the sticky
   provider once before switching providers mid-session. If the cooldown is a
   longer quota window, the router falls back to the next candidate without
   waiting.
2. **Last resort.** The candidates pass 1 skipped, capped at
   `CODEX_ROUTER_LAST_RESORT_MAX_ATTEMPTS` (default 2). Providers with no live
   agent go first, so concurrent exhausted requests spread over the skipped
   providers rather than piling onto one (the caller's own agent, often still
   live on the provider while it waits on its children, does not count); ties
   go to the soonest-to-lapse cooldown. A busy provider is ordered last, never
   excluded: Codex is the orchestrator tier's only provider and is nearly always
   live in some other session, and excluding it once turned a single transient
   failure into an instant 503 for every root turn for up to ten minutes, since
   nothing could make the attempt whose success clears the cooldown. Excluded:
   anything already attempted, a `config` cooldown, and
   a `hard` cooldown with a declared reset still in the future -- that provider
   has stated it will not serve yet, and attempting it anyway is exactly the
   hammering cooldowns exist to prevent. A success clears the cooldown, so the
   chain heals itself.
3. **Bounded wait.** If a cooldown lapses within
   `CODEX_ROUTER_EXHAUSTION_WAIT_MS` (default 20s), the router waits for it and
   makes one more attempt rather than ending the caller's turn. It happens before
   response headers, so the client sees a slow request rather than a stalled
   stream, and it is cut short if the client disconnects. Only a candidate whose
   lapse would let it serve is worth waiting for: a blip that clears, or a usage
   window the provider named as ending inside the wait window. A provider that
   said it is out of usage will not serve when its cooldown lapses, so waiting
   for it only delays the answer and re-attempts a provider whose quota is gone
   for hours on every window. Keep it small: a role
   request holds its subagent slot throughout, and the per-session limit is
   typically 2. An orchestrator turn holds no slot and its failure ends every
   child's work, so its window is at least one first-strike transient cooldown
   (`CODEX_ROUTER_PROVIDER_COOLDOWN_MS`, 30s): otherwise a single-provider
   orchestrator tier could never be rescued by waiting. Set
   `CODEX_ROUTER_EXHAUSTION_WAIT_MS` to `0` to disable waiting entirely. That is
   the wait window, not the cooldown: `CODEX_ROUTER_PROVIDER_COOLDOWN_MS=0`
   disables nothing, it silently falls back to 30s.

`CODEX_ROUTER_CHAIN_SELECTION_DEADLINE_MS` (default 120s) bounds how long the
router may spend _looking_ for a provider. It is checked only before starting a
candidate and never during one, so a long turn that lands on the last candidate
still gets the full `CODEX_ROUTER_UPSTREAM_TIMEOUT_MS`. If an in-flight provider
returns a fallbackable failure after the deadline, the router continues to the
remaining candidates: no response has been sent to the caller, and a slow quota
or availability failure must not suppress a healthy fallback. Without the
deadline, a tier of five hanging providers could hold a subagent slot for over
an hour.

All of these are millisecond environment variables, and every one of them except
the last is strictly positive: `0`, a negative value, or a non-number falls back
to the default rather than failing startup.
`CODEX_ROUTER_PROVIDER_COOLDOWN_MS` (30_000),
`CODEX_ROUTER_PROVIDER_COOLDOWN_MAX_MS` (600_000),
`CODEX_ROUTER_HARD_COOLDOWN_MS` (900_000),
`CODEX_ROUTER_HARD_COOLDOWN_MAX_MS` (21_600_000),
`CODEX_ROUTER_PROBE_COOLDOWN_MS` (5_000),
`CODEX_ROUTER_PROBE_COOLDOWN_MAX_MS` (30_000),
`CODEX_ROUTER_PROBE_TIMEOUT_MS` (700),
`CODEX_ROUTER_LAST_RESORT_MAX_ATTEMPTS` (2),
`CODEX_ROUTER_CHAIN_SELECTION_DEADLINE_MS` (120_000), and
`CODEX_ROUTER_EXHAUSTION_WAIT_MS` (20_000), which alone accepts `0` to mean
"never wait" instead of falling back. Because an unusable value is a silent
fallback rather than a startup error, a typo in one of the others leaves the
default quietly in place.

### Declared limits

A provider bridge that knows it hit a usage limit says so structurally rather
than only in prose, on both the streamed and non-streamed paths:

| Header                      | Value                                                                        |
| --------------------------- | ---------------------------------------------------------------------------- |
| `x-autodev-limit-class`     | `quota_exhausted`, `session_limit`, `throttled`, `capacity`                  |
| `x-autodev-limit-type`      | the provider's own window name, e.g. `weekly`, `five_hour`, `session`        |
| `x-autodev-limit-resets-at` | ISO-8601 UTC                                                                 |
| `x-autodev-limit-source`    | `reported` (the provider said so) or `inferred` (a bridge matched free text) |

A stated reset is kept on the cooldown entry whether or not it is trusted long
enough to sleep through. An `inferred` limit stays on the transient ladder — the
corroboration rule above is unchanged, and a long sleep is still not taken on the
strength of free text — but the window the provider named survives into
`cooldownResetsAt` and the exhaustion body. The two times routinely disagree, so
both are reported rather than one standing in for the other:

```text
antigravity: quota_exhausted, provider reports usage resets in 25m
  (2026-10-14T16:47:21.728Z); retrying in 480s
```

Reporting only the provider's reset would overstate the wait, since the router
will in fact retry sooner; reporting only the ladder hid the window the provider
had just given. When the retry lands on the reset within a minute the single time
is enough and is stated once.

The same shape appears as `error.limit` in a failure body -- a non-streamed
one, or a stream's `response.failed` -- and as
`response.incomplete_details.provider_limit` on a stream closed as incomplete,
so the router reads one shape wherever it finds it. `@simulatorlife/autodev-runtime/shared/provider-limits` is the single implementation imported by all
typed bridges, with `tests/provider-limits.test.ts` guarding the boundary.

Only `reported` corroborates a hard cooldown. A bridge classifying its CLI's
error text always reports `inferred`, which is enough to pick a better HTTP
status and a `Retry-After` but never enough to strand a provider for the hard
window.

### Partial results on provider exhaustion

A turn cut short after streaming has begun cannot be replayed on another
provider, so whatever the model already produced is all the caller will ever get
for that turn. It used to be discarded: the bridges emitted a bare
`response.failed` and threw away every token they had already sent, leaving the
parent with an error string in place of a partial result it could have acted on.

Once a CLI bridge has emitted an output item, it closes an interrupted turn
as an _incomplete_ response instead, in this order (a failure before the first
output item never reaches this epilogue -- see the next section):

```
response.output_text.delta          (a truncation notice, appended to what the client already saw)
response.reasoning_summary_text.done / _part.done / output_item.done   (reasoning, status "incomplete")
response.output_text.done / content_part.done / output_item.done       (message,   status "incomplete")
response.completed { status: "incomplete", incomplete_details: { reason, provider_limit } }
data: [DONE]
```

`incomplete_details.reason` is `provider_limit`, `provider_timeout` or
`provider_interrupted`. The truncation notice is deliberately in the text a model
will read, not only in metadata: a partial answer mistaken for a complete one is
worse than a failure.

This is not a way of reporting success. `responseWasNotCompleted` treats any
status other than `completed` as a provider failure, so the turn still counts as
a failure, still cools the provider, and now cools it on the class the provider
reported rather than a generic `upstream_error`.

The router applies the same contract as a backstop for what the bridges cannot
cover -- the bridge process being killed, or the socket dropping under it. A
stream that ends without a terminal event is closed by the router itself,
carrying the text it had already forwarded. The invariant: **the router never
ends a started stream without a terminal event.**

The `codex` route is the exception to the _incomplete_ shape, not to the
invariant. Its upstream is the stateless Responses API: nothing ran outside
Codex, so the request can simply be sent again, which is exactly what native
Codex does when a chatgpt.com stream drops. A dropped or stalled Codex stream is
therefore closed with a retryable `response.failed` and Codex replays it under
its own `stream_max_retries`. Closing it as a finished incomplete turn instead
stopped the orchestrator with "[Incomplete: The provider stopped unexpectedly
...]" after every network blip (observed 2026-09-24).

### Falling back from a stream that failed before any output

A bridge that opens its stream at once -- opencli, whose turns can outlast the
router's wait for response headers -- reports every later failure inside it. Read as an
HTTP exchange that is a success, so no such failure could fall back: the
router forwarded it, Codex retried, and the retry came back to the same
provider -- every time, for a refusal, which sets no cooldown.

A stream that has sent no output has told the client nothing it cannot be told
again, so the router treats its failure as the candidate's, not the turn's:

- **What counts as output.** Anything other than `response.created`,
  `response.queued`, `response.in_progress` and the terminal events. Those
  lifecycle events are forwarded as they arrive -- Codex accepts a second
  `response.created` and a different response id on one stream (replayed
  against Codex 0.167) -- so nothing is buffered and a healthy stream is not
  delayed.
- **What is withheld.** The terminal failure of a stream with no output:
  `response.failed`, a `response.completed` whose status is not `completed`,
  or the stream breaking off. The router records it as it would an HTTP
  failure -- class, limit (`response.error.limit`), cooldown, router event --
  and asks the next candidate, which answers on the same client stream.
- **While the stream is held** between candidates, the router sends
  `response.in_progress` every 15 seconds, which is what resets Codex's stream
  idle timeout (an SSE comment does not). Sticky-cooldown and exhaustion waits
  apply to a held stream exactly as they do before the response has started.
- **When the chain runs out** the held stream ends with one `response.failed`
  carrying the chain's account of every candidate, the same text a
  non-streamed request gets as its error body.
- **After output has started** nothing changes: the failure is the turn's and
  is forwarded, since another provider's answer would be spliced onto half of
  this one's.

Every bridge keeps a turn that failed **before its first output item** free of
output, so the router can try the next provider without mixing partial
results. How it says so depends on whether its stream is already open:

- **Claude, Antigravity and Copilot** hold the response -- headers and the
  `response.created` preamble alike -- until the CLI produces its first real
  output (text, a reasoning step, a tool call), so a failure before that point
  is still an HTTP answer: a 429 for a usage limit, carrying the declared
  limit as `error.limit` plus `x-autodev-limit-*` and `Retry-After` headers,
  and a 503 (or the bridge's typed 4xx/502) otherwise. No SSE is written, so
  there is no `response.output_item.added` and no incomplete epilogue. The
  router reads it as any HTTP failure and falls back.
- **opencli** must open its stream at once (a site's reply arrives whole,
  minutes later), so it reports the same failure inside the stream: one
  `response.failed` whose `response.error` carries the failure `type` and,
  for a site limit, the declared `limit` -- the case this section exists for.
- **MiniMax** is a pass-through to MiniMax's own Responses API: it forwards
  the upstream's status and events unchanged and adds no epilogue of its own.

After an output item has been emitted, every CLI bridge instead uses the
incomplete-response epilogue above to preserve partial text; the router cannot
switch providers for that turn. The pre-output and post-output halves are
pinned per bridge by the `provider_limit_before_output` and
`provider_limit_incomplete` cases in `tests/fixtures/contracts/` (Claude,
Copilot), by `tests/antigravity-stream-failure.test.ts` and the Antigravity
contract fixture, and by `tests/providers/opencli-routing.test.ts`;
`tests/router/stream-fallback.test.ts` guards the router side.

## Observability

The router makes its effective choice visible in two ways:

- Every response includes `x-autodev-provider`, `x-autodev-model`, and
  `x-autodev-request-id`. For a role request such as `autodev/explorer`, these
  identify the concrete provider/model selected after shuffling, load balancing,
  health checks, and fallback.
- An exhaustion response additionally carries `x-autodev-limit-class` and
  `x-autodev-limit-resets-at` for the soonest-resetting candidate, alongside
  `retry-after`.
- Router events carry a `selection` field naming the pass that chose a provider:
  `primary`, `last_resort`, or `exhaustion_wait`. The `phase` is unchanged, so
  every existing counter keeps working; `selection` only says how hard the router
  had to look. A waiting request also emits its own `exhaustion_wait` event.
- Per-provider `/status` entries report `orchestratorEnabled` and `subagentEnabled`
  (independent administrative booleans), `orchestratorStatus` and `subagentStatus`,
  plus overall health `status` (`"ready"` or an active cooldown failure class), `cooldownKind`,
  `cooldownFailureClass`, `cooldownResetsAt`, `cooldownUntil`, `cooldownRemainingMs`,
  `lastResortEligible`, `failureStreak`, and `probeFailureStreak` alongside the
  cooldown countdown, configured models, capabilities, and attempt/outcome counters.
  `configuredModels` is the model each configured tier is routed to
  (`RoutingPolicy.effectiveModels`): the Console assignment for the role that
  governs the tier (`orchestrator` or `subagent`) when the operator set one,
  else the routing config's. `agentModels` lists only the agent roles given a
  model of their own on that provider (`{"explorer": "opencli-chatgpt-fast"}`),
  which win over `configuredModels` for that role.
- The status payload exposes structured `routing` metadata (`status.routing`):
  `configSource` (`"default_codex_home"` or `"env_override"`), `configFileExists`,
  `orchestrator` (`alias`, `tier`, and pinned `reasoningEffort`), configured capability `roles`,
  `providerGroups` (ordered priority groups per tier), `configuredProviders`,
  `enabledOrchestratorProviders`, `disabledOrchestratorProviders`,
  `enabledSubagentProviders`, `disabledSubagentProviders`, and the active route map (`routes[*]` with
  pattern, `baseUrl`, `healthUrl`, `envKey`, and `credentialConfigured`). Secret API keys and
  absolute configuration paths are strictly excluded.
- The status payload exposes structured `limits` metadata (`status.limits`):
  the active effective thresholds for provider cooldowns (`providerCooldownMs`,
  `providerCooldownMaxMs`), hard limits (`hardCooldownMs`, `hardCooldownMaxMs`),
  probe checks (`probeCooldownMs`, `probeCooldownMaxMs`, `probeTimeoutMs`),
  `lastResortMaxAttempts`, `exhaustionWaitMs`, `chainSelectionDeadlineMs`,
  `upstreamTimeoutMs`, retry parameters (`upstreamRetryBaseMs`,
  `upstreamRetryMaxMs`, `concreteStatusMaxAttempts`, `upstreamTransportMaxAttempts`),
  `shutdownDrainTimeoutMs`, and `maxConcurrentThreadsPerSession`.
- The live `/status` payload reports the effective Codex per-session
  concurrency limit, the number of active session buckets, active role-based
  subagent slots, and denials caused by that limit. An active session is a
  session currently holding at least one role-based subagent slot; it is not a
  count of every Codex task or process connected to the router. The default
  local configuration permits one active subagent per session; callers must
  serialize additional work or deliberately raise the
  configured limit after checking provider capacity. The deprecated `max_threads`
  alias is no longer parsed, surfaced, or used as a fallback; only
  the canonical Codex key `max_concurrent_threads_per_session` -- multiline
  `[agents]` block or composer-generated inline `agents = { ... }` table --
  feeds admission. Role requests are gated before provider selection;
  direct concrete model requests
  are not counted as subagent slots. Session identification resolves explicit session
  headers or metadata (`session-id`, `x-codex-session-id`, `x-session-id`,
  `x-conversation-id`, `payload.session_id`, or turn metadata `session_id`).
  When explicit session fields are absent, the resolver falls back to the
  canonical Codex `thread-id` (or `x-thread-id` / metadata `thread_id`) as an
  identified session key (`scope: "identified"`), matching root Codex threads
  where thread ID equals root session ID. Only if neither session nor thread
  identifiers are supplied does the router fall back to the process-wide shared
  bucket (`scope: "process-fallback"`), where unrelated anonymous sessions can
  deny one another. `/status` exposes `processFallbackEnforcement` and
  `processFallbackActiveThreads` to make this unsafe fallback visible.
- They also aggregate usage by origin (`orchestrator`,
  `subagent`, or `direct`), role, and resolved provider/model. Each bucket
  includes attempts, outcomes, average/max turn duration, and tool-call counts
  inferred from Responses output items. A `role` request is classified as a
  subagent; a direct Codex model request is classified as orchestrator-originated.
  This is an operational inference: the router sees HTTP turns, not the full
  lifetime of a Codex session, and tool-call counts cover calls represented in
  Responses events only. The JSON `/status` payload keeps `usage.byOrigin` and
  `usage.byRole` as separate, unmodified buckets.
- Usage is also aggregated under `status.usage.byWorkspace`. Each workspace
  bucket contains a privacy-safe repository label (remote `owner/repository`
  when available, otherwise the cwd basename), the cwd basename, totals, and
  nested `byRole`, `byModel`, and `byProvider` dimensions. Full absolute paths,
  prompts, credentials, and remote URLs are not stored. Missing workspace metadata is attributed to
  `unknown` rather than guessed from the router daemon's cwd. The workspace
  bucket's scalar `toolCalls` is a response-output count inferred from
  Responses API tool-call items on that workspace's turns, the same inference
  the top-level `usage.totals.toolCalls` uses -- it is not a count of
  OTLP-named tool invocations. Historical/cross-workspace visualization belongs in the AutoDev Console **Usage** surface, not a router-local HTML dashboard.
- A workspace bucket may additionally carry `bySkill`, `byMcp`, and
  `bridgeTools`/`bridgeSkills`. These rows come from local causally-linked
  evidence: AutoDev request context and authenticated provider-bridge reports.
  The router no longer receives OTLP, so nothing else contributes to them.
  When resolving telemetry context across MCP, tool, skill, and bridge events, the router applies canonical precedence:
  (1) explicit event or resource attributes, (2) verified provider bridge or request context,
  (3) verified `conversation.id` -> session/thread-state join, and (4) `unattributed`.
  The router does not require Codex to emit `workspace_id`, does not distribute
  global metrics by guesswork, never infers ownership from static configurations or
  ambient concurrency, and attributes events lacking verified metadata to explicit
  `unattributed` dimensions. Requested and executed provider events remain separate.
- Role accounting keeps explicit Orchestrator, Subagent, and Unattributed buckets. Role-less activity stays `Unattributed` rather than being guessed into either role, and the buckets reconcile to `usage.totals.active`.
- `status.subagents` counts every subagent spawned behind the router,
  regardless of which provider spawned it and by which mechanism. This is
  distinct from `usage.byRole`, which counts _router requests_ made by
  subagents: a bridge-native child makes no router request at all, so it
  appears in `status.subagents` and nowhere else. `runtime/src/cli/router-status.ts` prints it under
  `Subagents spawned:`. See "Counting subagents across providers".
- The router-local HTML dashboard has been retired. Use `GET /status` or `pnpm autodev -- router status` for live diagnostics and the AutoDev Console **Usage** surface for historical/aggregate observability. Do not add new UI behavior to the router status endpoint.

### Grouped usage sections in the human CLI report

The human report from `runtime/src/cli/router-status.ts` renders the three usage
breakdowns together as one ordered group rather than spacing them across the
telemetry output. After a blank-line separator following the `Concurrency:`
summary, the report prints
`Usage by origin:`, `Usage by role:`, and `Usage by resolved model:` in that
order before any Codex OTEL or skill telemetry section. Each heading is
emitted even when its bucket is empty so the section order stays stable.

All three sections share one formatter for their per-row layout:
`<label>: <attempts> attempts, <successes> successes, <failures> failures, avg <avg-s>s, <toolCalls> tool calls`,
where `<avg-s>` is `Math.round(averageDurationMs / 1000)`. The origin row is
the only one that prepends an active-count prefix, yielding
`<label>: <active ?? 0> active, <attempts> attempts, ...`; the role and model
rows omit that prefix. The `--json` flag continues to print the unchanged wire
JSON and does not render these headings.

### Live agent activity vs. in-flight requests transport diagnostics

The `/status` provider projection is limited to configured router routes. A
missing provider identity is an attribution defect surfaced through
`liveAgentAttribution`, not a synthetic `unattributed` provider row. Provider
and model dimensions therefore contain only concrete router-selected values;
`unattributed` remains reserved for non-provider residual dimensions.

The router cleanly separates user-facing agent workflow activity from transport-level network requests:

- **Live agent activity (`Active` badges, KPIs, provider rows):**
- **Frozen `status.agents` reconciliation projection:**
  The router emits `status.agents` with schema `autodev-agent-status-v1`.
  `canonicalLiveCount` is the single canonical live-agent count, evaluated
  from `projectLiveAgents(at)` at the same `now` `getRouterStatus(now)`
  passes through. Live-status consumers must read this field exclusively rather than falling back to `status.liveActivity` or `status.usage.totals.active`. `byState`
  is the complete tracker histogram (live states, terminal `finished`/
  `failed`, and derived `stale`). `liveByKind` counts only actual agent
  kinds (`session` and `bridge_subagent`), never `subagent_slot`
  admission bookkeeping. `liveByRole`, `liveByOrigin`, and
  `liveByWorkspace` are live-only numeric partitions and retain an
  explicit `unattributed` residual; `liveByProvider` and `liveByModel`
  contain only concrete routed values, while records without attribution
  are surfaced through `missingProvider` / `missingModel`. `slotVsAgent` reconciles
  `agentLive`, `admissionSlots`, `activeAdmissionSessions`, and
  `processFallbackActiveThreads` against `status.concurrency`;
  `reconciledWithConcurrency: true` confirms all counters were evaluated
  at the same timestamp. The fixture and contract test in
  `tests/fixtures/contracts/agent-reconciliation-contract.json` and
  `tests/agent-reconciliation-contract.test.ts` freeze this shape.
- **Canonical live-agent count and role breakdown:** Consumers read
  `status.agents.canonicalLiveCount`, `status.agents.liveByRole`, and
  `status.agents.liveByWorkspace` directly. It never takes a `Math.max()`
  of that canonical count against provider active-request counts
  (`status.providers[*].active`) or concurrency-slot counts
  (`status.concurrency.activeSubagentThreads` / `activeSessions`),
  because those are transport and scheduling counters, not agent identities.
  The orchestrator/subagent/residual buckets sum to the canonical count;
  role-less activity remains an explicit `unattributed` residual instead
  of being guessed into a role.
- **Parent orchestrators remain live while children work:** Authenticated
  bridge spawn events may keep the explicitly identified parent request live,
  carrying the concrete provider/model selected for that request. A workspace
  containing children is not sufficient evidence to create a parent or provider row.
- **Workspace attribution is non-additive context:** The KPI's
  `workspaces with active agents` count comes directly from
  `status.agents.liveByWorkspace`, excluding `unattributed`/`unknown`.
  It is displayed next to `Active agents` as attribution context and is
  never summed into the agent total.
- **Concurrency slot counts are scheduling context, not agent counts:**
  `status.concurrency.activeSubagentThreads` and `activeSessions` remain
  admission counters. `status.agents.slotVsAgent` makes their relationship
  with live agents explicit without folding slots into the KPI.
- **In-flight requests transport diagnostics (`inFlightRequests`):**
  Represents currently open HTTP connections between the router daemon and upstream model provider endpoints. It is surfaced separately in the Status CLI's dedicated `In-Flight` column and must not be conflated with live-agent identity.

### Lifecycle event contract and configurable TTL

The router coordinates with agents and tool hosts via an explicit lifecycle event contract:

- **Normalized activity events (`{ type: "activity", state, childIds? }`):**
  the router settles every request itself from the response it relays -- a response ending in a tool call leaves the agent in `tool_wait`, one needing input in `user_wait`, a final answer `finished` (or `subagent_wait` while its children are live), an error `failed`. Provider bridges add only what the router cannot see: `{ type: "activity", state: "subagent_wait", childIds? }` while their own in-CLI subagents run and `resumed` when the last reports back (Antigravity), plus non-transitioning `heartbeat` refreshes. The endpoint refuses bridge-reported `tool_wait`/`user_wait`/`finished`/`failed`: they repeated the router's settlement late, and a per-response `finished` arriving after the router's `tool_wait` ended a working agent between two tool calls. Every event applies to the agent the reporting request belongs to (its activity subject, one per Codex thread), never to the session key an orchestrator shares with its subagents -- keyed that way, a MiniMax-served explorer's reports overwrote its orchestrator's record (observed 2026-09-19). User waits are never inferred from arbitrary assistant text.
- **Configurable freshness TTL (`CODEX_ROUTER_AGENT_ACTIVITY_TTL_MS`):**
  Configured via `CODEX_ROUTER_AGENT_ACTIVITY_TTL_MS` (defaults to `300000` ms / 5 minutes).
- **Activity states:**
  - `active`, `resumed`, `tool_wait`, `user_wait`, and `subagent_wait` count as live activity.
  - `finished` and `failed` are terminal.
  - An open agent request remains live until it settles. Silent non-terminal wait activity older than the TTL is reported as `stale` and removed from live counts without killing or restarting active processes.
- **Heartbeat freshness and the `Active agents` KPI:**
  Every lifecycle event refreshes that agent's last-seen timestamp, acting
  as a heartbeat. `status.agents.canonicalLiveCount` -- and therefore the
  `Active agents` KPI total, its role breakdown, and the `workspaces with
active agents` context count -- only counts entries whose heartbeat is
  still within the TTL window above. If an agent goes silent (its client
  vanished, or a bridge crashed mid-request), that agent ages out of every one of those counts
  once its heartbeat exceeds the TTL; there is no separate "stale but still
  counted" bucket in the KPI -- stale activity simply stops contributing to
  the canonical live count, and `status.agents.byState.stale` reports the
  abandoned count separately for diagnostic visibility.
- **Orchestrator `subagent_wait`:**
  An orchestrator whose response turn has ended but whose children are still
  active stays in `subagent_wait` on its original provider. Children's
  streaming touches keep the parent's TTL fresh, and the parent transitions
  to `resumed` only after all children settle. See "Active-subagent routing
  protection" above for the routing implications.

To verify the live router is receiving caller identities, inspect
`.concurrency.lastDenial.sessionScope` in `/status`; `identified` means the
per-session key was supplied, while `process-fallback` means anonymous callers
are sharing one bucket.

The router accepts the session/conversation identity from the explicit session
headers and body metadata, and also from `session_id` or `conversation_id` in
the structured `x-codex-turn-metadata` JSON. It never derives a session key
from a workspace path or task text.

The same status payload's `correlation` includes the router's live correlation with
the agents it serves: the bridge tool/skill/MCP events, the MCP servers the bridges
reached, and the skill usage. The canonical telemetry ownership, OpenLIT ingestion, and Usage semantics are defined in [`docs/autodev-console-target-state.md`](autodev-console-target-state.md).

Read-only roles (`explorer`, `docs-researcher`, `validator`, and
`browser-tester`) run with filesystem access broad enough to inspect approved
runtime state such as `$CODEX_HOME`/`~/.codex` and localhost diagnostics. Their
role instructions remain read-only: they must not edit, stage, commit, or push
those paths. The broader sandbox is intentional because Codex's `read-only`
policy restricts reads outside the active workspace; the parent must explicitly
scope any external inspection.

Router stderr is structured JSON (`autodev-router-event-v1`) and is retained by
launchd in `$CODEX_HOME/run/codex-model-router.launchd.err.log` (stdout uses
the sibling `*.out.log` so structured events are never interleaved with
incidental output). Every event of a request carries the Codex `thread` that
sent it (from the `thread-id` header or `client_metadata.thread_id`, noted
once when the request arrives), so a subagent's requests can be told apart
from a sibling's on the same role; the `autodev-session-diagnostics` skill
relies on it. The direct ensure fallback writes its own log at
`$CODEX_HOME/run/codex-model-router.fallback.log` and records its tracked
PID at `$CODEX_HOME/run/codex-model-router.fallback.pid`; both files are
created with mode 0600 inside a mode 0700 directory so the local user keeps
sole read/write access. Override the fallback paths with
`CODEX_MODEL_ROUTER_FALLBACK_LOG` / `CODEX_MODEL_ROUTER_FALLBACK_PID_FILE`
when sandboxing requires a different writable location. The legacy world-
writable `/tmp/codex-model-router.log` path is gone.

Every Control API change that reaches the Runtime -- accepted, refused or
failed -- is an `autodev-control-api-audit-v1` line in the same log. A change
the Console turns away before forwarding it never reached that audit, so the
Console's provider, model and agent mutation routes write their own line,
`autodev-console-mutation-rejected-v1`, to the Console's stderr
(`$CODEX_HOME/run/codex-autodev-console.launchd.err.log`): the route, the
resource, and a cause (`cross_origin`, `invalid_target`, `invalid_body`,
`invalid_return_path`, `invalid_fields`, `control_api_unconfigured`,
`runtime_rejected` with the Runtime's status and code, or
`runtime_unreachable`). It carries codes, never submitted values or messages.
A role change that shows in neither log never left the browser. An operator's
Disabled orchestrator role once reached neither the Runtime nor any log, and
the next session was routed to that provider with nothing to say why.

The router ensure hook rotates the launchd and fallback logs to a `.1` sibling
once they pass the same size budget, so a crash loop cannot fill the disk, and
it prints the tail of `codex-model-router.launchd.err.log` when the router fails
to come up under launchd. That tail is the first thing to read when an install
reports a launchd start failure: a crash-looping router usually names its own
cause there.

`$CODEX_HOME/run/` is the canonical home for router run-time state. The
installer creates it with mode 0700 on every run, and the launchd plist writes
its logs there too, so all router
operational data survives reboot, tmpfs clears, and `/tmp` rotation.

Provider counters, recent events, and the
versioned privacy-safe OTEL aggregate section are also persisted atomically in
`$CODEX_HOME/codex-router-state.json`, so they survive router restarts. Active
requests and in-flight sessions reset, and so do `transient`, `probe` and
`config` cooldowns -- those are the router's own guesses about a moment that has
passed, and a restart is a legitimate reason to go and look again. A `hard`
cooldown survives: a provider that declared it is out of usage until Tuesday is
still out of usage on Tuesday, and the router restarts often enough under launchd
that dropping it would put it straight back to re-probing an exhausted account.
Restored cooldowns are dropped if already past and re-clamped to
`CODEX_ROUTER_HARD_COOLDOWN_MAX_MS` on the way back in.
Failure classes include `session_limit`,
`throttled`, `quota_exhausted`, `capacity`, `timeout`, `unavailable`,
`authentication`, `invalid_model`, and `probe_unavailable` (a local bridge that
did not answer its health check). Of these, only `session_limit` and
`quota_exhausted` are _hard_, and only when the provider declared them. These are observations from upstream
responses and local health checks, not a provider's authoritative quota API;
the persisted counters remain available after the router process restarts. Use
the router instance ID and request ID to correlate a turn with its fallback
history. Rotate logs by restarting the router: launchd closes and reopens the
log file handles, and the ensure hook reuses the same fallback PID file
without leaking a stale tracker.

### Provider administration and disable semantics

Provider role enablement and model enablement are mutable runtime state. The supported control boundary is the dedicated AutoDev Control API, not the model-router HTTP surface:

- `GET /control/providers` (v2) returns each provider's route, credential presence, role enablement, tier models, priority groups, orchestrator reasoning effort, and live router health.
- `GET /control/models` (v2) returns each model the routing config maps a provider tier to, with its provider, tiers, and enablement.
- `PATCH /control/providers/:provider/roles/:role` and `PATCH /control/models/:model` accept only `{"enabled": boolean}`.
- Mutations require operator authorization, are audited, persist atomically, and roll back the in-memory change when persistence fails.
- `POST /control/providers/:provider/check` re-checks one provider now (operator-only, audited, no body): the router runs its live probe and that provider's model listing (`checkProvider` in `runtime/src/router/http.ts`) and answers with the check and the provider's health after it. A passing probe clears a probe-failure cooldown; a failing one starts one, as routing does; a declared quota or rate-limit cooldown stays. The check is kept as `lastCheck` in provider health (and persisted), and `providerHealthReadiness` counts a passing check newer than the last failure as recovery. A failed or empty model listing is retried by discovery itself (30 s, doubling) as well. A provider that is configured but has no route is known to the Control API, so its check answers rather than failing: there is nothing to probe, and the answer is a failing check with the `missing_route` failure class. A provider the Runtime does not know at all is still refused.

The router may retain a loopback-only direct mutation endpoint temporarily as a compatibility implementation detail while callers migrate, but it is not an AutoDev Console/API contract and must not be used by new UI or automation. The canonical target is to remove duplicate mutation paths.

#### Operator priorities decide tier membership and order

Each provider has four Console roles, each with a priority (`P1`, `P2`, `P3`
or `Disabled`), a model, and a reasoning effort. Which assignment governs a
request depends on the tier it routes through
(`RoutingPolicy.tierAssignment`):

- `orchestrator` governs the orchestrator tier;
- `default` and `smart` govern the tier of the same name;
- `subagent` governs the traffic of every subagent tier the operator has not
  given a role of its own (such as `browser-tester`), and its `Disabled`
  switches the provider off for all subagent traffic, direct concrete requests
  included.

One assignment governs both a provider's rank in a tier and whether it is
enabled for the role, and a tier the operator has said nothing about is
governed by the role that governs the traffic through it. The `default` tier
holds the subagent roles (explorer, worker, validator, playtester), so a
provider the operator enabled for subagents with no role of its own for that
tier serves it: reading the tier's rank from the tier's own role alone left
such a provider enabled for subagents and never asked, while the Console
reported it as enabled for them. A tier the operator _did_ speak for keeps
that answer: `Default: Disabled` keeps the provider out of the default tier
whatever its subagent role says.

`providerGroups` in `config/model-routing.json` is only the default ranking.
`RoutingPolicy.effectiveProviderGroups` overlays the operator's assignments: a
provider assigned `P<n>` for the governing role joins group `n` of that tier,
whether or not the config lists it there, and one assigned `Disabled` leaves
the tier. A provider neither listed nor assigned does not serve the tier. The
assignment's model and effort then apply to that tier. The orchestrator tier
additionally admits only providers whose execution-contract `delegation` is
not `none`, however they are ranked. `GET /control/providers` (`tiers`,
`priorities`) and the router status report these effective groups, so the
Console's Routing priority panel shows the order in force.

A provider that cannot serve a tier is dropped before the chain runs, without
a word: it is switched off, its role is disabled, or its model is. The
refusal that follows names the providers the chain tried and, since
`RoutingPolicy.excludedProviders`, the ones it never asked and why -- an
operator who had enabled a provider for the role could otherwise not see why
it was never used.

Before this, the priorities were persisted and reported but never read:
order came from the config alone, and the `default`/`smart` assignments
steered nothing.

#### Reasoning effort on a provider role

`PATCH /control/providers/:provider/roles/:role` carries a role's whole
assignment: a `priority`, the `model` the operator chose, and the
`reasoningEffort`. The effort is checked against the reasoning levels the
assigned model's catalog entry declares, and the catalog that owns a model is
the provider's own (`config/catalogs/<provider>-model-catalog.json`), with the
generated Codex catalog carrying the models the Codex profile routes.

The Runtime refuses an effort only when it can show that the model does not
support it:

- A model whose catalog entry declares levels must be given one of them. An
  effort the catalog contradicts is refused with
  `autodev_control_api_bad_body`.
- A model no catalog declares has _unobserved_ levels. The Runtime cannot show
  that such a model refuses an effort -- only that no catalog states which
  efforts it supports -- so the operator's effort is kept and
  `supportedReasoningLevels` is reported empty. A provider offers models its
  catalogs do not describe: the Claude account's own model list is the
  provider's, and refusing those made every one of them unassignable.
- An effort names the model it applies to, so a write that names no model
  carries no effort, and the role keeps the effort its configured model
  resolves.

The Console shows the effort in force in the effort cell even when the levels
are unobserved, so a role that runs at an effort the operator cannot change
does not read as a role whose effort is unknown.

#### Persistence and default behavior

- **Default state:** A provider with no assignment for a role is enabled for
  it at the rank `providerGroups` gives it; one the routing config does not
  list for a tier serves that tier only once it is assigned a priority.
- **Immediate atomic persistence:** Every accepted Control API change -- a
  role's priority, model and effort, a provider's or model's enablement, a
  provider's limits, a reset -- is applied and written to
  `$CODEX_HOME/codex-router-state.json` (`roleAssignments`,
  `disabledProviders`, `disabledModels`, `providerLimits`) in one serialized
  step, through a temporary file renamed into place. A write that cannot be
  persisted is rolled back and answered 500, so it never steers routing.
- **Survives restarts:** the router reads the file at startup and restores
  every section; an assignment for a provider no longer configured is
  skipped. A role set to Disabled keeps its model, and disabling and enabling
  the whole provider leaves the role's own Disabled in place.
- **Only the router writes the file.** There is no implicit persistence
  manager: the router module sets one, and anything that persists without it
  fails. Every test script loads
  `runtime/tests/support/isolate-codex-state.ts`, which points
  `CODEX_ROUTER_STATE_FILE` at a temporary file. Before both, the Control API
  tests replaced the live router's file with an empty state on every run
  from a maintainer's shell (91 such 94-byte writes were found stranded beside
  it), and a router that restarted before saving again came back with every
  role at its default.
- **Tested end to end:** `tests/router/role-change-persistence.test.ts` drives
  a role change from the Console's form route through the Control API over
  HTTP into routing, reads the state file, restarts, and checks the provider
  is still excluded -- including after the provider is disabled and enabled
  again -- and that an unpersisted change is rolled back.

#### Disable semantics across routing tiers

Role controls are independent:

- **Subagent role:** A provider disabled for subagents is omitted from capability role
  aliases and all subagent fallback passes. Direct concrete model requests use this role
  and fail with HTTP 400 `router_provider_unavailable` when their provider is disabled:
  no retry reaches a provider that is switched off.
- **Orchestrator role:** A provider disabled for orchestrators is omitted from
  `autodev/orchestrator` candidates, including session-continuation preference hoisting.
- **Both roles:** Disabling both roles reproduces full provider exclusion. If every provider
  for a requested role is disabled, the router returns HTTP 400
  `router_provider_exhausted` with `failureClass: "provider_disabled"`.

Each skipped candidate records skip reason `"disabled"` and failure class
`"provider_disabled"`; disabled providers are never probed, attempted, or counted against
attempt budgets for that role.

#### Model disable semantics

A disabled model is removed from every tier its provider serves with it, for both roles:
the provider is skipped for those tiers (it does not fall back to its `default` model), and
other providers in the tier's groups serve instead. A direct concrete request that names a
disabled model fails with HTTP 400 `router_provider_unavailable` and
`failureClass: "model_disabled"`. Fallback passes re-check enablement before each attempt, so
a model disabled mid-request is skipped with failure class `"model_disabled"`. A provider
that is itself disabled for the role reports `"provider_disabled"` first.

#### Provider and model controls

The retired router HTML dashboard is not a control surface. Provider-role and model mutations belong to the dedicated AutoDev Control API:

- `GET /control/providers` and `GET /control/models` return configuration, live state, and current enablement.
- `PATCH /control/providers/:provider/roles/:role` and `PATCH /control/models/:model` accept only `{"enabled": boolean}`.
- Mutations require the Control API's operator authorization, persist the setting, audit success/failure, and roll back the in-memory value when persistence fails.
- The AutoDev Console renders these controls in **Providers**: each provider's role toggles on its Providers row and detail page, and each model's toggle on its Models row, its detail page, and its provider's model list. Console routes forward to the authenticated Control API; browser code never calls a router-local endpoint. **Agents** shows provider eligibility read-only and links to Providers.

### Local provider/workspace diagnostics

The router extends the live `usage.byWorkspace` diagnostic contract with first-class event counters so attribution can fail closed on per-workspace tool and skill evidence. A workspace must receive a first-class event from a provider
bridge before its `bySkill` and `byMcp` rows move off the `unavailable`
state; the bridge's report is the only evidence the router holds, because it
no longer receives OTLP.

The new fields on every `usage.byWorkspace[*]` bucket are:

- `toolsExecuted`: count of `tool_executed` events the bridge reported for
  this workspace. Reaching a positive value is what unlocks per-workspace
  tool attribution.
- `toolsRequested`: count of `tool_requested` events. A model that asked
  for a tool but never ran it still moves this counter so diagnostics can
  distinguish "the provider never offered the tool" from "the provider
  offered it but something stopped it from running".
- `toolsUnavailable`: count of `tool_unavailable` events with the workspace
  where the bridge refused a tool (workspace settings, permission deny).
- `skillsExposed`: count of `skill_exposed` events. The first `skill_exposed`
  for a workspace is what unlocks per-workspace skill attribution.
- `bridgeTools`: the raw `tool_executed` rows the bridge reported for this
  workspace (`{ tool, server, count, byStatus }`). It is the workspace's tool
  list: the router's OTLP-sourced twin was deleted with the receiver.
- `bridgeSkills`: the raw `skill_exposed` rows the bridge reported for this
  workspace (`{ skill, count }`) -- evidence a skill was made available to the
  workspace, not that it was used. This is a distinct claim from `bySkill`
  (confirmed uses, the same source as `skillUses`): a workspace can have
  `bridgeSkills` entries with zero `bySkill` entries. Consumers must keep exposure and confirmed use distinct rather than folding them into one count.

The router also persists a derived snapshot of the local Codex state
database under `status.codexState`. The collector is read-only, opens
`state_5.sqlite` via the Node `node:sqlite` binding (or reports
`schema_only` when the binding is unavailable), and surfaces:

- `localTelemetry`: a capability report describing the open outcome
  (`ok`, `missing`, `schema_only`, `schema_unknown`, `error`, `pending`),
  the schema fingerprint, the bounded recency window, and the recent
  thread / project / edge counts.
- `recentThreads`: the threads the collector could read inside the bounded
  window, each normalized to a privacy-safe `owner/repository` workspace key,
  a `cwdBasename`, and the resolved `projectId`. Raw absolute paths never
  appear in the snapshot.
- `conversationThreads`: a `conversation.id` -> thread id join. The
  router cannot derive this from the request stream alone; the collector
  is the only component that owns this lookup.
- `spawnEdges`: `parent_thread_id` -> `child_thread_id` edges for the
  recent window.
- `projects`: the `projects` table rows Codex uses to group threads.

The path defaults to `$CODEX_HOME/state_5.sqlite` and is overridable via
`CODEX_STATE_DB_PATH`. The recency window defaults to 24h
(`CODEX_STATE_COLLECTOR_WINDOW_MS`) and the bound defaults to 500
(`CODEX_STATE_COLLECTOR_LIMIT`). A live poll refreshes the snapshot every
5s by default (`CODEX_STATE_COLLECTOR_POLL_MS`); the snapshot is also
refreshed on demand by `/status` calls. The persisted router state does
not contain the collector snapshot -- it is rebuilt from the file on
every router restart.

The collector never writes to `state_5.sqlite`. The router persists the
derived workspace counters and bridge observations under its own
`codex-router-state.json`, never the Codex-owned state file.

## Provider CLI versions

Every provider AutoDev routes to is served by a CLI, and the CLI's release is
the first thing an operator needs when a provider behaves differently than it
used to: a release note names a version, and a bug report needs one. Nothing
measured it, so the Console now reads it from the Runtime.

The Runtime reads the version from the binary it would actually spawn. The
Claude Code CLI is `CLAUDE_BIN` or `~/.local/bin/claude`, the Antigravity CLI
is `AGY_CLI_PATH` or `~/.local/bin/agy`, the Codex CLI is resolved by the
shared lookup the MCP launcher uses, the MiniMax CLI is `mmx` on `PATH`, the
Copilot CLI is resolved by the shared lookup the bridge uses, and opencli is
the package entry point the lockfile pins. The bridges and the version read
resolve the same files, so the number beside a provider is the number in use
rather than the number some other installation reports.

Each CLI is asked with `--version`, and the first dotted number in its output
is the version: `claude --version` prints `2.1.280 (Claude Code)`,
`codex --version` prints `codex-cli 0.154.0`, and `agy --version` prints
`1.5.3`. The read is bounded twice over -- the CLI has a deadline and its
output has a size bound -- and it happens in the background every ten
minutes, off the request path, because a Control API request must not wait on
six CLIs to answer a question about six numbers.

`GET /control/provider-versions` answers with one entry per provider. Each
entry is `observed` (the command, the version, and when it was read) or
`unavailable`, and the unavailable case says which kind it is: `not-installed`
(the CLI is not on this machine) or `not-readable` (it is there and would not
answer). A Runtime that has not started the discovery says so for every
provider rather than reporting a version it did not read.

The Console shows the version under the provider's name in the providers
table and in the header of the provider's own page. It is small text on
purpose: the version matters when an operator is comparing it with a release
note, and it is not worth a column of the table to say so. The provider,
requested-model and Skill filters do not narrow it -- the versions are a
property of the machine, not of a request -- so the page says which CLI a
provider is served by rather than implying the number was filtered.

## Supervision, liveness, and graceful drain

The router is supervised by a `KeepAlive` launchd job
(`com.codex.model-router`) so it survives app restarts, crashes, and sleep. The launchd plist lives at
`config/launchagents/com.codex.model-router.plist` and is materialized
under `~/Library/LaunchAgents/` by the installer. Five provider services are
materialized from portable templates, and the installer verifies their rendered
content before restarting them. Three contracts separate
"the process is alive" from "the process can serve":

- **Liveness** — `GET /health/liveliness` (or `/health`) returns
  `{"status":"ok","router":"codex-model-router"}` with HTTP 200 whenever the
  router's HTTP server is bound to `127.0.0.1:4100`. It does _not_ reflect
  upstream provider health; it only certifies that the router itself is
  alive enough to answer HTTP. Use it for `launchctl`-style "did the bind
  succeed" checks and for the ensure hook's readiness probe.
- **Readiness** — `GET /health/readiness` returns HTTP 200 while the router
  accepts work and HTTP 503 with `router_draining` while it is shutting down.
  It describes router lifecycle readiness, not the health of every upstream.
  Use `GET /status` for the detailed per-provider health, cooldown countdowns,
  live agent activity, in-flight request diagnostics, and `usage` snapshots needed to decide
  whether an upstream is usable.
- **In-flight drain** — on `SIGTERM`/`SIGINT` the router stops accepting new
  `/v1/responses` work and gives in-flight requests up to
  `CODEX_ROUTER_SHUTDOWN_DRAIN_MS` (30s by default) to finish before
  forcefully aborting them. It then persists its state, closes any connection
  still open, and exits. The plist sets `ExitTimeOut` to 45s
  so launchd's SIGKILL lands after the drain window completes, not in the
  middle of it. `ProcessType=Standard` keeps the router out of macOS's
  throttled background tier: every Codex request passes through it, and a
  `Background` job is starved of CPU and disk I/O whenever the machine is busy.

The `scripts/ensure-codex-model-router.sh` hook prefers the installed launchd
job and falls back to a direct `nohup` process only when launchd is genuinely
unavailable (for example, from inside the Codex sandbox where `gui/$UID` is
not reachable). It acquires an atomic private lock directory at
`$CODEX_HOME/run/codex-model-router.ensure.lock.d` so concurrent invocations
cannot race the bootstrap/nohup path. When the job is not loaded, the hook
bootstraps it (`RunAtLoad` starts it); when launchd owns a job that is not
answering, the hook `launchctl kickstart -k`s it; a healthy process is left
alone; the direct fallback is never allowed to start a duplicate `nohup`
next to a launchd job that is bound to the port. When launchd is the
supervisor but the router never becomes ready, the hook fails loudly
instead of masking the failure with a duplicate unmanaged process.

The fallback path records its PID in `codex-model-router.fallback.pid`
(mode 0600). A later ensure call reuses the recorded PID when it is still
alive and healthy, recycles it via `SIGTERM` (so the router can drain)
when it is alive but the port is unhealthy, and clears a stale PID file
before starting a new one when the previous process is gone. When an
untracked process already owns the port, the hook refuses to start a
duplicate and surfaces the conflict in the log; an operator must stop
the foreign owner (or hand the job to launchd) before the ensure hook
will bind. Readiness polling is bounded (default 5s total budget,
exponential backoff capped at 1s) so a slow bind surfaces quickly and the
hook never burns CPU waiting.

The installer respects the same preference: it links every launchd plist, then
`bootout`/`bootstrap`/`kickstart` cycles each label on the `gui/$UID` domain.
It does this on every run, not behind a flag -- installing new code and leaving
the old code running is not an install, and it fails silently, because the ports
stay healthy and the files on disk look correct either way. The router drains
in-flight requests on the `SIGTERM` that `bootout` sends, so a turn in progress
finishes rather than being cut off. The readiness probe loop in
the installer waits for the router (and each provider bridge) to bind
before the ensure hooks run, so the hooks observe healthy ports and
no-op instead of racing the agents.

## Retry and error correlation

Every proxied router response carries correlation headers:

- `x-autodev-provider` — the concrete provider selected after shuffling,
  load balancing, health checks, and fallback.
- `x-autodev-model` — the concrete model dispatched to that provider.
- `x-autodev-request-id` — the per-router-request UUID. It remains stable
  across provider fallback within one request; caller-side retries may have
  a new ID. Pair it with `x-autodev-router-instance-id` and
  `routerInstanceId` from `/status` to correlate a turn across restarts and
  the structured stderr event stream.
- `x-autodev-router-instance-id` — the router process instance that handled
  the request, useful for detecting a restart during an incident.

chatgpt.com's Codex backend has been observed recycling a pooled keep-alive
connection without warning, including immediately after a prior request on
that connection completed, which surfaces as an
ECONNRESET/EPIPE/UND_ERR_SOCKET write failure while the router tries to reuse
it for the next request. Rather than only retrying around this, every `codex`
route request sets `Connection: close` on the outbound request so it always
opens a fresh connection and is never drawn from Node's pooled keep-alive
connections -- removing the race at its source instead of catching it
downstream. Other routes run on the local loopback, are unaffected by this
failure mode, and keep reusing pooled connections.

A connection reset, broken pipe, connect timeout, or other pre-response
transport failure is retried in place on the same provider -- for a direct
concrete request and for every candidate of a role or orchestrator fallback
chain alike -- up to 3 attempts in total (tunable with
`CODEX_ROUTER_UPSTREAM_TRANSPORT_RETRY_LIMIT`). A severed connection says
nothing about the provider, and native Codex simply reconnects; only once the
attempts are spent is the provider cooled down and the chain moved on. Before
this, each EPIPE on an upload to chatgpt.com cooled Codex, the orchestrator
tier's only provider, and failed the root turn outright. Transient direct
concrete provider failures additionally get one retry of a completed HTTP
502/503/504 response, which is real signal, before the router returns a
structured error. Retries use a jittered 200–400ms delay by default and can be
tuned with `CODEX_ROUTER_UPSTREAM_RETRY_MS` and
`CODEX_ROUTER_UPSTREAM_RETRY_MAX_MS`; the router never retries after response
headers or client cancellation. The
response includes
`router_provider_unavailable`, the provider/model/request and router-instance
correlation fields, and a `retry-after` header after the provider is cooled
down. Concrete model requests are never silently rerouted.
Router-generated provider errors include stable `code`, `retryable`,
`failureClass`, `provider`, `model`, `requestId`, and `routerInstanceId`
fields in the JSON error object. Transport failures are logged as structured
`transport_error` events with only sanitized error name/code/syscall fields;
raw exception text, credentials, prompts, and upstream bodies are not exposed.
When no provider can complete a role request -- after the primary, last-resort
and bounded-wait passes have all failed -- the router returns a
`router_provider_exhausted` error code and the same `x-autodev-request-id`
header. The status is HTTP 503 with a `retry-after` header sized to the provider
cooldown window when another attempt might serve the request, and HTTP 400 with
no `retry-after` when none can (see "Retryable and terminal exhaustion").

The consumer of that error is a model deciding what to do next, so it carries
enough to act on rather than four repetitions of "cooldown active". `error.details`
holds `retryAfterMs`, `resetsAt`, `lastResortAttempts`, `selectionDeadlineReached`,
the per-candidate `providers[]` summary (`state`, `failureClass`, `resetsAt`,
`retryAfterMs`), and a `recommendedAction`:

- `summarize_and_yield` when every candidate is out of usage. There is nothing to
  retry into; the right move is to return a summary of the work completed so far.
- `fix_configuration` when every candidate failed for a configuration reason.
- `retry_after` otherwise, with the wait in `retryAfterMs`.

### Retryable and terminal exhaustion

The status of an exhausted request answers one question: could another attempt
serve it? Codex retries a 5xx, so a failure no retry can fix must not be one --
and it must not carry a `retry-after` either, because a client that honours that
header holds the turn open for the whole window with nothing happening in
between. Observed 2026-10-27: every provider the orchestrator tier could reach
was out of usage (Codex's ChatGPT quota, Antigravity's individual quota
"resets in 35h", Claude's session limit, Copilot disabled). The router answered
`503` with `retry-after: 8224`; Codex waited the two hours out and the turn
never ended.

So an exhaustion is terminal -- HTTP 400, `retryable: false`, no `retry-after` --
when every candidate is out of usage, switched off, or misconfigured. The
provider's own window still travels in `x-autodev-limit-resets-at` and in the
message, so the reader knows when to come back. It is retryable -- HTTP 503 with
a `retry-after` -- when some candidate failed for a reason another attempt could
clear: a blip, an unreachable bridge, a turn that did not complete.

The class that decides this is the one the request saw, not the one sitting in
the cooldown entry. A usage limit does not always earn a long cooldown -- an
inferred limit stays on the transient ladder, so the provider looks briefly
unavailable even though its quota is gone for hours -- and a later attempt
against the same provider supersedes the entry's class, because a cooldown only
ever moves later.

For the same reason the bounded wait below only spends itself on a candidate
whose lapse would let it serve: a blip that clears, or a usage window the
provider named as ending inside the wait window. A provider that said it is out
of usage will not serve when its cooldown lapses, so waiting for it only delays
the answer the caller needs now, and re-attempts a provider whose quota is gone
for hours on every window.

The message text says the same thing in prose, naming each provider and its reset
time, because that is what a model actually reads. Concurrency denials return HTTP
429 with `retry-after: 1` and the same `x-autodev-request-id`.

A started stream never ends without a terminal event on any of these paths: an
exhausted chain, a concrete-request failure, or an internal router error will
close the stream rather than leaving the caller with a truncated body that is
indistinguishable from a hung provider. Recent spawn failures retain request IDs and reasons in live status/event diagnostics so the same header can be traced from the API call through the router's event log.
The router's `concurrency.scope` is `router-admitted-child-requests`:
`activeSubagentThreads` reports only child requests currently admitted by the
router, not open Codex app child handles or provider CLI processes. Cumulative
`denials` and `spawnFailures` remain historical diagnostics. A Codex app
`thread limit reached` error can therefore occur while this router reports zero
active requests. The root delegation hook injects an executable current-parent
recovery preflight: when Codex App `read_thread` is available, it reads only
that parent's `collabAgentToolCall.receiverThreadIds`, waits each child, and
calls `close_agent` only for terminal statuses. The same owner-scoped preflight
is emitted before bridge-driven native spawn batches when the bridge has the
parent session id. The owning orchestrator can therefore reclaim terminal
handles before retrying; no global cleanup is safe.

The concurrency status carries the configured limit as `maxConcurrentThreadsPerSession`,
and it has three states rather than two. A number is a config file that was read and
declares that limit; `null` is a config file that was read and declares no limit, which
is the default deployment; and an **absent** field is a config file that was there and
could not be read, so nobody knows what it declares. The limit in force is
`effectivePerSessionLimit`, and it is published separately for exactly that reason: a
config file nobody read leaves the router enforcing no cap at all, which would be a
cap the operator set silently disappearing if the status reported it as a file that
declares no limit. `configFileExists` answers whether the file is there, which is a
different question from whether it could be read. The same status is published by
`/control/runtime`, `/control/routing`, and the router's `/status`.

`configSource` names where the limit in force came from, and it is a closed vocabulary
of three: `stored_override` for a stored override, `config_file` for the limit the
config file declares, and `default` for nothing that could be read declaring one. It
used to carry the config file's _location_ under this name -- `default_codex_home` or
`env_override` -- which is a fact about the read rather than about the limit; that
fact now travels as `configFileSource`. The limit's source and the file's location
are two different questions, and one field cannot answer both: when it tried, the
value the Console read was a value the router never published.

Its reasons are `provider_exhausted`, `selection_deadline` (the router spent its
provider-selection budget without finding one),
`max_concurrent_threads_per_session`, and `spawn_tool_unavailable`. Only child
requests count: a root orchestrator turn that exhausts its tier spawned nothing,
so it is reported through its `router_provider_exhausted` result, not here.

### Streaming resilience and keep-alives

Streaming responses (`stream: true`) to clients such as Codex Desktop are protected against idle disconnects and client disconnect cascades:

- **Downstream SSE Keep-Alives**: The router automatically transmits periodic `: codex-router keep-alive\n\n` SSE comments every 2 seconds while streaming. This prevents the downstream HTTP client (e.g. Codex Desktop's reqwest transport) from triggering an `idle timeout waiting for SSE` during quiet intervals when an upstream model or bridge is busy running tools, spawning subagents, or reasoning.
- **Client Disconnect Resilience**: When a downstream client disconnects or cancels mid-stream, write calls are guarded (`safeWrite`) against closed/destroyed response sockets, and the response stream absorbs socket errors (`EPIPE`, `ECONNRESET`, `ERR_STREAM_DESTROYED`, `ERR_STREAM_WRITE_AFTER_END`). Normal client socket drops are recorded as ignored transport events rather than escalating to fatal uncaught exceptions that would crash the router process. A disconnect also cancels the upstream request, whether or not the provider has answered yet, so a provider is never left working for a client that is gone; the request is recorded as `499 client_aborted` and never counts against the provider (see "A client leaving is not a provider failing").

## External-provider execution

The normal CLI path for an external role remains the repository launcher. It
starts the selected provider hook and local CLI profile:

```sh
scripts/run-provider-agent.sh \
  --role explorer --prompt 'Bounded task; report evidence.'
```

The caller specifies only the role. Direct terminal sessions use the tracked
`autodev/<role>` aliases through `local_model_router`; provider selection and
fallback remain inside the router. The launcher applies an explicitly configured role reasoning effort when one is
present, plus summary mode and sandbox settings; otherwise it leaves reasoning
effort unset so the active model or provider profile supplies the compatible
default.
The native app-server path is also configured and verified, but the desktop
high-level fanout service does not currently delegate through it.

The router can reroute a role request only after the Codex process has reached
the configured `local_model_router` and sent a request for an `autodev/<role>`
alias. It can retry another provider when that provider returns a fallbackable
response or becomes unavailable. A failure in the app-server before its model
request is emitted (for example, failure to create the child thread or resolve
its environment) never reaches AutoDev and cannot be redirected by this
router. Concrete provider model requests are intentionally not rerouted because
they represent an explicit provider choice; use a role alias for fallback.

All spawned roles are leaf agents. Native role aliases (`autodev/<role>`) and
external-provider model aliases are therefore excluded from the root
delegation hook; only the configured parent model receives that instruction.
For a Claude turn the bridge launches the real Claude Code CLI with
`--tools ""` (only `WebSearch,WebFetch` when Codex offered web search), so the
CLI has no `Agent`/`Task` tool and no other built-in tool at all. That CLI flag
is the enforcement: this repository carries no `.claude/settings.json`, so a
direct Claude Code session opened here is not bounded by it. Whether a Claude
turn may spawn is decided by Codex, exactly as for a Codex-served turn: only
the orchestrator's `tools` global carries `multi_agent_v1__spawn_agent`.
The root-delegation hook also exempts Claude model aliases,
while native `autodev/*` roles are excluded by their role alias, so leaf
providers do not receive the parent-only instruction to spawn more agents.
Keep these restrictions at the CLI/gateway boundary rather than
relying only on role prompt text. Provider bridges must treat the active
working directory as transport metadata and must never infer it from arbitrary
task prose. If no valid structured workspace is present, the bridge fails
closed with a diagnostic instead of silently selecting AutoDev; an explicit
`CODEX_PROJECT_ROOT` remains available only as an operator-controlled fallback
for intentionally pinned, single-repository service deployments.

### Agent role across the bridge boundary

The orchestrator tier can land the root turn on Claude, MiniMax, or
Antigravity. A bridge that assumes every request is a delegated leaf then tells
the parent it is a bounded leaf agent that must not spawn child agents, which
suppresses exactly the delegation the root turn exists to perform: the parent
announces a delegation and then silently does the work itself.

The router therefore names the role of every outbound request in the
router-generated `x-autodev-agent-role` header. The value comes from the
router's own alias dispatch, never from the inbound request: `downstreamHeaders`
builds its header set from scratch, so a client claiming
`x-autodev-agent-role: orchestrator` on a leaf request cannot escape the leaf
policy. Every bridge receives it as an ordinary request header; Antigravity
once also received it in the Responses `extra_headers` body field because the
LiteLLM hop that used to sit in front of that adapter dropped raw headers.

Every provider receives the same shared prompt layers, with the outer
transport responsible only for composing them:

| Consumer                   | Shared composition                                                                                                                               | Provider-specific boundary                                                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native Codex child         | `base.md` + `leaf.md` + optional `code-search.md` + role-specific `developer_instructions`                                                       | `runtime/src/config/render-agent-configs.ts` materializes the complete role TOML under `~/.codex/agents`; `agent_type` selects it at spawn time                                     |
| Antigravity/Copilot bridge | `base.md` + workspace + `leaf.md` (or `orchestrator.md` + orchestration skill) + optional `code-search.md` + role fragment + capability metadata | `composeProviderPrompt(role, cwd)` then appends the delegated task                                                                                                                  |
| Claude bridge              | Codex's own request context, like a native child: the role TOML's `developer_instructions`, the root bootstrap hook, and the conversation        | `renderCodexTranscript()` feeds Codex's input to the CLI on stdin; `systemPrompt()` replaces the CLI's system prompt with only how to act through Codex's tools, plus the workspace |
| MiniMax pass-through       | Native Codex request, including the rendered role configuration                                                                                  | The proxy remains transport-only and does not author a competing prompt                                                                                                             |

The orchestration skill is the single source of truth for delegation procedure,
child lifecycle, recovery, and role selection. The orchestrator prompt is only a
small bootstrap of root identity and a pointer to the canonical policy. The native root
hook injects the same skill content and recovery preflight; the Antigravity and
Copilot bridges use `runtime/src/agents/bridge-role.ts` to assemble the same role prompt,
and the Claude bridge passes Codex's own context through unchanged. Execution-contract JSON is a
generated projection for provider diagnostics; it is not a second editable role
capability list. Native child calls carry only `agent_type` and the task message.
Codex must load the selected role TOML before the first child turn and expose that
TOML's enabled MCP servers and skills; bridges must not attach skill paths or MCP
lists per invocation.

`agents/prompts/code-search.md` is the single shared CGC-first
code-navigation prompt. The bridge injects it only when the role contract
exposes `codegraphcontext`, `cocoindex-code`, and `lsp`; native role TOMLs use
`{{AUTODEV_CODE_SEARCH_PROMPT}}`, and the root hook loads the same file for the
orchestrator. Native Codex, Claude, Copilot, and MiniMax enforce role-specific
MCP surfaces directly. Antigravity's bridge builds a per-invocation MCP registry
and permission profile from that same execution contract, so the global CLI
registry does not expose code-search tools to `docs-researcher` or Playwright to
roles that do not declare it.

The tracked role TOMLs contain only role-specific policy plus composition markers;
they do not copy the universal base/leaf text. The installer renders them before
Codex can load them, and tests compare the installed files with the renderer's
output. A change to `base.md` or `leaf.md` therefore propagates to native and
bridge-backed children through their actual prompt path.

The Antigravity bridge has no equivalent CLI flag: `agy` exposes its subagent
tools unconditionally, so a leaf turn there is bounded by `leaf.md` prompt
policy alone rather than at the CLI boundary. `agy`'s own subagent definitions
do carry an `EnableSubagentTools` field ("Grant tools to define and invoke its
own subagents"), but the model sets it when it spawns a child, so it bounds
depth below the orchestrator rather than bounding the turn the bridge starts;
The canonical `orchestration` skill requires it to be withheld by default.

#### Isolation between concurrently running orchestrators

Several orchestrators can run on this machine at once, each with its own agent
tree. An agent's reach is meant to stop at that tree, in both directions.

- **Claude.** The CLI runs with `--tools ""` (web research aside), so it has
  no `SendMessage`, `ListAgents`, or any other built-in tool that could reach
  another session, whatever a future release exposes in print mode. Its reach
  is exactly Codex's tool surface for the turn, the same as a Codex-served
  agent's. Peer messaging between the user's own _interactive_ sessions is a
  separate, deliberate Claude Code feature that AutoDev neither creates nor can
  disable.
- **Antigravity.** `manage_subagents` is already scoped by `agy`: `list`
  reports "active **direct** subagents", and `kill` refuses an id that "is not a
  known active subagent". `send_message` takes an arbitrary "Conversation ID of
  the agent to message" and resolves it at run time (`recipient %q not found`);
  its documented use is parent/child within one run. No cross-run delivery has
  been demonstrated, but `~/.gemini/antigravity-cli/presence/` is a
  machine-wide registry of live conversation ids that an agent with shell
  access could read, so `leaf.md` and `orchestrator.md` both forbid acting on
  any agent id that did not come from spawning it or from the runtime-supplied
  parent id.

### The Claude bridge serves Codex's own context

The Claude bridge passes `--system-prompt`, which _replaces_ the Claude CLI's
default prompt, rather than `--append-system-prompt`, which leaves it in force
underneath. The default prompt's harness guidance describes tools a bridged
turn does not have and competes with the role policy.

The replacement prompt (`systemPrompt()` in `runtime/src/providers/claude.ts`) says only
how to act: the conversation that follows is the Codex agent's own context,
every action goes through the session's Codex tools, and the final message is
the agent's reply. It also states the workspace the bridge resolved from
structured request metadata, because a replaced prompt loses the CLI's
per-machine sections (`--exclude-dynamic-system-prompt-sections` is ignored
with `--system-prompt`). A Codex tool call exists only when the CLI uses the
native MCP interface; invocation-looking text in an assistant message remains
ordinary text and is never dispatched or parsed as a call. The prompt tells the
model to call the CLI-exposed `mcp__codex__…` tools instead of serializing a
call, and treats tool-call/output transcript entries as history; that
instruction is best-effort model guidance, not a structural guarantee.
`WebSearch`/`WebFetch`, when separately offered, remain provider-native research
steps rather than Codex tool calls.

Role policy is not in that prompt. It arrives in Codex's own context, which the
bridge renders with `renderCodexTranscript()` and writes to the CLI's stdin:
the role TOML's `developer_instructions` (`base.md` + `leaf.md` + optional
`code-search.md` + role fragment, as rendered for every Codex child), the root
bootstrap the `UserPromptSubmit` hook injects, Codex's skills catalogue and
environment context, `AGENTS.md`, and the whole conversation so far, including
every tool call and its output. A Claude turn therefore gets exactly the policy
a Codex-served turn gets, from the same source, with no second composed copy
to drift from it.

The bridge also exports `CLAUDE_CODE_DISABLE_BUNDLED_SKILLS=1`. Claude Code's
bundled skill catalogue is a second, unversioned source of instructions; a
bridged turn reads the skills Codex lists, through Codex's tools.

Anything that is not exactly `orchestrator` is treated as a leaf, so a missing
or unrecognized header fails closed to the bounded policy. The
`enforce-root-delegation.sh` `UserPromptSubmit` hook injects the orchestrator
bootstrap and the canonical `orchestration` skill, so the root agent gets one
delegation policy no matter which provider serves it. The Antigravity and
Copilot bridges share `runtime/src/agents/bridge-role.ts`; the Claude bridge takes the
same prompts from Codex's context. The installer materializes Runtime-owned modules from `runtime/src/` into the
established `$CODEX_HOME/src/` paths and script-backed bridge assets under the
hooks runtime, so a bridge uses the same relative layout in a checkout and an
installation: `../src/…` for typed modules and `./codex/prompts/…` for prompt
assets. That is what makes the bridges runnable and importable straight from a
checkout, so their pure request-shaping helpers can be unit-tested rather than
asserted against source text.

Because the copies keep their relative layout, the `RUNTIME_MODULES` manifest in
`runtime/src/platform/install-materializer.ts` must be closed under relative imports: a
module listed there whose own import is missing resolves in a checkout and fails
with `ERR_MODULE_NOT_FOUND` under `$CODEX_HOME`, which crash-loops the service
that imports it. `tests/platform/runtime-manifest.test.ts` walks the manifest's
transitive relative imports and fails with the exact entries to add, so adding a
new module under `src/` means adding it to the manifest in the same change.

Bare package imports break the same way, and pnpm's per-package layout is why.
pnpm installs each workspace package's dependencies into that package's own
`node_modules`, so a copy of `runtime/src/` living outside the repository resolves
nothing Runtime declares. That is how the router crash-looped on
`Cannot find package 'zod'`, imported by
`runtime/src/control-api/playtesting-human-studies.ts`: it resolved in the checkout
and not under `$CODEX_HOME`. `nodeModuleLinks()` is the one place that pairs each
`node_modules` tree with the `CODEX_HOME` path a copied module's walk-up reaches --
the repository root, which resolves the workspace packages
(`@simulatorlife/autodev-core`, `@simulatorlife/autodev-data`), and
`runtime/node_modules` beside the `$CODEX_HOME/src/` mirror root, which resolves
Runtime's own dependencies. `install --check` verifies both links, and
`tests/platform/runtime-manifest.test.ts` resolves every bare import of every
manifest module through that link set, so dropping or misplacing a link fails in
the test rather than in a supervised service.

A Claude turn has no delegation tool of its own to bound: the CLI runs without
`Agent`/`Task`, and delegation is Codex's `multi_agent_v1__spawn_agent`, which
Codex offers only to the orchestrator. The bridge's `autodev_spawn` shim is the
surface it reaches that spawn through, so the turn is bounded by the bridge's
own rule -- the shim is offered to an orchestrator turn and to nothing else --
rather than by a CLI tool a workspace could remove. A target repository's
`.claude/settings.json` deny list likewise no longer guards anything a bridged
turn does, because shell commands and file edits run in Codex under the role's
sandbox mode and AutoDev's Codex rules (`agents/rules/`), exactly as they do
for a Codex-served turn.

MiniMax is the exception, and it needs no role prompt: its adapter
(`runtime/src/providers/minimax.ts`) is a pass-through to
`https://api.minimax.io` rather than a local CLI gateway. It changes only the machine boundary (allowlisted headers, no `client_metadata`) and freeform `exec` calls. CI's `mini-max-codex` workflow starts the same adapter on loopback with the tracked `minimax` profile and catalog, so CI never sends Codex's turn metadata to MiniMax either; CI git authentication uses an env-backed credential helper, never a token in a remote URL. It forwards the
parent's own Responses payload, so the root turn arrives with the real Codex
context and the delegation policy the `UserPromptSubmit` hook already injected;
there is no bridge-authored prompt that could override it. That proxy therefore
strips `x-autodev-agent-role` and `x-codex-turn-metadata` instead of honouring
them: both are local routing metadata (the latter carries absolute workspace
paths and git remote URLs) with no meaning to a remote API.

### Counting subagents across providers

A native Codex spawn is visible to the router for free: the child thread's
`autodev/<role>` request _is_ the spawn. A bridge-native spawn is not visible at
all -- the CLI runs the child in-process and no request is ever made -- so an
orchestrator turn served by Claude or Antigravity reported zero subagents,
which is indistinguishable from a provider that refused to delegate.

The router therefore hands every spawn-capable bridge three generated headers
per request:

| Header                           | Value                                                                                   |
| -------------------------------- | --------------------------------------------------------------------------------------- |
| `x-autodev-request-id`           | the router's own request UUID                                                           |
| `x-autodev-subagent-spawn-tools` | comma-separated tool names to watch, from the execution contract provider specification |
| `x-autodev-agent-events-url`     | `http://127.0.0.1:4100/v1/agent-events`                                                 |

A bridge matches the tool names its CLI reports against the watchlist and
`POST`s `{ requestId, sessionId, events: [ { type: "subagent_spawn", tool, role, status, count, children } ] }`,
where `children` is one `{ id, model }` per subagent the call created.
The bridge therefore needs no routing config, no provider identity, and no
router address of its own; and because the request id is an unguessable UUID a
bridge only learns by serving the request, presenting it is also what
authorizes the report. A report naming an unknown request id is rejected with
`404 router_unknown_request` and counted nowhere. Reporting is best effort in
the bridge: a transport failure costs a count, never the model turn.

The post carries the session id as well, because the router's registry of live
requests is in memory: a restart loses it, and a long CLI turn keeps reporting
against the request it started with. The session outlives the restart, so the
router falls back to it and attributes the report to the session instead of
dropping it. An audited Antigravity turn lost 17,336 reports this way -- every
event of a turn that spanned a router restart -- which is how a bridge's
delegation can go unobserved entirely.

Codex receives none of these headers, and MiniMax receives no spawn-tool
watchlist -- the router already observes their children as role requests, so
reporting them again would double-count. MiniMax's adapter uses the request id
and events URL only for its tool telemetry and never forwards them upstream.

The watchlist names only tools that actually start a child. Antigravity's
`manage_subagents` lists and stops existing children and `define_subagent`
declares a type for later use; neither spawns, and `manage_subagents` in
particular is called far more often than any delegation happens -- in one
sampled proxy log, 104 `manage_subagents` calls against 4 `invoke_subagent`
calls. Adding it to the watchlist would turn every status poll into a spawn.

One `invoke_subagent` call dispatches a _batch_: agy is instructed to send
"subagents in batches of at most 16 per `invoke_subagent` call", and the tool
arguments are `{"Subagents":[{"TypeName":...,"Model":...,"Prompt":...}, ...]}`.
The bridge therefore reports one count per entry in that batch and takes each
child's role from its `TypeName` (falling back to the `name` a
`define_subagent` archetype registers), rather than reporting one roleless
spawn per call. A model id is never used as a role: it is the model, not the
role, and would fill `byRole` with model names.

Where those arguments sit inside the CLI's stream-json step update is agy's
business and has moved between versions, so the bridge finds the `Subagents`
array by shape anywhere in the update instead of pinning one path. A step that
exports no arguments still reports one roleless spawn -- the pre-batch
behaviour -- so a CLI change costs role detail and batch width, never the
spawn itself. Set `AGY_LOG_SPAWN_STEPS=1` on the Antigravity proxy to print the
structure of each spawn step (keys kept, string values truncated, so delegation
prompts stay out of the log) when confirming the shape against a new agy build.

#### When the workspace removes the delegation tool

A bridge-native CLI's own settings can remove its delegation tool from under an
orchestrator turn, which then does all the work itself and reports zero
subagents -- the exact reading as a provider that chose not to delegate. (A
Claude turn cannot hit this: it delegates through Codex's spawn tool, not a
CLI tool.)

The CLI's tool inventory is the only place that absence is observable: a
denied tool is simply missing from it and nothing later mentions it. On an
orchestrator turn the bridge compares that list against the router's
watchlist and, when none of the spawn tools are present, logs the workspace and
posts `{ type: "subagent_tools_unavailable", expected, available }`. The router
records it as a `spawn_tool_unavailable` spawn failure -- with the model that
was left unable to delegate -- so it appears in **Subagent spawn failure
telemetry** rather than vanishing into a zero. It is not a spawn, so it moves no
spawn counter.

Only the tool names are sent, capped at 100: a full tool inventory fingerprints
the workspace, and the router needs only enough to name the gap. The check runs
for the orchestrator alone, since a leaf having no delegation tool is the
policy working.

Both mechanisms land in one `status.subagents` aggregate: `total`,
`byMechanism` (`router_alias` / `bridge_native`), `byProvider`, `byRole`,
`byStatus`, and the 50 most recent spawns. `router_alias` spawns are attributed
to the provider that served the `autodev/orchestrator` turn for the same
session, which is the only join available: a child thread's request carries no
trace of which provider ran its parent. The join is skipped for callers that
supply no session id, because they all share one fallback bucket and would
otherwise be credited to an unrelated caller's parent turn. A role request with
no joinable parent turn is attributed to `unattributed` rather than guessed.
The projection publishes no second counter beside the router's: Codex's own
`codex.multi_agent.spawn` metric reaches OpenLIT, not the router, so a count
beside the router's would always read zero and claim a spawn count the router
never observed.

#### CLI-delegated children as measured turns

A spawn count says a child existed; it does not say the provider did the work.
Counting only spawns left the provider that actually ran a twelve-way fan-out
showing exactly one turn in **Provider health and usage**, and no subagent row
at all in **Usage by orchestrator and subagents** -- both tables are built from
router requests, and a CLI child never makes one.

The bridge's report is the only evidence those turns happened, so it is also
what opens a usage bucket for each child. A `subagent_spawn` opens one turn per
child, attributed to the provider, workspace, and model of the request the
bridge was serving; the matching `subagent_result`
(`{ type: "subagent_result", tool, role, outcome, durationMs, children }`)
closes it with the duration the CLI actually spent. The `id` on each child is
what pairs the close with its open, and is unique within the request.

Closing is an accuracy improvement, not a requirement. A CLI child cannot
outlive the parent turn that spawned it, so the router closes any child still
open when the parent request finishes, measured against the time elapsed since
its spawn. A bridge that never reports a close -- or dies mid-turn -- therefore
still has its children counted; only the per-child duration is lost. A report
that lands after the parent turn already ended is opened and settled at once
rather than dropped, because bridges post without awaiting.

##### What a spawn tool's completion does and does not mean

For Antigravity, closing on the dispatch step is _wrong_, and the parent-turn
bound above is the accurate path rather than the fallback. Captured directly
from `agy -p ... --output-format stream-json`, one `invoke_subagent` dispatch
emits exactly two updates:

```jsonc
{ "step_index": 2, "state": "ACTIVE", "step_type": "subagent", "tool_name": "invoke_subagent",
  "subagent_info": { "subagents": [ { "type_name": "research", "role": "Line Counter",
                                      "conversation_id": "b1655ed9-…", "log_uri": "file:///…" } ] } }
{ "step_index": 2, "state": "DONE",   "duration_seconds": 0.043191, … }
```

The turn containing that dispatch ran 45.2 seconds and the child genuinely did
the work. `invoke_subagent` is fire-and-forget: `DONE` reports that the
_hand-off_ finished in 43ms, and agy emits no later step when a child completes
-- the child's result reaches the parent as context, invisibly. The child's true
runtime is therefore not observable from this stream at all, and
`manage_subagents` is how agy tends children afterwards rather than a completion
signal.

So a bridge must not treat a spawn tool's `DONE` as its children finishing. Doing
so reported ~40ms for children that ran for minutes, which is worse than
reporting nothing: it fills the usage tables with a number that looks like a
measurement. Antigravity children stay open and close with the parent turn,
which bounds them honestly -- the child ran somewhere inside that window. A
terminal state other than `DONE` does close immediately, because that means the
hand-off itself failed and there was never a child to wait for.

Read a bridge-native child's duration as an upper bound, not a measurement.

These turns are deliberately _not_ fed through the router's event path.
Provider health, cooldown, and the fallback chain describe routing decisions
this router made, and a child it never routed must not move them. Only the
usage buckets -- which measure work done behind the router, not routing --
count them, tagged with the `subagent` origin.

Two details follow from that:

- `status.subagents.byStatus` is the breakdown of how spawns _ended_: a close
  moves a child from `started` to `success` or `failure`, and each row in
  `recent` carries its own `settled` tally so a batch shows how its children
  finished rather than only how many it began. It previously reported
  `{ started: N }` forever, which read as "none of these ever finished" about
  children that had all completed.
- A child whose spawn step exported no role is counted under
  `unattributed-subagent`, never the bare `unattributed` role. That key is
  roleless _orchestrator_ traffic, so folding children into it would credit a delegation to its parent. `status.subagents.byRole` still says `unattributed` for the same
  children; each key is unambiguous within its own table.
- A child's model is its own only when the batch entry names a concrete one.
  agy writes `inherit` when the child runs on whatever the parent was routed
  to, which is not a model id, so the router resolves it to the parent's model.
  A concrete child model that no tier configures still remains attributed to that provider in status/telemetry; accounting must not silently drop models merely because they are absent from the configured catalog. The cumulative `status.subagents.total` is distinct from
  the bounded newest-first `status.subagents.recent` window (capped at 50).
  When recent history cannot cover the cumulative count, the status CLI labels the summary and totals as `X recent / Y total`; it never inflates the recent subtotal to match all-time history.

The shared reporter is `runtime/src/telemetry/agent-events.ts`, exported as
`@simulatorlife/autodev-runtime/telemetry`. Provider bridges consume that
workspace contract; the installer links `CODEX_HOME/node_modules` to the
workspace rather than copying a second telemetry source file. The native spawn
script/SSE helper is `runtime/src/agents/spawn-tools.ts`, and the Antigravity and
Copilot bridges' per-turn `autodev_spawn` server launches the shared
`runtime/src/mcp/spawn-shim.ts`. Claude children are `router_alias` spawns: a Claude
orchestrator spawns through Codex, so its children are ordinary
`autodev/<role>` requests.

### Reasoning effort on the Antigravity bridge

`agy` encodes reasoning depth in the model id itself (`gemini-3.8-flash-high`,
`claude-opus-5-5-high`) and rejects the whole invocation when a separate
`--effort` disagrees:

```
Error: invalid model selection (--model "gemini-3.8-flash-high" --effort "medium"):
--model gemini-3.8-flash-high conflicts with --effort=medium
```

The router picks the model per tier and the caller's reasoning effort is an
independent value, so the two routinely disagree and the turn fails before the
CLI starts. The model id is the more specific choice, so it wins: the bridge
omits `--effort` entirely for any model whose id already carries a
`-low`/`-medium`/`-high` suffix, and passes it only for models that do not.
This covers the Claude 5.5 families too, since `agy` lists every Opus and Sonnet
variant with an effort suffix. `orchestrator.reasoningEffort.antigravity`
therefore has effect only through the model the orchestrator tier selects.

### Reasoning effort on MiniMax

Each MiniMax model declares its own reasoning levels in its model catalog
entries (`config/catalogs/minimax-model-catalog.json` and
`config/catalogs/codex-model-catalog.json`), and the proxy forwards the
requested effort unchanged:

- MiniMax-M3 supports only `none` or `high`. It does not support `medium` or
  `low`.
- MiniMax-M3.1-Flash-Preview supports `low`, `medium`, `high`, `xhigh`, and
  `max` (default `max`). Its thinking cannot be disabled, so MiniMax rejects
  `none` with HTTP 400. MiniMax currently serves this preview only to M Plan
  (and MiniMax Code) keys.

See MiniMax's [Model Invocation guide](https://platform.minimax.io/docs/guides/text-generation)
and [OpenAI-compatible API reference](https://platform.minimax.io/docs/api-reference/text-openai-api)
for the current model ID, entitlement, reasoning-effort values, and API details.

Every `MiniMax-*` model id routes to the MiniMax provider through
`MINIMAX_MODEL_PATTERN` in `runtime/src/shared/provider-model-ids.ts`, which
both the router's built-in route and the proxy lifecycle gate
(`runtime/src/platform/minimax-ensure.ts`) use, so selecting any MiniMax model
starts the compatibility proxy.

Agent config TOML files under `agents/roles/` omit role-level
`model_reasoning_effort` declarations so each child agent inherits
the configured model reasoning effort (e.g. `default_subagent_reasoning_effort = "high"`
under the MiniMax profile, or the orchestrator's pinned fallback effort). All
roles inherit their model's effort cleanly without triggering invalid effort
rejections on MiniMax. Similarly, `scripts/run-provider-agent.sh` omits
`-c model_reasoning_effort=...` when role effort is absent, allowing configured
model/profile effort to inherit rather than forcing a fallback medium effort.

### Streaming provider progress back to the parent

A bridge that reports only the final assistant message leaves the parent (and
the operator watching it) with a silent gap for the whole turn. The Antigravity
and Copilot bridges therefore stream the provider's intermediate output as
Responses reasoning summary events (`response.reasoning_summary_text.delta` on
a `reasoning` item at output index 0) alongside the answer text at output
index 1. The Claude bridge instead emits each item as it finishes -- see
"Claude bridge: Codex executes every tool":

- Antigravity: `step_update` tool and step activity.
- Copilot: `commentary`-phase message deltas, `report_intent` narration, and
  each `tool.execution_start`, parsed from the CLI's `--output-format json`
  JSONL stream.

Each bridge holds its SSE headers back until the provider produces real output
(reasoning, a tool call, or answer text). Until that point a provider failure
is still reported as an HTTP status the router can fall back on; after it, the
turn is genuinely under way and the parent watches it live. Synthetic
pre-run activity is buffered and flushed when the stream opens, so it never
commits the response on its own.

### Canonical turn metadata and `workspaces` map contract

Codex's canonical transport carries turn metadata as the
`x-codex-turn-metadata` request header (the local model router forwards this
verbatim to the chosen provider bridge). The metadata contains a
`workspaces` map whose key is the absolute repo/workspace path (the
Codex source inserts `repo_root` as the map key); each value carries
only git metadata. Provider bridges therefore consult each `workspaces`
map key as an absolute-path candidate first, and only fall back to the
legacy structured `cwd`/`project_root`/`working_directory`/`path` fields
inside each value when no key is a directory that exists on this host.
This matches the upstream Codex contract: values do not carry the path.

Callers that cannot set custom headers may instead embed the same JSON
under `client_metadata["x-codex-turn-metadata"]` in the request body;
the local router normalizes that back into the canonical header shape
so provider bridges only ever have to parse one form. A caller-supplied
`extra_headers` field is discarded outright rather than forwarded: it is an
SDK escape hatch that would bypass the router's credential and header
allowlist. The resolution
order inside `resolve_cwd` / `resolveCwd` is therefore:

1. Top-level `cwd`, `project_root`, or `working_directory` on the request.
2. The same fields inside `metadata`.
3. The canonical `workspaces` map keys (absolute paths).
4. The structured path fields inside each `workspaces` value.
5. The explicit `CODEX_PROJECT_ROOT` operator override.
6. Fail closed with a `400 invalid_request_error` (and a `WorkspaceResolutionError`
   in the bridge) listing the fields the request did carry, instead of
   silently defaulting to an unrelated parent in this repository.

Steps 3 and 4 refuse an ambiguity rather than resolving one. If more than one
listed workspace exists on this host and the request does not say which is
active, the bridge raises `AmbiguousWorkspaceError` (a `WorkspaceResolutionError`,
so it still surfaces as the same `400`). Taking the first would let JSON key
order -- which carries no meaning and which the caller does not control --
decide which repository a coding agent edits, so a turn rooted in one repo
could land in another with nothing but a changed working tree to show for it.

Every bridge answers step 6 through one owner: `sendWorkspaceResolutionFailure`
in `runtime/src/shared/provider-http.ts`, which logs which bridge rejected the
request and sends the `400 invalid_request_error`. The bridges pass their own
label (`claude`, `copilot`, `agy`) and nothing else, so the response contract
cannot drift apart between them.
`CODEX_PROJECT_ROOT` is the documented tiebreak and settles the ambiguity when
a multi-root turn is legitimate.

The router's telemetry label reads the same map from the other end, and the two
must agree: a label naming a different repository than the one the agent edited
is worse than no label. The router imports `WORKSPACE_KEYS` and `isDirectory`
from the shared resolver rather than reimplementing the path check. It also
imports `parseTurnMetadataJson` there, so turn-metadata object validation has
one owner. The router previously took the first non-empty key while the bridges
took the first key that is a directory here, so a stale first entry made
telemetry and execution disagree silently. Where the bridge refuses an
ambiguity, the router records no workspace instead of inventing one.
`tests/workspace-resolution.test.ts` and
`test_all_provider_bridges_resolve_a_workspace_identically` pin both halves,
the latter by running the shared resolver over the same inputs
and asserting identical answers.

The JavaScript CLI adapters share this resolver in
`@simulatorlife/autodev-runtime/shared/resolve-workspace`; the installer deploys that module
alongside the runtime adapter copies, at `codex/lib/` beneath the hooks
directory so the same `./codex/lib/…` specifier resolves in a checkout too. The typed Claude bridge imports the shared resolver and is covered by the same
workspace-resolution tests. Provider-specific code should pass its
operator override into the shared resolver rather than reimplementing request
metadata parsing or workspace selection.

Provider bridges also forward only delegated user-task content and add their
role boundary as provider-controlled instructions. Parent system/developer
messages are not serialized as fake `[system]` or `[developer]` turns, which
prevents a leaf model from mistaking orchestration context for a user prompt
injection. Agent creation failures that occur in the Codex app-server before a
request reaches the local router cannot be repaired or intercepted by AutoDev;
use an explicit `autodev/<role>` model, keep the parent task rooted in the
intended repository, and inspect the app task/log event for those failures.

### Claude bridge: Codex executes every tool

Claude is served as the model behind a Codex agent turn, not as a second agent
runtime. Before this design the CLI ran its own `Read`, `Edit`, `Bash`, `Skill`,
and `Agent` tools inside its process: Codex saw none of them, the app showed a
Claude-served thread with no tool calls, skills, or thinking, an interrupted
turn left no trace in the thread history, and a later provider continuing the
thread truthfully reported that nothing had been done while the edits sat in
the workspace (observed 2026-09-18, worker thread
`01a0b664-aa5f-7dd0-b848-3f321b1f680a`).

- **Tool surface.** `runtime/src/providers/claude-codex-tools.ts` mirrors the tools on
  Codex's request -- in code mode the `functions` namespace inside the
  `additional_tools` input item: the `exec` custom tool (JavaScript against a
  `tools` global carrying `exec_command`, `apply_patch`, the role's MCP servers,
  and, for an orchestrator, `multi_agent_v1__*`) and function tools such as
  `wait` -- into an MCP server, `runtime/src/mcp/codex-tools-shim.ts`, that the CLI is
  given with `--strict-mcp-config`. The CLI runs with `--tools ""`: no built-in
  tool, except `WebSearch`/`WebFetch` on turns where Codex offered its hosted
  `web_search`, which no tool script can perform.
- **Delegation.** The mirrored `exec` tool is Codex's, so a Claude model can only
  reach `multi_agent_v1__spawn_agent` through it -- and a turn Codex offered no
  tools to has no `exec` cell at all. The bridge therefore offers a second
  server of its own, `autodev_spawn`, written by the shared shim owner
  (`runtime/src/agents/spawn-shim-server.ts`), and hands it to the CLI with
  `--strict-mcp-config` whether or not Codex offered any tools. The model calls
  `mcp__autodev_spawn__spawn_subagent`; the bridge collects the children and,
  when the turn completes, emits one `exec` call of its own -- the script the
  Runtime builds, not one the model wrote -- so Codex creates real child
  threads. A leaf turn is offered no such server and is told nothing about
  delegating.
- **Parking.** When Claude calls a mirrored tool, the shim blocks and the bridge
  (`runtime/src/providers/claude-turn.ts`) emits the call as a `custom_tool_call` or
  `function_call` item, completes the response, and keeps the CLI parked. Codex
  runs the call in the turn's sandbox with its approvals and hooks, the app
  renders it, and Codex's next request carries the output; the bridge matches
  its `call_id`, resolves the shim call, and streams the rest of the turn into
  that request's response. Calls from one assistant message go out together.
  Codex appends its own messages after a call's output -- a
  `<subagent_notification>`, a user's steer, a `<turn_aborted>` notice -- so the
  awaited results are the outputs in the input's tail, allowing such messages
  (`@simulatorlife/autodev-runtime/shared/responses-continuation`), and those messages reach the parked
  turn with the results rather than being lost.
  `CLAUDE_CODE_BRIDGE_PARK_SECONDS` (default 1800) bounds how long a parked turn
  waits; the CLI's idle timeout does not run while Codex holds a call.
- **Resuming without the CLI.** A continuation whose calls the bridge no longer
  holds (a restart, or a park timeout) starts a fresh CLI from the rendered
  transcript, which includes every earlier tool call and output, so the turn
  continues rather than starting over blind.
- **Incremental items.** Each thinking block, text block, tool call, and native
  web-research step (`Searched the web: …`) is emitted as its own item and
  finished as soon as it ends, so Codex records it immediately and an
  interrupted turn keeps what already happened. A failure after output has
  streamed ends the response `incomplete` with the shared limit notice.
- **Cancellation.** A client that disconnects mid-response cancels the turn and
  kills the CLI; nothing keeps working after its client went away. Stopping the
  bridge (SIGTERM/SIGINT, as a launchd restart or reinstall does) cancels every
  live turn first, so no parked CLI survives as an orphan.
- **Telemetry.** A call is reported `tool_requested` on the request that emits
  it and `tool_executed` (with the exact wait) on the request that returns its
  output, as the MiniMax adapter does. Skill reads go through Codex's tools and
  are observed by Codex's own skill-read hook.
- **Routing.** The router prefers the provider that issued the calls a request
  is answering (see "Tool-result affinity"), so the continuation reaches the
  parked turn.

### opencli: web chat sites as models, Codex executes every tool

[opencli](https://github.com/jackwener/opencli) (`@jackwener/opencli`, pinned
in `runtime/package.json`) drives a chat site's own web UI through the user's
signed-in browser and returns the reply as JSON. (Moving this off the user's
own Chrome onto a dedicated browser, and why headless is not viable, is
investigated in [`opencli-separate-browser.md`](opencli-separate-browser.md).)
Each site is its own
provider -- `opencli-chatgpt` and `opencli-gemini` -- with its own route,
catalog (`config/catalogs/<provider>-model-catalog.json`), discovery, and the
models that site offers, so the Console assigns a site model per role as for
any other provider. Both providers are served by the one bridge on `:4004`.
`OPENCLI_PROVIDER_SITES` in `runtime/src/shared/provider-model-ids.ts` is the
single list; the route patterns and the site registry in
`runtime/src/providers/opencli-turn.ts` derive from it.

- **Models.** A model id is `<provider>-<site model>`; the prefix keeps every
  id distinct from the other providers' (Antigravity's are `gemini-...`).
  - `opencli-chatgpt-<level>`: `fast`, `balanced`, `advanced`, `xhigh`,
    `pro`, `gpt-5.6-pro` -- the targets of opencli's `chatgpt model`
    (`CHATGPT_MODELS`; ChatGPT has no model-list command). Very High is
    `xhigh`, opencli's alias for it, because an id ending `-high` reads as an
    effort variant under Antigravity's id convention. The model is an account
    setting: the bridge runs `chatgpt model <level>` before a turn only when
    the turn asks for a different level than it last selected, and only once
    per bridge rather than once per turn. Switching drives the composer's
    picker with native input, which needs the browser's opencli window
    visible and uncovered ("Native input requires a visible browser page");
    the patched adapter falls through to the site's own settings API when
    the picker is out of reach, and a switch that still cannot be made
    leaves the turn at the level the site has instead of failing it.
  - `opencli-gemini-<model>`: whatever `opencli gemini models` lists for the
    account (`3.5-flash-lite`, `3.8-flash`, `3.1-pro`, `4-argon`,
    `4-carbon`), read from the site by the bridge's `GET /v1/models` and kept
    five minutes; each turn passes `--model`. opencli 2.0.3 is patched
    (`patches/@jackwener__opencli@2.0.3.patch`) so a model's id is its own
    name and version alone -- the one text part of the picker item that
    starts with a version ("4 Argon" is `4-argon`) -- never the description
    the site shows beside it ("Code & analysis"), which it rewords and moves;
    so `--model` accepts every id its own `models` lists and selects the
    item by that same id; and so a selection whose read-back is empty is not
    reported as failed: the picker now shows only the variant ("Flash"),
    never the version. A model the account is out of usage on stays in the
    picker with "Limit resets ..." in place of its description: `models`
    reports that text as the row's `limit`, and `ask --model` refuses the
    model under `MODEL_LIMIT` with it, which the bridge reads back as a usage
    limit with the reset the site named.
    Gemini is also the site with a **thinking level** of its own (`low`,
    `medium`, `high`, read from the site's own "Thinking level" submenu), and
    the site renamed them: opencli knew only `standard` and `extended`, so
    `--thinking` refused every level the site offers and the level could not
    be selected at all. The patch teaches the adapter the site's names, waits
    for the submenu to expand (its items have no size until it does), and
    finds the "Thinking level" entry wherever the menu keeps it. It also
    finds the **picker** itself: the site labels the composer's picker "Open
    mode picker, currently Flash-Lite High" and shows the model without a
    version, so none of opencli's name patterns matched it, no menu ever
    opened, and Gemini's models were never read -- which also failed the
    model's own discovery, so a turn that asked for a model or a level ran at
    the model the site already had, without saying so. The bridge asks for
    the level the operator chose for the role, and only when it differs from
    the one the site has; a level the site cannot take is a preference it
    declined, so the turn answers at the level it has rather than failing,
    and a model it cannot take is reported the same way. ChatGPT has no
    thinking level of its own: its intelligence level _is_ its model, so the
    catalog names the model's level and the bridge switches the model instead.
  - Each provider's discovery asks the bridge for its own list
    (`GET /v1/models?provider=<provider>`). Reading Gemini's list drives the
    browser and waits behind any turn using that tab, which outlasts the
    Runtime's 8 s discovery timeout, so the bridge answers from its cache at
    once and refreshes in the background; only the very first read waits,
    briefly, and answers `503` if no list has been read yet. An empty read
    (the picker did not render) keeps the last list, in the bridge and in the
    Runtime's discovery alike (see `docs/autodev-console-target-state.md`). A
    background refresh takes the tab only while nothing else wants it: it is a
    refresh of what the site can answer rather than a request, and one that
    queued behind a turn would hold the tab away from the turns that arrive
    after it -- a listing that cannot read the site's models holds it for its
    whole timeout.

- **The site's own tools are not the agent's.** A ChatGPT `advanced`
  orchestrator turn (session `01a1b319-fa94-7ff2-875f-7dd06e895984`) made no
  tool call and reported that `multi_agent_v1__spawn_agent` was unavailable
  and the repository inaccessible -- the conclusion of a check run in the
  site's own sandbox, where neither exists. The response rules say so: a chat
  site's Python, file search and browsing run elsewhere; a path or a `tools`
  function is checked only through a tool call to the agent, and nothing is
  reported unavailable unless a tool result shows it. The bridge logs each
  turn's offered tool count and prompt size.
- **No tool API, so a text protocol.** A site has no function calling. The
  bridge renders the turn into one prompt -- response rules, Codex's
  `instructions`, the full reference for every tool Codex offered
  (`codexToolReference`), and the transcript -- and asks the model to request
  calls as `<tool_call name="exec">…</tool_call>` blocks, the same shape the
  transcript already uses for earlier calls. Each block in the reply becomes a
  `custom_tool_call`/`function_call` item that Codex executes in the turn's
  sandbox with its approvals and hooks; prose becomes a message item. A call
  to an unknown tool or with non-JSON arguments is passed through as written
  so Codex's own error output tells the model what it got wrong.
- **ChatGPT.** A turn runs `opencli chatgpt ask-file`, names the
  conversation to continue with `--conversation <id>`, and reads the id from
  the reply row. The prompt reaches the site one of two ways, by size:
  - **Typed (up to 32 KB): `--inline true`.** AutoDev's patch types the
    prompt file's text into the composer after a marker line
    (`Codex agent turn turn-<random>.`). The site renders a typed message's
    Markdown, so the bubble it shows no longer equals the prompt opencli pairs
    replies against -- unpatched, opencli waits out its timeout on a reply
    that already arrived. The marker is plain words that rendering leaves
    alone and is unique to the turn: the bubble that starts with it is the
    turn's, and the reply is paired against that bubble's own text. What the
    model receives is the text as sent (underscores, runs of spaces and
    fences were checked live). **32 KB is the bridge's conservative routing
    threshold, not a measured ChatGPT composer maximum.** The largest
    recorded live typed prompt was 31 KB and was answered in 35 seconds;
    larger typed prompts have not been tried. Compaction of MCP reference
    declarations is an offline prompt-size optimization, not evidence that
    the composer accepts larger typed prompts.
  - **Uploaded (over 32 KB):** the prompt is attached as `turn-<random>.md`
    with a constant short message. Each turn attaches under a fresh name:
    ChatGPT renames an upload whose name it has seen
    (`turn(20261106-183651).md`), and opencli matches its attachment chip
    only by the uploaded name, so a reused name failed every later turn with
    "new ready attachment chips did not appear".

  Typing is the default because **ChatGPT rations uploads**: an account gets
  a fixed number in a rolling window (80 in three hours on the plan observed).
  The bridge used to upload every turn's prompt, and an orchestrated session
  spent the allowance in about an hour -- twice on 2026-11-11, each time
  exactly 80 successful turns after the window opened (sessions
  `01a1c878-f7d4-77a2-a80e-3878b72663b0`,
  `01a1cc30-c0ce-7fa3-8489-70e37f81a4a1`). Nine follow-up prompts in ten are
  under 32 KB, so uploads are now spent only on a chat's first message and on
  a follow-up carrying a very large tool result.

  **Bridge-side upload accounting.** The bridge records successful prompt
  attachments by site in a persistent upload log, retaining timestamps from
  the three-hour rolling window across bridge restarts. An upload that would
  exceed the observed ChatGPT allowance (80 per window) is rejected before
  invoking opencli, with the same `UPLOADS_EXHAUSTED` rate-limit contract as a
  site refusal. Typed prompts do not spend this allowance. Per-provider
  `GET /health?provider=opencli-chatgpt` reports `uploadsUsed` (attachments
  recorded within the window) and `nextResetAt` (the earliest recorded
  attachment's expiry as an ISO timestamp, or `null` when none remain).
  The accounting is per site: Gemini activity does not consume ChatGPT's
  upload allowance. Window expiry is determined from the recorded timestamps,
  not process uptime. These are locally observed uploads, not a live reading
  of the account's quota; uploads from another client can still cause the
  site to refuse an attachment earlier than expected.

- **A site that has stopped taking uploads is a rate limit.** Once the
  allowance is spent, ChatGPT's page still shows its file inputs but none of
  them takes the file ("file input is missing (0 of 4 file input(s) on the
  page accept this file)"). That is not a page still rendering, and it was
  handled as one: three attempts in the chat, three more in a new chat, about
  two minutes of the site's only tab per failing turn, then a
  `response.failed` the router read as a refusal -- so the provider was never
  cooled down, Codex's retries all came back to it, and the turns queued
  behind spent their whole budget waiting ("the site's tab was busy for the
  whole of the turn"). Now the adapter stops asking after three lookups that
  find inputs and no taker, the bridge does not run the command again, and a
  prompt too long to type ends the turn as `UPLOADS_EXHAUSTED`: a `throttled`
  limit (HTTP 429, or `response.failed` with `error.limit` on a stream) whose
  `resets_at` is three hours after the oldest upload the bridge recorded in
  the window -- or 15 minutes on, when the bridge saw none of them.
  The router cools the provider down until then and serves the turn from
  another route. Turns that fit in the composer never reach this path.
- **Gemini.** `opencli gemini ask` takes the prompt on the command line, and
  the chat with `--conversation <id>` or `--new` (both AutoDev's opencli
  patch adds or extends; the patch also declares them in opencli's
  `cli-manifest.json`, without which the CLI refuses the flag). The chat a
  reply belongs to comes from the reply itself: `ask` returns the URL of the
  very page snapshot the reply was read from (`url`, `/app/<id>`); a URL read
  after the reply once named a chat the turn never touched, although the
  prompt and reply were both in the right one. A separate `status` after the
  answer read another Gemini tab once, and a subagent's follow-ups went into
  an older chat holding other sessions' turns, which it then answered from
  (session `01a1b8ef-0797-73d2-82bd-a887418caf2b`). `ask` also prefixes every reply with `💬 `,
  which the spec strips.
- **A Gemini first prompt names MCP tools instead of documenting them when
  it would not fit.** `exec`'s description documents every nested tool, and a
  root orchestrator in the Codex app carries enough connector and MCP tools
  that its first prompt reached 204-302 KB. Every such Gemini root failed at
  once with a 400 (session `01a1b914-9431-7620-ad4a-e6362957b1e6`), and the
  composer did not take a 300 KB prompt within 270 s even when tried by hand.
  The bound is the composer, not the command line (1 MiB): the largest Gemini
  prompt that ever succeeded was 61 KB, and a 150 KB one lost its tab's
  debugger after 223 s, so a site that takes its prompt on the command line is
  given at most 100 KB. A first prompt over that is rendered again with every
  `mcp__*` tool reduced to its name and summary line under its server heading
  -- or to its name alone if that is still too long -- while the built-in
  tools (commands, files, delegation) keep their full sections, and the model
  is told to read a tool's full description from `ALL_TOOLS` inside `exec`
  before calling it, as Codex itself does for a subagent's deferred tools.
  Only a prompt still over 100 KB is refused as `provider_request_unsupported`.
  A continuation is held to the same bound: a Gemini chat that fell behind --
  the session's turns went to another route while Gemini was unavailable --
  has the whole gap to send, and an opencli-gemini root was refused every
  turn with a 105-345 KB continuation while its compacted first prompt was
  95 KB. A continuation over the bound starts a new chat with that first
  prompt instead, and the bridge log says how far behind the old chat was.
  ChatGPT attaches its prompt and keeps the full reference.
- **Conversation continuity.** Codex re-sends the whole conversation each
  request. Without continuation the prompt grows with every tool output: a
  Gemini worker turn was refused after ~25 tool calls once its prompt passed
  the command-line limit (session `01a1b1d9-7a1e-73c3-947b-1a953fb708eb`).
  After each reply the bridge records a rolling digest of the transcript that
  reply ends; a request whose transcript starts with a recorded prefix sends
  only what follows (the tool outputs and new messages) into the same web
  conversation. Entries are single-use, so a retry or fork starts a fresh
  conversation rather than appending to one whose history no longer matches.
  Tool-result affinity routes a call's output back to opencli, so the
  continuation normally lands here.
  The first message of a site conversation carries everything (response
  rules, instructions, the orchestrator role, the full tool reference, the
  transcript); a follow-up carries a one-paragraph restatement of the call
  syntax, an index of the tools (with the functions `exec` exposes), and the
  new items -- not the reference again, which made every attachment tens of
  kilobytes for one tool output. The index stays because, given only a tool
  output, ChatGPT once lost track of the `wait_agent` call it needed next.
- **Every agent keeps its own chats.** A ledger entry is keyed by site, Codex
  thread and transcript digest. The thread -- one per agent: a root and each
  subagent -- comes from Codex's turn metadata (forwarded by the router) or
  the body's `client_metadata.thread_id`; a root and its subagents share a
  session but never a thread. Keyed by content alone, two agents whose
  transcripts began alike (subagents spawned with the same task and given the
  same plain reply) could resolve to one chat.
- **A prompt only ever goes into its own chat.** Every agent and session takes
  turns in a site's shared pool of browser tabs, so any tab may have shown
  another agent's chat last, and a tab can be moved by anything else driving
  the browser -- someone clicking another chat in it, or another opencli
  client. So one opencli command is the whole turn (`ask-file` /
  `ask` with `--conversation <id>` or `--new`), and AutoDev's patch makes it,
  on the page that sends and immediately before sending: open the chat, stop
  a reply an interrupted turn left running there, and confirm the tab shows
  the turn's chat (a new chat for a fresh turn). If it does not, nothing is
  sent ("prompt was not sent"), and the bridge retries the command, which
  opens the chat again. A reply that came from any other chat fails the turn
  (`CHAT_MISMATCH`) and is not recorded; a ChatGPT reply is also paired by a
  message unique to its turn. A tab moved between turns is therefore
  harmless, and one moved during a reply can fail a turn but not misroute it.
- **Router admission avoids an occupied opencli tab when another route is available.**
  Each opencli provider declares `maxConcurrentRequests` in the routing
  configuration -- 3 for ChatGPT, 1 for Gemini -- independently even though
  they share the bridge port. It is also the number of browser tabs the
  bridge runs that site's turns in (see "Tab pool" below), so the router and
  the bridge admit the same number of turns. The router reserves a per-provider request slot before
  dispatch. A role fallback chain defers a saturated provider when another
  eligible, non-cooling provider has room; if alternatives fail, or the chain
  has only that provider, the request waits for its slot instead of failing
  immediately. Direct concrete-model requests always remain on their chosen
  provider and queue. Waiting requests can be cancelled without being sent.
  Capacity is not a provider failure: it does not cool the provider, change
  its health, or count live agents as active transport requests. The bridge
  still admits turns per site into its tabs and retains its wait/turn budgets.
  Provider-specific `/health` reports `busy` (every tab holds a turn), `tabs`,
  `activeTurns` and `queueDepth` (running plus waiting) diagnostically; a
  healthy occupied site continues returning HTTP 200.
- **One budget per turn, and a busy site is not a broken site.** A site runs
  one turn per tab, so a turn that finds every tab busy waits for one. A turn has two allowances of the same length (the turn
  timeout): one to wait for the tab, and one to hold it. The second starts
  when the turn first takes the tab, and every command in the turn draws on
  it: the command opencli runs is given the time the turn has left, and a turn
  that continues its chat in a new one runs its second command on what is left
  rather than on a fresh timeout. Counted as one budget from acceptance, a
  turn that had waited eight minutes behind other agents was given the two
  that were left and timed out on a site that was answering. A turn still
  cannot hold the tab longer than its timeout, so the site's liveliness
  endpoint (`GET /health/liveliness?provider=<provider>`) reports it wedged
  only when a command stopped answering -- a turn that is merely slow is
  reported as `busy`, with HTTP 200. A turn that waited for the tab for longer
  than a whole turn timeout is not started: the bridge refuses it with
  the typed `provider_request_unsupported` refusal, so the router's chain moves
  on to a route that can serve the request while opencli stays healthy.
  Refusing is what a bridge does for a request it cannot serve; answering
  `503` would tell the Runtime that the provider itself is down, and it would
  cool the provider down and mark it unavailable for being busy.
- **A failure before the prompt was sent is run again.** Nothing was sent, so
  running the command again cannot put the prompt into the chat twice, and each
  attempt navigates the tab and rebuilds the composer -- so the next attempt
  sees a different page. This covers a tab that has no composer yet and an
  attachment opencli could not target: ChatGPT's page carries several file
  inputs, and opencli refuses to attach the prompt when it cannot find
  exactly one it can use ("file input is missing or ambiguous"). That refusal
  was the largest single cause of failed opencli turns, and it was terminal:
  the turn died even though nothing had been sent. A page whose file inputs
  are all there and all refuse the file is the exception -- the site has
  stopped taking uploads, the next attempt is refused the same way, and it is
  reported as the rate limit it is (above) instead of being run again.
- **The file input is found where the page keeps it, and the page is given
  time to show it.** The prompt reaches ChatGPT as an attachment, so the turn
  needs the page to show a file input to attach it through. The page does not
  always keep that input where the adapter looked first -- it may sit beside
  the composer, or in the portal the attach menu opens -- and it mounts the
  input a moment after the composer itself is there. The patched adapter
  (`patches/@jackwener__opencli@2.0.3.patch`) searches every place the page
  keeps one, in order, and asks again for a few seconds while the page is
  still rendering; a page that shows more than one eligible input has one
  chosen, deterministically, instead of the turn being refused. When there is
  still none, the reason says how many inputs the page had and how many of
  them accept the file, so the failure is diagnosable instead of a bare
  "file input is missing". A session whose every root turn died that way
  (`01a1c6a9-dc62-7a10-ac7e-a20047d5489d`) is the case this fixes.
- **A long conversation is shortened for the model.** The prompt a new chat
  gets is the whole conversation, and the conversation grows with every tool
  result: a root session that had run dozens of tools sent 169 KB of
  transcript to ChatGPT on every new chat. The prompt is bounded for the
  model as well as for the page -- narrowing the tool reference first, since
  a listing the model can read the rest of from inside `exec` is the
  cheapest thing to give up, and shortening the conversation only when that
  was not enough. What is left out is the middle of the conversation: the
  task and the most recent turns are what the next call needs, and the model
  is told that the rest is gone rather than left to find a conversation with
  a hole in it.
- **The site's intelligence level cannot fail the turn.** ChatGPT's model
  picker is opened with a native click, and a tab in the background cannot be
  clicked: the switch failed with "Native input requires a visible browser
  page" whenever the operator was not looking at the tab, which is how a
  machine runs when nobody is watching it. The patched adapter falls through
  to the site's own settings API, which needs no visible page, and the
  bridge treats a switch that still cannot be made as what it is -- a
  preference the site could not take, not a broken provider: the turn runs at
  the level the site has, the way Gemini's does when its model picker is out
  of reach.
- **Interrupts, steering and queued messages.** An interrupted turn records
  nothing, so the agent's ledger entry still names its chat; Codex's next
  request (the interrupted message, its `<turn_aborted>` marker and the new
  message, such as "Continue") continues that chat with those items. The
  site may still be writing the abandoned reply, which would block the
  composer; the turn stops it before sending. A steering message arrives in
  the agent's next request after its tool outputs and a queued message as
  the next request, so both are new items of the same thread and go to the
  same chat.
- **Google's unusual-traffic check.** Rapid navigation can make Google
  replace Gemini with its CAPTCHA page (`www.google.com/sorry/...`) until
  someone solves it in the browser. The patched commands report it as a rate
  limit ("Gemini is rate limited: ..."), a 429 the router cools the provider
  down on, instead of a missing chat or a reply that timed out.
- **Tested against a simulated site.** `tests/providers/opencli-routing.test.ts`
  drives the bridge over HTTP against simulated ChatGPT and Gemini sites that
  keep each chat's history and the tab's current chat: concurrent sessions
  with roots and subagents on both sites, twins with identical tasks and
  replies, an interrupt followed by "Continue", a steer and a queued message,
  and a chat opened in the tab between turns or just before sending. A test
  in `tests/providers/opencli.test.ts` checks every flag the specs pass
  against the installed opencli's own parser.
- **Continuity survives restarts.** The conversation ledger is written to
  `$CODEX_HOME/run/opencli-conversations.json` (atomically, on every change;
  `OPENCLI_CONVERSATION_LEDGER_FILE` overrides it) and read at startup. Held
  only in memory, it was lost on every deploy, crash or reboot, and the next
  message in an AutoDev session -- a "Continue" an hour later -- started a new
  chat whose first message was the whole transcript (225 KB in session
  `01a1b6e5-ba5b-7f83-a471-0669d92f0ee1`) instead of continuing the chat the
  session had used. If a recorded chat no longer opens (deleted, or a Gemini
  chat that loads with no visible turns) and continuing fails before anything
  was sent, the entry is dropped and the turn runs once more as a new chat
  with the whole conversation, so the session does not stick on a dead chat.
- **Turn log.** Each finished turn logs one line to the bridge log: the
  calls the model made, the tools offered, the bytes of the prompt actually
  sent, whether it continued a chat, and that prompt's bytes per kind of
  conversation item (`user`, `assistant`, `developer`, `system`,
  `tool_call`, `tool_output`) -- only the new items for a continued chat,
  every item for a new one or for a chat that could not be continued, such
  as `new items: tool_output 14210 B in 3, developer 1102 B in 1`. A large
  delta therefore shows whether tool output, an injected message or the
  turn's own messages filled it. The line also says where the turn's time
  went -- `queued Ns` waiting for one of the site's tabs, `on site Ns` holding
  one (driving the page and waiting for the model), summed over both attempts
  of a turn that restarted its chat -- so tab contention and model latency
  can be told apart. The same two numbers ride on the completed response as
  `autodev_phases: {queued_ms, on_site_ms}`
  (`runtime/src/telemetry/provider-phases.ts`, the one contract between a
  bridge and the router). The router -- the only OpenTelemetry owner -- records
  them on the attempt's `gen_ai.client_operation` span as
  `autodev.provider.queue.duration` and `autodev.provider.site.duration`
  (seconds) and in the `autodev.provider.phase.duration` histogram
  (`autodev.provider.phase` = `queued` | `on_site`), and the Console's Usage
  page shows their P95s beside the attempt P95 under **Attempt latency**. A
  web chat reports no token counts, so its response carries no `usage` at all
  rather than zeros.
- **One round trip, as much work as it can carry.** A ChatGPT turn's p50 is
  114 s, and 1130 of 1194 turns over two days made exactly one tool call, so a
  40-step task took 40 round trips. The response rules tell the model that
  every reply costs minutes: batch every independent read, search and command
  the next step needs into one `exec` script (`await Promise.all([...])`),
  read a file once, and never repeat a call whose result is in the
  conversation. The root bootstrap (`agents/prompts/orchestrator.md`) likewise
  makes a root wait on all its children in one `wait_agent` call of at least
  300 s: a root polling at 10 s spent an Advanced-model turn, and one of the
  site's tabs, on every wake.
- **Tab pool.** A site runs its turns in as many browser tabs as its route's
  `maxConcurrentRequests`, one turn per tab. With one tab per site, more than
  half of a ChatGPT turn's time (p50 114 s; 51 s of it the site actually
  working) was spent queued behind other agents' turns, two to six of them
  deep for most of the day. The bridge passes the pool to opencli as
  `OPENCLI_SITE_SLOTS` (`chatgpt:3,gemini:1`): each command borrows a free
  persistent tab (`site:<site>#<n>`) from opencli's daemon and gives it back
  when it ends. Three concurrent ChatGPT turns in background tabs -- two
  continuing chats and one new -- each answered correctly in 38-48 s. Gemini
  keeps one tab: its model picker does not render in a background tab.
  The bridge admits turns in arrival order, as many at once as the site has
  tabs (`SiteTabs` in `opencli.ts`). A site's model is an account setting
  (`chatgpt model` changes the account's last-used model), so turns share
  the site only while they want the model it is on: a turn that wants
  another waits for the site to drain and runs alone, so its switch cannot
  change the model under a turn in another tab, and turns behind it wait for
  it. ChatGPT's upload allowance is checked once a turn has a tab, counting
  the uploads the site's other tabs are making, so concurrent turns cannot
  both spend the last one. Different sites run in parallel. A command the
  bridge cancels ends at once, but opencli's daemon keeps its tab until that
  command's browser step finishes; a refusal with `SESSION_BUSY` is waited
  out (retrying every 5 s) until the turn's own timeout instead of failing
  the turn.
- **A finished ChatGPT reply is read within about two seconds.** The patched
  adapter reads the reply every second (it was every 3 s) and still returns
  it only once the page has stopped generating and the same text has been
  read three times in a row, which is what guards against a half-rendered
  reply. At 3 s every turn waited 6-9 s after the reply had already ended.
- **Keep-alives are events.** The 15 s keep-alive is a `response.in_progress`
  event, not an SSE comment: an SSE parser drops comments, so Codex never
  counted the old `: keep-alive` lines and aborted every site turn that ran
  past its own 5-minute `stream_idle_timeout_ms` (`client_aborted` at 300 s,
  then retried until "idle timeout waiting for SSE"; session
  `01a1b6e5-ba5b-7f83-a471-0669d92f0ee1`). Two agents sharing one site queue
  behind each other's turns, so such turns are common.
- **Retrying what was never sent.** A command opencli failed before the prompt
  reached the site -- no composer yet ("requires an authenticated session
  with an active composer"), an attachment that never became ready ("prompt
  was not sent") -- is retried twice, 3 s apart; a failure after sending is
  not, so a prompt is never put in a chat twice. Gemini's model picker does
  not render in a hidden or covered window, and opencli then selects no model
  at all ("model discovery returned no selectable models"); such a turn is
  asked with the model Gemini already has rather than failing.
- **A Gemini model that is out of usage is its usage limit.** The site keeps
  such a model in its picker and replaces its description with "Limit
  resets Nov 9, 9:26 PM". The model keeps its id; `opencli gemini models`
  reports the site's text as the row's `limit` (null otherwise), and
  `gemini ask --model` refuses the model before sending anything, under the
  error code `MODEL_LIMIT` ('Gemini model "4-argon" is out of usage: Limit
  resets Nov 9, 9:26 PM'). The bridge (`geminiModelLimit`) reads that back
  as `quota_exhausted` (HTTP 429 or a stream's `error.limit`) with the reset
  the site stated, taken in local time; a stated time that has already
  passed is a label the page has not refreshed and names no reset.
- **Per-site health isolation and live probe resilience.** Both opencli
  providers share the `:4004` bridge process, but each route probes its own
  site via `http://127.0.0.1:4004/health/liveliness?provider=<provider>`.
  The bridge tracks queue depth and turn activity per site; a wedged turn or
  stuck tab on one site (running past its turn timeout) reports `503` for
  that provider while the other continues answering `200 ok`. Live probes
  retry transient timeouts once with an extended deadline before declaring a
  failure. Operator checks are observational: a failing probe records
  evidence without deepening cooldowns or incrementing failure streaks, and
  model listing failures are reported in `check.models` without failing the
  provider health verdict. Cancelled turns escalate from `SIGTERM` to `SIGKILL`
  after a 2-second grace period, preventing abandoned commands from holding
  the site session lock busy.
- **Request refusals do not pollute provider health.** A request refused
  before the turn starts -- an oversized Gemini prompt on argv (over 100 KB),
  an unsupported capability, or an unknown model -- returns a 400 refusal
  (`unsupported_request`, `invalid_model`). Refusals are classified as client
  and request failures and are not recorded against the provider health or
  lastFailure, so an individual prompt exceeding limits never flips the
  Console provider badge to Unavailable.
- **Streaming and failures.** A streamed turn (Codex always streams) opens at
  once: headers and `response.created` go out before the site is asked, and a
  `response.in_progress` event follows every 15 s. A site turn can outlast five
  minutes -- a slow model, or a queue behind other turns on the same tab --
  and the router's HTTP client abandons a response whose headers have not
  arrived by then (`UND_ERR_HEADERS_TIMEOUT`); the router's retry of such a
  turn once handed a ChatGPT root the whole transcript in a new chat, and it
  answered that `wait_agent`/`close_agent` did not exist (session
  `01a1b2dc-a3fa-7191-ad54-1f090091b088`). A failure then ends the stream with a
  single `response.failed` and no output items, carrying its error type and,
  for a site limit, the declared limit as `error.limit`: the router cools the
  provider down on it where the class calls for that and answers the turn
  from the next route on the same stream. Requests refused before the turn
  starts -- an unknown model, an image, an oversized Gemini prompt -- are still
  plain HTTP errors (`400`, `provider_request_unsupported`), and a
  non-streamed request still answers `429`/`408`/`503`. Images are refused as
  `provider_request_unsupported`. A client that disconnects kills the opencli
  command.
- **Orchestrator role prompt.** A root orchestrator's policy reaches Codex as
  the root-delegation hook's additional context, and Codex truncates it: an
  `opencli-gemini` root turn received only its first ~10 KB ("Warning:
  truncated output (original token count: 6282)"), without the delegation
  sections, and did every step itself instead of spawning. The CLI bridges
  add the full role prompt from the router's `x-autodev-agent-role` header
  (`composeProviderPrompt`); opencli does the same for the orchestrator role
  (`roleInstructions`: bootstrap, canonical orchestration skill, and role
  contract) as a `## Your role` section in the conversation's first message; a follow-up reminds the model it is still orchestrating and names the spawn, wait and close functions. A leaf's instructions arrive whole in Codex's input (its role
  TOML's developer instructions), so leaf turns get no extra section.
- **Delegation.** The execution contract declares `delegation: "native"`:
  the bridge relays Codex's own `exec` tool, whose `tools` global carries the
  `multi_agent_v1__*` spawn and lifecycle functions on an orchestrator turn,
  and Codex runs the calls the model writes in it -- the same path a
  Codex-native model takes, with no shim. A child is therefore a real Codex
  thread, routed through its own `autodev/<role>` alias, and opencli may serve
  the orchestrator tier once the operator gives it an Orchestrator priority.
  A parent's `wait_agent` is a Codex tool call, not a held site tab, so a
  child served by the same site does not deadlock behind its parent. Usage
  reports zero tokens and the models are priced at zero, as the user's own
  subscription.
- **Opt-in routing.** Neither opencli provider is in a `providerGroups` tier,
  so no role reaches a browser tab until the operator gives one a priority in
  the Console (for example `opencli-gemini`, `Default: P3`, model
  `opencli-gemini-3.1-pro`), exactly as for any other provider (see
  "Operator priorities decide tier membership and order"), or a request names
  an `opencli-*` model directly.
- **Reply normalisation.** Each site spec's `reply` strips what the adapter
  adds around the model's text (opencli's `gemini ask` prefixes every reply
  with `💬 `), so the decoration never reaches Codex.
- **A turn that never reached the site is a refusal, not an outage.** A site
  can fail before the prompt reaches it: the tab had no composer, the page
  showed no file input, the site session was held by another command. The
  provider is healthy in every one of those cases and holds nothing of the
  turn. The bridge reports them as the typed refusal the router already knows
  (`provider_request_unsupported`), in the plain path and in the stream, and
  the router reads the error a failed response carries: a refusal leaves the
  provider serving, and only a provider that failed the request is cooled
  down. Cooling a provider for a browser tab that was not ready yet pushed
  every other agent off a working route, and the session ended with a refusal
  that named none of the providers that were excluded.
- **A daemon of another version is replaced, not fatal.** opencli's daemon is
  shared machine-wide on one port, so the CLI the repository pins can meet the
  daemon a global install left running. The CLI's own remedy is to stop the
  daemon by hand; the bridge owns the CLI it runs, so it stops the daemon and
  runs the command again instead of failing the turn.
- **The prompt a site is given is bounded.** A site that takes its prompt on
  the command line takes at most 100 KB, and one that takes it as an
  attachment is bounded the same way for the model: a root orchestrator's tool
  reference carried 280 KB of MCP declarations and took the model 85 seconds
  to answer. The reference is compressed -- the MCP tools listed by name and
  summary, then by name -- and the built-in tools keep their declarations. The
  conversation itself is never cut. The nested functions a code-mode tool
  exposes are named where the model looks first: a model that could not find
  `multi_agent_v1__spawn_agent` in a ten-kilobyte description reported the
  delegation tools as unavailable.
- **One version.** opencli is patched, so the version appears in the Runtime
  manifest, the pnpm workspace's `patchedDependencies` key, the patch file's
  name and the lockfile. `runtime/src/shared/opencli-version.ts` is the one
  place it is written down; `node runtime/src/cli/opencli-version.ts --check`
  refuses to leave the four apart (`--write` puts them back together), and
  `tests/opencli-version.test.ts` asserts the repository agrees, including
  that the installed package is the pinned one.
- **Sites.** MiniMax is not served: opencli 2.0.3's `minimax` adapter has only
  a `music` command, no chat. Adding a site is one `OPENCLI_PROVIDER_SITES`
  entry plus its `OPENCLI_SITE_SPECS` entry (turn commands and model list),
  route, catalog, and contract entry; the load-time check refuses a site
  without a spec.
- **Prerequisites.** opencli's daemon starts on demand, but its Browser Bridge
  Chrome extension and each site's sign-in are the user's. Check them with
  `node runtime/node_modules/@jackwener/opencli/dist/src/main.js doctor` and
  `… chatgpt status`; sign in with `… chatgpt login`.

### Antigravity: agy executes its own tools, so its reasoning stream is the record

Antigravity is the opposite of the Claude bridge above, and the difference is
structural rather than a gap that can be closed the same way. `agy` runs as a
full agent runtime: the bridge gives it its own MCP servers
(`runtime/src/providers/antigravity.ts`) and it runs its own tools inside its own
process. Nothing is handed to Codex, so Codex has no `function_call` item to
render, no change tracking, and no approvals to gate — which is why a turn shows
no tool cards while plainly having run `view_file`, `run_command`, and
`write_to_file`. Measured across the AutoDev workspace, Codex recorded 1 tool call
for 393 Antigravity attempts, against ratios near 1.0 for codex, MiniMax, and
Claude.

What the bridge now does is run agy as an agent whose only tools are Codex's.
The shim is registered in agy's `mcp_config` alongside the role's own servers,
the turn's tools are mirrored into it, and the turn runs under an agent
definition with `excludeDefaultComponents: true` — so the built-ins leave the
advertised set and every action becomes a call Codex executes and the app
renders. A turn parks while Codex runs a call: the response **completes** at the
`function_call`, and the request carrying that call's output resumes the same
agy rather than starting a second one. The registry that maps a shim call back
to the turn holding it is shared with the Claude bridge
(`runtime/src/providers/codex-tool-turns.ts`).

Parking has to close the response as a finished turn, not just end the stream.
A stream that ends with no terminal event is what a crashed provider looks like,
and the router says so — `closeSseStream` turns any such upstream stream into an
incomplete response — so ending at the call would report every tool call as the
provider having stopped unexpectedly, while the turn in fact continues and
succeeds. A completed response whose output is a `function_call` is what a native
Responses turn ending at a tool call looks like, and it is what the Claude
bridge has always emitted when it parks.

Two agy mechanisms carry that, both tested against the installed agy rather
than inferred from its help text:

- **`--agent` works, and resolves from a workspace root and nowhere else.**
  agy takes `agy --agent <name>`, and custom agents load from
  `<workspace>/.agents/agents/<name>/agent.md` with YAML frontmatter and an
  H1-delimited prompt. An unknown name fails fast with
  `unknown agent "x" (available: ...)` before any model call, and the message
  lists what _is_ registered — which is what makes it usable as a probe.

  "Workspace root" is the whole of it. Measured with a name-defined-nowhere
  control at each end: an agent under the process's cwd resolved, and a
  byte-identical one under `$HOME/.agents/agents/` did not. `$HOME` is not a
  customization root for agents, so the bridge's isolated home cannot hold one.

  What does work is `--add-dir`, which makes a directory a workspace root. An
  agent under an added directory resolved and appeared in the registry that the
  control arm reported. The bridge writes each turn's agent definition into the
  invocation's own directory and adds it, rather than writing into the user's
  workspace — a per-turn artifact in someone's own tree is not a thing to leave
  behind, and two concurrent turns in one workspace would race on the same path.

  Two more measured details of the same probe. agy takes the token after `-p`
  as the prompt itself, so a flag placed between `-p` and its prompt is
  swallowed as prompt text and the real prompt is silently ignored;
  `--agent`/`--add-dir` therefore go last. And the agent registry is cached
  globally across runs, so a freshly created agent name can fail to resolve for
  a while even though the file is on disk.

- **`excludeDefaultComponents: true` removes the built-in tools, and the
  camelCase spelling is the one that works.** Measured against the installed agy
  with a positive control at each end, asking the agent to read a real file and
  watching for the tool step rather than the reply:

  | agent frontmatter                | `view_file` | MCP tools |
  | -------------------------------- | ----------- | --------- |
  | none (no `--agent`)              | used        | —         |
  | none, `--agent` selected         | used        | —         |
  | `excludeDefaultComponents: true` | **absent**  | **used**  |
  | camel + `enable_mcp_tools: true` | **absent**  | **used**  |
  | `exclude_default_components`     | used        | —         |

  So the field is the agy equivalent of Claude's `--tools ""`: the built-ins
  leave the advertised tool set entirely, and MCP tools remain — which is the
  split the shim needs, since the shim arrives as an MCP server. `enable_mcp_tools`
  is not required for MCP to survive; adding it changed nothing. The
  snake_case spelling is inert, which is worth knowing because the protobuf field
  is `ExcludeDefaultComponents` and a reader may reasonably try either.

  Two measuring notes, since this took several wrong turns to pin down.
  `init.tools` is a static list of globally registered tools — it reports the same
  60 entries in every arm, baselines included — so it cannot detect this at all.
  And a behavioural probe driven by a custom agent's own prompt is worthless,
  because that prompt governs the reply: an agent described as "bounded" answers
  "I have no such tool" whatever it has. Watch for a tool _step_, and keep a
  no-flag control at each end of the run.

- **`PreToolUse` hooks load but do not fire under `-p`, so they are not a
  backstop.** This corrects an earlier claim here that they work and that
  `decision: "deny"` survives `--dangerously-skip-permissions`. The hooks are
  found and parsed — agy's own log says `loaded 4 named hooks from 1 hooks.json
file(s)` — but no hook command executed during a turn that demonstrably called
  a built-in (`view_file`, two `step_update` tool events, and `run_command`
  approval granted). Four matcher spellings were tried in one run: the tool's
  own name, `""`, `".*"`, and `"*"`; none fired. The probe's hook commands were
  plain `cat >> <file>` and `printf`, with no dependency on `PATH` or `node`,
  so a failed command cannot explain a file that stayed empty.

  What is _not_ ruled out is folder trust: agy's changelog records a fix for
  workspace hooks not loading "after trusting a folder", and the probe folder
  was created minutes earlier and had never been opened. Until that is
  measured, a deny hook must not be described as a safety guarantee — a backstop
  that never fires reads like one and is not.

  For the same reason, the settings file is not a backstop today either, for a
  reason that has nothing to do with hooks: headless mode _does_ auto-deny a
  tool with no allow-rule (agy says so and names the fix — "a tool required the
  `read_file` permission that headless mode cannot prompt for, so it was
  auto-denied. Add an allow-rule under `permissions.allow` in settings.json"),
  but `agyArgs` passes `--dangerously-skip-permissions` by default, which
  approves every permission request and so removes that gate. Making the
  settings authoritative for these turns means dropping that flag for them and
  granting the MCP entry point by name, which is a separate change with its own
  verification.

  The one fact that does matter for the shim's shape: MCP tools are not separate
  advertised tools. agy reaches every MCP server through a single built-in,
  `call_mcp_tool`, which is why `excludeDefaultComponents` has to leave it.
  `init.tools` lists all 60 built-ins, of which `call_mcp_tool` is the only one
  that can reach Codex's tools.

  Because of that, the mirrored tool's own description cannot be enough. Each
  mirrored entry says "Full reference: the `<tool>` section under "Codex tools"
  in your instructions" -- the CLI truncates MCP tool descriptions, so the
  reference lives in the model's instructions instead. The Claude bridge puts it
  there in its replacement system prompt. The Antigravity bridge did not, so a
  turn had a `codex` server offering `exec` and a description pointing at a
  section that did not exist: the model guessed the tool's name instead
  (`read_file`, `exec_command`, `shell`, `write_file`), the bridge refused every
  guess with "Codex did not offer a tool named `<tool>` on this turn", and the
  turn ended as a capability failure that named a missing capability rather than
  a misnamed call. Observed 2026-10-31 on subagent thread
  `01a19538-1438-72f2-b813-3c942260a484`.

  A bridge that reaches MCP servers through a dispatcher therefore has to publish
  the reference in the dispatcher's terms: `codexToolReferenceForDispatcher` in
  `runtime/src/providers/claude-codex-tools.ts` names the server, the tool, and
  the `ServerName`/`ToolName`/`Arguments` the call has to carry, and the
  Antigravity bridge puts it in the prompt for exactly the turns whose `codex`
  server it registers -- a turn told about a server it does not have would look
  for tools that are not there.
  `tests/antigravity-codex-tools-prompt.test.ts` covers it.

Ordering matters, and it is why the shim landed first: removing the built-ins
while the shim is unregistered would leave agy with no execution path at all.

What the bridge does instead is make its own stream legible, because agy's
`step_update` events carry the detail and the old wording discarded it. Each tool
step reports what it was called with and how it went, reading `args`/`tool_input`
and `duration_seconds` from both places agy emits them, and the first field that
identifies the call (`path`, `command`, `pattern`, `query`, `url`, …):

```text
Antigravity is using run_command: pnpm test --filter provider.
Antigravity finished run_command: pnpm test --filter provider (2.4s) — exit code 1.
Antigravity finished view_file: src/providers/antigravity.ts (300ms).
```

A failed call previously reported the bare word `error.`, which read as progress
rather than as something needing attention. This is narration, not parity: it
gives no tool cards, no diffs, and no approvals, and it should not be described as
if it did.

### Tool-result affinity

The router picks a provider per request, and Codex sends a tool's output on a
new request. Without affinity that request can land on a different provider
from the one that asked for the call, so a single turn hops providers mid-step
(the 2026-09-18 worker turn went Antigravity → MiniMax → Claude). The router
therefore records the `call_id` of every tool call a provider streams
(`@simulatorlife/autodev-runtime/router/tool-call-ownership`, bounded to the most recent 4096), and a
request whose input ends in outputs for those calls -- after which Codex may
have appended its own user or developer messages -- moves the issuing provider
to the front of its candidates, for role and orchestrator turns alike.
It is a preference, not a pin: a disabled or cooling provider is skipped as
usual and the next provider continues from the replayed history. An
orchestrator with no owned calls to answer keeps its existing session
preference.

### Measuring a provider hop

Affinity keeps a turn's tool results with the provider that asked for them. It
does not keep the _agent_ on one provider for the life of its session: the
routing tiers, the cooldowns and the operator's own switches all move an agent
from one provider to another, and when that happens the agent's work moved with
it.

A hop is therefore measured, because "we keep changing providers" is otherwise
only visible as the gap between two requests that named different providers.
The router tracks the provider that last served each agent (its live-activity
subject, together with the role it runs under, so a delegation from an
orchestrator to a subagent is not a hop) and publishes a hop on the request that
observed the change:

- `autodev.hop.from` and `autodev.hop.to` -- the two providers.
- `autodev.hop.route` -- the pair as one label, because an operator's question
  is about a pair ("we keep moving from Claude to Minimax"), not about either
  provider alone.
- `autodev.hop.reason` -- `fallback` when the provider the agent was on failed
  while serving the request, `skipped` when it was never tried (disabled,
  cooling down, or unable to serve the role), `reselection` when nothing the
  router observed explains the change.
- `autodev.hop.failure_class` -- the bounded class that explains a `fallback`
  or a `skip`, when one applies.

The attributes are hop-scoped. The logical-request span still carries no
`gen_ai.provider.name`, because a logical route can touch several providers and
a hop names only the two it is about. The hop lives with the request because
that is the thing that observed it, and the Usage page reads it from the same
trace the request it belongs to is read from.

The tracker is bounded: it remembers the current provider of the most recently
served agents and forgets the oldest beyond that bound, so a long-lived router
cannot grow its state with the number of agents it has ever seen.

The local router owns the GPT branch separately and forwards it to
`https://chatgpt.com/backend-api/codex/responses` with the existing Codex OAuth
token and account ID from `auth.json`.

The five LaunchAgents under `config/launchagents/` are the supported
persistence path for this Desktop host. The installer loads them with `KeepAlive`
and also retains idempotent direct-start hooks as a fallback when `launchctl` is
inaccessible.

Long-running agent turns are supported with two complementary watchdog mechanisms:
an inactivity watchdog (`CODEX_ROUTER_STREAM_IDLE_TIMEOUT_MS`, default 15 minutes / 900,000 ms)
that monitors data flow on active streams and resets every time chunks or synthetic reasoning
heartbeats arrive, and an overall wall-clock ceiling (`CODEX_ROUTER_UPSTREAM_TIMEOUT_MS`, default
2 hours / 7,200,000 ms; set to `0` for unbounded). If an upstream timeout occurs, the router
retains the downstream connection and cleanly emits a terminal `response.failed` SSE event
with the failure detail rather than abruptly dropping the socket. In addition, the Antigravity
CLI bridge sets `--print-timeout 0` by default (`AGY_PRINT_TIMEOUT`, 0 = wait until turn completes)
and detects background task waiting loops on CLI stderr, maintaining active heartbeat pulses
so long delegating turns remain live throughout.

## Versioned integration, source of truth, and setup

`agents/` and `config/` own the versioned machine-local Codex integration materialized
into `$CODEX_HOME` through managed symlinks and runtime copies. Keep provider credentials in
`$CODEX_HOME/.env` or Keychain; no secret belongs in this
repository.

All non-secret user-level provider configuration, profiles, model catalogs,
provider adapters, startup hooks, shared skill content, and installer logic
are versioned in this repository under `agents/`, `config/`, and `scripts/`. The
installer is the only supported materialization path into
`$CODEX_HOME`; materialized runtime copies and symlinks, logs, and
`.env` credentials remain machine-local and are not versioned.

- User-level skills: `.rulesync/skills/{lsp-mcp-server,orchestration,remove-legacy-shims}`
  are versioned directories owned by AutoDev in the single canonical skill
  source (also the Rulesync input). The installer creates absolute,
  directory-level symlinks under `$HOME/.agents/skills/`, so Codex reads the
  canonical skill files without a second copied source of truth. Keep each
  source `SKILL.md` as a regular file; `--check` rejects file-level or relative
  skill links because Codex currently skips symlinked `SKILL.md` files.
- Native command rules: `agents/rules/default.rules` is the versioned
  source for restrictive Codex `prefix_rule` entries. The installer symlinks it
  to `$CODEX_HOME/rules/default.rules`; it replaces the old custom Git hook and
  is testable with `codex execpolicy check` before restart. These prefix rules
  cover direct command tokens and the native engine's supported shell parsing;
  they are not a general-purpose parser for arbitrary environment wrappers or
  global-option placement. Explicit localhost diagnostic URLs are allowed for
  `curl`; remote curl commands remain subject to the normal approval policy.
  Destructive `git clean`, `git rebase`, whole-tree `git restore`, force branch
  deletion, force push, superuser/raw-disk formatting, and root/home wildcard
  deletion commands are forbidden.
- Current user-level role projection: `agents/roles/*.toml`, rendered from
  the shared `base.md` + `leaf.md` prompt layers and materialized as managed
  regular-file copies under `$CODEX_HOME/agents/`. These files remain a transitional input: RuleSync 43.8.0 generates native subagents for the configured targets, but that support does not encode AutoDev's complete cross-provider role contract losslessly. The target is canonical RuleSync ownership with Codex TOML as a generated projection, not a second editable authority. The role loader must receive
  regular files rather than symlinks; the installer replaces symlinks and
  verifies exact rendered content matches. Code-oriented roles (`default`,

  `cocoindex-code`, and `lsp` servers with the `ccc` and `lsp-mcp-server`

  enable the user-level `playwright` MCP server with the approved browser tool

- `.codex/config.toml` is project execution configuration only. It does not

### Operational notes

- `run-provider-agent.sh` prefers the newest executable matching
  `$HOME/.nvm/versions/node/*/bin/codex`; set `CODEX_BIN` to override that
  selection.
- Profile names are configuration files selected with `codex --profile`, not
  `[profiles.*]` tables.
- After changing registry or profile configuration, run `codex doctor --json`
  and restart Codex when applicable so the role registry is reloaded.
- Every execution surface must resolve the same flat role entry. The role file
  is the authority for the provider/model pair; CLI profiles and provider
  startup hooks provide transport only and must not define a second role
  registry.
- The native app-server can select the external provider from the loaded user
  catalog/registry. Fully quit and reopen the Desktop app, then start a new
  thread, after changing this user-level provider configuration; an existing
  process can retain the previous provider registry. A fresh `spawn_agent`
  result is only valid when its effective provider/model metadata or provider
  logs confirm the custom route; a ChatGPT-account model error means that the
  request was rejected before the custom provider was selected.
- The active parent provider is the tracked `local_model_router` at
  `http://127.0.0.1:4100/v1`. It dispatches by `model`: GPT/Codex models go to
  the Codex OAuth Responses endpoint, while `sonnet`, MiniMax, and Gemini
  models go to the existing provider bridges. The parent runs on the
  `autodev/orchestrator` alias (see **Orchestrator routing and fallback**),
  which keeps orchestration on the primary Codex model while allowing the
  router to degrade to another provider when Codex is out of usage.
  `default_subagent_model = "autodev/default"` likewise ensures native default
  child work enters the multi-provider priority groups instead of bypassing
  them with a concrete Codex model.
- `[agents].max_depth = 1` in the Codex config limits native Codex child
  creation, including a Claude turn's: the Claude CLI runs with no built-in
  tools, so it can only delegate through Codex's own spawn tool.
- All six services -- the router and the five provider bridges -- are launchd
  agents with `RunAtLoad` and `KeepAlive`, managed by the installer.
  `launchctl bootout`/`bootstrap`/`kickstart` refresh every one of them on each
  install, while direct-start hooks remain an idempotent fallback for a
  sandboxed run where `launchctl` is unreachable. Those hooks adopt the agent
  when one is loaded rather than backgrounding a rival copy beside it: a process
  launchd does not own is one nothing restarts, so it survives installs still
  running the code it loaded days earlier.

## Build vs. delegate

This integration sits next to two off-the-shelf components that advertise
overlapping capabilities -- LiteLLM (native Anthropic/OpenAI/Gemini providers,
routing, fallbacks, cooldowns) and the Codex app-server. What is custom here is
custom deliberately. This section records why, so the question does not have to
be re-derived.

### The provider bridges are not model gateways

Three of the four bridges spawn a subscription-authenticated coding-agent CLI.
The Antigravity and Copilot bridges return a _completed agent turn_ -- file
edits, tool calls, and for Antigravity its own subagents -- not a model
completion. The Claude bridge is the exception: it serves Claude as a model
whose every tool call Codex executes (see "Claude bridge: Codex executes every
tool"):

| Bridge                                 | Authenticates as                                                                                                                                                                                                            |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runtime/src/providers/claude.ts`      | the `claude` CLI's Claude Code OAuth subscription. `claudeEnvironment()` **removes** `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` from the child environment so the CLI cannot silently fall back to metered API billing. |
| `runtime/src/providers/antigravity.ts` | the `agy` CLI's Antigravity subscription. `ensure-codex-antigravity-proxy.sh` refuses to start unless `useAiCredits=false` and `useG1Credits=false`.                                                                        |
| `runtime/src/providers/copilot.ts`     | the `copilot` CLI's own login.                                                                                                                                                                                              |
| `runtime/src/providers/minimax.ts`     | a plain `MINIMAX_API_KEY`; no subprocess.                                                                                                                                                                                   |
| `runtime/src/providers/opencli.ts`     | the user's own signed-in browser session on each chat site, through opencli's Browser Bridge extension; no credential reaches the bridge.                                                                                   |

LiteLLM's `anthropic/*` and `gemini/*` providers speak HTTPS with an API key:
a different account, a different meter, and per-token billing where these have
a flat subscription. They would also return a completion where these return an
agent turn, so delegation across provider bridges could not hold. MiniMax
is the one bridge whose _auth_ would suit a LiteLLM deployment, but most of it
is the `multi_agent_v1` namespace flatten/re-expand round-trip that LiteLLM has
no equivalent for; without that the orchestrator emits plain text instead of
delegating.

### The router owns routing, not LiteLLM

LiteLLM genuinely implements fallbacks, cooldowns, retries, load balancing, and
model aliases, so that part of the router overlaps it on paper. The router keeps
the job because its fallback is entangled with semantics LiteLLM cannot express:

- per-provider orchestrator `reasoningEffort`, applied per fallback candidate;
- the spawn-capability validation that fails the process at config load;
- the session-to-provider join that attributes `router_alias` subagents to the
  provider that ran the parent turn;
- namespaced-tool flattening for every non-Codex provider;
- the declared-limit contract: cooldowns keyed to a provider's own stated reset
  time rather than a generic backoff curve, and a last-resort pass that treats a
  cooldown as advice rather than a bar so an orchestrator turn survives a tier
  that is briefly all cooling at once;
- the `x-autodev-*` headers, which the router **generates** per request from its
  own alias dispatch. LiteLLM can forward allowlisted client headers; it cannot
  mint them, and a forwarded client value would be exactly the spoofable input
  `downstreamHeaders` refuses to trust.

LiteLLM was previously deployed in front of the Antigravity adapter. It routed
nothing -- one upstream, an identity model map, `num_retries: 0`, no callbacks,
budgets, caching, or provider translation -- and it cost a config-drift
self-healer (LiteLLM reads its YAML once at start), a header workaround (it
dropped raw headers, so the router smuggled its own through the Responses body),
and a correctness bug (it mistranslated `response.failed`, so the adapter faked
a _completed_ response carrying the error as assistant text). The router calls
the adapter directly now and all three are gone.

### What the Codex app-server does and does not offer

The app-server exposes thread, turn, `command/exec`, `model/list`, filesystem,
and approval methods over JSON-RPC. It has no provider selection, fallback,
retry, model aliasing, usage telemetry, OTLP export, or concurrency limiting;
`thread/start` accepts a `model` but no provider orchestration. It therefore
does not overlap the router's job. A `thread/list` snapshot was surfaced in
`/status` for a while; nothing in routing, concurrency, or fallback ever read
it, and it cold-spawned a `codex app-server` process on every refresh, so it
was removed rather than reworked.

### Where the agents' telemetry goes

The agents export their logs, traces, and metrics to OpenLIT's authenticated
first-party receiver on port 4318, and the Console reads that store. The
router does not receive OTLP: it has no OTLP routes, no historical
aggregation of its own, and no metric series. What it keeps is the live
correlation it observes itself -- the tool, skill, and MCP events the
provider bridges report -- because those are the facts about the agents it
serves that only it can hold. The router owns provider selection, fallback,
cooldown, concurrency, and origin telemetry because Codex emits none of those
semantics.

## Distribution and validation strategy

Split a task into independent items and distribute those items across providers
when useful. Select a primary implementer per item based on the task, while
using the overall provider mix to distribute load. Assign disjoint files,
cross-check important work with a different provider, and finish with an
independent validator. Keep prompts bounded and report skipped, stalled, rate-
limited, or quota-exhausted providers as missing evidence rather than success.
Always close completed child handles so the agent pool is released.

Target state and current verification:

| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenAI/Codex orchestrator and tracked user-level cross-provider TOMLs | Configured under `agents/roles/` and materialized as verified regular-file copies under `~/.codex/agents/`. The orchestrator runs on the `autodev/orchestrator` alias so it degrades to Claude Opus, MiniMax, then Gemini when Codex is out of usage. |

| Versioned scripts/hooks/config installed into `~/.codex`              | Configured; profiles/catalogs/config are symlinked and app-executed hooks are checksum-checked runtime copies; `scripts/install.sh --check` passes.                                                                                                   |
| Native app-server custom-provider routing                             | Verified: `thread/start` selects the custom provider; Claude reached its upstream session-limit response.                                                                                                                                             |
| Direct CLI provider turns                                             | Transport paths verified; Claude was session-limited, MiniMax was upstream high-demand limited, and Antigravity was quota-limited.                                                                                                                    |

configured and validated.

### Cross-provider execution contract

`config/execution-contract.json` is the current generated runtime contract for role kind, read-only intent, expected MCP/skill capabilities, and adapter spawn-tool metadata. Today it is projected from native role TOMLs by `runtime/src/config/render-execution-contract.ts`; the installer rejects drift. This is a transitional projection path, not a long-term competing source of truth: RuleSync 43.8.0 supports provider-native subagent output, but the remaining AutoDev role fields and runtime semantics still lack a proven lossless mapping. Once RuleSync owns those corresponding semantics losslessly, generate/validate the runtime contract from canonical RuleSync state and remove duplicate editable role authority. The Antigravity and Copilot bridge prompt paths append the canonical
role fragment from `agents/prompts/roles/` and use this JSON only for
capability metadata; the Claude bridge receives the rendered role TOML's
instructions in Codex's own context. The installer deploys both beside the bridge runtime
modules. Native TOML role files remain the current Codex runtime configuration surface; the target is for them to become generated RuleSync projections once parity is proven. Prompt or
capability changes must be validated with the bridge-role matrix and native
prompt-rendering tests.

### Route manifest ownership

`config/model-routing.json` now owns provider
route metadata: model-family patterns, local bridge URLs, health probes, and
credential environment keys. The router derives its route table from that
manifest and validates every provider entry. Native model capability metadata
(such as supported reasoning levels) remains in `config/catalogs/`, while
role MCP and skill exposure is currently projected through the native role TOMLs/execution contract. RuleSync 43.8.0 supports native subagent generation, but AutoDev role fields and runtime behavior still require a lossless mapping before moving that authority into RuleSync and removing the duplicate editable input. Older installed routing files that lack the new `routes`
block temporarily use the built-in migration defaults until the installer is
rerun; the versioned source is the authoritative routing configuration.

### Optional local router authentication

The router supports an opt-in Bearer-token boundary for `/v1/responses` via
`CODEX_ROUTER_AUTH_TOKEN`. Set the same token in the provider client environment
(`CODEX_ROUTER_AUTH_TOKEN`) and keep it in the private `$CODEX_HOME/.env`; the
launcher loads that file without printing it. Authentication is disabled when
unset so existing installations remain operational during migration. After
setting it, restart the router and Codex together and confirm
`/status.authentication.responseRequests` is `true`.
