- [ ] **FEAT**: All providers should dynamically load/fetch/pull-in their available models, so we don't have to maintain our own local model-lists. Every provider already knows what it can serve — `agy models` enumerates Antigravity's Gemini and Claude families with reasoning depth encoded in the id, and each other bridge or upstream API exposes its own model list — but today that discovery is thrown away and re-encoded by hand: adding Claude Opus 5.5 and Sonnet 5.5 to Antigravity meant hand-writing six entries in `config/catalogs/antigravity-model-catalog.json`, two tier assignments in `config/model-routing.json`, and matching OpenLIT pricing rows, and getting the ownership split wrong between the two Claude-serving providers was enough to throw at config load and take down the whole router. Keep the ownership boundary sharp: which models a provider *can* serve is a provider fact and belongs to the provider, while which model serves a routing tier stays an operator decision in `config/model-routing.json` and is not something a fetch may silently rewrite. Fetching must not sit in the routing hot path (a turn should never wait on a network call to discover a model), an unreachable or slow provider must surface as explicit `unavailable`/`stale` state rather than an empty list or a stale-looking success, and the Console must remain a reader of that state rather than becoming a second model-catalog authority.
- [ ] **FEAT**: Let the operator adjust the maximum concurrently-active subagents for an orchestrator from the UI/Console. Today this cap — `max_concurrent_threads_per_session`, which is what actually bounds how many children one orchestrator can have live at a time, since the orchestrator itself never consumes a subagent slot — lives only in `config/config.autodev.toml` and is parsed at router startup. The Console can see it but not touch it: `concurrencyStatus()` is exposed read-only on the Control API, and the Agents list and agent detail render `effectivePerSessionLimit` as plain text, so changing the cap means editing a file and restarting the router. (This is a different axis from the provider-wide agent limits already adjustable on Providers — those cap a provider's agents, this caps one orchestrator's children.) Mutate it through the Runtime's typed concurrency owner the way provider limits go through `setProviderLimits`, never by having the Console rewrite the TOML, so the Console stays a mutator over the Control API and not a second authority over config. The change must survive a restart, and because `concurrencyStatus` already reports `configSource` and `configFileExists`, the UI has to say whether the stored value or the config file currently wins — otherwise an operator edits the file, sees the number not change, and has no way to tell which one is live. A cap lowered while children are already live must apply to new admissions rather than cancelling or stranding in-flight agents. `null` is the existing, meaningful "Unlimited" value and must stay representable instead of collapsing to zero (zero reads as "no agents allowed", which is a different decision that would silently stop the orchestrator spawning). Show the cap next to the state it governs — `activeSubagentThreads`, `activeSessions`, `denials`, `denialsByReason` are already reported — so an operator can tell a deliberately tight cap apart from an unhealthy system, and follow the rest of the Console: revision-checked, auto-saving, no separate Save button.
- [ ] **FEAT**: Let the operator configure reasoning "effort" per role and per provider from the Providers page in the UI/Console. Effort is only half-configurable today: `orchestrator.reasoningEffort` in `config/model-routing.json` is a per-provider map, but it applies to the orchestrator tier alone, it lives only in the config file, and the Console renders it as static text (`orchestratorReasoningEffort` on the provider record) — the Control API carries no effort mutation at all. Three things make this more than a dropdown. (1) The effort vocabulary is model-specific, not global: `MiniMax-M3` accepts only `none`/`high`, `MiniMax-M3.1-Flash-Preview` accepts `low`/`medium`/`high`/`xhigh`/`max`, and Gemini/Claude accept `low`/`medium`/`high`, so the control must offer only the levels the selected model actually supports, derived from each catalog entry's `supported_reasoning_levels`. Today's validation merely requires a non-empty string, which is why `minimax: "medium"` loads cleanly and then fails at the provider; the UI must not be able to write a combination it knows is invalid. (2) On Antigravity an effort override is inert on its own: `agy` encodes reasoning depth in the model id and rejects a disagreeing `--effort`, so the bridge omits `--effort` entirely for an id that already carries a `-low`/`-medium`/`-high` suffix and the setting only has effect through the model the tier selects. Do not ship a control that silently does nothing — either express Antigravity's depth through the tier's model choice, or show the override as not-in-force. (3) "Per role" is genuinely different from "per tier": six roles share the `default` tier and two share `smart`, so the key has to be (role, provider) rather than tier, or setting effort for `worker` would silently also change `docs-researcher`. Mutate through the Runtime's typed routing owner the way `setProviderAssignment`/`setProviderLimits` do, persist across restart, and follow the rest of the Providers page: revision-checked, auto-saving, no separate Save button, with the effective and observed effort shown so an operator can tell a configured value from one actually in force.- [ ] **FEAT**: Let the operator watch in-progress playtest runs live from the Playtesting Console instead of clicking Refresh by hand. - [ ] **FEAT**: Let the operator select several playtests and run post-playtest analysis over them together from the Playtesting Console. Analysis is deliberately single-session today and that invariant is correct per-review: `playtest.prepareReview` returns only the durable selected packet, `playtest.submitReview` demands the packet/artifact/SHA-256 identity and rejects any citation outside that exact packet, and a new submission is required to declare cross-session context *unavailable* because the prepared packet is single-session. What's missing is the batch shape, and it is the shape both the target state and a human actually want — the first milestone selects at most 40 complete-session critiques from a batch of up to 1,000 assignments, and "analyze these fifty sessions" is not expressible anywhere in the UI today. Selection must be explicit and shareable through the existing URL discipline (workspace/build/filter/step preserved across refresh, Back and view changes), not hidden in component state. Dispatch belongs to Runtime, which already owns the reserved/persisted critique ledger and enforces the cap before a new analyst review; the Console triggers and observes, it does not become a second analysis authority. The rules the existing single-session path already enforces must survive the multi-select version: exclude partial, cancelled, crashed, infrastructure-failed and truncated sessions, show which selected sessions produced packet-unavailable receipts rather than quietly dropping them, make clear how many critiques the selection actually consumed against the 40 cap before spending them, and keep every claim cited into the packet of the session that produced it — a cross-session output must cite each contributing session's own windowed evidence and must never let a claim reference a step from a session it never received. Cross-session synthesis has to stay labelled as cross-session rather than being smuggled into a single-session review, because the report-completeness contract is what stops an analyst's synthesis from reading as one session's grounded evidence.
- [ ] **FEAT**: Onboard a game to Playtesting by adding one declarative config file to its repo, instead of hand-writing an adapter process, protocol glue and manifest-hash scripts per game. RacingGame measured the current adoption tax precisely: its first adapter came to roughly 1,000 lines of hand-written scripts plus ~360 lines of manifests, for a game that *already* had a clean deterministic `src/game` core and an existing seeded headless driver. Delivery Slice 8 has been accepting that cost by only requiring "game adapter/scenarios/rubric change", but an adapter is not a config — it is a protocol implementation a game author has to design, debug against hash contracts and keep in sync with every schema change. AutoDev should ship a **generic adapter runtime** that binds to a game's engine from declarations instead: an entry module and factory (reset), an observation projection, the legal-action space, the step function, the terminal predicate, and the seeded-RNG entry points. Be honest that this is **tiered**, not universal, and say which tier applies: (1) a convention-bound game — a deterministic headless simulation exposing a bindable API shape — onboards with the config alone and writes no code; (2) any other game gets a scaffold AutoDev generates from that same config plus a conformance test that proves each declared binding resolves and drives a real episode, so the author edits a generated file instead of implementing a protocol from scratch. Fold in the standard `.autodev/` home for this single file, and make `autodev playtest init` / `autodev playtest check` own laying out and verifying it. The automation must cover the plumbing end to end — transport, hash chain, manifest regeneration, approval binding — or "one file" is cosmetic: a game should never hand-maintain `evaluatorHash`, `schemaHash` or `contentHash`, and a drifted hash must be a failed `check`, not a surprise at approval time. What stays irreducibly game-owned is *measurement intent* — which metrics matter, what "good play" means, what the intended difficulty curve is — and AutoDev must not invent that on a game's behalf. Also remove the current sharp edge this convention depends on: `playtest.config.json` is a hardcoded `CONFIG_FILENAME` resolved against the checkout root, so it cannot live in `.autodev/` today, and because approval requires `git status --porcelain --untracked-files=all --ignored=matching` to be empty, gitignoring `.autodev/` fails the run with a message that reads like general repo untidiness rather than "you ignored the integration directory" — make the config location configurable and give that failure an actionable message.
