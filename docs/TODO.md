- [ ] **FEAT**: Let the operator adjust the maximum concurrently-active subagents for an orchestrator from the UI/Console. Today this cap — `max_concurrent_threads_per_session`, which is what actually bounds how many children one orchestrator can have live at a time, since the orchestrator itself never consumes a subagent slot — lives only in `config/config.autodev.toml` and is parsed at router startup. The Console can see it but not touch it: `concurrencyStatus()` is exposed read-only on the Control API, and the Agents list and agent detail render `effectivePerSessionLimit` as plain text, so changing the cap means editing a file and restarting the router. (This is a different axis from the provider-wide agent limits already adjustable on Providers — those cap a provider's agents, this caps one orchestrator's children.) Mutate it through the Runtime's typed concurrency owner the way provider limits go through `setProviderLimits`, never by having the Console rewrite the TOML, so the Console stays a mutator over the Control API and not a second authority over config. The change must survive a restart, and because `concurrencyStatus` already reports `configSource` and `configFileExists`, the UI has to say whether the stored value or the config file currently wins — otherwise an operator edits the file, sees the number not change, and has no way to tell which one is live. A cap lowered while children are already live must apply to new admissions rather than cancelling or stranding in-flight agents. `null` is the existing, meaningful "Unlimited" value and must stay representable instead of collapsing to zero (zero reads as "no agents allowed", which is a different decision that would silently stop the orchestrator spawning). Show the cap next to the state it governs — `activeSubagentThreads`, `activeSessions`, `denials`, `denialsByReason` are already reported — so an operator can tell a deliberately tight cap apart from an unhealthy system, and follow the rest of the Console: revision-checked, auto-saving, no separate Save button.
- [ ] **FEAT**: Let the operator configure reasoning "effort" per role and per provider from the Providers page in the UI/Console. Effort is only half-configurable today: `orchestrator.reasoningEffort` in `config/model-routing.json` is a per-provider map, but it applies to the orchestrator tier alone, it lives only in the config file, and the Console renders it as static text (`orchestratorReasoningEffort` on the provider record) — the Control API carries no effort mutation at all. Three things make this more than a dropdown. (1) The effort vocabulary is model-specific, not global: `MiniMax-M3` accepts only `none`/`high`, `MiniMax-M3.1-Flash-Preview` accepts `low`/`medium`/`high`/`xhigh`/`max`, and Gemini/Claude accept `low`/`medium`/`high`, so the control must offer only the levels the selected model actually supports, derived from each catalog entry's `supported_reasoning_levels`. Today's validation merely requires a non-empty string, which is why `minimax: "medium"` loads cleanly and then fails at the provider; the UI must not be able to write a combination it knows is invalid. (2) On Antigravity an effort override is inert on its own: `agy` encodes reasoning depth in the model id and rejects a disagreeing `--effort`, so the bridge omits `--effort` entirely for an id that already carries a `-low`/`-medium`/`-high` suffix and the setting only has effect through the model the tier selects. Do not ship a control that silently does nothing — either express Antigravity's depth through the tier's model choice, or show the override as not-in-force. (3) "Per role" is genuinely different from "per tier": six roles share the `default` tier and two share `smart`, so the key has to be (role, provider) rather than tier, or setting effort for `worker` would silently also change `docs-researcher`. Mutate through the Runtime's typed routing owner the way `setProviderAssignment`/`setProviderLimits` do, persist across restart, and follow the rest of the Providers page: revision-checked, auto-saving, no separate Save button, with the effective and observed effort shown so an operator can tell a configured value from one actually in force.
