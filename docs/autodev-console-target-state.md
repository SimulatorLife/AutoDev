# AutoDev — Unified Target State

> **Authority:** This is the single living source of truth for AutoDev's agent runtime, Console, configuration, dependencies, security, OpenLIT fork and observability. Implementation status belongs in [the migration tracker](autodev-console-migration.md); operational details belong in [local-setup.md](local-setup.md).
>
> **Problem:** AutoDev must orchestrate provider-independent agent roles across authenticated desktop applications, IDE agents, coding-agent CLIs, tool-call-capable inference CLIs and browser-backed models, while honoring priorities, request-outcome cooldowns, permissions and sessions and displaying provider quota reports faithfully. Defining skills, hooks, MCPs and agents once, maintaining separate provider adapters, and minimizing costly remote turns must not require duplicate routing, transport or resilience frameworks.
>
> **Target:** A reliable, TypeScript-first monorepo with independently replaceable workspaces, package-managed maintained open-source dependencies, a single control plane, shared agent configuration and accurate operator observability across managed and enrolled native client sessions. Detailed requirements below govern behavior, not implementation sequence.

## 1. Canonical-document contract

Changes that alter AutoDev runtime, orchestration, provider transport/routing, dependency ownership, permissions, Console product behavior, telemetry/control boundaries, memory, or acceptance requirements must update this document in the same PR.

Keep these concerns separate:

- **This document:** durable, implementation-independent requirements and architectural decisions.
- **autodev-console-migration.md:** observed implementation status, gaps, cutover ordering, and verification evidence.
- **local-setup.md:** commands, ports, environment variables, secrets materialization, and local/runtime operating instructions.
- **Focused subsystem docs:** detailed subsystem design that does not redefine shared product/ownership rules.

Update decisions in place. Do not preserve competing active plans. If a focused document conflicts with this document on shared Console, OpenLIT, RuleSync, observability, or control-plane behavior, this document is authoritative.

Implementation history that is no longer relevant to the current state belongs in Git/PR history, not in the target requirements.

## 2. Product target

Build a **single-user AutoDev control and observability console** as a deliberately reduced product built on useful OpenLIT infrastructure.

The final product is **AutoDev Console**, implemented by the root console/ Next.js application. OpenLIT remains an implementation foundation for OTLP ingestion, ClickHouse storage/querying, and selected reusable capabilities/components. It is not a second user-facing application in the target state.

The product should look and behave like a small purpose-built AutoDev operator console that happens to reuse OpenLIT infrastructure, **not** like a customized general-purpose OpenLIT installation.

### Canonical resource surface

The canonical top-level resources are:

```text
Configure
├── Overview
├── Agents
├── Providers
├── MCPs
├── Skills
├── Hooks
├── Prompts
├── Permissions
└── Tools

Observe
├── Usage
├── Evaluations
└── Playtesting

Operate
├── Workspaces
└── GitHub
```

The grouping is presentation only; all top-level resources have first-class routes. **Playtesting** is the Observe resource at `/playtesting`; its detailed requirements are in [Playtesting Target State](playtesting-target-state.md).

There is no separate generic Home/Dashboard page. The root route should redirect to a useful canonical resource rather than introduce a second dashboard. **Overview** is the Configure landing page and concise cross-system snapshot: it retains links to the canonical resources while surfacing bounded live activity, provider readiness/quota verdicts, recent failures, and a small recent-telemetry summary. It complements rather than replaces the detailed resource pages.

Use **Workspaces**, not OpenLIT Projects, for AutoDev repositories/workspaces. OpenLIT project/environment/organization/account tenancy must not reappear under different names.

**Overview** is a Configure landing page and high-level system snapshot, not a duplicate detail dashboard. It shows active Runtime sessions/threads and agents as distinct live facts, provider readiness and quota-exhaustion verdict counts, a bounded recent-failure summary, and a small explicitly ranged telemetry summary, then links to the canonical resources for detail. Each value comes from its owning authority; an unavailable or unobserved read is never shown as zero, and the page does not invent a combined health score. Live Runtime and provider reads are no-store; historical Usage telemetry is explicitly ranged and can be up to five minutes stale. **Providers** is listed directly after Agents in the Configure navigation. It is the canonical surface for model providers (for example Claude, Codex, Copilot, Antigravity, and MiniMax) and their models: per-role priority and model assignment across the four fixed roles (Default, Smart, Orchestrator, Subagent), provider-wide concurrent-agent limits with an Unlimited option, a provider-level disable that preserves its configuration, routes, and live readiness, health, cooldown, and failure state. Models is a tab inside Providers, not another top-level resource. Agents shows each role's effective provider/model eligibility as a read-only summary that links to Providers. Historical provider/model observability remains in **Usage**.

The Agents table shows the current active instance count for every configured role, the Providers table shows the count for every provider, and the Models tab shows the count for every model. These counts come from Runtime's live agent-activity projection, not historical Usage data, and refresh every five seconds while these views are open. A missing live source is **Not observed**; an observed entity missing from a live-count map is **0**. Provider/model attribution gaps remain visible as missing activity attribution rather than being assigned to a guessed entity.

Configuration, desired state, actual runtime state, health, activity, and historical telemetry should be composable on the same resource pages while remaining separate architectural data/control paths.

## 3. Product and UI simplicity contract

UI simplicity is a product requirement, not merely a styling preference.

AutoDev Console is an operator console, not a general AI platform, generic observability workbench, documentation portal, chat application, dashboard builder, or multi-tenant SaaS shell.

### One application and one design system

- Use one React/Next.js shell and one shared TypeScript/TSX design system.
- All AutoDev-owned Console application/control code is TypeScript/TSX.
- Do not iframe, embed, or visually stitch together OpenLIT, LiteLLM, MCPJam, LangWatch/Langfuse, Unleash, or other dashboards.
- Reuse/adapt useful TypeScript components and interaction patterns into the shared AutoDev system instead of preserving foreign application shells.
- One resource should look and behave consistently regardless of whether its data originates in RuleSync, the Control API, OpenTelemetry/OpenLIT, GitHub, or evaluation storage. Future memory integration is postponed.
- Non-TypeScript infrastructure may remain underneath the product (for example ClickHouse and the OTel receiver), but no second AutoDev-facing application/runtime should be introduced.

### Dark-only visual system

The AutoDev Console has **one dark visual theme**.

Do not ship a theme feature:

- no light theme;
- no Light/Dark/System selector;
- no theme toggle;
- no prefers-color-scheme product behavior;
- no product-level theme persistence;
- no parallel light chart palette or page-specific light styling.

Use a small semantic dark token set for background, elevated surface, input/card surface, hover/selected surface, border, primary/secondary text, accent, success, warning, error, and chart series.

The background/surface hierarchy (background, surface, surface-raised, input, hover, selected) is **black/neutral-charcoal, like OpenLIT's dark surfaces**: each token's red, green, and blue channels stay within a narrow tolerance of each other so the surface reads as true near-black gray, not a purple- or blue-tinted dark gray. The separate `border` and `border-strong` tokens use full-opacity brighter neutral grays so component, menu, and control edges remain distinguishable against every dark surface at **>= 3:1 non-text contrast**; do not attenuate neutral outline tokens with opacity modifiers. Status-colored borders retain their hues but also maintain >= 3:1 contrast at their rendered opacity. Accent, success, warning, error, and the chart-series tokens keep their own distinct semantic hues; the neutral border change must not desaturate or collapse those roles into each other. WCAG 2.1 AA thresholds (>= 4.5:1 for text and >= 3:1 for UI component boundaries) remain enforced by the contrast assertions in [`tests/autodev-console-target-state.test.ts`](../tests/autodev-console-target-state.test.ts).

Prefer adapting OpenLIT's useful dark styling/components where they fit. Remove dead light-theme assets/tokens after dependency verification. A third-party primitive may internally carry unused theme code, but AutoDev must not expose or maintain light mode as a product capability.

### One styling vocabulary, checked against the stylesheet it produces

A Tailwind utility is a claim about the theme: it says "this element takes the Console's accent", and the theme answers by emitting a rule for it. Four such claims fail silently -- the page still renders, it just renders differently from what the source says -- so each is checked against what the Console actually writes rather than against a list of class names:

- **Every utility names a token the theme defines.** A utility the theme has never heard of emits no rule at all: the element wears no background, no colour and no hover state, and nothing in the page says so.
- **No class string writes two utilities for the same property.** The stylesheet decides the winner by its own order, not by the order they were written in, so one of them is dead and the author never learns which -- a muted colour written beside a status colour loses, and the status the operator is supposed to read never reaches the page.
- **No utility names a raw Tailwind palette value**, including the directional forms (`border-l-amber-500` is the same palette entry as `border-amber-500`).
- **No class string carries a literal interpolation.** An interpolation written inside a string that is not a template literal renders as the literal text `${...}`, so the element wears the classes around it and none of the ones the shared constant held.

The first three are checked against the compiled stylesheet, so a utility the theme does know about is never reported and one it does not know about always is.

The Console's source is checked for all four in [`console/tests/style-vocabulary.test.ts`](../console/tests/style-vocabulary.test.ts), and the absence of raw palette utilities is checked against the source as well in [`tests/autodev-console-target-state.test.ts`](../tests/autodev-console-target-state.test.ts).

A role has **one spelling**, owned by the shared vocabulary under `console/src/components/ui/` and `console/src/components/forms/`: the control chrome (button, select, text field, checkbox), the text treatments, the status tones, the link treatments, the callouts and the headings. A feature view consumes those owners instead of restating them, and a role that needs a size or a weight of its own composes the shared treatment rather than copying it -- the section heading is the shared section label with a margin and a weight, and the action link is the shared link treatment with the caller's size.

### Page structure and density

Prefer a small number of consistent page templates:

- resource list/table;
- resource detail;
- configuration form/panel;
- scoped observability/activity view.

Prefer dense tables, compact status summaries, tabs, drawers/sheets, and inline actions over large hero cards, decorative dashboards, nested wizards, or bespoke page layouts.

Advanced diagnostics belong in secondary tabs/drawers unless they are the page's primary purpose. Charts belong primarily on Usage/history/observability surfaces; inventory/configuration pages should not become mini dashboards merely because telemetry exists.

Shared primitives must cover at least navigation, page headers, breadcrumbs/context where needed, filters, tables, tabs, stat summaries, charts, status badges, forms, dialogs/drawers, empty/loading/error/unavailable states, permission matrices, activity/history, and read-only code/config viewers. A shared primitive covers a control _role_, not a single control: buttons, selects, text fields, and checkboxes each have one chrome, one size, and one accent for the whole product, and a feature view does not spell a control's chrome itself.

A control's chrome has to say what the control does. The pointer is the primary signal that a thing is clickable, so every control that opens a list, toggles a value or applies an action shows it; a control that takes text shows the caret instead. The shared control chrome therefore carries no cursor of its own, and each role names its own. A button never wears a form input's chrome, and a form input never wears a button's chrome: the input chrome reserves space for a select chevron that a button does not draw, so a button wearing it is neither a button nor an input. A select that wears the shared chrome draws the shared chevron, so the space the chrome reserves for the indicator is never an empty gap, and a select never declares its own focus treatment -- the product has one canonical focus ring, defined once in `app/globals.css`.

At narrow widths, navigation defaults to the compact rail; expanding it overlays rather than compresses page content. Selecting a destination or pressing Escape collapses the expanded navigation, while modified link-open gestures leave the current view state unchanged.

**A viewport-dependent default is a stylesheet decision, not a post-hydration one.** The server-rendered page is the first thing an operator sees, and it is all a client without JavaScript ever sees, so a default that only JavaScript can settle is a default that is wrong until it is right. The narrow-width rail is settled by `app/globals.css` at first paint, and the component carries only the operator's explicit choice (`data-nav-preference`: `auto`, `collapsed` or `expanded`). The navigation must never cover the page it navigates: on a 390px viewport the rail is 56px beside the content, and the expanded overlay is reachable only by the operator asking for it.

**Table implementation:** Use `@tanstack/react-table` as the shared headless engine for column/row models and applicable sorting, filtering and pagination. The Console owns accessible markup, compact styling, responsive layout and server/URL navigation; remove superseded custom table behavior rather than keeping parallel systems.

Table columns declare a relative width weight, never an absolute CSS length. The shared table resolves weights to percentages of its own width, so a table fills its container instead of overflowing the page. The table keeps a minimum width equal to the widest declared weight total: below it the table region scrolls horizontally rather than shrinking columns under the budget their content was measured for. Column headers wrap at word boundaries rather than truncating, and a single-word header that still cannot fit breaks rather than hiding which column it labels. A column's weight must be large enough for its own header: a header that renders as an ellipsis is a layout defect, not acceptable truncation. Discrete cell content (chips, badges, model ids, environment variable names) stays atomic and wraps between items, never mid-token; flowing prose wraps on word boundaries and is clamped; single-value cells truncate with the full value reachable on hover.

Workspace detail routes use separate owner/repository URL segments (`/workspaces/{owner}/{repository}`), rather than relying on a percent-encoded slash inside one dynamic segment. The Workspaces list links each workspace's approval status to its detail view, where the operator manages exact-build playtesting approval and revision-bound revocation through same-origin server routes with in-place server-confirmed updates; Control API credentials never enter browser markup.
The canonical workspace catalog (`config/workspaces.json`) is the one source of a workspace's configuration, and the Workspaces surface is where it is changed: one configuration control appears on each workspace's row on the list and on that workspace's detail view, and it writes the catalog through `PATCH /control/workspaces/{owner}/{repository}`. That write is a compare-and-swap on the catalog's revision (the sha256 of the file's exact bytes, published by `GET /control/workspaces`), so a write decided on a catalog that has since moved is refused as a conflict rather than applied over the newer catalog; `id` is not editable and `enabled`, `baseBranch` and `agentRoles` are. The catalog publishes the shared desired-vs-actual view like every other canonical source, and the write reports it together with the fields it changed: the observed generation is a second read of the canonical catalog rather than a copy of the generation the write produced, so a catalog that moved again between the write and the observation is pending and a catalog that cannot be read is not observed, and the Workspaces surface says converged, pending or not observed instead of leaving the operator to infer convergence from a write that reported success.
Portable permission declarations live in `.rulesync/permissions.jsonc`; canonical AutoDev role and session policy that RuleSync cannot represent losslessly remains in its named repository sources (including `agents/roles/` and `config/config.autodev.toml`). Permissions is a read-only view of those declarations and their effective Runtime/provider projections, not another policy owner. Preserve the distinction between declared and composed policy, and between independent source reads. A role's sandbox is read from that role's own declaration (`agents/roles/<role>.toml`), not from a boolean derived from it, and a role whose declaration cannot be read is reported as not observed rather than as the nearest sandbox the product knows. A role whose declaration names no mode inherits the policy's, and that inheritance is not observed either when the policy could not be read: the nearest mode the product knows is not a mode any source stated. The effective role matrices are the execution contract's roles, and the accessor that reads the contract falls back to an empty contract when the read fails, so the Permissions surface publishes whether the contract was read: an empty matrix set, an empty tool-exposure line and a navigation badge reading 0 are three ways of saying the contract declares no role, which is not what happened when nobody read it. The policy's own read is a separate fact, and a policy that was read says nothing about the contract.
Do not duplicate provider, routing, MCP, tool, or workspace controls across several resources for convenience. Showing a supported operational control on its own list row and detail view inside its owning resource is not duplication. Never offer source or assignment mutation for the four read-only configuration resources, including on Agents, MCPs, Tools or other related pages.

### Read-only RuleSync configuration views

Skills, Hooks, Prompts (including slash commands and role prompts), and Permissions retain their existing first-class routes and detail links. Their purpose is inspection, not authoring. Show actual canonical properties/values, target overrides, source provenance, role/workspace assignments and effective/applied or observed evidence where available. Keep useful filtering, searching, history/diff and copy affordances read-only. Remove edit forms, assignment checkboxes, enablement toggles for these resources, Save/Apply actions, unsaved preview, validation-for-save and mutation feedback. Do not leave permanently disabled editor controls behind. Changes are made in the canonical repository sources and applied through the existing reviewed generation/installation/reconciliation workflow, never a Console write or an alternate UI override.

Use a single shared accessible **Rendered | JSONC** view selector for JSONC-backed declarations, defaulting to Rendered. Rendered presents the same source's meaningful properties in tables, grouped settings, matrices or other existing read-only primitives. JSONC shows the actual source text, retaining comments, order, values and source/target scope (subject to server-side secret redaction). For Markdown/frontmatter-backed skills and prompts, use the same component labelled **Rendered | Source** (or Markdown); for any other native canonical format label the raw mode truthfully (e.g. TOML). Where a page includes several actual sources, allow inspection of each identified source rather than inventing a merged JSONC document. If displaying a generated/effective JSON view, label it as a projection and never imply it is canonical source. Preserve selection, focus, URL context and source revision across view changes; switching is a presentation action only, with no write, regeneration, or live reconfiguration.

Both modes are produced from the same authoritative read/revision using existing Data/Runtime parsing and projection logic. Do not round-trip JSONC through JSON serialization, implement an alternative parser in the browser, or fetch arbitrary paths. Raw and rendered views share source availability, validation and redaction semantics; secrets, resolved environment variables, credentials and private values must not reach browser payloads, copy output, logs or errors. Missing/invalid source is explicit, not a fabricated empty view. Keep declared, generated, applied and observed facts separate. Reuse existing code/config display, Markdown rendering, tabs/segmented controls and status primitives; no rich editor or duplicate resource-specific source viewer.

The boundary that satisfies the redaction requirement is the source's own kind, not a filter applied to its text. A canonical declaration -- a rule sync source in the repository -- is published whole, comments included, because it is a declaration and its comments are part of what it says. A composed or applied configuration -- the user configuration the Runtime composed and applied -- is published only as the values parsed from it, never as text, because that is the file that can hold credentials, resolved environment variables and private values. Applying a filter to the canonical source instead would publish a document that is not the source, whose revision would not name the bytes on the page, and whose rendered and raw views would disagree about what was withheld.

### Contextual controls

Controls live with the item they act on. There is no separate settings, admin, or control page for state that belongs to a listed item.

- An item's enable/disable toggle and other item-scoped actions appear on that item's row or card in its resource list view **and** in that item's detail view. The toggle that disables a model provider sits on that provider's row in Providers and in that provider's detail view; the toggle that enables or disables a model sits next to that model in the Models view and in that model's detail view.
- Each configured Agent role's enable/disable control appears once on its Agents row and once on its detail view. Agent enablement is Runtime-owned admission policy for the matching named `autodev/<role>` alias, including the separately configured orchestrator alias; it is not provider-role assignment and does not disable direct concrete-provider model requests.
- When a detail view lists child items, each child row carries its own controls; a provider's detail view lists its models with their model toggles.
- Each rendering of a control uses the same typed Control API operation and the same current, pending, and could-not-be-confirmed states. A list control and a detail control are one shared component, not two implementations.
- Pages outside the owning resource show the item's state read-only and link to it; they do not embed its controls.
- For a normally mutable operation that is temporarily unavailable (for example missing credentials or unobserved state), keep its control disabled with the reason. Intentionally read-only resources have no mutation controls at all.

### State correctness

Missing evidence must remain explicit:

```text
unknown
not observed
unavailable
pending
error
```

Never synthesize ready, converged, healthy, connected, zero, or success merely because configuration exists or telemetry is absent.

A count is the sharpest case of that rule, because a count over a scope whose elements were only partly read still looks like a measurement: the number is exactly right for the elements that were read and merely incomplete for the ones that were not. A count is therefore a number only when everything it counts was observed; otherwise it is not observed, and the page says how much of the scope was missing. Two independent reads are observed separately, so one unread read never turns the other's count into a zero. A measured zero is a measurement and stays a number: "nothing was there" and "nobody looked" are different claims, and only the first is a count.

A read that falls back to an empty result is still a read that may have failed. The accessor that reads the execution contract returns an empty contract when the contract cannot be read, so the roles it contributes look exactly like a contract that declares no roles, and the two are not the same claim. The producer of a read publishes whether the read happened, and a consumer does not infer it from the emptiness of the result: an empty result standing in for a failed read is an absence of evidence wearing the shape of evidence.

The same rule governs a detail. A detail that cannot be produced because its source was never read is not an unknown resource: nobody looked. "This role does not exist" and "the file that says which roles exist was not read" are different claims, and an operator can act on the second and not the first. The rule holds for every detail the Runtime serves, and it is the read that knows which of the two happened: a read returns what it found, and when it cannot answer, it says why rather than leaving the route to probe the same source again and infer. A 404 for a detail that could not be read claims the resource does not exist, and a 404 whose own message says the source could not be read is worse than either answer, because the status and the reason disagree.

A detail composed from a catalogue is held to the same rule, and the catalogue's own observation fact decides it. Some resources have no read of their own: a hook event, an MCP server and a tool are entries in a declaration, and the route finds its entry in the catalogue the Runtime published. It can only say the entry is absent when the catalogue was read. A catalogue that was read and found broken, and one nobody read, publish no entries, and a route that turned either of them into "not found" would claim the entry does not exist -- while the declaration that named it a moment ago is still there, and the read that would have named it again is what failed. Those two answer "this could not be read", with the reason the Runtime published beside it, and the reason is what tells the operator whether to fix the declaration or to look for the entry under another name. The badge above such a detail counts the catalogue only when the catalogue was read, because the length of an unread catalogue's empty list would claim the repository declares none.

One published word has one owner. When a fact is composed of two reads, the layer that composes them publishes it, and a layer that contributed only a part publishes only what it read. A second derivation of the same word over a narrower scope is how two authorities drift apart: each is defensible on its own, and then one surface contradicts another about the same fact.

A capability has one path as well as one owner. A helper that forwards to another without adding anything is a second path to the same thing, and the second path is where the two drift apart: the copy that is called less often is the one whose callers were migrated first and whose behaviour was checked last. A pass-through that no production caller reaches is not a convenience -- it is a second answer to a question that already has one -- and a re-export that exists so a test can import a symbol is a second published home for a value its owner already publishes. The same holds for the files that hold a capability: a module's entry is the path into it, and a caller that names one of the module's implementation files reaches a capability the entry publishes without going through the entry -- so the entry and the files behind it can answer for the same capability without either of them knowing the other exists.

A count over a partly-observed scope names the scope. The count may be exactly right for what arrived -- a workflow the Actions API did not report cannot be counted active, and an unread half of a catalogue contributes no entries -- but the operator has to be told how much of the scope arrived, or a number that is right about half the catalogue reads as a number about all of it.

Configuration does not prove runtime availability. Eligibility/exposure does not prove execution. Historical tool use does not define current permissions.

### Accessibility and interaction consistency

- Every editable configuration control persists its change immediately; do not require a separate Save button. A safe, reversible single-choice setting applies as soon as the operator changes its select. Do not place a second Apply/Save control beside one selection; submit the complete owning form through its existing route. A grouped setting that must remain atomic submits its complete desired value on each change (for example, a role checkbox auto-submits the full selected role set). Preserve expected-revision checks and show pending, confirmed, or failure state accessibly.
- Apply remains appropriate for non-persistent filter groups that are deliberately staged as one URL state, preview/validation steps, or consequential actions that need review or confirmation. Make that boundary explicit; do not stage a lone workspace/scope choice or turn configuration edits into unsaved drafts.
- Visual hierarchy is explicit per interaction group: within any toolbar, form, row, or dialog that offers more than one action, exactly one renders with the highest-emphasis style; secondary and destructive actions use lower-emphasis or outline styles, and heading levels track page > section > item nesting rather than decorative sizing. A page is not required to carry a primary action merely because it has content.
- Immediate mutations stay server-authoritative: do not claim success optimistically. The refreshed control value is the confirmed state, and an unconfirmed or failed write must produce an accessible, actionable notice.
- System status is shown adjacent to the control or resource it describes, not centralized on an unrelated page. Asynchronous actions that remain in place show a visible pending state and announce it accessibly until completion. Changing or submitting any Console form or control must not cause a full document reload: configuration changes auto-save, filters may use an explicit Apply action where staged URL state is intentional, and GET/POST updates use in-place client navigation while preserving URL state and server-confirmed feedback. In-place requests provide visible pending feedback during execution, preserve keyboard focus and visible focus states, and show Runtime-confirmed values or an accessible, actionable failure notice when confirmation fails.
- Root-level form feedback stays visible while work is pending. Completed and failed feedback dismisses after five seconds with a visible seconds countdown and a keyboard-accessible close button; the countdown does not repeatedly trigger live-region announcements. Closing or replacing feedback cancels its pending dismissal.
- Every control keeps a persistent accessible name, keyboard operation, visible focus, and a reason when disabled. Auto-submit must work for keyboard selection as well as pointer input; never rely on color, hover text, or position alone.
- An auto-submitting select is submitted by one page-level listener installed by an inline script in the root layout, so a change made before the page hydrates, or on a page whose scripts did not load, is still sent as a native form submission. It shows the server-rendered value, the operator's choice only while that write is in flight, and the server's value again when the page is re-read; the page is re-read after every write, refused and failed ones included. A select that keeps showing a refused choice reads as a setting the Runtime does not hold.
- Prefer recognition over recall: operators choose from visible, labeled, searchable lists, dropdowns, and breadcrumbs instead of memorizing resource IDs, slugs, or command syntax, and a form shows the currently effective or previously entered value rather than requiring the operator to recall it from elsewhere.
- Keep labels, controls, and their state feedback in one aligned group. At phone widths, controls wrap or scroll within their owning region rather than hiding the action or breaking the relationship between a label and its value.
- Core workflows must be operable at both phone and desktop widths. Navigation and primary content may reflow into a single scrollable column, and secondary detail may progressively disclose into drawers or tabs, but all controls needed for core workflows remain reachable without hover- or pointer-only access.
- Use consistent keyboard/focus behavior and visible focus states.
- **An in-place navigation moves the focus to the new page's heading.** The navigation owner does it, because the navigation owner is the one segment an in-place navigation does not replace, and because a focused heading is also how the page change is announced -- no separate live region says it twice. The heading is focusable (`tabIndex={-1}`) and out of the tab order. A form navigation restores the focus to the field that was submitted, and that field wins over the heading. The initial load never takes a focus the operator had already put in a field. **A navigation that names a fragment lands on that fragment instead**, because the link asked for that element -- the detail drawer is opened by a link carrying the drawer's own anchor, and the operator asked for the panel, not the page it sits under.
- Every interactive target meets the WCAG 2.5.8 minimum of 24x24 CSS px, or qualifies under one of that criterion's own exceptions (inline in a sentence, sufficient spacing, an equivalent control, or essential to the task). The floor is carried by a shared class rather than per call site, and it is carried on a **block box**: `min-height` is inert on a non-replaced inline box, so a target that merely carried `min-h-6` while staying inline would measure the same 22px as before and look fixed in the source. A button is an inline-block box and takes the floor like any other control -- the state-coloured button that enables and disables an agent role is a target, not a piece of prose.
- Preserve WCAG 2.1 AA contrast (>= 4.5:1 for text, >= 3:1 for large text and UI component boundaries) in the dark-only palette; enforced by the `contrastRatio` assertions in [`tests/autodev-console-target-state.test.ts`](../tests/autodev-console-target-state.test.ts) (test: "Console semantic text and status surfaces meet WCAG AA contrast").
- Use the same status vocabulary, icon sizing, spacing, table density, dialog behavior, and destructive-action confirmation patterns across features.
- A section heading names the section it labels; it never repeats the page's own title, and a page whose content is a table names that table's section. The shell owns the page's `h1`, so a heading that restates it adds an outline level that carries no information.
- A link's accessible name says what it points at. When the same destination appears in more than one context on a page, each occurrence names the context it appears in, and the name still contains the visible text so a voice-control user can say what they see.
- A stated accessible name carries the same information as the content beside it. A control whose name is stated rather than taken from its content -- because the content is hidden in one of its modes -- must carry everything the visible content says, including a count in a badge. The sidebar's "Providers 3" is audible as "Providers (3)"; a name that stopped at the section name left a sighted operator able to read a number a screen reader never heard.
- Spacing follows shared context tokens: `PageBody` owns the page-section rhythm, related sibling blocks reuse it, and shared panel/heading components own common surface padding and heading offsets. Do not hand-roll these shared relationships in individual views; denser spacing within controls and rows remains context-specific.
- URL-addressable list/detail/filter state is preferred when it improves operator navigation and debugging.
- **A list that can grow past a screenful can be narrowed.** A catalogue the operator has to scroll to reach the entry they meant is a list with no way in. Every list in the Console that holds more than a handful of rows -- the RuleSync prompt catalogue, the tool catalogue, the evaluations, the memory records -- carries the product's own filter bar, so the narrowed list is a URL state like every other filtered view. A filter that matches nothing says so in its own words: "found matching the current criteria" is not "are configured".
- **Narrowing a list does not narrow what the page counts.** The summary row above a list is about the catalogue, not about the view of it: a card that counts every canonical entry must not shrink because the operator narrowed the rows below it. Whatever narrows the list -- the page or the view -- the counts come from the catalogue and the rows come from the narrowed list. A card that reported the narrowed count would claim a smaller catalogue than the navigation badge beside it says, which is a different claim from the one the card makes.
- **The navigation badge is a count too.** The sidebar's badge answers "how many are there", and a count is a number only when everything it counts was observed. A catalogue that was invalid or never read publishes an empty list, and a badge with that list's length would claim the repository holds none -- a claim about the read rather than about the repository. So the badge carries no number when the catalogue was not observed, and the page states what was read.
- Internal resource and tab links use Next.js in-place navigation, not full-document reloads; they remain ordinary URL-addressable anchors for keyboard access, bookmarking, sharing, and browser history. Full dynamic-route prefetch starts only on pointer, touch, or keyboard intent, never for every visible view or tab. The warm-up must be a full prefetch: a partial one answers with the route's loading state rather than with the page, and a navigation that finds that answer waiting for it never commits -- the URL stays and the page does not move. A committed navigation moves the address bar and the page together: a page showing the destination under the previous URL is a navigation that did not commit.
- Dynamic routes show the active Console shell and an accessible loading placeholder while server-owned page data is pending; the final page replaces it with Runtime-confirmed content and counts.
- **A page that has its content is not yet a page that responds.** The Console's pages are server-rendered, so the markup arrives before the client does, and everything the operator does with the keyboard -- the palette's shortcut, the filters, the write controls -- belongs to the client. A key or a click in that gap goes nowhere, and a page measured in that gap answers every question about what it shows and fails every question about what it does. The page therefore publishes the difference: the loading placeholder says the content is not here yet, and a marker rendered with the page's own content says the client has taken the page over. The marker is rendered with the content and not with the shell, because the shell is also what the pending state is rendered with, and a marker the pending state set would report a client that had taken over a page that had not arrived. It is the last thing in the page's content, so it is set after everything the content is made of has mounted.

## 4. Repository and module architecture

### Exclusive pnpm and Node.js runtime toolchain

AutoDev-owned JavaScript installation, local checks, CI, launch scripts, provider
bridges, and service reconciliation use **standalone pnpm as the only package
manager**. pnpm manages the Node.js runtime as well: the root `package.json`
pins pnpm through `packageManager`, `.node-version` pins Node for pnpm's
project-aware `node` shim and CI, and `engines.node` defines the supported
runtime range. The pnpm workspace catalog single-sources `@types/node`,
whose major must match the pinned runtime. Provision Node with
`pnpm runtime set node "$(cat .node-version)" -g` from the repository root; do
not require an npm, npx, NVM, or Corepack executable, or use them as a fallback
in first-party install, build, test, provider bootstrap, or validation paths.

Launchd and hook subprocesses must resolve the installer's explicit
`AUTODEV_NODE_BIN` or the pnpm-managed `PNPM_HOME/bin/node` even under a
minimal PATH. Global CLIs may be found under `PNPM_HOME/bin`. The Codex CLI
is resolved by one lookup owned by the Runtime
(`runtime/src/shared/executables.ts`): an explicit `CODEX_BIN` wins, and
otherwise the newest CLI installed wins over a stale one on the default
`PATH`, so no surface runs a different CLI than another. Missing pnpm
tooling is a visible prerequisite failure, never an implicit switch to a
different package or runtime manager. Installation must not create or rewrite
the operator's `.zprofile` to select Node. JavaScript target repositories
run by AutoDev's generic workflows must declare `packageManager: pnpm@<version>`;
an npm-only target is refused rather than installed with npm. Upstream
third-party container builds (such as OpenLIT's own Docker build) may use
their upstream package manager _inside the container_: that does not add
a local npm prerequisite or authorize npm in AutoDev-owned code.

**Acceptance:** an installation on macOS with standalone pnpm and its
managed Node, but no npm/npx/NVM/Corepack on PATH, passes the install
preflight, local scripts, hooks, service launch, validation and CI;
no first-party script silently falls back to another toolchain.

AutoDev is a **small, flat pnpm TypeScript monorepo** with isolated, independently testable workspaces. Do not introduce apps/, packages/, or modules/ wrappers merely to classify code, and do not create a package per navigation resource.

| Monorepo benefit                         | Architectural consequence                                                                                                         |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Atomic cross-project changes             | Related contracts, producers, consumers, tests and documentation are merged together even when delivered through several commits. |
| Reuse and discovery                      | Typed public package APIs and an ownership map expose reusable code without private cross-package imports.                        |
| Consistent tooling, CI/CD and onboarding | One lockfile, root TypeScript/lint/format/test standards, workspace-local tests and dependency-aware CI.                          |
| Better AI-assistant context              | Source, contracts, tests, workspace READMEs and dependencies remain discoverable in one versioned checkout.                       |
| Simplified dependency management         | Centralized versions and package-manager workspace links; avoid redundant libraries, bespoke forks and duplicate tools.           |
| Replaceable implementations              | Router, provider transports, Console UI and storage adapters depend on contracts rather than each other's internals.              |

```text
AutoDev/
├── console/                 # unified Next.js AutoDev UI
├── runtime/                 # request serving, agents, providers, orchestration, Control API
├── core/                    # pure domain types and portable contracts
├── data/                    # typed configuration, persistence and telemetry adapters
├── .rulesync/               # canonical agent-facing configuration
├── config/                  # portable runtime/deployment configuration
├── .github/                 # CI and GitHub automation
├── docs/
├── scripts/
├── tests/
├── package.json
├── pnpm-workspace.yaml
└── rulesync.jsonc
```

**Baseline package responsibilities** (additional packages are permitted when justified):

| Workspace  | Public responsibility                                                                                                        |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `core/`    | Infrastructure-independent domain contracts, routing ports, types and pure business rules.                                   |
| `data/`    | Typed repositories/adapters for Rulesync, OpenLIT/ClickHouse, memory, evaluations, workspaces and other external sources.    |
| `runtime/` | Orchestration, provider/CLI bridges, routing composition, runtime state, MCP, permissions, Control API and reconciliation.   |
| `console/` | Sole AutoDev UI and feature folders; typed API clients and read-only projections, not direct database or provider internals. |

**Workspace extraction decision**

| Condition                                                                                              | Decision                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One coherent domain, independently testable public API and genuine replacement/multiple-consumer value | A dedicated workspace is appropriate.                                                                                                                                                                                                                                                                                 |
| Merely a navigation resource, one implementation file or a forwarding wrapper                          | Keep a feature module in its owning workspace; do not create a package per navigation resource.                                                                                                                                                                                                                       |
| Routing becomes an independent policy engine with a stable contract                                    | A dedicated **model-routing workspace** (`router/`) may own deterministic selection and state-transition policy. `core/` owns the `ModelRouter` port; `runtime/` still owns provider discovery, CLI processes, quota-axi invocation/report publication, durable request-outcome cooldown storage and the Control API. |
| The new package introduces cycles, private imports, a duplicate control plane or mostly passthroughs   | Do not extract until its boundary can be made independent.                                                                                                                                                                                                                                                            |

**Dependency direction** (arrows point to permitted imports; `router/` is optional):

```text
core       # no AutoDev dependencies
data   ──> core
router ──> core                # optional: pure model-routing policy
runtime ──> core, data, router? # owns execution, state and Control API
console ──> core, data         # data: exported server-only read projections
```

- `console/` may import exported, read-only `data/` query/projection interfaces on the server, but never query databases through private modules, mutate canonical/runtime state or carry storage credentials in browser code. **console/ never bypasses the Control API** to mutate state; all writes, approval actions and live state changes use authenticated Control API routes.
- core/ remains infrastructure-independent. It owns portable Control API contracts; Runtime and Console independently validate and authorize their boundaries. `data/` adapts sources without becoming another source of truth. `runtime/` owns mutation/reconciliation and composition.
- Inside `console/`, **keep navigation resources as feature folders**. **Do not create agents/, skills/, mcps/, prompts/, etc. as separate packages** merely because they appear in navigation. The Console owns its shared UI library **until a real second UI consumer exists**.
- Shared producer telemetry belongs under `runtime/src/telemetry/` until another independent producer justifies an extracted package. `.rulesync/`, `config/`, `.github/` and `docs/` remain root-owned configuration, not code workspaces. **all four code workspaces share root formatting/lint/test/TypeScript policy**; any additional workspace must use the same standards.

**Verifiable independence**

- Package manifests declare `workspace:*` dependencies and explicit public `exports`; imports between the four code workspaces must use those declared package exports, never relative paths or deep imports into workspace internals. Enforce this with TypeScript/import-boundary lint rules and CI. Same-workspace relative imports are allowed. Root-level test harnesses may import implementation files directly to exercise them; `workspace:*` alone does not enforce encapsulation.
- A swappable port exposes versioned/compatible typed inputs, outcomes and error semantics, cancellation/lifecycle, authorization and telemetry contracts without leaking concrete adapter classes. Consumer-driven contract suites run against the incumbent and replacement adapter at the public boundary.
- Each package documents owner/domain, public API and exports, dependencies, local typecheck/test/build commands and replacement contract in its package README. Maintain a root ownership/dependency map.
- A cross-workspace change **merges atomically** with its affected API, implementation, migration, tests and documentation; it need not be one commit. CI checks all changed packages and their transitive dependents, runs isolated tests and relevant integration contracts, and offers a full monorepo validation gate for merges/releases.
- Independent workspaces can be installed/tested without launching the Console, external providers or unrelated services; use injected adapters and deterministic fakes for external boundaries.
- Keep modules cohesive and files named for their actual responsibilities; avoid oversized mixed-purpose files and one-function forwarding layers without architectural value.
- The authenticated Control API request handler composes resource owners. Source validation, runtime projection, and resource-specific caches stay with the owning resource rather than accumulating in the request dispatcher.
- Apply DRY to **behavior and configuration ownership**: one implementation for routing selection, failure classification, capability scope, MCP/skill policy, telemetry events, shared validation and tool resolution. Delete dead/duplicate adapters when a package or shared domain module satisfies the same contract.

## 5. Architecture and ownership

### Observability plane

```text
AutoDev producers
      │ standard OTLP
      ▼
OpenLIT first-party OTLP receiver
      │
      ▼
OpenLIT storage/query layer
      │
      ├── traces
      ├── metrics
      ├── logs
      ├── Usage
      └── resource-level historical analysis
```

Use standard OpenTelemetry traces, metrics, and logs. Prefer official GenAI/MCP semantic conventions. Add a minimal autodev.* namespace only where no suitable standard exists.

Do not restore an AutoDev-owned historical aggregation database, general-purpose telemetry query backend, compatibility dashboard, or pass-through Collector. Add another Collector only for a documented need such as pre-export redaction, routing, or fan-out.

### Control plane

```text
AutoDev Console
      │ same-origin server path
      ▼
AutoDev Control API
      │
      ├── canonical configuration mutation
      ├── validation/generation/apply
      ├── desired-state reconciliation
      └── runtime/status reads
```

OTLP and telemetry queries are observation-only. Never use telemetry as a command/configuration channel.

Mutable resources expose desired and actual state separately:

```text
canonical desired configuration
          ↓
validated apply / queued action
          ↓
runtime/controller
          ↓
observed actual state
          ↓
converged | pending | error
```

The reusable reconciliation contract should include desired state, actual state, desired generation, observed generation, diff, convergence status, last apply, last observation, last error, and operation history.

Every mutable resource the Console writes publishes that view with its write, and it is the same shared contract for all of them: a resource that answers with the applied value alone leaves "the write was accepted" and "the Runtime is serving this" as one claim, and only the second one says what the operator will actually get. The generations are comparable within a resource -- a limit of `8` and a limit of `unlimited` are two generations, not a number and a missing field -- and a write the Runtime accepted but has not observed is neither a refusal nor a failure, so the Console says that rather than claiming the new value.

Use desired/live/convergence interaction semantics similar to Argo CD where useful, but implement them through AutoDev Runtime/Control API rather than shipping OpenLIT's Controller daemon.

### Single installation and lifecycle entrypoint

**One supported user-facing installation workflow** is the canonical way to configure, install, update and reconcile AutoDev. Its script name, command syntax, internal implementation and aliases may change without altering this contract. Provider-specific helpers may exist for diagnosis or recovery, but a complete supported installation must not require users to run them separately.

- **Deterministic reconciliation:** Re-running unchanged desired configuration makes no writes or duplicate registrations. The installation workflow provides a **read-only verification mode** that reports local drift, prerequisites and pending changes without mutation, secret disclosure or authenticated provider calls.
- **Installation scope:** Reconcile selected provider and desktop/IDE/CLI client integrations, native plugins and shared harness configuration, global agents/skills/MCPs/hooks, commands/prompts, role and permission projections, binaries and managed Runtime/Console/gateway services. Preserve unrelated user settings, credentials, sessions and project files; surface ownership conflicts instead of overwriting them.
- **Failure and recovery:** Apply staged/atomic changes where supported; on interruption preserve or restore a working prior state, and make reruns safe. Report configured, converged, pending, failed, skipped and unavailable items separately.

| Validation level                                                                          | Required behavior                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read-only local verification                                                              | No-write verification of files, tool discovery, declarations, generated projections, manifest/config compatibility and managed service definitions; returns actionable drift/errors without presuming provider readiness.                                                                                                         |
| Local post-install                                                                        | Verify actual generated configurations, executable discovery, installed service ownership and reachable **local** Runtime/Console health where running.                                                                                                                                                                           |
| Authenticated end-to-end smoke check (opt-in or explicitly required by deployment policy) | Exercise approved provider tool/MCP/permission behavior and compatible Control API/Usage responses only where credentials, consent and connectivity exist. Record each probe as `observed` (with evidence), `unavailable` (attempt failed), or `skipped` (not attempted/not authorized); never promote skipped checks to success. |

**Acceptance:** A clean installation, idempotent repeat, read-only drift verification, optional-provider absence, existing user configuration, partial failure/recovery and two workspaces converge without duplicate services, modified secrets or false validation claims.

### Unified user-chat and CLI execution entrypoints

**Target:** ChatGPT and the `codex` CLI — along with every other supported provider (`claude`, `antigravity`, `copilot`, `mcode`) — are **first-class, provider-agnostic agent participants** connecting to **one AutoDev task/session, role, and permission boundary**, with AutoDev routing for Runtime-managed execution and supported explicit native routing integrations. ChatGPT is never treated as a permanently restricted read-only external MCP consumer. Equivalent agent roles receive equivalent effective MCP exposure, tool permissions, skills, execution capabilities, and restrictions regardless of provider, host application, transport, or whether the connection is local or external. This target is **unmet** until an authorized end-to-end ChatGPT session demonstrates authorized execution and XACPX delegation against the shared gateway; any provider, host or transport limitation is a parity defect to resolve, not a permanent architectural exception.

```text
ChatGPT client (authenticated gateway/tunnel ingress) ──┐
                                                        ├─> AutoDev task/session boundary
Codex / Claude / Antigravity / Copilot / mcode ─────────┘      └─> canonical role + workspace resolution
                                                                 └─> router + effective role grants

                                                                           └─> Runtime state + OTel history
```

| Client integration requirement           | Evidence                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authenticated transport and capabilities | External authentication (such as OpenAI Secure MCP Tunnel + gateway Bearer auth) establishes trusted agent identity and authorization, **never** a separate read-only capability model. | Role-driven execution and orchestration  | ChatGPT supports both direct task execution (including workspace-confined filesystem mutations when its assigned role has `readOnly: false`) and subagent orchestration through the canonical `xacpx` MCP interface (when its assigned role enables `xacpx`, such as `orchestrator`). - **Cross-client identity:** Preserve AutoDev task ID, actor, role, workspace, parent/child lineage and auditable activity across a handoff. A ChatGPT conversation ID, Codex thread ID and native provider session ID are **not interchangeable**.
- **Native continuation:** Reuse a provider session across clients only if its transport proves import/resume support. Otherwise begin a distinct, explicitly linked session with a source-backed handoff summary and prior approvals/side effects reconciled; do not pretend it is the same native conversation or replay a potentially mutating turn automatically.
- **Transport or host parity gaps:** Report unsupported host UI, transport, or approval limitations explicitly as **parity defects**, never as accepted permanent restrictions or false parity claims.

### Unified desktop, IDE, CLI and external agent integration

**Target:** AutoDev is shared agent infrastructure, not only a CLI router or a launcher. First-class participation includes both Runtime-initiated execution and operator-enrolled sessions initiated directly in native applications, IDEs, terminals or web clients. Reuse the same canonical skills, hooks, rules/instructions, commands/prompts, agent-role and subagent definitions, MCP catalogue, execution grants and telemetry wherever the host supports them. Project only unsupported format differences through a minimal reviewed adapter; prefer upstream support. Do not copy editable definitions per app, maintain independent registries, invent hook events, or create custom IDE extensions/agent runtimes merely to replicate native functionality. Plugin bundles and client settings are generated projections, not canonical authorities.
- **Same effective authorization, two session origins.** Runtime-launched sessions retain router allocation, pinned provider/model, native ACP injection and full execution admission. Externally initiated sessions join using supported authenticated client/session registration or scoped ingress, independently bound to a canonical role, authorized workspace and coordinator; an app launch, subscription, local port, profile setting or prompt is never an execution grant. Native model selection remains host-owned unless an explicit supported routing integration exists. Do not claim externally selected model calls were routed by AutoDev. Handoffs use the existing cross-client identity/continuation contract.
- **All AutoDev MCPs through Supergateway.** Generate authorized gateway references for enrolled native desktop/IDE/CLI profiles and native plugins, including standalone MiniMax; no direct backend stdio launch, direct remote URL, npx invocation or provider-specific gateway bypass. Where a native client lacks a required transport, use only supported gateway-facing adaptation or report a parity defect. A static registration cannot grant broader access than its authenticated session; enforce discovery, invocation, workspace switching, revocation and task/child ownership at the server boundary.
- **Shared execution and delegation.** Canonical role/subagent definitions and prompts are consumed by native clients where losslessly representable; XACPX remains the exclusive AutoDev agent-delegation/lifecycle interface, not a second host-native spawn path. The allowlisted commands MCP supplies approved deterministic execution without model delegation. Preserve managed-turn tool/permission isolation; for enrolled standalone hosts, distinguish AutoDev-governed operations from native platform capabilities that cannot be disabled or observed. Do not claim native host-wide enforcement from a plugin or prompt. Required unenforceable capabilities block the affected AutoDev role/operation, not grant a permissive fallback.

Prevent duplicate hook registration/emission when several surfaces share a harness.

Measure available model calls/tokens, latency, errors, tools, skills, hooks, commands, delegation and lifecycle with source-backed client surface and session attribution; do not infer invisible native activity, capture private conversations unnecessarily or double-count an operation observed at several boundaries. Preserve unrelated preferences, credentials, conversations and extensions; report configuration conflicts instead of overwriting them. Reuse the existing Console resources and Control API for enrollment/readiness, capability coverage, effective grants, drift, diagnostics and optional grant narrowing. No second dashboard, gateway, telemetry store or provider-specific configuration authority.
- **Staged convergence and evidence.** Inventory supported client/harness/version combinations; qualify native support per capability (skills, rules, hooks, commands/prompts, agents, MCP, approvals, telemetry); consolidate generation and migrate managed registrations to the shared gateway; bind externally initiated sessions; configure native observation; enable XACPX/commands only after isolation gates; reconcile and exercise actual clients. Track supported/observed, configured-not-verified, unsupported, unavailable and skipped states separately. A capability gap is not successful parity, and unavailable or unsupported features must not induce custom text tool protocols or unsafe fallbacks. Test both managed and standalone launches, two workspaces and roles, native profile precedence, conflicts, actual hook events, gateway discovery/calls, denial and revocation, XACPX lineage, command lifecycle and source-backed telemetry. Record implementation evidence in the migration tracker.

### Role-oriented execution and provider routing

The orchestrator selects a **named task role and capability contract**, not a provider/model. The router chooses an eligible provider and execution transport using explicit operator priorities and observed state. The role mapping must be declared and validated, not guessed:

| Agent identity                                                                                  | Routing tier and policy                                                               |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Root orchestrator                                                                               | `Orchestrator`: its own model priority and session affinity.                          |
| Named `smart` role when deliberately assigned smart-tier execution                              | `Smart`: distinct from the `smart` agent name itself.                                 |
| `worker`, `explorer`, `validator`, `docs-researcher`, `browser-tester` and other named children | `Subagent` unless their execution contract explicitly selects another supported tier. |

`Orchestrator` and `Subagent` are **provider roles**, not aliases for the named-agent catalogue: `Orchestrator` governs the root agent and `Subagent` governs every tier a subagent runs in. An unmapped or conflicting role/tier must fail validation; a concrete, explicitly selected provider/model request is not silently reinterpreted as a named role.

```text
Task → named role + capabilities → validated routing tier
 → explicit selection / session affinity → eligibility / health / request-outcome cooldowns
 → configured per-tier priority and deterministic candidate ordering
 → supported executor (native ACP via `acpx` or browser-backed `opencli` with native role-bound MCP access)
 → outcome + attempts + child sessions + evidence
    ├── Runtime / Control API → Console (live control)
    └── OpenTelemetry → OpenLIT OTLP → ClickHouse → Usage (history)
```

**Selection order**

| Order                 | Required behavior                                                                                                                                                                                                                                                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Explicit intent    | Honor an explicit provider/model/effort selection or return a typed unsupported/unavailable error; never silently substitute another model.                                                                                                                                                                                                  |
| 2. Session continuity | Pin the provider, model and role when an ACP session is created. Resume only on that same backend; bounded waits may outlast recoverable cooldowns. If the pinned backend cannot serve, report the blocker. Any authorized transfer starts a distinct linked session with reconciled effects, never a mid-session hop.                       |
| 3. Eligibility        | Filter by role, authentication, configured enablement, model routeability and sandbox/permission requirements. Tool support is **not** an eligibility input: every provider carries the full tool surface (see [Tool parity across providers](#tool-parity-across-providers)). Unsupported content is a refusal, **not** a provider failure. |
| 4. Live availability  | Apply provider/model health, request-outcome cooldowns, session/concurrency capacity and known reset times attached to those outcomes. The separate quota-axi report is display data, not a routing input. Treat unavailable evidence as unknown, not healthy.                                                                               |
| 5. Priority/fallback  | Apply operator per-tier priority and fallback groups; use a declared stable tie-breaker when priorities are equal. Never globally reorder providers instead of their per-tier preferences.                                                                                                                                                   |
| 6. Retry or reroute   | Use the cooldown last-resort rules when allocating a new session or before admission. Reconcile unknown side effects before retrying; no retry or fallback switches an existing pinned session to a different provider.                                                                                                                      |

**CLI categories**

| Backend type                          | Examples                                     | Contract                                                                                                                                                                                                        |
| ------------------------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Complete autonomous coding-agent CLIs | `codex`, `claude`, `agy`, `copilot`, `mcode` | Own their agent/tool loop and context/auto-compaction; integrate via ACP with native tools, skills, prompts, and ungranted MCPs disabled so RuleSync owns configuration. Quota collection comes from quota-axi. |
| Browser-backed model CLI              | `opencli`                                    | Serves authorized agent roles, including orchestrator, through native site MCP integration, plus browser-backed endpoints; preserves site queues, idempotency and an accepted-turn ledger.                                                       |

**Browser-backed provider isolation.** A provider that automates a signed-in web application owns a dedicated visible Chromium process and private profile; it never drives the operator’s everyday browser or a shared browser extension/daemon. CDP is bound to loopback and each concurrent command receives its own browser target. The profile contains site cookies, stays under AutoDev’s private runtime directory outside the repository, and is never copied, synced, logged, or committed. Browser installation is pinned by the Runtime dependency and reconciled by the typed installer; site sign-in remains an explicit operator action.

Provider authentication, subscription allowances, reset windows and model discovery are backend-specific; do not assume that all CLIs share one quota/authentication model or automatically offer an API-compatible wire protocol.

**Failure vs. outcome:** Provider failure classes include authentication, invalid model/configuration, transient upstream error, bridge probe failure, throttling, reported quota exhaustion, session limit and unsupported request. Execution outcomes are `success`, `failure`, `cancelled`, `partial` and `unknown`. A transport timeout after work might have begun is **unknown completion** until verified, not proof of provider failure or a safe-to-replay request.

**Delegation contract:** Each child must have a parent/child identity, recorded spawn and completion/failure events, live state, tool/result association, resource/permission budget and observable Codex/Console status. A different transport/UI event format is acceptable only if these invariants and multi-turn continuation survive verified contract tests. Children are owned by the single XACPX delegation interface; provider-private spawn paths are not permitted.

### Mandatory shared MCP gateway

**Target: all AutoDev-managed MCP access goes through one provider-agnostic Supergateway service.** All enrolled desktop applications, IDE agents, standalone/native CLIs (Codex, Claude, Antigravity, Copilot, mcode and all other supported providers), ACP clients, opencli-backed execution, and authenticated ChatGPT agent sessions use the same mandatory gateway infrastructure and canonical role contracts. The gateway is a managed Runtime dependency, not a ChatGPT-only feature. The OpenAI Secure MCP Tunnel is an optional authenticated external ingress; local clients never require it, and external ingress never imposes a separate read-only capability model.

- **No direct-provider MCP connections or fallback.** Providers and bridges connect to gateway endpoints using native Streamable HTTP; any necessary client-side protocol adaptation uses the gateway too. Only the gateway starts/manages local MCP backends over stdio or connects to remote MCP backends. Migrate and remove direct provider stdio launch entries and direct remote backend URLs; no compatibility, performance or isolation exceptions. A missing required gateway capability or unavailable endpoint fails closed with a typed actionable error; fix the integration rather than bypass it. Native non-MCP provider surfaces remain subject to the existing tool-parity contract.
- **One declaration and projection pipeline.** `.rulesync/mcp.jsonc` remains the canonical backend declaration source (rendered directly via `jsonc-parser` without provider-specific MCP exclusions or a temporary Codex TOML projection), and `agents/roles/*.toml` -> `config/execution-contract.json` + `.rulesync/permissions.jsonc` remain the canonical role and permission authorities, projecting full role capabilities (`readOnly`, `shell`, `hooks`, `mcp`, `mcpTools`, `mcpApprovalMode`, `mcpEnvVars`, `skills`, `skillsPolicy`, `reasoning`) and failing closed on unknown or empty roles. Legacy provider-specific delegation/injection fields (`spawnTools`, `roleMcpInjection`, `roleScopedMcp`, `allowProviderHop`) and Codex-only plugin MCP entries (`codex_app`) do not belong in the canonical provider-agnostic role contract. ACP provider profiles (`runtime/src/acp/provider-profiles.ts`) pass native ACP `mcpServers` on `session/new`, publish truthful per-provider CLI isolation gaps rather than asserting uniform CLI-level isolation, and enforce role, shell, native-file-surface, and read-only boundaries at AutoDev's ACP permission and gateway boundaries. Reuse canonical commands, arguments, remote URLs and secret references; never duplicate a server registry, launch configuration, tool inventory or permission authority. Discover tools and schemas through native MCP discovery with truthful upstream tool annotations (never forged read-only hints); explicit tool grants are role-bounded authorization, not a second inventory.
- **Native gateway capabilities first.** Use the pinned Supergateway dependency's individual and combined Streamable HTTP endpoints, backend transports, discovery, namespacing, routing and session/process lifecycle. Preserve individual MCP identities and tool namespaces for local providers and expose the role-contracted combined endpoint for ChatGPT without provider-specific backend exclusions. Support all canonical local and remote/authenticated MCP backends — including `filesystem`, `lsp`, `cocoindex-code`, `codegraphcontext`, `xacpx`, `playwright`, `playtest`, `github`, and documentation servers — wherever the assigned role authorizes them. Resolve capability gaps through maintained upstream public interfaces; do not implement a second aggregator or transport framework.
- **One service lifecycle, separate access scopes.** The canonical installer reconciles, verifies and supervises the gateway independently of optional tunnel provisioning. Disabling or losing the tunnel must not disable local MCP access. Bind locally to loopback, authenticate each ingress, and expose only the authenticated role-bound endpoint through the tunnel. Localhost reachability alone does not grant access to privileged endpoints or gateway configuration. Reuse existing service reconciliation and recovery.
- **Server-side authorization and confinement.** Bind authenticated callers/sessions to their assigned canonical role, effective execution grants, and resolved workspace using trusted structured Runtime context. Enforce exact role-contracted tool/capability grants, read-only vs. workspace-writable confinement, path/network/process confinement, child ownership, concurrency limits, and credential isolation uniformly at the gateway/backend boundary; provider-side configuration is defense in depth, not sufficient authorization. Reject forged role/workspace/session metadata and never impose blanket ChatGPT-only read-only limits. Operators may optionally narrow grants within a role's canonical contract, never widen beyond it. Reuse existing workspace resolution, execution contract, tool filter and OS confinement rather than duplicating policy. Reuse secret management and inject credentials only into the backend or ingress that needs them; never expose secret values to providers, tool output, logs or telemetry.
- **Session and workspace isolation.** Use native stateful Streamable HTTP session lifecycle and appropriate backend process isolation. Bind each session to its authorized workspace, role, and coordinator ownership scope; isolate mutable backend state, indexes, browser state and credentials as required. Concurrent providers, sessions, and workspaces must not inherit one another's grants, children, or state. Workspace switching, role changes, revocation, disconnect, restart, timeout and cancellation must not broaden permissions or replay mutations. A shared gateway does not require sharing backend subprocesses across unrelated sessions.
- **One operator surface and observability.** The Console MCPs resource owns gateway health, discovery, effective role access, enrolled-client role/workspace bindings, read-only effective grants, and supported MCP lifecycle enable/disable controls through the existing authenticated Control API and revision-aware reconciliation. Reuse OpenLIT/OpenTelemetry MCP observations; correlate provider/client surface/role/workspace/session and tool outcome without logging arguments, results or secrets or duplicating spans/metrics.

**Acceptance:** All supported providers (including ChatGPT, Codex, Claude, Antigravity, Copilot, and mcode) exercise authorized MCP calls through the gateway with equivalent role-contracted capabilities, preserved tool identity, truthful annotations, arguments, results, approvals and telemetry. Verify canonical generation without provider-direct launch/remote entries; independent gateway/tunnel lifecycle; real local and remote backends; authorized workspace mutations and `xacpx` delegation for writable/orchestrator roles; denied mutations and delegation for read-only/leaf roles; required/optional failure behavior without bypass; repeated and concurrent sessions; separate roles/workspaces; denied direct access, forged grants, role escalation, cross-session operations, protected files/credentials and unauthorized tools; cancellation, revocation, restart/reconnect and reconciliation; and end-to-end tests exercising the actual ChatGPT gateway ingress. Remove superseded direct-launch and external-only read-only paths during migration. The target is unmet until the provider matrix and isolation gates are observed, not merely configured.

### Resilience mechanics and provider cooldown policy

**Cockatiel owns generic retry, backoff, timeout, circuit-breaker, bulkhead and fallback mechanics wherever its policies preserve the documented attempt, deadline, cancellation, scope and concurrency contracts.** Runtime owns failure classification, request-outcome cooldown scope, persistence and routing policy; quota-axi owns quota collection and the report's provider identities and semantics. The Router's persisted cooldown authority, promptly cancellable capacity queue and ordered provider-selection fallback remain domain policy where a generic Cockatiel policy would duplicate or alter those contracts.

| Kind        | Eligibility and scope                                                                                                                                                 | Last resort                                                                                                                                | Persistence / recovery                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `transient` | Recoverable failure or limit only inferred from prose; bounded escalating backoff on the affected route.                                                              | Eligible only when healthy alternatives are exhausted.                                                                                     | Ephemeral across restart; clears on expiry or scoped successful observation.                                                     |
| `hard`      | A structured provider response reports `quota_exhausted`/`session_limit`; preserve the affected provider/model route and any reset deadline carried by that response. | **Ineligible while a known reset time is in the future**; if the provider supplied no reset, bounded last-resort probing may be permitted. | Durable across restart with source, route scope, deadline and recovery metadata; expire/revalidate by the response's reset time. |
| `probe`     | Failed bridge health check, not an account/model quota event; short bounded escalating suppression.                                                                   | Eligible after regular candidates are exhausted.                                                                                           | Ephemeral; recheck bridge health independently without cooling unrelated routes.                                                 |
| `config`    | Invalid model disables **only that model**; authentication affects the credential/account/profile scope, not unrelated accounts.                                      | Ineligible pending correction or explicit successful recheck.                                                                              | Ephemeral suppression; persistent configuration errors remain visible until corrected, without unbounded retries.                |

- Only structured request-response evidence creates hard cooldowns; lexical guesses remain transient. A successful attempt clears only its own route. Antigravity's `antigravity-gemini`, `antigravity-argon` and `antigravity-claude-gpt` routes remain separate routing/model-family boundaries, not quota identities: quota-axi reports its own `agy` identity, and its report never sets or clears those route cooldowns.
- A request failure cools only the provider or model route identified by that response; a single throttled model must not render unrelated routes unhealthy. Quota-axi availability is a separate, scoped Console presentation and does not define Runtime provider health.
- Scope each cooldown to its affected provider or model route, publish kind, failure class, source, response reset time and last-resort eligibility, and restore durable hard deadlines after restart without resetting their clocks. Do not infer account or quota-pool cooldowns from the separate quota report.
- Cancellation or client disconnect never creates a provider cooldown. Request-content refusal is not a provider outage. A known configuration error returns a non-retryable, actionable result. Never multiply retries through nested wrappers or reroute a turn with unknown side effects without reconciliation.
- **Dependency-first parity rule:** Where Cockatiel's public APIs satisfy the same bounded attempts, deadline, cancellation, scope and concurrency behavior, delete the superseded AutoDev-owned generic resilience mechanism. If a provider-specific behavior cannot be expressed, retain only a documented, tested policy adapter—not a second general-purpose retry framework.
- Test the mapping with injected clocks, response-supplied reset times, independent provider/model routes, concurrent requests, cancellation, restart, recovery, last-resort selection and indeterminate mutating turns. Resilience library breaker state is never the authority for quota semantics or per-tier priority.

### Agent execution transport contract: ACP, MCP, and OpenCLI

**ACP** controls native coding agent CLIs (`claude`, `antigravity`, `copilot`, `mcode`, `codex`); **MCP** exposes tools through Supergateway, with `xacpx` as the exclusive subagent management MCP for all providers; **`opencli`** controls browser-backed agent sessions, including ChatGPT and Gemini, and serves browser-backed endpoints. Execution transport does not determine role authorization.

**ACP boundary:** A maintained ACP client (`@agentclientprotocol/sdk` / `xacpx`) replaces per-provider `/v1/responses` translation bridges, custom continuation state, and custom compaction logic. Each ACP provider launches with native tools, built-in skills, native prompts, and ungranted MCPs disabled so AutoDev's RuleSync projections and role-scoped MCPs are the sole execution surface, while each provider manages its own session history and native auto-compaction. AutoDev retains routing, session-to-provider pinning, request-outcome cooldowns, observability, and authorization.

| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| [`acpx/runtime`](https://github.com/openclaw/acpx) / ACP                    | All interactive coding agents (`claude`, `antigravity`, `copilot`, `mcode`, `codex`) | Reuse session/process/cancellation/permission transport; AutoDev retains routing, request-outcome cooldowns, observability, and authorization. |
| [ACP TypeScript SDK](https://github.com/agentclientprotocol/typescript-sdk) | Typed ACP client transport and session lifecycle                                     | Use the public SDK (`@agentclientprotocol/sdk`) instead of custom provider HTTP translation bridges.                                           |
| `@jackwener/opencli`                                                        | Browser-backed agent sessions (ChatGPT, Gemini), `opencli-browser` / health & models server | Browser-backed role execution through native site MCP access; any role whose contract the transport can enforce, including the orchestrator; no general `/v1/responses` translation bridge. |

**Transport selection:** Native CLI roles execute over ACP (`POST /v1/acp/sessions` and `/v1/acp/sessions/:sessionId/*`); browser-backed providers execute through `opencli`. The orchestrator and other named roles are eligible on either transport when their complete canonical role contract can be enforced. Eligibility is decided only by the execution contract: `providers[].delegation` states whether a provider may drive orchestrator delegation and `providers[].mcpIngress` states how its transport reaches role-scoped MCP surfaces (`gateway`, `local`, `site-native`, `none`). No code path may special-case a provider name for role eligibility. The existing bounded `github-worker` workflow remains supported; it is not a permanent ceiling on OpenCLI capabilities. Custom `/v1/responses` translation bridges are retired.

**OpenCLI orchestration parity:** `opencli-chatgpt` and `opencli-gemini` support the orchestrator role through the same native `xacpx` MCP exposed by Supergateway, not native spawning or text-encoded tool calls. Each browser conversation is bound to an authenticated, Runtime-authorized role, workspace and coordinator identity; the exact MCP/tool/skill/prompt contract, session pinning, child ownership, concurrency, cancellation and telemetry are enforced. The binding is the site's own native MCP integration: ChatGPT exposes installed apps in its composer menu, `opencli chatgpt ask --app <app>` selects the role's app before the prompt is sent, and ChatGPT stores that app reference with the turn. A shared account-level plugin is not by itself proof of session isolation, so the shared gateway publishes one role-scoped surface per published role — its own tool allowlist, its own coordinator and its own read-only confinement — and the secure tunnel publishes one channel per role. Missing native integration or isolation is a typed parity defect, not a permanent role restriction: an unsupported assignment is rejected with a specific actionable diagnostic rather than claiming capability or silently routing through an unsafe fallback.

**Site reachability is a separate axis from transport.** `opencli-chatgpt` reaches the shared gateway through the connected AutoDev app. `opencli-gemini` cannot: Gemini's native MCP connectivity requires a publicly reachable remote MCP server registered in the Connected Console, and AutoDev's gateway is loopback-only with no Google private-tunnel client. That is an upstream reachability gap recorded as `mcpIngress: "site-native"` for the site-native role surface; it must not be worked around by publishing the private gateway, and it is not a role restriction.

### Latency, local delegation and OpenCLI

Optimize **successful end-to-end task completion at equal quality and safety**, not isolated model speed. Attribute queue time, CLI startup, browser submission/polling, generation, local tool execution, retries and recovery.

- **Session/turn ledger:** Persist each OpenCLI site, session/conversation ID, logical request/turn ID, accepted/submitted/completed status and response correlation. Serialize each browser site's composer; deduplicate retries. If a turn was accepted but the response was lost, reconcile the ledger/browser state or resume before considering replay. Do not silently submit twice.
- **Context:** Reuse authenticated sessions and retrieve only relevant skills and scoped memory once per task/context change. Respect provenance, retention, permission and context-window budgets.
- **Deterministic local plan contract:** Strong-model plans contain ordered/bounded operations, allowlisted tool/arguments, explicit permission/resource budget, expected observations, checkpoints, validation/stop conditions and retry/escalation triggers. Execute safe approved steps locally, validate results, and replan remotely on unexpected effects or consequential uncertainty.
- **Local-model option:** Add small function-calling inference only when deterministic handling is insufficient and a predefined benchmark shows lower completion latency **without lower correctness/safety**.
- **Ownership:** An optimization never weakens the owning harness's tool authority, approvals, serialized browser state, session continuity or OTel provenance.

### Execution observability and experience

All transports normalize **the same** logical task, physical attempts, pinned sessions, child sessions and partial/unknown outcomes. Historical provider-hop observations remain readable, not an active execution feature. Detailed telemetry is defined in §10; memory is postponed as described in §9.

| Fact                                               | Single authoritative producer / consumer                                                                                                                                                                                                                                                        |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Task, route, provider, attempt, retries and errors | Runtime routing/executor → live Control API and correlated OTel spans.                                                                                                                                                                                                                          |
| Child lifecycle and tool results                   | Owning agent/executor → Runtime, parent-child IDs, Console and status; ACP events map to the same outcome contract.                                                                                                                                                                             |

Durable Mem0 integration is postponed; the custom PostgreSQL/pgvector memory engine has been removed. Do not reintroduce a memory store or UI as an incidental transport migration. |

Live configuration and health remain Control API facts, not telemetry commands. Keep sensitive prompts, raw paths, secrets, user content and tool arguments out of metric dimensions.

## 6. RuleSync and configuration authority

Use the pinned RuleSync tool as the source of truth for every agent-facing configuration surface it can represent **losslessly**.

RuleSync-owned concerns include, as supported:

- rules/instructions;
- commands and prompt assets;
- portable agent/role declarations and provider-specific projections where needed for ACP execution (not a second provider-native delegation mechanism);
- Agent Skills and supporting files;
- MCP declarations and target-specific overrides;
- hooks;
- permissions/tool capability policy.

RuleSync source files are authoritative. Desktop, IDE and CLI configuration and native plugin outputs are generated projections of the same sources, including Codex/Claude/Copilot/Antigravity/MiniMax wherever supported. Share a native harness projection when several interfaces actually consume it; do not assume identical host capability or overwrite unrelated operator state. For MCPs, generate backend declarations for Supergateway and provider-facing gateway endpoint references from the same effective catalogue; no provider projection may independently launch or directly contact an AutoDev-managed MCP backend.

OpenLIT Prompt/Agent/MCP/Skill views are read models, not configuration databases.

For repository-owned Skills, Hooks, Prompts/Commands and Permissions, edit the canonical files through normal repository development/review, then use the existing pinned RuleSync generation, installation and verification workflow. Console/Control API consume read-only source and effective projections. Do not expose source writes, role/skill assignment mutations or permission overrides through these resources or another route.

For the remaining explicitly mutable RuleSync-backed MCP configuration, the existing named Control API operation validates, writes canonical input, generates/applies and observes runtime. Runtime-owned operational mutations keep their typed owners and reconciliation. This exception does not authorize editing permission grants, skills, hooks or prompts through MCP or Agent pages.

Preserve target-specific overrides. Do not invent another AutoDev configuration schema merely to force unsupported semantics into RuleSync.

AutoDev-specific runtime state that RuleSync does not model—provider credentials, live health, pricing/catalog facts, routing/cooldown/concurrency state, scheduler/runtime policy—remains owned by typed AutoDev configuration/runtime APIs.

When RuleSync cannot round-trip an Agent `enabled` field losslessly, Runtime owns named-role enablement and its revision generations; no generated role TOML or provider projection may invent unsupported fields. Runtime enforces disabled named-role aliases at admission. Target-specific flags such as Antigravity `mainAgent`/`subagent` do not substitute for portable role enablement. The dedicated orchestrator alias must not collide with any named role alias; Runtime configuration validation rejects collisions rather than letting two Agent controls govern one request identity. Only a request carrying a configured named AutoDev alias has that Agent identity; concrete provider/model requests remain governed by Providers and Models.

Conceptually:

```text
Desired agent configuration  ← RuleSync sources
Generated provider configs   ← RuleSync projections
Actual runtime state         ← Runtime / Control API
Historical behavior          ← OpenTelemetry / OpenLIT
```

**Subagent/permissions projection parity:** Provider-native agent configuration generation is not proof of AutoDev cross-provider role parity and does not authorize native delegation. All orchestrators delegate through the `xacpx` MCP. For each CLI, validate the native configuration fields and their supported project/global scope (which can differ among Codex, Claude, Copilot and Antigravity), approval semantics and effective tool/role behavior. A feature being supported by upstream Rulesync does not mean AutoDev has enabled it or that its outputs are losslessly equivalent.

### User-level capabilities and workspace-local resolution

AutoDev discovers user-level agents, skills and MCPs plus trusted workspace-local rules, hooks, tools and configuration. It builds **one invocation-scoped effective catalogue** without changing global definitions or treating discovery as authorization.

| Stage                     | Contract                                                                                                                                                                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Discovery              | Read global and selected workspace roots separately; record source, revision, resource kind and trusted root. Repository-declared MCP launch commands are **untrusted candidates**, not executable permissions.                                 |
| 2. Identity/conflict      | Use stable qualified identities such as `user/skill/review` and `workspace/<id>/skill/review`. Same-named entries remain distinct; unqualified lookup succeeds only when exactly one eligible candidate exists.                                 |
| 3. Role/task eligibility  | A typed manifest distinguishes **required** and **optional** capabilities, allowed tools, provider compatibility and approval categories. Local additions may become eligible through approved role policy without pre-existing global entries. |
| 4. Execution grants       | Enforce operator hard denies/limits, workspace restrictions, role/tool allowlists, session limits and required approvals at the **actual Runtime/CLI/OS boundary**. Discovered but ungranted entries cannot execute.                            |
| 5. Projection/observation | Produce provider-specific invocation-scoped configuration and expose source, eligibility, grants, actual availability, omissions/denials and revisions through Control API/Console.                                                             |

**Deterministic collision rules**

| Case                                                            | Required decision                                                                                                                                                                                                                 |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Same unqualified name in global and workspace scopes            | Never silently shadow: require qualified reference or operator-approved binding to exactly one qualified resource. Until resolved, the unqualified name is **ambiguous/unavailable**.                                             |
| Two declarations with identical qualified identity in one scope | Reject as invalid before executing; no filesystem/load-order precedence.                                                                                                                                                          |
| Explicit per-workspace binding                                  | Save the selected qualified ID and expected source revision in AutoDev-owned workspace-scoped configuration. Other workspaces/global defaults remain unchanged; source revision changes invalidate the binding until revalidated. |
| Explicit deny, untrusted launch or incompatible policy          | Denial wins; no project file, prompt, ACP approval transport or provider fallback can turn it into an implicit grant.                                                                                                             |

- **Capability versus permission:** Installation/discovery is not eligibility or authorization. A local capability missing from global defaults can be added by a **reviewed workspace-scoped role assignment** if operator policy permits it. Execution also requires caller/session approval and enforcement; a hard deny cannot be approved away.
- **Approval:** An eligible but approval-gated MCP executable/tool requires the configured AutoDev reviewer before launch/use. Revising the policy itself is a separate authorized configuration mutation; arbitrary workspace files cannot rewrite the reviewer or tool grants.
- **Provider isolation:** Normalize native project formats without treating them as higher authority. For CLIs supporting only global MCP registration, use an invocation-isolated profile and tool filter. Reject a backend missing required capabilities or restrictions; report optional omissions explicitly.
- **Workspace switching:** A new invocation loses the previous workspace's local tools, prompts, secrets and memory scope while retaining global defaults. Revision changes must not silently widen grants in active sessions.
- **Acceptance:** Test colliding global/local names, duplicate identities, approved bindings and stale revisions, denied/untrusted MCP launch, optional versus required tools, simultaneous providers and workspace switching. Compare each provider's actual tool exposure and approval behavior with the effective manifest.

### Policy ownership and enforcement

| Concern                                   | Authoritative contract                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Desired permissions and role capabilities | Rulesync defines portable policy and agent configuration wherever losslessly supported; otherwise explicit AutoDev/provider-native configuration remains the named authority. Discovery is never a permission grant.                                                                                                                                                                               |
| Runtime and native enforcement            | AutoDev enforces role admission, effective grants and MCP tool filters; the native agent/OS/container sandbox enforces file, network and process restrictions. Approvals and prompt text alone do not enforce restrictions.                                                                                                                                                                        |
| ACP / external harness approvals          | `acpx` transports ACP permission requests/decisions; it is **not** the policy authority or sandbox. Pi may enforce the approved policy **inside its own agent runtime** when chosen as an executor but cannot override AutoDev. The same AutoDev reviewer handles approvals, and native enforcement must be verified. Children gain no additional authority; unsupported restrictions fail closed. |
| Effective state                           | Source → deterministic projection → applied runtime → observed result (`converged`, `pending`, `error`). Every enabled executor must demonstrably enforce equivalent permissions/skills/agent roles; target-specific deviations must be explicit and approved.                                                                                                                                     |

## 7. OpenLIT fork boundary

OpenLIT is retained as infrastructure and a source of useful components/patterns. Do not preserve generic OpenLIT product features merely because they already exist. The retained OpenLIT server renders URL-filtered telemetry pages at request time; its image build must not statically prerender routes that consume search state.

### Keep/adapt

Retain or adapt:

- OpenTelemetry/OTLP ingestion;
- ClickHouse telemetry storage and generic query plumbing;
- trace, metric, and log querying/exploration;
- GenAI usage/cost foundations;
- time-range, chart, widget, trace, table, filter, status, form, dialog, and detail primitives that fit the AutoDev design system;
- telemetry query/source abstractions;
- Mem0 connector/domain capabilities are postponed for a future iteration; the custom PostgreSQL/pgvector memory engine and any temporary OpenLIT Memory bridge have been removed;
- Evaluation definitions/results/history capabilities that remain independent of removed product concepts;

- useful Agent presentation patterns, but not OpenLIT discovery/instrumentation semantics;
- desired/live/convergence interaction patterns, reimplemented through AutoDev Runtime/Control API.

OpenLIT auto-pricing may persist a computed cost to a trace, but it must batch span updates into bounded, partition-pruned ClickHouse mutations. Never issue one `ALTER TABLE ... UPDATE` for each span: MergeTree mutations rewrite immutable parts, so per-span updates amplify writes and can saturate the local telemetry database. The maintained patch series owns this adaptation; OpenLIT remains the sole telemetry store and cost values keep their existing source/estimate semantics.

The custom PostgreSQL/pgvector memory subsystem has been removed and Mem0 integration is postponed; neither OpenLIT nor `console/` currently exposes a `/memory` product route.

- **GPU dashboard/monitoring product surface.**
- **OpenLIT agent discovery/instrumentation and Controller daemon:** discovered/instrumented statuses, service discovery, instrumentation toggles, eBPF/SDK injection, OpAMP/Controller product flows.
- **Otter/chat:** chat routes, chat history/settings/usage, floating/sidebar chat entry points, Otter-only resource-management tools/APIs/stores, AI-analysis affordances that require Otter, and its provider/model configuration. If AutoDev later adds natural-language console administration, it must use AutoDev agents plus typed Control API operations rather than resurrecting Otter.

The Console's Prompts surface owns prompts and reads them from the canonical source through the Control API. A writable copy of a prompt surface whose tables a projection sync overwrites is not an authority: the operator's write would not be what the system reads. The removed product's tables are dropped from existing installs rather than left orphaned — storage with no owner is still a place something can read rows from.

The Console's Agents surface owns agents and reads them from the canonical execution contract through the Control API. The removed product's tables are dropped from existing installs rather than left orphaned.

## 8. Component reuse and reference projects

Reuse should reduce custom UI code without importing foreign product structure.

Prefer in this order:

1. adapt an existing OpenLIT component that cleanly fits the AutoDev design system;

3. reproduce a proven interaction pattern in AutoDev components;
4. write new bespoke UI only when the domain requires it.

Before copying third-party code, verify the source revision, license/attribution requirements, dependency cost, and compatibility. ### Agents

Agents are configuration-defined, not discovered/instrumented applications.

Useful states include:

```text
Configured
Valid / Invalid
Ready / Unavailable
Converged / Pending / Error
Last activity
```

Agent detail may combine canonical role/prompt, assigned capabilities, a read-only effective provider/model summary linking to Providers, generated projections, actual readiness/health, and scoped activity/usage.

The Agent enablement control is revision-bound through `PATCH /control/agents/{role}` and is shown on both the Agent row and its detail view. Runtime rejects a stale expected revision, persists the policy before confirming the mutation, and enforces disabled aliases before provider selection or subagent admission. Missing Runtime aliases render as unavailable and nonmutable; they are never represented as disabled or silently mapped to a provider assignment. This control has no effect on a concrete provider/model request, which does not carry a named Agent alias. Attribution is a separate fact: a concrete request on the root thread of an identified session is that session's root agent and is attributed to the `orchestrator` role in activity, usage, router events and spans, whichever provider serves it; one on a child thread is a subagent whose role stays unattributed; one with no thread identity is direct. The provider never decides the role.

The session concurrency limit is a mutable resource too, and it is the one the Router enforces rather than the canonical source: `PATCH /control/runtime/concurrency` writes a stored override over the config file's limit, and a reset asks for the config file's limit rather than for "no change". The write publishes the shared reconciliation view, so the desired generation is the limit that was asked for and the observed generation is the limit the Router is enforcing -- and because both are limits, `unlimited` is a generation of its own rather than the absence of one. A write the Runtime accepted but has not observed is reported as unobserved, not as the new limit.

The concurrency limit's config file is read as an observation too, for the same reason. A config file that is there and cannot be read declares no known limit, and that is not the same claim as a config file that was read and declares none: the first says the cap the operator set is not being enforced, the second says no cap was ever configured. The Runtime therefore publishes the file's limit only when it read the file -- absent means nobody read it, and `null` means the file declares no limit -- and the Console says the config file was not read instead of naming its contents, whether the limit in force comes from the file or from a stored override beside it. A reset to a config file nobody could read has no generation to ask for, and the write says so rather than claiming the limit in force is the one that was configured. "Could not read" covers every way the declaration is unknowable: an I/O failure, a TOML syntax error anywhere in the file (parsed in full by `smol-toml`), an `agents` entry that is not a table, or a limit that is not a non-negative safe integer. Only an absent file, or a valid file without the key, declares no limit. Parser diagnostics never echo TOML source lines or values; third-party parser errors are reduced to a generic category.

The limit's own source is published too, and it is a different fact from the file's location. An operator reading a cap of eight has to know whether it is a cap they set in the config file, a limit a stored override put in place, or a cap nothing declared -- and the Runtime knows which of those it is enforcing. So the Runtime publishes the source of the limit in force as a closed vocabulary of three words, and the Console renders that word instead of inferring it from the numbers beside it. Which config file the router read travels under its own name, because the file's location is a fact about the read and the limit's source is a fact about the limit; one word cannot carry both, and when it tried, the word the Console read was never the word the Runtime published -- so every limit an operator had configured was labelled as a default. A source the Console has no word for is not observed rather than a default.

The agent catalogue is the execution contract's roles, and the accessor that reads the contract falls back to an empty contract when the read fails. An empty contract and a contract nobody read look the same to a caller that only sees the roles, and they are not the same claim: the first says the contract declares no role, the second says nobody read it. The Runtime publishes whether the contract was read, the count over the catalogue is a number only when it was, and the list says which read did not happen instead of rendering an empty catalogue as a configured one. The skills catalogue draws its role assignments from the same contract and answers the same way.

The role's prompt is read as an observation, for the same reason. A role whose prompt file is there and cannot be read has no known prompt, and the detail says so -- it does not publish an empty prompt, which would claim the prompt was read and held nothing, and it does not publish a digest of nothing as the prompt's canonical revision, which is an identity that names no prompt. A path that is there and is not a regular file cannot be read as a prompt, and it is not one. A role with no prompt file at all has an empty prompt, and that was observed.

### Providers

Providers is the one place an operator decides which model providers may serve the fixed agent roles, in what priority order, with which model, and under which concurrency limits. Its **Providers** tab is a single compact configuration table with exactly **five primary columns**:

| Column            | Contract                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Provider**      | Provider ID linked to its detail view, displayed without truncation, with the CLI's version beneath the name (`claude 2.1.280`) and the provider's external **Usage ↗** and **Docs ↗** links beneath that.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Status**        | Overall provider usability, see below. Rendered as a status pill: `Ready` in the healthy style, a blocking state in the blocking style.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Active Agents** | The current Runtime-reported live count for this provider. A missing live source is **Not observed**; a missing provider in an observed count map is `0`. Hovering a count shows the roles it is made of, one per line, largest first (`1 Orchestrator`, `1 Worker`), from Runtime's `byProviderRole` split (`byModelRole` for a model's count).                                                                                                                                                                                                                                                                                  |
| **Roles**         | The two fixed roles — **Orchestrator, Subagent** — each with a white-outline icon plus three controls: a priority dropdown containing exactly `P1`, `P2`, `P3`, `Disabled`, a model dropdown populated from that provider's currently available models (its first option, `Auto`, leaves the tier's configured model in force), and a reasoning effort dropdown offering model-specific supported levels (derived from catalog `supported_reasoning_levels`, with `Default` fallback, an indicator badge when fixed by Antigravity model slug, or a placeholder when not supported). The column header carries a help affordance. |
| **Agent Limits**  | Provider-wide concurrent-agent limits for **Per session** and **Across sessions**, each a compact `− n +` stepper, plus an **Unlimited** control and a provider-level **Disabled** control. The column header carries a help affordance.                                                                                                                                                                                                                                                                                                                                                                                          |

The page header names the surface and states its purpose — _Configure which providers to use, which models to use for each role, and agent spawn limits._ — and offers **Reset to defaults**. The Console configures providers already registered by Runtime; adding another provider requires a code change that supplies its Runtime adapter, not a Console control.

**Status is a single verdict, not a summary of parts.** It reads `Ready` only when the provider is healthy, all required configuration and credentials are present, and no fresh, known quota scope is authoritatively exhausted. Otherwise it names the specific blocking state rather than degrading to a generic warning — for example `Missing CODEX_ROUTE`, `Missing credential`, `Disabled`, `Sign-in required` (a web-chat provider whose site is signed out in the browser it is driven through: an action for the operator, shown in the blocking style with the provider's own message on hover), the live health state (`Cooling down`, `Unavailable`), or a fresh, known quota-axi scope (`Quota exhausted`, with the scope named in the badge title). A provider whose parts are individually fine but which cannot currently serve a request must not read `Ready`. **Every** verdict carries a re-check control inside the badge, not only a failing one: a refresh symbol that posts to `POST /api/providers/{provider}/check`, which asks Runtime (`POST /control/providers/{provider}/check`) to re-run the provider's live probe -- its credential and bridge health endpoint, or Codex's own auth -- and its model listing. The control is on every verdict because routing re-probes a provider only when a request is about to use it, so a verdict nobody has re-checked is only as current as the moment it was observed and can be stale in either direction; an operator who wants to know whether a provider is serving now should not have to wait for it to fail first, and a provider with recovered health reads `Ready` only after somebody looked again and no fresh, known quota scope is exhausted. While the check runs the symbol is a spinning circle: the form owner marks the badge's form `aria-busy`, and the icons follow it, so the control holds no client state. The redirected page carries the new verdict. A verdict that is a configuration fact -- `Disabled`, `Missing CODEX_ROUTE`, a missing credential -- does not change because of a check, because a probe cannot conjure configuration into existence; the check still records the provider's live evidence, and Runtime answers a provider that has no route with the fact that there is nothing to probe rather than failing the request. A passing check clears a probe-failure cooldown and is recorded as health evidence (`lastCheck`) that outranks an older request failure; a failing probe cools the provider down as routing does. A cooldown recorded from a provider request response -- a quota or rate limit -- is not something a probe can disprove, so the Runtime-health verdict stays `Cooling down` until it resets. The separate quota-axi report never sets or clears Runtime health; when no higher-priority configuration, sign-in, or live-health blocker applies, a fresh, known scope whose `runway.status` is `exhausted_now` appears as a yellow, explicitly scoped `Quota exhausted` presentation only. The verdict tracks the provider's _live_ availability rather than the order of its last two events: a failure that describes a condition which passes -- a rate limit, a throttle, a busy upstream, a timeout, a 5xx -- speaks for the provider only while Runtime is still cooling it down for it, and stops speaking for it once that cooldown has passed, because Runtime routes to the provider again at that point. A failure that is not a condition but a fact about the provider (`authentication`) stays live until the operator fixes it. Without that, one failed request left a provider reading `Unavailable` for as long as it went unused -- hours for a provider that is P3 in every tier -- while the Runtime was already routing to it again.

**Roles are the two fixed roles, not a capability set.** Orchestrator and Subagent are the canonical roles; a provider's participation in each is expressed by its priority rather than by a separate enablement flag. Selecting `Disabled` for a role disables and **dims that role's model and reasoning effort selectors** — the controls stay present so the previously chosen model and effort are visible and recoverable, but they can no longer be changed into an active selection. Fixed Antigravity model slugs (`-low`, `-medium`, `-high`) display an inline fixed indicator reflecting the model's depth.

**The Subagent model is one hierarchical select.** The Subagent row's model control wears the same select chrome as the Orchestrator's, and shows the Subagent model plus how many agent roles have one of their own (`sonnet +1`). Opened, it lists `All subagents` (the Subagent role's model) and then every agent role whose tier the provider serves (`explorer`, `worker`, `smart`, ...), each with the model it runs; each opens to that provider's models, led by `Auto`. A role's own model wins over the Subagent model, which wins over the tier's configured model, and a role's `Auto` names the model it falls back to. Choosing an option applies it at once. The menu opens as a row of its own under the role's controls (`HierarchicalSelect`, a reusable form component), so the scrolling role strip never clips it. Closed menus do not render their option buttons until opened, keeping the provider matrix from eagerly adding hundreds of hidden choices to the page DOM. They are written through `PATCH /control/providers/<provider>/agents/<role>` with `{ "model": <id> | null }`, persisted as `agentModels` in the router state, cleared by the providers reset, and shown read-only on the Agents page's provider chips.

**Model availability is provider-owned, observed state.** Runtime discovers each provider's available model IDs through its authoritative local CLI or upstream listing API, outside request, routing, and page-load hot paths. Discovery is bounded and refreshed independently of routing; it never rewrites operator-selected tier/role assignments or pricing. The typed Runtime projection distinguishes an observed list, a stale last-known list, and an unavailable source; absence of a new response is never rendered as an empty catalog or current success. A listing that fails or comes back empty after the provider has listed models keeps the last non-empty list as stale -- a provider does not lose every model between two reads, and a browser-driven site (opencli) returns an empty list whenever its picker fails to render -- so an observed-empty list is reported only for a provider that has never listed a model. A failed or empty listing is retried at 30 s, doubling to the 15-minute refresh interval, rather than waiting for the next refresh. A provider-discovered ID is not automatically routeable: Runtime validates it against that provider's route matcher and adapter capabilities. Discovered-but-unsupported IDs remain visible with an explicit reason and cannot be selected until the route supports them; they are not silently dropped or described as unavailable at the provider. Model IDs are preserved verbatim, including case, because casing is part of the provider wire identifier. The Console reads this projection and owns no second model catalog. Static metadata may enrich a discovered ID, but cannot claim that a model is currently available. New role assignments and model-enablement writes require a provider's current observed, routeable list. While discovery is stale or unavailable, keep the existing role assignment visible and preserve it unchanged; do not treat a last-known ID as a new choice or clear it implicitly.

**Dropdown styling is neutral, with one deliberate exception.** Role identity is carried by a distinct, consistent **white-outline icon** and label for each role. The single exception is the `Disabled` priority itself, which is highlighted so that "this role will not be used" is visible at a glance rather than having to be read. P1, P2 and P3 share one neutral style.

**Agent Limits are provider-wide**, not per-role, and carry a provider-level **Disabled control beside the Unlimited control**. That control globally disables use of the provider regardless of individual role settings, **while preserving its configured priorities, models and limits** so re-enabling later restores the same configuration rather than requiring it to be re-entered.

**Agent Limits controls:** The **Unlimited** button clears the operator-set ceiling on both concurrency axes. Steppers restore a finite limit at the minimum allowed value when leaving Unlimited. A **Disable / Enable** button changes provider availability while preserving the provider's configured models, role priorities and limits. Each action uses the established server-confirmed mutation flow.
**Reset to defaults** first opens a confirmation modal; the always-visible checkbox is not the confirmation mechanism. The modal states that confirming clears Runtime-owned provider overrides (per-role assignments, provider/model enablement, and provider agent limits) and restores canonical routing defaults without editing `config/model-routing.json`. It also states that named-Agent admission, provider discovery snapshots, live health/cooldown evidence, and Runtime concurrency limits are preserved. The operator must explicitly choose the modal's reset action before the Console sends the confirmation-bound, operator-only `POST /control/providers/reset`; opening or cancelling the modal never mutates state. The operation is audited and reports the same server-confirmed reconciliation vocabulary as other Control API mutations.

The Providers tab has five columns: **Provider, Status, Active Agents, Roles, Agent Limits**. **Status** summarizes provider usability and configuration; a fresh quota-axi scope whose authoritative `runway.status` is `exhausted_now` also appears as a yellow **Quota exhausted** status, with its scope and limiting window named in the badge title. This is a scoped Console presentation, not Runtime health evidence or a routing/cooldown input; stale reports, unknown scopes, bound conflicts, and raw percentages do not change the status. **Active Agents** reports Runtime's current count; **Roles** exposes per-role priority/model assignment. Each matching provider row shows compact display-only quota-axi percentage-used bars (blue when available, yellow over 95% used, red at 100% used) with refresh times beneath its provider identity, not in a separate quota report section. A provider the quota report knows about but whose reading it could not draw as bars says so in the same cell — `Quota rate limited` with the moment to retry it, `Quota sign-in required`, `Quota unavailable`, `Quota read failed`, `Quota stale` — so a provider whose quota read was refused is visibly different from a provider quota-axi has no source for. That state is the report's own, it never becomes a quota value, and it never becomes a provider verdict: the row's Status still comes from health, credentials and the exhaustion scopes alone. Matching `agy` windows are shown on their corresponding Antigravity route rows (`antigravity-gemini`, `antigravity-argon`, `antigravity-claude-gpt`), with unprefixed `agy` windows shown on all three. The **Models** tab lists models across providers, each with its current active count and enable/disable control under the contextual-controls rule.

Useful states include:

```text
Status:   Ready / Disabled / Missing CODEX_ROUTE / Missing credential / Sign-in required / Cooling down / Quota exhausted / Unavailable
Priority: P1 / P2 / P3 / Disabled
Limits:   Per session, Across sessions, Unlimited
```

**The CLI's version belongs to the provider, and it is small text.** Every provider AutoDev routes to is served by a CLI, and the release it is on is the first thing an operator needs when a provider behaves differently than it used to. Runtime reads the version from the binary it would actually spawn — `claude --version`, `codex --version`, `agy --version`, `mcode --version`, `copilot --version`, and opencli's own entry point — so the number beside a provider is the number in use. The read is bounded, happens off the request path, and is refreshed in the background; the Console never spawns a CLI itself. The table shows it under the provider's name, and the provider's own page shows it in its header beside the live agent count. A CLI that is not on the machine reads **Not installed**; one that is there and would not answer reads **Not read**; a Runtime that has not read any version says **Not observed**. None of them reads as a version of zero, and the provider, requested-model and Skill filters do not narrow the version, because it is a property of the machine rather than of a request.

Provider detail may combine its enable/disable controls, configured routes, its models with their own toggles, per-tier models, the tier priority/fallback groups the provider appears in, the CLI's version, live readiness/cooldown/failure evidence, small scoped Usage summaries that link to Usage, and the provider's external Usage and Documentation links. Those two links are focused contextual links: each provider's URLs live once in its `providers.<id>.links` routing-config entry, reach the Console through the providers Control API record, open in a new tab, and are omitted when unconfigured; the Console keeps no URL list of its own. Mutations go through typed Control API provider/routing operations. Credentials are shown only as configured/missing status, never as values, and Providers must not become a second credential or model-catalog authority.

### Tools

The Tools resource is the composite effective catalogue, not one source's list. It is built from two independent reads -- the RuleSync tool declarations and the execution contract's role projection, which says which roles reach which tools -- and the two are observed separately. Every entry carries its own source and source authority, so the RuleSync declaration and the contract's projection of the same capability are one entry with one authority rather than two rows, and no capability is presented twice.

The catalogue publishes what was observed about each read, and the page's claims follow from those facts rather than from the shape of the result. The execution contract's accessor returns an empty contract when the contract cannot be read, so the roles it contributes look exactly like a contract that declares no roles; the Runtime publishes whether the contract was read, and the Console states the catalogue's counts and every entry's role exposure as not observed when it was not. The entries that arrived are still shown -- they are what was observed -- but the page states no total it cannot know, and it does not claim that a tool has no roles when nobody read the source that assigns them.

The page has one count authority: the entries it renders. The sidebar badge, the summary row and the narrowed filter summary all count those same entries, and they are numbers only when the catalogue was fully observed. A catalogue whose role projection was never read holds the entries the RuleSync source alone declared, and the number of those is exactly right for what arrived and incomplete for what the unread source would have contributed. Availability is a separate observation from exposure: a tool that is configured but was not observed is rendered with the vocabulary of the thing that was observed, not as a configured one.

The catalogue's coverage has one owner, and it is the layer that composes the two reads. The data layer publishes what it read -- the RuleSync source's state and the entries it produced -- and no coverage of its own, because a coverage derived from one read answers a narrower question than the composite's coverage answers, and the two then disagree: the projection called an invalid source "unavailable" while the composite called it "unknown". The Runtime, which merges the RuleSync projection with the contract's role projection, publishes the coverage of the composite.

### Prompts

The prompts catalogue is every canonical prompt and command in the repository, and it is two independent reads: the RuleSync command catalogue and the canonical role-prompt directory at `agents/prompts/roles/`. The two are observed separately, and the catalogue publishes both facts. The role prompts are null when their directory could not be listed, because a list that stands in for a failed read claims the repository holds no role prompt; an empty list beside a directory that was read and holds none is a measured zero and stays a list.

A count over the catalogue is a number only when both reads were observed. The "Canonical Prompts" card states the catalogue's own size, the "RuleSync Commands" and "Agent Role Prompts" cards state their own source's size, and each card is a measurement only of the read behind it. The page says which read did not happen, and the entries that arrived are still shown: they are what was observed.

The prompt's detail tells the same story about one prompt. A prompt has two canonical sources -- the RuleSync command catalogue and the role-prompt directory -- and each read answers one of three things: the prompt was read, the prompt is not there, or the source could not be read. The third is not the second. A command file that is present and cannot be parsed is a source that could not be read, and the detail says so, with the reason, rather than answering that the prompt does not exist. A prompt nobody wrote is an unknown prompt; a prompt nobody could read is a source that could not be read. A committed revision of a prompt is read the same way: a revision nobody committed is an unknown revision, and a commands catalogue that was read and found broken is a source that could not be read.

### Skills/capabilities

Keep stages distinct:

```text
Configured/Enabled
      ↓
Eligible
      ↓
Selected / Exposed
      ↓
Injected
      ↓
Used
```

Canonical skill definitions and descriptive metadata come from `.rulesync/skills`; role eligibility is joined from the execution contract by skill name. One read-only Skills table shows the complete canonical skill catalogue, each skill's observed role assignments, and its state, including skills with no assigned roles. Use labels, icons or text rather than interactive assignment checkboxes. The page explicitly surfaces role references with no canonical source. A missing or invalid RuleSync catalog is not a successful empty catalog. Only an owning producer may assert observed exposure/use/error. Do not infer later stages from configuration or eligibility.

The unresolved role assignments are a join between the execution contract's assignments and the catalogue's names, so they are observed only when the catalogue was read. A catalogue that was missing, invalid or never read leaves the join unperformed, and the set is then not observed rather than empty: an empty set there would claim every assignment resolves, which is a claim the catalogue did not make. A catalogue that was read and resolves every assignment is a measured empty set and stays one.

Each skill links to a URL-addressable read-only detail with the shared Rendered/Source selector, canonical `SKILL.md` body/frontmatter, source provenance and role assignments. Edit the tracked source and reconcile via the standard repository/installer workflow; there is no Console editor or enable/disable mutation.

The skill's own routes follow the same rule as every other detail. A catalogue that was read and found broken does not name any skill, so the skill is not an unknown skill: the route answers with the catalogue's own reason, and the status says the source could not be read. An absent catalogue holds no skill, so the skill is genuinely not there.

### Memory

### Evaluations

Retain useful evaluation definitions/results/history and trace linkage without Rule Engine or OpenGround prerequisites. Evaluations target explicit AutoDev resources/telemetry. A result is passed/failed only when its source supplies an explicit verdict; missing verdicts, missing metrics, or unknown verdict values remain **Not observed**, never inferred from an arbitrary score threshold. An unavailable or malformed evaluation source must not be represented as a successful empty result set. A malformed row invalidates that query sample rather than silently dropping the row and biasing displayed totals or pass-rate denominators.

### Playtesting

**Playtesting** is a top-level **Observe** resource at `/playtesting`. It uses the shared AutoDev dark React/Next.js Console, navigation, filters, tables, cards, drawers, charts and server-authoritative controls. The [Playtesting target state](playtesting-target-state.md) defines adapters, player/analyst agents, episodes, scoring, evidence and UI reuse; this document defines shared Console layout, navigation, ownership, data semantics and security.

**Visual-first operating principle:** The game can be explored by an approved Smart/Jev-directed browser agent without checked-in game-specific JSON. Accelerated/headless sessions and scripted regression remain distinct modes with their own evidence limits. The operator interaction, privacy, readiness, live transport and measured provenance rules are defined **once** below; [Playtesting Target State](playtesting-target-state.md#3-architecture-and-ownership) owns the agent/driver decision loop and [Measurement Contract](playtesting-measurement-contract.md) owns scientific interpretation.

**Data ownership:** Playtesting owns workspace-scoped batches, episodes, decision timelines, gameplay outcomes, immutable replay/media evidence, critic reviews, findings, experiments, matched comparisons and consented human-study aggregates. `core/src/playtesting/` owns typed contracts, `runtime/src/playtesting/` owns approved execution/evidence access: `run-control.ts` is the single `PlaytestRunControl` owner for run lifecycle, cancellation, evidence and analyst dispatch; `mcp.ts` is the MCP gateway for tool registration, role/session authorization and schemas, delegating to that owner. `data/src/playtesting/` owns a dedicated indexed ClickHouse schema and parameterized queries through the [existing Data client](../data/src/clickhouse/clickhouse-client.ts). Runtime owns bounded content-addressed replay/media artifacts; detailed traces and frames stay out of ClickHouse and OTLP. This V1 implementation is validated with synthetic repository fixtures; live backend migration, retention operations and real approved-game evidence remain separate acceptance gates. **Evaluations** owns source-authored formal evaluation results and verdicts (including explicitly projected batch assertions), and **Usage/OpenLIT** owns inference traces/costs. Store **evidence status, investigation workflow, external GitHub issue state, batch execution, game outcome, and critic calibration** independently; each is grounded in its owning source.

#### Canonical Playtesting UI/UX contract — launch, browse, watch, inspect

**Ownership and information architecture.** The _only_ primary Playtesting navigation is **Overview | Sessions | Findings | Compare**. Route `/playtesting` opens **Overview**, not a separate Run page. **Play** (play icon, accessible name **Start playtest**) is the one prominent persistent primary action in the Playtesting page header on every subsection; the dialog is an action, **not** a fifth tab. **Sessions** includes active, historical and interrupted episodes plus a separately labeled **Pending runs** subsection where no episode exists. **Watch** and archived Replay are states of the same full-page `/playtesting/sessions/[id]` view, where `id` is always the episode ID. Batch overview is **exactly** `/playtesting/runs/[batchId]` and never impersonates a single episode. **Findings** and **Compare** remain source-backed analysis destinations. Optional Human validation is disclosed within Compare. Navigation, filter/search/sort, list/grid layout and step/time selection use shareable URLs and Back/refresh restoration; centralize route helpers, not page-specific hard-coded strings. Overview prioritizes launch, recent sessions and confirmed outcomes; no duplicate launch form or parallel dashboard.

**Play dialog and readiness.** Clicking **Play** opens one accessible **New playtest** dialog with approved **workspace / game target** selector, **execution mode** (visual, adapter-accelerated, scripted regression), policy/persona when available, relevant scenario/seed (optional for visual), and bounded **episodes/steps/time/cost** with an obvious safe one-session default. Hide advanced batch tuning behind disclosure; show capabilities before submit rather than letting users choose an impossible combination. Mode readiness comes from the **same server-authoritative permission/capability response** that will validate launch: (1) workspace/target enabled and approved with stable identity; (2) supported browser/driver/input modality installed and authorized (for visual); (3) approved engine binding/visibility contract (for accelerated); (4) chosen policy/model backend available, configured, licensed/compatible and within quota; (5) sandbox/browser resource and allowed origin ready; (6) current role's launch permission and sufficient tool/inference/media budgets. Each failure has a typed reason and next permitted action; loading/unknown is neither Ready nor an empty list. Mark options `Ready`, `Unavailable` or `Check required` with accessible explanatory text and disable only the unavailable combination. Default **Autonomous visual** only when **visual driver and the selected policy actually pass preflight**; if Jev is unavailable, offer **Autonomous visual + `smart-direct` policy** (separately labeled **Smart-only exploration**, subject to bounded per-decision Smart calls) if permitted, or **deterministic baseline** with a clear disclaimer — never silently substitute random/first-legal while labeling a run Jev. Revalidate immediately before launch and fail explicitly on a readiness/permission race. **Gated targets:** each approved visual target declares `entryRequirements` (`none`, `consent-or-age-screen`, `local-account`, `credentialed`) and a control-timing class (`turn-based`, `pausable`, `continuous — unsupported yet`); Play shows these as readiness facts. P1/P2 run only `entryRequirements=none`; any other requirement shows **Requires operator-assisted setup — not yet supported** instead of implying zero-config coverage, and a gate detected during play (login wall, age/consent prompt, account creation) ends focus as `blocked` with reason `auth-or-setup-required`. The agent never clicks an age attestation, accepts terms, creates accounts, enters credentials or makes purchases. Operator-assisted setup is a separately gated capability ([P2.5](plan/playtesting-target-state-implementation.md#p25--operator-assisted-setup-for-gated-browser-games)): an authorized operator performs setup manually inside the same isolated transient browser while agent input, model calls and all capture/recording are paused (password fields and setup frames never reach models, telemetry or artifacts), then explicitly hands back; Runtime records a content-free `manual-setup` segment with actor and timestamps and a new visibility/provenance boundary before agent play resumes, and the transient profile and its session cookies are destroyed at episode end. That takeover surface is distinct from Watch, which stays read-only.

**Areas of focus (optional natural-language intent).** Include an optional multiline **Areas of focus** input, plus nonmandatory suggestions such as **Test the main menu**, **Play endless mode only**, **Explore onboarding**, **Stress unusual strategies**, **General exploration**. Empty means broad exploratory play; store the raw intent/preset and a versioned **interpretation** separately. Director interprets a goal into `objective`, `in-scope` actions/areas, optional `do-not-enter` constraints, and observable `stop criteria` **subject to approved tool/target boundaries**. Examples: "test main menu" explores its interactions and records menu coverage; "endless only" attempts to discover and enter that mode and refrains from knowingly playing alternatives; "general" samples multiple reachable mechanics within budget. No JSON action script or assumed feature existence. If absent, gated by a login/tutorial, ambiguous or unreachable, log attempted discovery/obstacle; return focus status **achieved / partially achieved / blocked / not attempted / unknown**, with evidence and explicit limits. Never infer the user approved account creation, payment, third-party navigation or credential entry. **Precedence is strict:** security/approved target and human cancellation > user `do-not-enter` exclusions > user focus objective > any optional **in-scope minimum exploration** > maximum time/step/cost budget as hard upper bounds. The optional minimum is a versioned, operator/plan-selected count of **meaningful in-scope decision opportunities** (default `0` for focused sessions), never a reason to violate an exclusion. If a focus is achieved early, stop and report unused budget unless the operator explicitly requested further **in-scope** exploration; if blocked, report why and stop rather than exploring prohibited alternatives. Budget exhaustion is a terminal limit even if the goal remains incomplete. Clarify ambiguous input conservatively through bounded exploration and an evidence-backed partial result; don't silently broaden permission.

**Launch identity/idempotency.** Submit through existing authenticated run owner with a unique **client-generated requestId/idempotency key**, stable across retries and refresh until reconciliation; server atomically binds `(workspace, actor, requestId)` to a single immutable launch-intent hash and **batchId**, rejecting changed payload for the same key. Pending button disabled locally is additional UX, not the safety mechanism. If the POST times out or the connection drops, query the owner by idempotency key and show the accepted receipt or a retriable unknown outcome; **never automatically submit a new key**. An accepted batch contains one or more frozen assignments `assignmentId`. Only an assignment that actually starts gameplay obtains `episodeId/sessionId`. Until that exists, display a real **Pending run** receipt with batch/assignment and queue/start/error status and no pretend session ID or game counters. A batch with several episodes has its own aggregated overview (counts labeled **batch**), and each episode gets an individual **Watch** link when created. Parent/child links remain valid if an assignment fails before episode creation; no ghost sessions or duplicated attempts.

**Session browser and shared List/Grid.** **Sessions** shows running and past episodes from exactly one **workspace-scoped**, indexed server query; provide a clear **List / Grid** icon segmented toggle, accessible names/pressed state, responsive layouts, persistent `layout=list|grid` URL selection, and stable search/filter by session ID, optional commit/deployment, text focus, status, mode, policy/persona, date, result and debrief availability. A separate labeled **Pending runs** group uses batch/assignment receipts rather than manufacturing episode rows. In both layouts, use identical underlying row identities and facts; no frame/log preloading. Sort with a **stable snapshot cursor** or pinned sort epoch rather than resorting beneath users as live status changes; provide **Updates available** plus a user-triggered refresh to reclassify active→history and preserve keyboard focus, selection, scroll and pagination. Define server tie-break `(startedAt or queuedAt, episodeId)` for stable order within a status cohort, pinned epoch and cursor; never infer total from page length. Show useful empty/permission/error/loading states, local timestamps with an unambiguous full absolute time in detail/tooltips, and accessible mobile fallbacks without hiding full metadata. **Cross-workspace discovery without widening scope:** the Playtesting header's workspace switcher lists only workspaces the actor may read, each with its **active session and pending run counts**, obtained by fanning out the existing workspace-scoped active-runs read per authorized workspace (bounded concurrency, per-workspace `unavailable` state, no global unscoped episode query, no widened permissions); inaccessible workspaces are neither listed nor counted. Switching keeps workspace-independent URL state (`view`, `layout`, `status`, `mode`, `sort`) and drops workspace-specific state (`buildSha`, `targetId`, `cursor`). Test two authorized workspaces with active runs plus an inaccessible third that never appears or leaks a count.

**Per-session card/row minimum — triage first.** Every row/card leads with a one-line **Player outcome / key observation** copied from a persisted source, never generated on the list page: the debrief `focusOutcome` plus its first `highlights[]`/`frictions[]` item, else the deterministic objective outcome summary, else an explicit **No summary yet**; the line carries its source label (`player testimony`, `objective`, `analyst`). Beside it show separate counts of **unverified issue candidates** (debrief), **analyst hypotheses** and **verified findings**, each with its own availability (`not applicable`, `pending`, `0`), and requested-focus status when measured. Then show copyable **episode/session ID** (full on detail), status, workspace/game, execution mode, start time and gameplay **elapsed/duration**. **Grid** cards prioritize status, outcome line, issue counts and the next action (Watch, Request review, Open finding); raw **game inputs**, **driver/tool invocations**, **logical Jev decisions** and Smart counts are **List** columns and detail facts, not card content. Secondary fields: focus, persona/model, last frame preview **only from actual captured evidence**. Test missing-debrief, `not-applicable` baseline and no-issue sessions. For **adapter-accelerated approved clean checkout** or a visual deployment with independently verified build attestation, display short **verified commit SHA** with full exact commit link only when checkout/producer provenance supports that claim; distinguish (`sourceKind=repo-checkout | deployed-build | URL-only | native-install`), repository/branch, commit, clean/dirty/untracked status, runtime artifact/asset fingerprint or deployment ID, approved target URL/origin, and confidence/source of the build mapping. For P1 visual sessions the operator supplies an **already-running approved URL**, which AutoDev only browses; it does not run build/serve shell commands. A local dirty checkout is not executed by the adapter and never appears as clean SHA-only; an externally served local dev build might be dirty but its specific rendered bytes require deployment attestation, not a guess from HEAD. If rendered deployment cannot be mapped to commit, show **Build unknown** even if HEAD is known. A pure URL-only game without a known repository shows **Commit not applicable**; an expected but missing repository SHA shows **Commit unknown**. Never guess a hash from the URL. Show source provenance in detail separately from what was merely inferred.

**Counters and clocks — one versioned server producer.** Core/Runtime supplies source-versioned `sessionTelemetry`, not JSX-derived calculations: `inputAttempts`, `inputValidated`, `inputDispatched`, `inputAcknowledged`, `inputRejected` (reason and acknowledgement unknown distinct), `driverToolCalls` by type (`observe`, `screenshot`, `act`, `wait`, `other`; optional `video` only when P4+ capture is approved), `jevLogicalRequests`, `jevProviderAttempts` (retries/ensembles), `smartDirectorRequests`, `smartDirectDecisions` (P1 `smart-direct` choices), `baselineDecisions` (random/first-legal/scripted), `affordanceGroundingRequests` (AffordanceProposer vision/Smart grounding calls, counted separately from director planning and Jev choices), `analystRequests`, and `captureCount`. Counts refer to **one episode** and specify an exact event/identity dedupe rule: one requested semantic input can dispatch multiple physical mouse/keyboard tool operations (count logical interaction once and physical tools separately); failed/stale tool actions cannot count as accepted gameplay, and retries must not inflate logical Jev requests. A policy may use multiple Jev members in one ensemble (physical model calls distinct). Include telemetry producer/version, ``covered/partial/absent`and explicit nullable values. **Not measured** differs from measured zero. Raw attempts/costs and missingness remain available on detail; a summary may display`Inputs N (M rejected)`and`Jev decisions N`. Separate **queue wait** (request accepted to actual start), **execution wall duration** (actual session start to terminal; frozen on finish), **game-native actionable/animation durations** and **simulation ticks/inference time**. Running elapsed derives from confirmed start with server time offset; not-started is not 0m.

**Live Watch and permalinked evidence.** Clicking an active episode opens the full-page session detail **Watch** state, identifying episode, parent batch and persona. The leading panel shows latest **actual captured game screenshot** (P1); an optional bounded true stream is **P4+ only after separately approved media transport**, original capture timestamp, modality, source and frame-age; a still screenshot never masquerades as continuously streaming video. If no media or headless, provide **No frame available: [reason]** and bounded state/event timeline rather than a fabricated image. Show actual latest known activity, stated focus/interpretation, available game phase, validated action receipts, player prediction and visible consequence, Jev/Smart source and fallback, errors and recovery, counted metrics, live runtime, server heartbeat and independently measured media freshness. Every ordered event has a stable `eventId` / monotonic `sequence`, `episodeId`, step, optional decision/media locator, authoritative server timestamp and clock type. Step/media references are immutable and signed/scoped; click a decision to seek its time-aligned before/after screenshot/frame (or P4+ approved clip) and permalink `?step=N&event=ID`; support keyboard next/previous, scrub/jump and **Copy link**. Selecting historical evidence switches to **Viewing history** without pausing the actual game; **Follow live** explicitly returns to latest and does not forcibly steal keyboard focus on new events. Expired media shows an honest placeholder and artifact reason, while timeline/text/citations remain navigable.

**P1 media boundary and later video/audio contract.** **P1 captures real time-stamped still PNG/JPEG/WebP frames only**; it does not offer continuous streaming, replay clips, live video or audio. P1 can infer observed UI transitions from before/after screenshots but must decline claims that require animation smoothness, actual sound or continuous pacing. At **P4+** a separate approved capture/transport capability may add bounded **MP4 (H.264/AAC) or WebM (VP9/Opus)** clips and optionally audio with explicit container/codec allowlist, maximum bytes and duration/segment count per episode set from measured budgets, poster frame, capture source and timestamps. Implement an authenticated `/episodes/{episodeId}/media/{artifactId}` route with MIME-specific validation, `Content-Type`/`nosniff`, HTTP `Range`/`206` support only for validated bounded clip objects, `Accept-Ranges`/`Content-Range`, workspace-scoped short-lived handles and the **same redaction-before-persistence** policy as screenshots. Streaming transports (WebRTC/HLS/MSE) are **not in P1 or P4's initial clip milestone**; add one only by separately documented security/latency and retention acceptance. Missing clips/audio produce `unsupported-modality`, never a fake stream. Do not put raw media in OTLP or ClickHouse rows.

**Live transport/recovery contract.** Reuse the singleton authorized Runtime run owner (incremental subscription if available, otherwise bounded backoff polling). Event list responses include `nextCursor`, `latestSequence`, status/heartbeat timestamps, media locator/freshness and explicit `gap` markers if retention skips events; clients dedupe by event ID, apply monotonically, and fetch backlog before resuming Follow live. An event already acknowledged never reappears as a new interaction; reconnect/refresh does not start gameplay. Distinguish `queued`, `starting`, `running`, `finishing`, `completed`, `failed`, `cancelled`, `interrupted` from `temporarily-disconnected` / `stale` / `source-unavailable` presentation states. The server owns terminal state and status, not the last screenshot. Define heartbeat and frame-stale thresholds **from measured workload-specific latency SLOs**, expose actual last-updated ages, and test a documented max observed lag under a bounded reference DOM+canvas workload; do not invent an unmeasured universal refresh interval. Respect 429/5xx/backoff, cancellation and Runtime restart with typed recovery. Stop polling at terminal; preserve history. An authorized **Cancel** operates on exact batch/assignment/episode scope with confirmation and server receipt; Watch never issues gameplay actions or assumes native pause/resume.

**Security, privacy and artifact lifecycle.** Visual game pages/screenshots/DOM, audio, console logs and model tool responses are **untrusted input**, not instructions. Run in isolated transient browser profile without user cookies/credentials; approved origin allowlist, restricted outbound navigation, least-privilege input and bounded capture volume. Preflight capture permissions and sensitive-surface policy; redact/mask passwords/secrets/private inputs and unsafe window/DOM fields **before** models, telemetry, artifacts and screenshots where possible, and **fail closed / mark capture unavailable** when effective redaction cannot be assured. Never silently share personal data or record unrelated windows. Every frame, clip, input event, debrief and media URL requires authenticated workspace/session-scoped ACLs and no arbitrary external public URLs; use expiring bounded handles, audit accesses, delete/expire under configured retention and consent policy. No browser/client exposure of provider keys, runner secrets, sandbox internals or Control API service token. Verify cross-workspace reads, unauthorized Watch/Cancel, hostile page prompt injection, redacted screenshots and retention expiry. Distinguish media expired, capture forbidden, never captured and corrupted artifact states.

**Player debrief: eligibility, schema and evidence authority.** Authorship follows **which agent actually observed or supervised the experience**, not whether the tactical decision model can write prose. Eligible authors: (a) the P1 `smart-direct` player, which both observed and chose; (b) in a P2 Jev-policy session, the **supervising Smart director context** that held the episode's player-visible observations and decisions, which writes its **own observation report** with `authorRole=supervising-director`, names the underlying Jev `policyId`/model, links the decisions it observed, and never attributes preferences or feelings to the Jev policy ("the Jev policy chose X; I observed Y"); (c) a language-capable policy only if it itself held the observation history. Random, first-legal, non-reflective heuristic or scripted regression sessions **with no supervising player context** use `not-applicable` for first-person testimony, even after normal completion, and keep optional **objective outcome summary** and a **separate analyst report**. A reflective player writes bounded **checkpoint notes during play** so an abrupt process loss can preserve an honest observed prefix. At orderly termination it serializes a versioned `PlayerDebriefV1` envelope (`episodeId`, `authorAgentId`, `authorRole=player|supervising-director`, `policyAndModelVersion`, `generatedAt`, `completeness=complete|partial`, `focusAttempt`, `focusOutcome=achieved|partial|blocked|not-attempted|unknown`, `highlights[]`, `frictions[]`, `issueCandidates[]`, `learned[]`, `untested[]`, `suggestedFollowups[]`, `evidenceRefs[]`, `narrative`). Each issue/highlight item has observation kind (`observed|inferred|subjective-model-impression`), uncertainty, observed symptoms, exact episode/step/frame reference where possible; unsupported assertions are visibly marked. Report status is `pending|complete|partial|not-applicable|unavailable` with a reason for unavailable; preserve immutability and source provenance. On cancel/crash, persisted player-authored checkpoint notes may yield **partial-player-authored** content; a different agent can provide an **analyst reconstruction**, but must never impersonate the stopped player or label it a first-person debrief. No forced positive/negative notes or auto-promoted bugs/fun scores. Session detail shows readable **Attempted/achieved, Liked, Frustrating/confusing, Issues/surprises, Learned, Untested, Next** sections and evidence links, with **Copy/Export debrief** via existing safe export mechanisms (respect ACL/redaction), and clearly separated later analyst critique, deterministic findings and consented human outcome data. A normal reflective completion generates its player debrief without waiting for independent analyst dispatch. Session detail also offers an operator-only **Request independent review** action ([P1.5](plan/playtesting-target-state-implementation.md#p15--first-independent-review-of-visual-sessions)) that dispatches the existing read-only analyst over a discovery evidence packet; its output is labeled **analyst hypotheses**, never scores or verified bugs.

### GitHub

Workflow files (`.github/workflows/*.yml`) remain authoritative for workflow _definitions_ and configured cron triggers. `config/workspaces.json` is the target owner for workspace identity, enablement, and resource scope. Scheduler weights/policy remain in the scheduler's canonical policy. The Console must not fork any of these into a second schedule/configuration authority, and the GitHub page must never expose raw provider credentials, arbitrary workflow IDs, or arbitrary workflow inputs to the browser.

The Console `/github` resource and the Control API `GET /control/github` are an authenticated, read-only path that pairs parsed workflow definitions with the corresponding observed GitHub Actions runtime state:

- YAML definition facts (`name`, `path`, sorted trigger events, sorted cron schedules) come from a typed Data reader (`GithubWorkflowRepository`); `.github/workflows/*.yml` files are parsed using YAML 1.2 `on:` semantics (preserving strings vs booleans). A missing `.github/workflows` directory or any workflow file that fails YAML parse yields an explicit `unavailable`/`invalid` catalog status without synthesizing a workflow count.
- The Control API exposes an authenticated GET-only collection endpoint (`/control/github`, `schema: autodev-control-github-v1`, `readOnly: true`) that requires valid Control API service credentials and actor verification, and strictly rejects non-`GET` methods with HTTP 405 Method Not Allowed.
- Server-side `AUTODEV_GITHUB_REPOSITORY` and optional/required `AUTODEV_GITHUB_TOKEN` are validated against an enabled canonical workspace: `AUTODEV_GITHUB_REPOSITORY` (or standard runner `GITHUB_REPOSITORY`) must reference a recognized workspace entry in `config/workspaces.json` that is explicitly enabled (`enabled: true`); an unrecognized workspace, a disabled workspace, or malformed repository coordinates surface as `invalid`. `AUTODEV_GITHUB_TOKEN` is optional for public repositories because GitHub REST workflow and run GET endpoints are reachable anonymously, though authenticated requests are preferable for stable rate limits. Private repositories still require a least-privilege server-side token with read-only Actions permission (and read-only Metadata). When accessing private repositories without a token, or when requests are forbidden (HTTP 403) or rate-limited (HTTP 403/429), runtime facts surface as `unavailable`; invalid credentials (HTTP 401) surface as `invalid`. `AUTODEV_GITHUB_TOKEN` remains strictly server-side, is never transmitted to the browser, and is redacted (`[REDACTED]`) from error messages.
- Observed Actions API runtime facts — workflow enabled/disabled state, workflow id, html URL, recent run count, last run status/conclusion/timestamp/URL, and a bounded recent run sample — come from a typed Data adapter (`GithubActionsAdapter`) enforcing strict network and parsing invariants:
  - Octokit ownership: use `@octokit/rest` typed Actions operations, authentication, response decoding, and its pagination iterator for GitHub API reads; do not handcraft REST URLs or pagination. Keep AutoDev-specific response limits, timeouts, repository validation, and fail-closed collection/record checks in the Data adapter;
  - Fixed origin: configure Octokit with the fixed `https://api.github.com` base URL and permit only GET requests to that origin, including pagination links (using Octokit's optional server-supplied token authentication, or anonymous access for public repositories); caller-supplied hosts are forbidden;
  - Redirects denied: all HTTP redirects are rejected (`redirect: "error"`);
  - Path safety: repository coordinates are validated before calling Octokit's typed methods; path traversal segments (`.` and `..`) are rejected before any network call;
  - Streamed byte caps & timeouts: responses are streamed and strictly capped at 1MiB (`MAX_RESPONSE_BYTES = 1_048_576`), and request timeouts (`DEFAULT_TIMEOUT_MS = 10_000`) remain actively enforced throughout body consumption;
  - Fail-closed record validation: malformed collection payloads and malformed workflow or run records fail closed (`invalid_payload` / 502) rather than silently dropping or coercing records;
  - HTTP error preservation: oversized, unreadable, or unparseable error response bodies do not erase HTTP auth/rate status codes (HTTP 401 Unauthorized, 403 Forbidden, 429 Too Many Requests, and 404 Not Found remain authoritative);
  - Configured workflows cap: workflow listing is capped at 100 (`per_page=100`), failing with explicit partial status (`partial_result` / 502) if more than 100 workflows exist.
- Bounded latest-run statistics (`totalRuns`, `successfulRuns`, `failedRuns`, `inProgressRuns`, `cancelledRuns`, `successRate`) are computed over a bounded recent-run sample (default 30 runs, max bounded limit 100):
  - `successRate` denominator is strictly all sampled completed runs (in-progress, queued, waiting, requested, and pending runs are excluded; non-success conclusions including failure, timed_out, action_required, startup_failure, cancelled, or missing conclusions remain in the denominator);
  - `successRate` is null (never synthesized as zero or 100%) until at least one completed run has been observed in the sample.
- State correctness and distinctions preserved: missing credentials for private repositories, unconfigured repository scopes, forbidden access, rate-limited requests, disabled workspaces, or GitHub API failures surface as explicit `unavailable` or `invalid` runtime states with redacted diagnostic messages; the page never synthesizes idle/healthy or zero counts.
- The bounded recent-run sample is null when the Actions read did not happen, and an empty list only when the read happened and the workflows had no runs. An empty sample beside an unread Actions API would claim the workflows had never run, which is a claim about the repository rather than about the read; a measured empty sample is a measurement and stays a list.
- Dispatch, cancel, rerun, and schedule mutation controls remain **explicitly unimplemented** in both the GitHub resource surface and Control API. The Console must not expose them as browser-side affordances, and `GET /control/github` rejects non-`GET` methods with HTTP 405.
- Acceptance boundary: runtime state and statistics are verified through the pinned Data, Runtime, and Console test suites against injected fetch adapters. An unauthenticated live read of public `SimulatorLife/AutoDev` confirmed the GitHub Actions workflow and run endpoints; production-credential and browser acceptance remain separate open verification steps.

## 10. Usage and telemetry contract

### Logical requests versus physical attempts

A logical routed request and physical provider attempts are distinct:

```text
AutoDev logical routed request
├── provider/model attempt 1
└── provider/model attempt 2 (fallback/retry)
```

A failed OpenAI attempt followed by a successful Anthropic fallback is one logical request and two physical attempts.

- Provider reliability, attempt latency, tokens, cache use, and provider cost belong to attempt observations.
- End-to-end duration and final outcome belong to the logical request.
- Do not duplicate attempt token/cost totals on the parent.
- Keep requested-model identity distinct from the actual physical provider/model target.

An explicitly selected session may expose a bounded, paginated trace evidence view. Its fixed span summary is an allowlist of source-confirmed operational fields (including actual attempt provider and `gen_ai.conversation.id` where present), timestamps/status/duration and selected usage/routing facts; it never returns arbitrary span/resource attributes, prompts, tool payloads, or free-form errors. Conversation identity is high-cardinality trace context only: it may be retained per span for session/thread investigation, never as a metric dimension. Missing provider or conversation identity remains `null` (unknown), not a guessed value. The endpoint bounds each page to at most 200 spans and reports source truncation separately from pagination; a long session alone is not partial evidence.

### Semantic conventions and privacy

- Prefer current official gen_ai.* and MCP conventions.
- The current MCP convention pin is open-telemetry/semantic-conventions-genai@bcc7f9c2856fa7f4feb753f54d4ebba9455cc3dc and must be revalidated when producer semantics change.
- Use standard input/output/cache token attributes where reported.
- Cache-read rate is cached input tokens divided by input tokens only where both exist; missing evidence renders unavailable, not zero.
- Keep IDs, raw paths/URLs, prompts/responses, credentials, raw tool arguments/results, and free-form errors out of metric dimensions.
- Keep dimensions bounded and stable.
- Attach provider/model/role/workspace attribution at the producer that knows it. Do not invent downstream attribution.

### Context compactions

Context-compaction telemetry is a target requirement for Usage and any future per-resource aggregate view.

Emit a bounded source-owned counter such as `autodev.context.compactions`, unit `{compaction}`, only when the producer actually performs or explicitly reports a compaction. Record it at the producer/provider boundary that can establish the event. Do not infer compaction from token counts, context pressure, truncation, long prompts, or request success.

Correlate the event with the logical request and bounded workspace/provider/requested-model/agent dimensions **only when the owning source actually knows those values**. A retry/fallback must not duplicate one compaction event.

Prompt/context contents, request/session IDs, raw paths, and other high-cardinality or sensitive values never become metric dimensions. Optional compacted/retained token counts or duration are valid only when the source reports the actual measurement.

Target Usage may show count/time-series and bounded breakdowns by workspace, provider, requested model, and agent/role where those dimensions are source-confirmed. A per-request compaction rate is valid only when the compaction numerator and logical-request denominator are defined for the **same scope and time range**. Unsupported/unobserved signals remain unavailable, never zero.

The current Console derives its compaction count, time series, and workspace/requested-model/agent-role/provider breakdowns from the source-confirmed `autodev.request_kind=compaction` attribute on successful logical routed-request spans. It does not query the `autodev.context.compactions` metric for these widgets: the pinned OpenLIT generic metric time-series path averages datapoints, which is not a valid counter aggregation. The widgets use OpenLIT's structured trace-query path, share the logical-request time range and applicable workspace/model/agent filters, and show a per-request rate only over that same scope. Provider and Skill filters do not have source-confirmed semantics on this logical-request signal, so compaction panels explicitly report unavailable when either filter is selected; they are not silently ignored and are never attributed to a guessed provider or Skill. The provider breakdown is source-confirmed on the compaction's own span: a compaction is served by exactly one provider, so the router publishes that provider as `autodev.compaction.provider` on the compaction span, and the widget groups by it. The logical-request span still carries no `gen_ai.provider.name`, because a logical route can touch several providers. Live ingestion and browser acceptance of the provider breakdown remain open.

### Provider hops

Historical observations only; new sessions use the pinned ACP lifecycle.

ACP sessions are strictly pinned to their original provider/model and role. **Mid-session provider hopping is retired**, including for the orchestrator. A retry, new-session allocation fallback or explicit linked handoff is not an in-session hop. A pinned session that cannot continue reports a typed blocker; it does not reconstruct another provider's conversation or replay ambiguous mutations.

Historical Usage and diagnostics may display source-confirmed pre-ACP hop events with their original `autodev.hop.from`, `autodev.hop.to`, `autodev.hop.route`, `autodev.hop.reason` and optional failure class. Preserve historic provenance and distinguish an observed zero from unavailable data. Do not synthesize new hop events from provider allocation attempts, child launches or linked handoffs, or recreate hop logic to populate a legacy widget. New attempts and handoffs use their owning Runtime/ACP identities and correlation.

Report queue and site/execution phase timings only when the owning executor reports them. Historical `autodev.provider.queue.duration`, `autodev.provider.site.duration` and `autodev.provider.phase.duration` remain readable with their original units/scope. Usage latency percentiles count only attempts with the relevant measurement; unsupported phase timing is unavailable, not zero.

### Client surface

Every session records the client surface it was started from, so origin-specific behaviour, failures and usage patterns can be compared. Codex names its own client in the `originator` it sends with every model request (the `originator` header, and the product token of its `User-Agent`) and records the same value in each rollout's `session_meta`. `core/src/diagnostics/client-surface.ts` is the single owner of mapping that observed value onto the closed `ClientSurface` set: `codex_desktop` (the Codex app), `codex_cli` (the interactive CLI), `codex_exec`, `codex_vscode` (the VS Code extension) and `other` (an originator that was observed but is not recognised). A session that carried no originator has no surface (`null`, shown as **Not observed**); it is never guessed from the provider, the model or the rollout's `source`.

- The router resolves a request's surface at ingress (`originator` header first, then `User-Agent`) and records it as `autodev.client.surface` on the request spans, as a bounded dimension of the request and usage metrics (`unknown` when not observed), on the persisted router event (`clientSurface`) and on the live session identity (first observed wins; Control API contract v37). The attribute is span-scoped, not a Resource attribute: the router is a shared daemon serving every client.
- Session diagnostics read the surface from each rollout's `session_meta.originator`: every thread carries its own observed value, and the session report, the recent-sessions list and the fleet scan expose the root thread's.
- The Console shows it as **Client** in the live sessions table on Usage, in the session diagnostics header beside the CLI version, and as a column of the recent-sessions table.
- Provider identity and client surface are separate: Claude Code, Antigravity, Copilot, Codex and opencli execution may serve different clients. Preserve the historical Codex originator mapping, and record new client surfaces only from authenticated/source-confirmed ingress metadata. A standalone client outside AutoDev is unobserved until it has a supported reporting integration; do not infer origin from the executing provider. Extend the shared source-backed ClientSurface mapping to verified desktop, IDE, CLI, web and externally initiated sessions using native metadata; preserve historical identifiers. Distinguish client surface, provider/model, harness, session origin and routing observation. Reconcile native exporter, hook, gateway and Runtime observations at their owning boundaries without double-counting; token/model metrics not reported by the host remain Not observed. See [unified client integration](#unified-desktop-ide-cli-and-external-agent-integration).

### Git change metrics

Git change-output telemetry is a target requirement for Usage and for bounded per-resource aggregate views. It answers "what did the work actually produce" next to "what did it cost".

Emit one bounded source-owned observation per commit an AutoDev-managed agent actually creates. The Runtime does not create commits itself, so the observation is recorded where the commit can be established and attributed. Recommended instruments follow the existing `autodev.*` shape and bounded-unit style of `autodev.context.compactions`:

- `autodev.git.commits`, unit `{commit}`
- `autodev.git.files_changed`, unit `{file}`
- `autodev.git.files_added`, unit `{file}`
- `autodev.git.files_deleted`, unit `{file}`
- `autodev.git.lines_added`, unit `{line}`
- `autodev.git.lines_removed`, unit `{line}`

The Runtime's OTLP metric exporter explicitly uses CUMULATIVE temporality for these counters, overriding a process-wide delta preference; changing this requires a new query that proves equivalent window-boundary semantics.

**Attribution comes from the commit, never from the observing Runtime.** An agent commits under its own bounded AutoDev committer identity, and the actor is read back out of the commit. This is required rather than merely preferable: agents and their subagents share one workspace, so commits form a single stream with no per-actor markers, git records a committer but not which model wrote the code, and there is no subagent lifecycle boundary at which a per-agent range could be read. A session-scoped or time-windowed attribution would therefore credit every subagent's commits to the orchestrator's role and model.

The identity is bounded and permanent-safe, because a commit outlives the session and may be pushed: a fixed local domain plus an allowlisted role and provider. It carries no session id, model id, path, URL, or free text. An out-of-vocabulary provider collapses to `other` rather than being written verbatim, and an unknown role yields no identity at all, so that commit remains the operator's rather than becoming agent output attributed to nobody. The identity is supplied as process environment, not repository configuration: nothing is persisted into the workspace, managed workspaces stay read-only, and the operator's own commits are unaffected. The identity must be attached to the process that actually executes Git; setting it on a model-provider proxy or MCP forwarding shim that only relays tool calls does not establish commit authorship.

Every commit carries an `autodev.git.attribution` dimension from a closed set of `commit_identity` and `unattributed`. An actor supplied by the observer rather than read from the commit is dropped from the dimensions and recorded as `unattributed`, so a shared-workspace commit cannot be blended onto a role; a query grouping commits by role, provider, or model must exclude unattributed commits rather than average over them.

Definitions must be exact, because these words are otherwise used loosely:

- a **commit** is counted once for the commit object actually created. An amend, rebase, cherry-pick, or revert is a distinct commit and counts as one; re-reporting an already observed commit does not count again.
- **files changed** is the count of distinct paths whose status in that commit's diff is added, modified, deleted, or renamed. Files added and files deleted are **subsets** of files changed, not additions to it — a displayed total must never sum all three and double-count.
- **lines added** and **lines removed** are the insertions and deletions reported for that commit's diff. A merge commit is measured against its first parent (the mainline integration diff); file-status and line-count totals must describe that same diff. A root commit is measured against the empty tree.

Only report a measurement the source actually observed:

- do not infer commits, files, or lines from tool-call counts, task success, edit counts, session end, or diff-size heuristics;
- do not attribute a change to a provider/model/agent/role the producing source did not know at commit time. Git records that a commit exists; it does not record which model wrote it. Correlation with session, requested model, agent/role, provider, and workspace is valid only where the owning Runtime source actually knows those values, under the same bounded-dimension and allowlist/`other` rules as other `autodev.*` producers;
- merge commits, binary files, and diffs the source cannot summarize are either measured or explicitly excluded with a stated reason. They are never silently folded into a total, and a partial measurement is reported as partial rather than as a complete, smaller number;
- where diff statistics are unavailable, the value is unavailable, never zero. If any commit in the selected range has partial/unknown diff statistics, keep independently measured commit and file counts, report the partial-commit count, and make total lines added/removed unavailable rather than presenting a smaller sum or zero as complete.

Privacy and cardinality are stricter here than for most signals:

- file paths, repository URLs, branch names, and commit metadata never become metric dimensions — aggregate counts only;
- per-file and per-commit detail belongs in traces/events with bounded redacted identifiers, never in metric labels;
- commit SHAs and session/request identifiers stay out of dimensions, consistent with the semantic conventions and privacy rules above.

Deduplication and scope:

- the same commit must not be counted twice when more than one producer can observe it, for example a session producer and a later workspace reconciliation pass;
- a rate or ratio — commits per logical request, lines per commit, files per session — is valid only when numerator and denominator are defined for the **same scope and time range**. Otherwise it renders unavailable.

Target Usage may show counts, time series, and bounded breakdowns by workspace, provider, requested model, and agent/role where those dimensions are source-confirmed, plus a per-session view where session identity is source-confirmed. This telemetry observes change output; it does not become a second Git, workspace, or GitHub authority, and it grants the Console no Git mutation path.

**The observer watches a directory, and the directory has to be a path.** The commit observer reads the repository on disk, so it needs the workspace's directory. The session's remembered turn metadata is a JSON document, not a path, and handing that over makes every observation fail its directory check: no commit is measured, no counter is emitted, and the Git panels stay empty while the agents commit. The session's workspace is therefore remembered as a path as well as as metadata, and the observer resolves the repository that contains it, so a workspace that is a subdirectory of the checkout is still measured from the repository root -- `diff.relative` would otherwise report only the paths under the current directory and undercount every commit that touched anything above it.

### Usage dashboard

Keep one **Usage** product surface; do not add a redundant Analytics page.

Use the retained OpenLIT time-range control. Core owns the canonical `USAGE_VARIABLE_IDS` tuple shared by Console and Data; the fixed OpenLIT endpoint mirrors this bounded list at its service boundary and accepts no arbitrary variable IDs. Typed single/multi-select + All variables should support URL persistence where applicable:

- workspace;
- provider;
- requested model;
- agent/role;
- skill only where safely present.

Filter-option discovery must be time-bounded and scoped to the AutoDev service and attribute scope that own each value: router span attributes for provider/model/skill and workspace/role, plus source-confirmed MCP gateway/backend attributes for workspace/role. Do not enumerate distinct values across unrelated OpenLIT telemetry services.

Widgets opt in only to variables whose semantics apply. Unsupported signal/filter combinations fail closed rather than silently changing semantics. Bind selections through typed parameterized inputs; never concatenate browser-controlled SQL. Provider-attempt spans carry only validated `autodev.workspace` and `autodev.agent.role` context from the logical request so those filters work without a cross-span join; these remain span attributes, never metric dimensions. Canonical `owner/repository` workspace keys may be at most 100 characters; path-derived workspace labels remain capped at 64. An invalid or absent key stays unattributed rather than being inferred from a path, provider, or nearby request.

**"Not observed" and "not applicable" are different facts, and the Usage page says which one it is.** A signal the source did not report is unobserved; a signal the source reported but the selected filter cannot describe is not applicable to that selection. A panel renders the second as an unobserved panel when the two share one wording, and a reader then concludes a capture is missing when it is there -- which is how a working metric gets mistaken for a broken one, and how an attribution bug gets misdiagnosed as a collection bug. Every panel whose signal is ruled out by the selected filters therefore names the filter that rules it out, and a count that the selection excludes is not counted as "Not observed" either.

The session is a dimension of the _view_, never of the metric. The router publishes `autodev.session.id` on the logical request and provider attempts only when an exact source session ID was supplied; an internal routing key, thread ID, request ID, tag, or process fallback is not a substitute. That bounded opaque ID is trace context for exact-session investigation, not a Usage filter variable or metric dimension: session ids are high-cardinality, and the Usage dashboard's bounded variable list is workspace, provider, requested model, agent/role and skill. The process-wide anonymous bucket is not a session and is never published as one -- attributing unrelated requests to a single conversation would be worse than having no session at all. Requests without an explicit session ID remain un-attributed for per-session reads.

The Console's same-origin server calls only fixed read-only Usage telemetry endpoints with a dedicated server-to-server credential. The summary endpoint is `POST /api/autodev/usage` (`autodev-openlit-usage-v5`): it accepts bounded time/filter selections, not raw SQL or arbitrary widget IDs, and returns fixed validated widget data, supported filter values, bounded Git-change counters/breakdowns, and a bounded recent-attempt list. Git counters use a parameterized metrics query over source-confirmed `commit_identity` observations; the metrics signal may not use raw SQL or average cumulative counters. The fixed Usage API schedules widget, filter-option, attempt, and Git reads through one process-wide bounded queue shared across overlapping requests, below the ClickHouse adapter's connection-pool capacity; it must not launch one query per widget without a concurrency bound. This scheduling protects query execution only: it does not aggregate metrics or change the semantics of a failed/unavailable read. The trace-detail endpoint accepts only a validated OpenTelemetry SpanId and resolves its TraceId server-side. The exact-session endpoint is a fixed authenticated `POST /api/autodev/usage/session` (`autodev-openlit-session-usage-v2`): it accepts one session ID in the request body plus a bounded historical range, queries spans by exact `service.name=autodev-router` and `autodev.session.id`, and returns a paginated page of whitelisted span summaries together with the exact `total`, the `hasMore` flag, the requested `limit`/`offset`/`sortDirection` and the full-session `estimatedCostUsd`. The 200-row wall is gone: the page size is bounded (1–200) and the caller walks the session with `offset`. The response omits the session ID and raw span attributes/events. Both endpoints use the dedicated Usage credential and never reuse mutation credentials.

Before starting the Console, the root development lifecycle reconciles OpenLIT against the pinned source and current patch-set image, then validates a bounded Usage snapshot through the same Data client/parser the page uses. A healthy OpenLIT root page is not proof that its Usage API matches the Console contract; an old or malformed response must stop startup with an actionable integration error rather than leave every Usage view broken.

Target views include logical requests, attempts/provider reliability, input/output/cache tokens, cost, latency, failures, MCP activity, relevant skill evidence, traces, source-confirmed context compactions, and historical provider-hop evidence where available. Usage presents a bounded recent-attempt list; selecting a span opens its privacy-filtered trace detail. Current verified widgets/evidence belong in the migration tracker. Evaluation-to-trace navigation uses the same fixed read-only `GET /api/autodev/usage/span/:spanId` endpoint with the dedicated Usage service credential. It accepts only a validated OpenTelemetry SpanId, resolves its TraceId server-side, and returns at most 200 privacy-filtered span summaries (IDs/parent, operation/service, timestamp, duration, status) without span attributes, events, prompts, responses, tool arguments, SQL, or tenant context.

Use OpenLIT's compact time-scope, summary, and breakdown-chart patterns ([Costs analytics](https://docs.openlit.io/latest/openlit/costs/analytics)) inside the AutoDev-owned dark Console; do not import its generic shell, dashboard builder, or tenant model. If the Usage request is unreachable, unauthorized, fails HTTP, or returns an invalid schema, keep the shared scope/filter controls and show one shared unavailable state, but do not render metric cards or charts as if a validated snapshot had been read. Distinguish transport failure from invalid response. A valid partial snapshot may still show its observed metrics alongside per-signal `Not observed` states.

Cost is read only from OpenLIT's `gen_ai.usage.cost` attribute and is labeled as an estimate, not a provider bill: stock OpenLIT may compute it from a pricing catalog when no provider-reported amount exists. If no attempt carries a cost value, the Console reports `Not observed`; an empty aggregate is not a measured `$0`.

Model breakdowns keep requested and served models distinct under `autodev-openlit-usage-v5`: `requests-by-model` groups logical `autodev.routed_request` spans by `autodev.requested_model` (the attribute the router publishes on logical request spans; opts in to `workspace`, `model`, `agent` and intentionally ignores `provider` and `skill`), and `attempts-by-model` groups physical `gen_ai.client_operation` spans by served `gen_ai.response.model` (opts in to `workspace`, `provider`, `model`, `agent` and ignores `skill`). Both widgets require their grouping attribute to exist so unattributed spans are omitted rather than fabricating a served model from `gen_ai.request.model` or rendering an empty bucket.

### Session diagnostics and session-scoped Usage

A session is investigated in exactly one place, and every surface reaches the same engine.

**One engine, four faces.** The diagnostics engine lives in `@simulatorlife/autodev-data/diagnostics`; its contract, validators and text formatters live in `@simulatorlife/autodev-core`. It reads the Codex rollouts (active and archived), the router's rotated event logs, the bridge logs, `hooks.log`, the skill-read telemetry and -- only inside the running Runtime -- the live router state. The Console, the `autodev diagnostics` CLI, the `autodev-session-diagnostics` skill wrapper and the Control API all read that engine; there is no second parser to keep in sync, and a fact reported by one surface is the same fact reported by the others.

**The API is read-only and authenticated.** `GET /control/diagnostics/...` (Control API contract revision 36) publishes:

```text
/control/diagnostics/sessions/recent   # newest sessions across active and archived rollouts
/control/diagnostics/sessions/scan     # fleet efficiency, failure and skip scan across recent sessions
/control/diagnostics/hooks              # PreToolUse denial summary over a bounded window
/control/diagnostics/sessions/{id}      # the full diagnostics report for one session or thread
```

Each route accepts `format=json|text` and only allowlisted, bounded query parameters; an unknown or malformed parameter is a `400`, a non-`GET` method is a `405`, and an invalid session identity is a `400` rather than an empty answer. The routes never mutate anything, never expose raw prompt bodies, and never return a credential; bearer tokens, provider key prefixes and secret assignments are redacted in the evidence they quote. The session identity in the path is always validated as a session identity before anything is read.

**The CLI is the same engine.** `pnpm autodev -- diagnostics <session-or-thread-id>` answers the same questions from the same code. In its default online mode it asks the Control API, because only the running Runtime can see the live router state; with `--offline`, `--codex-home` or `--router-log` -- or when the Control API is not running -- it runs the engine directly on disk. The `autodev-session-diagnostics` skill wrapper is a thin, standalone script over that same pair of paths.

**The Console scopes the page, not a panel.** The Usage page's top filter bar carries the **Session ID** as a view scope (`GET /usage?range=24H&sessionId=<id>`), submitted with **Apply filters**. A session ID scopes the entire page: the fleet-wide aggregate read is skipped, the page renders the session's diagnostics, and the fleet-only multi-selects are hidden rather than silently ignored. The session ID is a _view_ scope, not a metric dimension and not a Usage variable: it stays excluded from OpenTelemetry metric dimensions and from `USAGE_VARIABLE_IDS`, and it is always validated with `safeAutoDevSessionId` before it reaches a query. The session-scoped view has five tabs -- **Overview**, **Threads & Turns**, **Failures & Hooks**, **Router Requests** and **OTel Spans** -- and the last one pages through the session's spans with the shared Pagination component instead of stopping at a fixed cap.

Per-thread provider attribution uses the owning Runtime/ACP session pin for current sessions, not a bounded sample of OpenLIT spans. The diagnostics engine's historical Router event summaries preserve pre-ACP provider-hop evidence. Exact thread matches are displayed directly; legacy events matched only by model and time window are explicitly labelled with that match method. A missing or unknown provider remains unobserved rather than inferred from the configured route, rollout metadata, or a truncated span page.

**Unscoped, the same page sizes the fleet.** Without a session ID, the Usage page keeps **Aggregate usage** as its default and adds **Recent sessions** (the fleet scan, with one-click links into a session-scoped view) and **Hook denials** (the policy-level denial summary over 1/7/30 days).

**Independent degradation.** The diagnostics read and the OpenLIT span read are separate sources with separate failure modes, so each degrades on its own: a Control API that is down must not blank the span evidence, and a missing span store must not erase the rollout and router evidence. A missing source is named as unavailable; it never renders as a measured zero.

### Operational coverage, attribution and freshness

The single AutoDev Console combines **live Runtime/Control API state** with **historical OpenTelemetry → OpenLIT/ClickHouse evidence**. A configured, enabled, healthy, exposed, actively used and historically used capability are different facts; never present one as another.

| Signal                             | Live truth / operator view                                                                                                                                                                                                                                                                                        | Historical evidence                                                                                                                                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Root orchestrators and leaf agents | Runtime-observed active, queued, waiting, blocked and in-flight counts by role, workspace, actual provider/model and session; pending launches are **not** active agents.                                                                                                                                         | Source-owned lifecycle, durations, terminal outcomes and root/leaf agent-type counts.                                                                                                                  |
| Root-orchestrator launch           | Root task attempted, admitted, denied, launched or failed-before-start; a rejected/root-start failure remains visible despite never creating an agent session.                                                                                                                                                    | Root launch attempts and failure reasons, linked to requesting client, workspace and provider, separate from terminal task outcome.                                                                    |
| Orchestrator-to-child delegation   | Child spawn requested, admitted, denied, started, pending or failed-before-start; parent and child IDs remain linked.                                                                                                                                                                                             | Source-owned child-spawn success/failure/denial/timeout reasons, distinct from root launches and subsequent child completion outcomes.                                                                 |
| Providers and models               | Availability, active agents, effective routes, health, request-outcome cooldown/reset evidence, and the separate quota-axi report with its own source freshness.                                                                                                                                                  | Logical requests versus physical attempts, success/error/throttle/fallback rates, latency distributions, token/cache usage, estimated cost and historical model/provider-hop evidence where available. |
| Skills and tools                   | Canonical/effective eligible skills and tool capabilities per role/workspace; observed runtime availability when applicable.                                                                                                                                                                                      | Source-confirmed skill reads/uses/errors and tool invocation count, failures and latency; configuration/exposure alone is not usage evidence.                                                          |
| MCP servers                        | Distinguish **declared**, **enabled**, **role-exposed**, **connected/healthy** and **currently in use**. In use means Runtime has observed an **in-flight MCP tool invocation** for that server, attributed to an active task/role/workspace; mere registration, connection or session exposure does not qualify. | Source-confirmed completed MCP tool calls, errors, latency and role/provider attribution. If Runtime cannot observe in-flight calls, live usage is **Not observed**, not inactive.                     |
| Safety and operations              | Permissions/approval requests, denials, cancellations, load, dropped capacity and live error states where Runtime exposes them.                                                                                                                                                                                   | Rejection/failure classes, retries, circuit/cooldown events, tool denials and recovery results without exposing sensitive inputs.                                                                      |
| Telemetry completeness             | Last observation, producer/receiver health, observation timestamp, scope coverage and partial/unavailable status.                                                                                                                                                                                                 | Last ingested event/lag and missing or unsupported source signals; never manufacture an empty successful history.                                                                                      |

- **Freshness:** While a view is visible, poll live Runtime agent/provider state at least every **five seconds** (or use an equivalent source-driven stream) and revalidate after mutations. Historical Usage widgets **automatically refresh at least once every 60 seconds while visible** unless explicitly paused; also offer manual refresh. Pause or back off when hidden, rate-limited or source-down rather than creating an unbounded retry loop. Always show observation and last-success timestamps. On refresh failure, label any retained last-known snapshot **stale** and surface the error/partial scope; never convert missing evidence to zero or silently show stale counts as current.
- **Scope:** Active Sessions remains a live Runtime selection, not a historical timerange. Historical refresh never reconstructs active agents from recent spans or replaces authenticated Runtime evidence.
- **Attempt semantics:** Track separate root-launch and child-spawn identities and stages: `attempted` (received), `admitted` or `rejected` (routing/permission decision), `started` or `failed_before_start` (executor result), and terminal `succeeded`/`failed`/`cancelled`/`unknown` (work outcome after start). Emit each stage at most once per attempt; a retry is a separately correlated attempt, not a duplicate logical task. Count launch success as **started / resolved launch attempts** (started + rejected + failed-before-start); exclude still-pending attempts and report pending/unknown explicitly. Terminal task success uses a separately named numerator/denominator and never treats missing terminal evidence as success.
- **Aggregation:** Preserve one logical task versus N attempts, and one spawn attempt versus N child lifecycle events. A metric has a source-defined numerator, denominator, time window, attribution scope and unknown-value behavior; avoid double-counting retries, nested agents, failed spawns, and tokens.
- **Usability:** Filter and drill down by workspace, role/agent type, provider/model, outcome and relevant skill/MCP/tool **only where the producer actually knows that dimension**. Link source-confirmed live instances to their permitted session detail and historical observations to redacted traces. Missing dimensions fail closed rather than silently dropping filters.
- **Evidence:** Each dashboard signal requires a documented source, time scope, producer/consumer ownership, refresh and error semantics, authentication boundary, aggregation definition and source-backed cases for positive, observed zero, partial/truncated, source-down, authorization denied and stale last-known readings. Do not introduce sample data or another dashboard to conceal missing signals.

### Active Sessions

The Usage scope selector gains an **Active Sessions** option that scopes the page to sessions running right now, instead of to a historical interval.

It is presented in the same control as the time ranges, because that is where an operator looks when changing what Usage shows, and moving it to a second control would trade that discoverability for a distinction the label can already carry. The control's label must therefore name both kinds of selection and must not keep reading **Time range**: label the control **Usage scope**, and list Active Sessions alongside Last 24 hours / 7 days / 30 days / 90 days / Custom range.

That is a presentation requirement, not a semantic one. Behind the control, Active Sessions is a scope over live runtime state, not a temporal window, and the selection must be represented as such end to end. It is deliberately not a retained OpenLIT time-range value, because every retained value maps to a bounded historical query while this one has no window at all. Implementations must not approximate it as a shortened or derived range, and must not synthesize an active-session set from span recency: **absence of telemetry is not evidence that a session is inactive.**

"Active" is defined solely by the Runtime's own live session/concurrency state published on the authenticated read-only Control API runtime projection — the same authority behind the Agents runtime panel. There is no second session registry and no Console-side session cache that could disagree with it. Runtime v3 adds `liveSessions` from the existing AgentActivityTracker: it groups only explicit source session IDs, returns a deterministically sorted list capped at 100, and reports the exact identified count and list truncation separately. Each identity includes source-observed provider, model, and role; each dimension independently uses the newest non-null activity observation, with equal timestamps resolved to the lexically smallest value. Missing dimensions remain `null`. Activity records without an explicit ID are counted separately as unattributed activity records (not guessed sessions). The existing `concurrency.activeSessions` scalar remains a separate Runtime concurrency reading; neither reading is inferred from or substituted for the other. The Runtime must not derive identity from an internal session key or bridge tag.

The Usage active-session projection is schema v3 to carry these attribution fields without changing the meaning of the existing counters or identity evidence.

Because this scope reaches from the observability plane into the control plane:

- it reads runtime state through the Control API with the existing scoped service credential, and does not issue a Usage telemetry query for it;
- it stays read-only. Active Sessions never mutates, cancels, or acts on a session; session control stays on the owning resource;
- results are bounded, and a truncated result reports partial/overflow explicitly rather than quietly showing fewer sessions.

State semantics follow the shared rule that missing evidence stays explicit:

- when the Runtime is unreachable or a particular signal is unobserved, that signal renders `unavailable` / `not observed`; it must never render a synthesized `0` active sessions, because no evidence and an idle Runtime are different facts. A reported concurrency count remains distinct from the identified-session list, which can be unavailable or partial;
- a measured zero — runtime reachable and reporting no live sessions — is a valid reading and renders as `0`;
- sessions that end, or that the runtime never registered, simply leave the scope. That is normal, not an error, and it must not be backfilled into the scope from history.

Widget applicability is explicit rather than inherited. Under Active Sessions, window-based widgets whose semantics require a bounded interval render their not-applicable/unavailable state instead of continuing to display the previous window's numbers, while genuinely live readings (current active sessions, in-flight requests, live concurrency and denial state) render from the runtime projection. The existing Usage filter dimensions still apply where the runtime source actually knows them, and unsupported signal/filter combinations fail closed rather than silently changing semantics. The CUSTOM range start/end inputs do not apply to this scope and are not presented as though they did.

Selection state is shared with the rest of the Usage selection: Active Sessions is URL-persisted, restoring that URL reproduces the scope, and entering or leaving it must not carry stale window state into a reading whose semantics differ.

Session identifiers stay out of metric dimensions, and any per-session rows carry bounded redacted fields only, consistent with the semantic conventions and privacy rules above. The live list masks identifiers in the rendered Console. Historical investigation is a separate exact-session view scoped by the top filter bar's session ID (`GET /usage?range=24H&sessionId=<id>`), which never creates a per-session metric series: the ID selects which session's evidence the page shows, and it is not a metric dimension, a Usage variable, or a query parameter for an aggregate. This scope adds no new historical aggregation store, compatibility dashboard, or query backend.

## 11. Control API and authorization

The Control API is the only AutoDev mutation/action boundary.

Target resource families include:

```text
/control/agents
/control/providers
/control/provider-models   # provider-owned availability snapshots, not routing assignments
/control/models
/control/mcps
/control/mcp-runtime   # the Runtime's observations of the MCP servers it has reached
/control/mcp-applied   # the MCP configuration the Runtime published, against the canonical declaration
/control/skills
/control/hooks
/control/hooks-applied   # the hook configuration the Runtime published, against the canonical declaration
/control/permissions
/control/prompts
/control/workspaces
/control/routing
/control/runtime
/control/tools
/control/memory
/control/evaluations
/control/playtesting   # indexed reads plus typed run/status/cancel operations
/control/github
/control/diagnostics   # read-only session diagnostics: recent, fleet scan, hook denials, one session
```

The operator-only `PATCH /control/mcps/{name}` writes one MCP server's launch configuration for the target the Runtime applies. It changes canonical RuleSync input -- that target's own declaration -- and then executes generation/apply, so the Runtime publishes the projection and reports what it observed. The write is a compare-and-swap on the canonical document's revision, which the MCP catalog publishes, and a stale revision is returned as a conflict rather than applied. It owns the launch keys only: the declaration's governance keys and its comments are preserved, and the shared declaration is left alone.

MCP `http_headers` values may carry credentials. They remain in the canonical RuleSync source and Runtime's applied projection, but public Control API reads and mutation responses expose header names only. Runtime compares the actual values when computing desired/applied generations; the Console, audit records and telemetry never publish them. `bearerTokenEnvVar` is the environment-variable name only, never its resolved value. Read and parse failures for the applied catalogue use fixed, source-independent diagnostics; raw parser/OS error text must not echo source fragments.

Remote MCP connection preflight resolves declared credential references only in the backend's own environment/secret reader, validates effective header names and values using native HTTP APIs, and rejects missing or malformed references, case-insensitive collisions (including explicit Authorization versus a bearer-token declaration), and overrides of SDK-owned session/protocol headers or HTTP framing. Invalid-header diagnostics must not contain credential values or native exceptions that disclose them. Use the MCP SDK's native header handling and same-origin redirect policy rather than another transport implementation.

At the remote MCP transport boundary, SDK exceptions and upstream JSON-RPC error diagnostics may contain credential-bearing response text. Publish only bounded HTTP status or numeric JSON-RPC code and a fixed diagnostic message; never forward raw error messages, data, URL-parser errors, causes or stacks to clients, logs or telemetry. Preserve authorized tool results and tool-level outcome payloads; this error-boundary rule is not a general content-redaction or remote-backend trust guarantee.

Hooks, skills, prompts/commands and permissions collection/detail/source reads are authenticated GET-only. `GET /control/hooks-applied` retains its declared-versus-applied comparison. Use a fixed, typed, bounded source-read contract for the shared viewer, including source kind, format, revision, redacted source, validity/availability and existing rendered data. Resolve only known canonical resource identities server-side, not caller-supplied paths.

Canonical skill source reads use `GET /control/skills/:name/content`; prompt detail and committed version/history reads remain read-only. Remove `PATCH /control/skills/:name`, `PATCH /control/skills/:name/content`, `PATCH /control/prompts/:name`, `PATCH /control/hooks/:event`, `PATCH /control/permissions`, and any other write/preview-of-unsaved-content endpoints for these resources, including their same-origin Console proxy/actions. Existing resource routes reject non-GET methods with HTTP 405 and `Allow: GET`; removed write-only routes must be absent. No alternate role-assignment or permission-grant mutation path may bypass this policy.

Every collection read publishes whether it has a supported canonical write path. Skills, hooks, prompts, permissions, tools, GitHub workflows and evaluation history report read-only. Agents retain only Runtime-owned named-role enablement, Providers/Models retain routing/operational controls, MCPs retain their explicitly owned launch and lifecycle operations, and Workspaces retain their named configuration operations. Remove stale mutation capability flags and update the shared API compatibility contract; do not preserve aliases for retired writes.

The operator-only `PATCH /control/workspaces/{owner}/{repository}` writes one workspace's canonical configuration to `config/workspaces.json`. It is a compare-and-swap on the catalog's revision, which `GET /control/workspaces` publishes as the sha256 of the file's exact bytes, and a stale revision is returned as a conflict rather than applied. It owns that entry's `enabled`, `baseBranch` and `agentRoles`; the workspace's `id` is not editable. The write rewrites the catalog in place -- the same shape, key order and indentation -- and replaces it atomically, so a reader never sees a half-written catalog. It answers with the shared reconciliation and the diff: the generation the write produced, the generation a second read of the catalog observed, the convergence between them, and the fields that actually moved -- a field set to the value the catalog already held is not a change.

Skill assignment reads retain observed empty sets separately from unavailable/unobserved assignments. Read-only configuration pages may report desired/applied differences, revisions, drift and validation, but do not accept or reconcile UI-submitted desired state.

Use named typed operations only; no arbitrary command endpoint.
The operator-only `POST /control/providers/reset` is the explicit, confirmation-bound reset action for Runtime-owned provider overrides; it never rewrites static routing source or resets Agent admission, discovery, health, or Runtime concurrency state.

The authenticated, read-only `GET /control/provider-models` publishes Runtime-refreshed model availability separately from operator routing assignments. Each provider snapshot is `observed`, `stale` with its last confirmed list, or `unavailable`; each source-reported ID separately states whether the active Runtime route and adapter can serve it. Discovery runs off request/routing hot paths. The Console reads this snapshot and never performs provider discovery itself.

Agent list/detail reads report Runtime alias enablement explicitly. The operator-only `PATCH /control/agents/{role}` accepts `{enabled, expectedRevision}` and mutates only Runtime's named-alias admission policy; it does not write RuleSync role files or change provider/model routing. Revision conflicts are returned rather than applying a stale form.

For explicitly mutable MCP launch configuration, mutations change canonical RuleSync input and execute validation/generation/apply. Skills, hooks, prompts/commands and permissions expose authenticated read-only projections; source changes are reconciled through the repository/installer workflow. Runtime-owned resources mutate their typed owner. Tools is primarily a composite read model. Usage uses its dedicated fixed read-only telemetry path rather than becoming a mutation/control resource.

`/control/github` is a fixed read-only collection route that pairs parsed workflow definitions with observed Actions API runtime state/statistics (the schema is `autodev-control-github-v1`); it rejects non-`GET` methods with HTTP 405 and never exposes dispatch/cancel/rerun/schedule mutations. Tokens, repository coordinates outside the workspace registry, and arbitrary workflow inputs are enforced server-side; the browser never sees raw credentials or accepts arbitrary workflow identifiers.

`/control/evaluations` is a fixed read-only collection route publishing evaluation history, pass rates, and metric breakdowns from OpenLIT telemetry (`openlit_evaluation` in ClickHouse); its schema is `autodev-control-evaluations-v1`. It enforces valid parameterized SQL count and window pagination, isolates parameters, and is validated by `verifyControlApiCompatibility` during Console startup so an unready or misconfigured telemetry store fails fast at boot rather than rendering broken pages.

`/control/diagnostics` is a fixed read-only route family publishing one session's diagnostics from the AutoDev diagnostics engine (schemas `autodev-session-diagnostics-v1`, `autodev-session-recent-v1`, `autodev-session-fleet-scan-v1`, `autodev-session-hook-denials-v1`). It adds no mutation surface, exposes no prompt body or credential, and takes only allowlisted bounded query parameters; an invalid session identity or parameter is a `400` and a non-`GET` method is a `405` with an `Allow` header. Because the live router state is in-process, the Runtime serves these reads directly rather than making the engine reach back over HTTP.

The browser uses same-origin TypeScript server routes/proxies. The private Control API listener remains separate from the model/OTLP router listener.

The authenticated, read-only `GET /control/contracts` endpoint publishes the Control API compatibility revision shared by Core, Runtime, and Console. Increment that revision when the Console begins requiring a new Control API capability or path, or when an existing payload or authorization contract changes incompatibly. Development and production Console launchers must validate it before serving pages, in addition to validating the OpenLIT Usage response; a missing, stale, or malformed contract blocks startup rather than making every resource page discover incompatibility independently. Do not add legacy payload fallbacks.

The Runtime installer owns the production Console release lifecycle: it materializes the Console LaunchAgent and launcher, confirms service ownership before touching the production artifact, builds into an isolated Next output directory, promotes only a completed build, then reloads and verifies the managed Console process after Runtime. The production launcher validates both backend contracts before serving. A materialization-only operation does not build or restart a live Console; starting the framework directly without the managed launcher is not a supported deployment path because it bypasses those guarantees.

### Single-user identity and security

AutoDev has no built-in account system.

When no explicit viewer/operator allowlists are configured, the Control API may use the fixed local autodev-local operator identity only alongside its server-side service credential. The Console attaches trusted actor identity server-side; browser-supplied actor/role headers are never trusted. Configured allowlists disable the implicit local identity and require an explicit allowed actor.

Requirements:

- no AutoDev account/login/signup product;
- same-origin browser mutations with CSRF protection;
- **every** write route checks the origin, including the ones that answer a JSON caller. The route holds the service credential, so the origin is the only thing that separates the operator's own click from a page on another site making the request on the operator's behalf -- and a cross-site form post is a _simple_ request: no preflight, and a content type the page chooses, including the `text/plain` body a JSON reader will happily parse. The check comes before the body is read, so a refused request costs nothing and a body nobody may submit is never parsed;
- private/scoped server credential from Console to Control API;
- installation/operator authorization appropriate to deployment;
- optional reverse-proxy/SSO protection for remote exposure without AutoDev accounts;
- least privilege per resource/action;
- redacted audit record for each mutation;
- no bearer token, external identity secret, or raw mutation body in telemetry.

A completed control action may emit bounded control telemetry; OTel is never the command path.

## 12. OpenLIT maintenance strategy

Maintain a dedicated AutoDev OpenLIT fork/distribution. Upstream contributions are optional and must not block AutoDev.

Keep ingestion, OTel semantics, storage schemas, and generic query execution as close to upstream as practical while allowing substantial divergence in product shell, navigation, domain modules, and control pages.

Do not rewrite foundational OpenLIT storage/query abstractions merely to remove hidden singleton tenancy internals.

Receiver authentication remains mandatory. Retain the local bearer-auth patch for OTLP/HTTP and OTLP/gRPC until the pinned upstream behavior genuinely replaces it.

The retained auto-pricing path computes costs from the existing pricing catalog and stores them in `SpanAttributes`. Its ClickHouse write path batches at most 200 spans per mutation and restricts each update to the affected `toDate(Timestamp)` partitions; do not regress to one mutation per span or compensate by only lowering ClickHouse background-thread limits.

Every upstream upgrade must verify:

- the pinned patch/application sequence;
- retained receiver/storage/query behavior;
- AutoDev Usage/query behavior;
- removal of excluded product features;
- the single AutoDev Console shell;
- dark-only styling and canonical navigation;
- retained component integrations;
- no reintroduction of account/tenancy/discovery/Controller concepts.

Current OpenLIT version/image/patch evidence belongs in autodev-console-migration.md.

The catalogue reads are hooks, MCPs, tools, skills, prompts, agents and permissions; the last two are the execution contract's roles, so an unread contract is an unread catalogue rather than an empty one, and a count over a catalogue that was not read is not a count.
- Useful filters/detail routes are URL-addressable where appropriate.
- Browser/visual regression acceptance covers the shared shell and representative list/detail/form/observability pages.
- Acceptance waits for the client, not only for the markup. The shared page wait requires the page's hydration marker as well as its content, so a spec that presses a key or clicks a control measures the page after it has taken over rather than in the gap between the server's answer and the bundle's. An acceptance assertion also addresses the element the Console owns: the document carries the framework's own streaming scaffolding beside the product, and a locator that matches every element of a kind measures the scaffolding along with it.

### GitHub

- `.github/workflows/*.yml` files remain the authoritative source for workflow definitions and cron schedules; the Data reader preserves YAML 1.2 `on:` semantics and exposes `valid`/`invalid`/`unavailable` catalog status without fabricating a workflow count.
- The Data `GithubActionsAdapter` uses `@octokit/rest` typed Actions operations and Octokit's pagination iterator for GitHub API interactions; handwritten HTTP/REST request construction is not permitted. Octokit is configured for the fixed `https://api.github.com` origin, GET-only requests, redirects denied (`redirect: "error"`), and optional server-side token authentication (or anonymous access for public repositories). AutoDev-specific safeguards remain in the adapter: validated repository coordinates, origin-checked pagination, streamed 1MiB response bounds, active timeouts, fail-closed handling of partial/malformed results, preserved HTTP auth/rate status for oversized or unparseable error bodies (401, 403, 429, 404), and token redaction. Missing credentials, repository scope, or API evidence never produces a synthetic zero/healthy result.
- The Control API `/control/github` route is an authenticated, read-only GET endpoint (`schema: autodev-control-github-v1`, `readOnly: true`, `runtimeFactsAvailable` flag) requiring Control API credentials and rejecting non-`GET` methods with HTTP 405; the Console renders explicit `Unavailable`/`Invalid` runtime status with redacted messages rather than synthesizing zeros or healthy state.
- `AUTODEV_GITHUB_REPOSITORY` validated against an enabled canonical workspace in `config/workspaces.json` (`enabled: true`) is required for observed runtime facts; unrecognized or disabled workspaces yield `invalid`. `AUTODEV_GITHUB_TOKEN` is optional for public repositories (accessible anonymously, though authenticated requests are preferred for stable rate limits) and required for private repositories (least-privilege with read-only Actions permission); missing credentials for private repositories, forbidden access, or rate-limited requests yield `unavailable`.
- Workflows are capped at 100 with explicit partial status (`partial_result`) if more exist; run statistics are computed over a bounded recent-run sample (default 30 runs); `successRate` denominator is all sampled completed runs (in-progress excluded; non-success/missing conclusions in denominator; null when 0 completed runs in sample).
- Dispatch, cancel, rerun, and schedule mutation controls remain explicitly unimplemented in both the Console resource and the Control API; tests must not relax this and must not introduce mutation routes.
- GitHub runtime facts must be verified from source-owned, authenticated or explicitly public evidence. Missing credentials or unobserved results remain unavailable; tests must not infer a healthy or zero state.

## Final target

AutoDev is a **TypeScript-first, provider-independent, subscription-capable agent platform** with role-based orchestration, native ACP and role-authorized browser-backed `opencli` execution, strict and observable permissions, durable routing and resource policy, and package-managed, maintained open-source dependencies rather than duplicated custom infrastructure.
