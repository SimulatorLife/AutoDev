## Boundaries and decisions

- Core owns game-neutral schemas, measurement, comparison, triage, validity and evidence rules; Runtime owns approved visual/engine execution, bounded evidence and analysis invocation; Data owns indexed workspace-scoped records; Console owns server-filtered browsing and operator actions. The **optional game adapter** owns engine semantics and structured player-visible projections; the **visual gameplay driver** observes the actual UI without per-game JSON configuration. Root/Workspaces retain authorization, budgets and reporting gates.
- Preserve the in-progress worktree changes. Do not revert, overwrite, or
  duplicate uncommitted changes from other processes; coordinate by file scope.
- Synthetic fixtures validate protocol/mechanics only and are never production
  evidence. Never run a game or substitute a fixture for an explicitly approved
  target-game run. Workspace enablement is not approval.
- Human study, issue publication, model-weight/license, upstream reuse, and
  target-game claims retain their explicit authorization/evidence gates.

### Ordered delivery plan — complete these gates before declaring the new playtesting target done

**Decision scope:** OneJev 1.6-4B is the selected _implementation target_ for P2, not an already-deployed service, a mandatory installation for P1, or evidence of P2 acceptance; see the P2 gate below and the target-state model decision.

**Milestone separation (normative):** **P1 = discrete-turn/pausable browser play through an explicit `smart-direct` policy (bounded per-decision Smart cost), session UI, and source-honest baselines**; a live Jev decision backend is **not** part of P1 acceptance. **P2 = actual Jev decision inference, policy cohorts and correct Jev telemetry**. The product may show the Jev counter as **Not available / Not measured** in P1; it may not claim fully intelligent **Smart/Jev** gameplay until P2 passes a real-game test. The [Console UI/data contract](../autodev-console-target-state.md#playtesting) is the _single_ detailed UI source; this checklist records ownership, order and tests only, not competing design requirements.

### 2026-10-20 the observation captured the game before it had booted

The episode failed at step 0 with a rendered decision but a blank frame: the captured PNG was 4 259 bytes of one flat colour and the observation listed no controls, while the browser was showing the RacingGame's full cockpit. A decision grounded in a blank screen is grounded in nothing.

**The cause was that the driver captured the moment the document parsed.** `PlaytestVisualBrowserDriver.open()` navigated with `waitUntil: "domcontentloaded"` and returned as soon as the document existed. Measured against the real game, the boot takes about 1.4 s after the load event: at load + 230 ms the page has no canvas at all, at load + 945 ms the canvas exists but is hidden and flat, and at load + 1 405 ms the canvas is visible and painted and the page shows its controls and its text. Every measurement before the paint produced the same 4 259-byte blank frame.

**The fix asks the page whether it has shown the game.** The driver now waits, bounded and once per page, for the page to show itself, and it answers that from the page rather than from a delay: a visible canvas whose pixels are not one flat colour is a painted scene, and a game that renders into the DOM shows itself as rendered text or as a control on screen. The check runs inside a frame callback, because a drawing buffer that is not preserved is emptied once the frame has been composited.

**Three earlier attempts at this signal were wrong, and each was caught by measuring the real game rather than by reasoning about it.** Treating "the page has no canvas" as "the page has nothing to wait for" captured the blank frame, because a game creates its canvas only once it has booted. Sampling the canvas alone was not enough either, because the boot screen renders pixels before the canvas exists. Reading `textContent` to decide that the page had text was worse: `textContent` counts the text of hidden descendants, and the game's root container matched it while the screen was still blank. `innerText` counts only the text the browser laid out, and it is empty until the game is on screen, which is the signal the driver uses now.

**A fixed settle delay would have been the wrong fix.** Waiting for the network to go quiet or for a fixed number of milliseconds hides the defect behind a number that happens to be large enough today, which is the same class of defect as the 15-second decision deadline: a magic constant standing in for a question the system should be able to answer. It also breaks the driver's own staleness check, which refuses coordinate input when the frame changed since the observation, because a settle delay lets the game move on before the frame the player is looking at is taken. The network-settle wait was tried, removed, and the staleness test (`visual browser refuses coordinate input when the captured canvas frame changes`) passes with the pixel-based gate.
